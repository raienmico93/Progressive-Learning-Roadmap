# Git Common Ignored Content: A Comprehensive Programming Cheat Sheet

---

## Topic Overview

### Definitions

**Core Definition**
Common ignored content refers to the categories of files and directories that are routinely excluded from Git tracking via `.gitignore` patterns because they are generated, machine-specific, sensitive, or otherwise unsuitable for version control.

**Technical Definition**
Common ignored content encompasses files that fall into eight broad categories: (1) build artifacts and compiler outputs, (2) dependency directories, (3) IDE and editor configuration files, (4) operating-system-specific desktop files, (5) log files and runtime diagnostics, (6) temporary files and swap data, (7) environment file templates vs. live configuration, and (8) secrets, API tokens, keystores, and private credentials. These files share the property that they are either machine-local, regenerable, or security-sensitive, and thus should not be committed to a shared repository.

**Beginner-Friendly Explanation**
When you work on a project, your folder fills up with files that Git shouldn't save: compiled code, downloaded dependencies, your editor's settings, log files, temporary files, and—most importantly—secret keys and passwords. This cheat sheet shows you which files to ignore and how to write the patterns in your `.gitignore` file. Ignoring these files keeps your repository clean, safe, and focused on what actually matters: your source code.

### Key Characteristics

- **Regenerable**: Build artifacts and dependencies can be recreated from source or configuration files.
- **Machine-Specific**: IDE settings, OS files, and local configuration differ between developers.
- **Sensitive**: Secrets, credentials, and API tokens must never be committed.
- **Noisy**: Logs, caches, and temporary files change frequently and clutter the repository.
- **Pattern-Based**: Each category has well-established `.gitignore` patterns.

### Prerequisites

- Git installed (version 2.28+ recommended).
- A Git repository with a `.gitignore` file (or the ability to create one).
- Basic understanding of `.gitignore` syntax (see the "Ignoring Files" cheat sheet).

### Related Programming Areas

- **Version Control Systems (VCS)** : Git, Mercurial, Subversion.
- **DevOps & CI/CD**: Clean build environments and secure pipelines.
- **Software Development**: Maintaining clean, reproducible repositories.
- **Security**: Preventing secret leakage.

### Core Concepts / Features

1. **Build Artifacts and Compiler Outputs** — `dist/`, `build/`, `__pycache__/`, `*.class`.
2. **Dependency Directories** — `node_modules/`, `vendor/`.
3. **IDE and Editor Configuration** — `.vscode/`, `.idea/`, `.DS_Store`.
4. **Operating-System Files** — `Thumbs.db`, `desktop.ini`.
5. **Log Files and Runtime Diagnostics** — `*.log`, `npm-debug.log*`.
6. **Temporary Files and Swap Data** — `*.swp`, `*~`.
7. **Environment File Templates vs. Live Configuration** — `.env.example` tracked; `.env` ignored.
8. **Secrets, API Tokens, and Credentials** — `*.pem`, `credentials.json`, `*.key`.

## 1. Build Artifacts and Compiler Outputs

### Definitions

**Core Definition**
Build artifacts and compiler outputs are files generated during the process of compiling, transpiling, packaging, or bundling source code into executable or distributable form.

**Technical Definition**
Build artifacts include compiled object files (`.o`, `.class`), bytecode (`__pycache__/`, `*.pyc`), distribution bundles (`dist/`, `build/`), compiled binaries, and packaging metadata (`*.egg-info/`). These files are derived from source code and can be regenerated by running the build toolchain. They are not part of the source and should not be version-controlled.

**Beginner-Friendly Explanation**
When you run your code, your computer creates new files—like compiled programs or packaged bundles. These files are like leftovers from cooking: they're useful right now, but you can always make them again from the recipe (your source code). Git doesn't need to save them.

### Purposes

- To keep the repository focused on source code.
- To avoid committing large binary files that bloat the repository.
- To prevent merge conflicts in generated files.
- To ensure clean, reproducible builds from source.
- To reduce clone and fetch times.

### Syntax Rules and Structure

**Common Patterns**

| Language/Stack | Patterns |
|----------------|----------|
| Python | `__pycache__/`, `*.py[cod]`, `*$py.class`, `build/`, `dist/`, `*.egg-info/`, `.eggs/` |
| Java | `target/`, `*.class`, `*.jar` (except wrapper), `build/` |
| JavaScript/TypeScript | `dist/`, `build/`, `out/`, `.next/`, `.nuxt/`, `*.tsbuildinfo` |
| C/C++ | `*.o`, `*.obj`, `*.so`, `*.a`, `build/` |
| Rust | `target/` |
| Go | `bin/`, `*.exe` |

**Syntax Rules**

- Use directory patterns (trailing `/`) to ignore entire build directories.
- Use `**/` to match build directories at any depth in monorepos.
- Negate specific files if needed (e.g., keep a checked-in distribution file).
- Build artifact patterns are typically placed at the top of `.gitignore`.

**Constraints and Limitations**

- **Regeneration required**: Developers must run the build toolchain after cloning.
- **Toolchain dependency**: The build environment must be reproducible.
- **Negation complexity**: Re-including files inside ignored directories requires parent re-inclusion.

### Annotated Code Examples

#### Example 1: Python Build Artifacts

```gitignore
# Byte-compiled / optimized / DLL files
__pycache__/
*.py[cod]
*$py.class

# Distribution / packaging
build/
dist/
*.egg-info/
.eggs/
```

**Why these patterns work:** `__pycache__/` ignores all Python bytecode directories at any depth. `*.py[cod]` matches `.pyc`, `.pyo`, and `.pyd` files. `build/` and `dist/` ignore standard packaging output directories. These are the patterns from GitHub's official Python.gitignore template.

#### Example 2: JavaScript/TypeScript Build Output

```gitignore
# Build outputs
dist/
build/
out/
.next/
.nuxt/
.svelte-kit/
*.tsbuildinfo
```

**Why these patterns work:** Each pattern targets a specific framework's build directory. `*.tsbuildinfo` ignores TypeScript incremental build metadata. These patterns are standard in Node.js projects.

### Real-World Cases

- **Python package**: A developer runs `pip install -e .`, generating `build/`, `dist/`, and `*.egg-info/`; these are ignored so the repository contains only source.
- **React application**: `npm run build` generates `dist/` or `build/`; these are ignored so CI/CD regenerates them from source.
- **Monorepo**: Multiple packages each have `dist/`; `**/dist/` ignores them all.

### References

- GitHub gitignore Repository: Python.gitignore — https://github.com/github/gitignore/blob/main/Python.gitignore
- GitHub gitignore Repository: Node.gitignore — https://github.com/github/gitignore/blob/main/Node.gitignore
- Python Packaging User Guide — https://packaging.python.org/en/latest/

## 2. Dependency Directories

### Definitions

**Core Definition**
Dependency directories are folders where package managers install third-party libraries and frameworks that a project depends on.

**Technical Definition**
Dependency directories (e.g., `node_modules/` for npm, `vendor/` for Composer and Go, `venv/` for Python virtual environments) contain externally sourced code that is declared in a manifest file (`package.json`, `composer.json`, `go.mod`, `requirements.txt`). These directories are regenerable by running the package manager's install command (`npm install`, `composer install`, `go mod download`, `pip install -r requirements.txt`).

**Beginner-Friendly Explanation**
Your project depends on other people's code. Instead of copying that code into your project, you download it into a special folder like `node_modules/`. Git doesn't need to save this folder because anyone can recreate it by running the install command.

### Purposes

- To avoid committing thousands of third-party files.
- To keep the repository small and fast to clone.
- To ensure dependencies are resolved from the manifest file.
- To allow different developers to use different dependency versions as declared.
- To follow package manager best practices.

### Syntax Rules and Structure

**Common Patterns**

| Ecosystem | Directory | Manifest File |
|-----------|-----------|---------------|
| Node.js (npm/yarn/pnpm) | `node_modules/`, `.pnpm-store/` | `package.json`, `package-lock.json` |
| PHP (Composer) | `vendor/` | `composer.json`, `composer.lock` |
| Go | `vendor/` (optional) | `go.mod`, `go.sum` |
| Python | `venv/`, `.venv/`, `env/` | `requirements.txt`, `pyproject.toml` |
| Ruby | `.bundle/`, `vendor/bundle/` | `Gemfile`, `Gemfile.lock` |
| Rust | `target/` | `Cargo.toml`, `Cargo.lock` |

**Syntax Rules**

- Use the directory pattern with a trailing slash: `node_modules/`.
- For nested dependency directories in monorepos, use `**/node_modules/` or list specific paths.
- **Always commit the lock file** (`package-lock.json`, `composer.lock`, `go.sum`, `Gemfile.lock`) to ensure reproducible installs.
- Virtual environments (`venv/`, `.venv/`) should be ignored, but the `requirements.txt` or `pyproject.toml` should be committed.

**Constraints and Limitations**

- **Installation required**: Developers must run `npm install` (or equivalent) after cloning.
- **Network dependency**: Dependency resolution requires network access.
- **Lock file must be committed**: Without the lock file, installs are not reproducible.

### Annotated Code Examples

#### Example 1: Node.js Dependencies

```gitignore
# Dependency directories
node_modules/
jspm_packages/
web_modules/

# Package manager caches
.npm/
.yarn/cache/
.pnpm-store/
```

**Why these patterns work:** `node_modules/` is the standard npm dependency directory. The cache directories are machine-local and regenerable. The lock file (`package-lock.json`) is **not** ignored and should be committed.

#### Example 2: Python Virtual Environment

```gitignore
# Virtual environments
venv/
.venv/
env/
ENV/
```

**Why these patterns work:** Virtual environments are machine-specific and regenerable from `requirements.txt`. Ignoring them keeps the repository clean.

### Real-World Cases

- **Node.js project**: A developer clones a repository and runs `npm install` to recreate `node_modules/`.
- **PHP project**: `composer install` recreates `vendor/` from `composer.json` and `composer.lock`.
- **Python project**: `python -m venv .venv` and `pip install -r requirements.txt` recreate the virtual environment.

### References

- GitHub gitignore Repository: Node.gitignore — https://github.com/github/gitignore/blob/main/Node.gitignore
- Composer Documentation: Should I Commit the Dependencies in My Vendor Directory? — https://getcomposer.org/doc/faqs/should-i-commit-the-dependencies-in-my-vendor-directory.md
- npm Documentation: package-lock.json — https://docs.npmjs.com/cli/v10/configuring-npm/package-lock-json

## 3. IDE and Editor Configuration Files

### Definitions

**Core Definition**
IDE and editor configuration files are machine-local settings created by integrated development environments (IDEs) and text editors to store project-specific or user-specific configuration.

**Technical Definition**
IDEs such as VS Code, JetBrains (IntelliJ, PyCharm), and Eclipse create project directories (`.vscode/`, `.idea/`, `.settings/`) containing workspace settings, run configurations, and plugin metadata. Text editors such as Vim, Emacs, and Sublime Text create swap files (`*.swp`, `*~`, `*.sublime-workspace`). These files are machine-local and should not be committed, though shared baseline configurations (e.g., `.vscode/extensions.json`) may be selectively tracked.

**Beginner-Friendly Explanation**
Your code editor saves its own settings in hidden folders. Since every developer uses different settings, these files shouldn't be shared. However, you might want to share a recommended extensions list or launch configurations so everyone on the team has a consistent setup.

### Purposes

- To avoid committing machine-local editor settings.
- To prevent conflicts from differing IDE configurations.
- To keep the repository clean of editor-specific metadata.
- To allow each developer to use their preferred editor.
- To selectively share baseline configurations when beneficial.

### Syntax Rules and Structure

**Common Patterns**

| Tool | Patterns |
|------|----------|
| VS Code | `.vscode/*`, `!.vscode/extensions.json`, `!.vscode/launch.json`, `!.vscode/settings.json`, `!.vscode/tasks.json` |
| JetBrains | `.idea/`, `*.iml`, `*.ipr`, `*.iws` |
| Eclipse | `.settings/`, `.project`, `.classpath` |
| Vim | `*.swp`, `*.swo`, `*~` |
| Emacs | `*~`, `#*#`, `.#*` |
| Sublime Text | `*.sublime-workspace` |

**Syntax Rules**

- Ignore the entire directory first (`.vscode/*`), then negate specific files to share (`!.vscode/extensions.json`).
- The negation must come **after** the ignore pattern.
- Use `**/` for monorepos to ignore IDE directories at all depths.
- JetBrains `.idea/` should be ignored entirely; there is no standard shared baseline.

**Constraints and Limitations**

- **Shared baseline trade-off**: Sharing `.vscode/settings.json` can conflict with personal preferences. Share only `extensions.json` and `launch.json`.
- **Negation order**: The negation pattern must appear after the ignore pattern.
- **Nested negation**: If `.vscode/*` is ignored, `!.vscode/extensions.json` works because the parent directory is not excluded.

### Annotated Code Examples

#### Example 1: VS Code with Shared Baseline

```gitignore
# VS Code: ignore all, share baseline
.vscode/*
!.vscode/extensions.json
!.vscode/launch.json
!.vscode/settings.json
!.vscode/tasks.json
```

**Why these patterns work:** `.vscode/*` ignores all files in the `.vscode` directory. The `!` patterns re-include specific files that are useful for the whole team. This is the recommended approach: share project configuration, not personal editor state.

#### Example 2: JetBrains IDEs

```gitignore
# JetBrains / IntelliJ
.idea/
*.iml
*.ipr
*.iws
out/
```

**Why these patterns work:** `.idea/` contains machine-local project metadata. The `*.iml`, `*.ipr`, and `*.iws` files are IntelliJ module and project files that are regenerated. These are ignored entirely.

### Real-World Cases

- **Team with mixed editors**: A team uses VS Code, IntelliJ, and Vim; each developer ignores their own editor's files, and the repository contains no editor-specific configuration.
- **VS Code extension recommendation**: A project shares `.vscode/extensions.json` so all developers are prompted to install recommended extensions.
- **Remote development**: VS Code's Remote-Containers configuration (`.devcontainer/`) is **committed** because it defines the development environment for all developers.

### References

- GitHub gitignore Repository: Global/VisualStudioCode.gitignore — https://github.com/github/gitignore/blob/main/Global/VisualStudioCode.gitignore
- GitHub gitignore Repository: Global/JetBrains.gitignore — https://github.com/github/gitignore/blob/main/Global/JetBrains.gitignore
- VS Code Documentation: Workspace Settings — https://code.visualstudio.com/docs/getstarted/settings

## 4. Operating-System-Specific Desktop Files

### Definitions

**Core Definition**
Operating-system-specific desktop files are metadata files automatically created by the operating system's file manager or desktop environment to store thumbnails, folder view settings, or resource fork data.

**Technical Definition**
macOS creates `.DS_Store` files in every directory to store Finder view settings and icon positions. Windows creates `Thumbs.db` (thumbnail cache) and `desktop.ini` (folder customisation) files. Other OS artefacts include `.Spotlight-V100/`, `.Trashes/`, `.fseventsd/`, `$RECYCLE.BIN/`, and `*.lnk` shortcuts. These files are machine-specific, binary, and have no relevance to source code.

**Beginner-Friendly Explanation**
Your operating system creates hidden files to remember how you like to view your folders—like thumbnail images or icon positions. These files are different on every computer and have nothing to do with your project. Git should ignore them.

### Purposes

- To prevent OS-generated noise from appearing in `git status`.
- To avoid committing binary metadata files.
- To keep the repository clean and cross-platform compatible.
- To prevent conflicts between developers on different operating systems.
- To reduce repository size from unnecessary binary files.

### Syntax Rules and Structure

**Common Patterns**

| OS | Patterns |
|----|----------|
| macOS | `.DS_Store`, `.AppleDouble`, `.LSOverride`, `._*`, `.Spotlight-V100/`, `.Trashes/`, `.fseventsd/`, `.TemporaryItems/`, `.VolumeIcon.icns`, `.com.apple.timemachine.donotpresent` |
| Windows | `Thumbs.db`, `Thumbs.db:encryptable`, `ehthumbs.db`, `ehthumbs_vista.db`, `Desktop.ini`, `[Dd]esktop.ini`, `$RECYCLE.BIN/`, `*.lnk` |
| Linux | `.Trash-*`, `.directory` |

**Syntax Rules**

- Use literal file names for specific OS files.
- Use directory patterns for OS-generated directories.
- Use character classes (`[Dd]esktop.ini`) for case-insensitive matching.
- These patterns are often placed in a "System Files" or "OS Files" section.

**Constraints and Limitations**

- **Case sensitivity**: On case-sensitive filesystems, `Desktop.ini` and `desktop.ini` are different files; use `[Dd]esktop.ini` to match both.
- **Hidden files**: These files are hidden by default; `git status` may still show them if not ignored.
- **macOS resource forks**: `._*` files are created when copying files to non-HFS filesystems.

### Annotated Code Examples

#### Example 1: Comprehensive OS Ignore Section

```gitignore
# macOS
.DS_Store
.AppleDouble
.LSOverride
._*
.Spotlight-V100/
.Trashes/
.fseventsd/
.TemporaryItems/
.VolumeIcon.icns
.com.apple.timemachine.donotpresent

# Windows
Thumbs.db
Thumbs.db:encryptable
ehthumbs.db
ehthumbs_vista.db
Desktop.ini
[Dd]esktop.ini
$RECYCLE.BIN/
*.lnk
```

**Why these patterns work:** This covers the most common macOS and Windows artefacts. `.DS_Store` is the most frequently ignored file on macOS. `[Dd]esktop.ini` matches both capitalisations. These patterns are drawn from GitHub's official macOS and Windows gitignore templates.

### Real-World Cases

- **Cross-platform team**: Developers on macOS, Windows, and Linux all contribute to the same repository; the OS-specific patterns prevent their respective system files from being committed.
- **macOS `.DS_Store` noise**: A developer notices `.DS_Store` appearing in `git status`; adding it to `.gitignore` solves the problem.
- **Windows thumbnail cache**: `Thumbs.db` files appear in image directories; ignoring them keeps the repository clean.

### References

- GitHub gitignore Repository: Global/macOS.gitignore — https://github.com/github/gitignore/blob/main/Global/macOS.gitignore
- GitHub gitignore Repository: Global/Windows.gitignore — https://github.com/github/gitignore/blob/main/Global/Windows.gitignore
- OpenJDK Mailing List: Add Windows/macOS System Files to .gitignore — https://mail.openjdk.org/pipermail/build-dev/2018-November/023536.html

## 5. Log Files and Runtime Diagnostics

### Definitions

**Core Definition**
Log files and runtime diagnostics are files generated by applications, servers, and development tools to record events, errors, debugging information, and performance metrics during execution.

**Technical Definition**
Log files (`*.log`, `logs/`) record runtime events. Diagnostic reports (`report.*.json`, `npm-debug.log*`) are generated by Node.js and npm when errors occur. Test coverage reports (`coverage/`, `.nyc_output/`) and linting caches (`.eslintcache`) are runtime diagnostics. These files are transient, machine-specific, and regenerable.

**Beginner-Friendly Explanation**
When your program runs, it writes notes about what happened—errors, warnings, and other messages—into log files. These files change every time the program runs, so Git doesn't need to save them. They're useful for debugging right now but not for version control.

### Purposes

- To prevent constantly changing log files from cluttering the repository.
- To avoid committing diagnostic data that is only relevant locally.
- To keep the repository focused on source and configuration.
- To reduce `git status` noise from runtime-generated files.
- To ensure test coverage reports are regenerated by CI, not committed.

### Syntax Rules and Structure

**Common Patterns**

| Category | Patterns |
|----------|----------|
| Generic logs | `logs/`, `*.log` |
| npm logs | `npm-debug.log*`, `yarn-debug.log*`, `yarn-error.log*`, `lerna-debug.log*`, `.pnpm-debug.log*` |
| Node diagnostic reports | `report.[0-9]*.[0-9]*.[0-9]*.[0-9]*.json` |
| Coverage | `coverage/`, `*.lcov`, `.nyc_output/` |
| Linting caches | `.eslintcache`, `.stylelintcache` |
| Runtime data | `*.pid`, `*.seed`, `*.pid.lock`, `pids/` |

**Syntax Rules**

- Use `logs/` to ignore a log directory and `*.log` to ignore log files at any depth.
- Use wildcard `*` in `npm-debug.log*` to match versioned log files.
- Coverage directories are typically ignored; coverage configuration files (e.g., `.nycrc`) are committed.
- PID files and runtime data are machine-local and should be ignored.

**Constraints and Limitations**

- **Some logs may be committed intentionally**: In rare cases, a project may commit a sample log for documentation purposes; use negation to allow specific files.
- **Log rotation**: Log files may be rotated (e.g., `app.log.1`, `app.log.2.gz`); `*.log*` matches these.
- **CI artifacts**: Coverage reports are often uploaded as CI artifacts, not committed.

### Annotated Code Examples

#### Example 1: Node.js Logs and Diagnostics

```gitignore
# Logs
logs/
*.log
npm-debug.log*
yarn-debug.log*
yarn-error.log*
lerna-debug.log*
.pnpm-debug.log*

# Diagnostic reports
report.[0-9]*.[0-9]*.[0-9]*.[0-9]*.json

# Runtime data
pids/
*.pid
*.seed
*.pid.lock
```

**Why these patterns work:** `logs/` ignores the entire logs directory. `*.log` catches all log files. The npm/yarn/lerna patterns match the specific debug logs generated by each package manager. The diagnostic report pattern matches Node.js's crash reports.

#### Example 2: Coverage and Linting Caches

```gitignore
# Coverage
coverage/
*.lcov
.nyc_output/

# Linting caches
.eslintcache
.stylelintcache
```

**Why these patterns work:** Coverage reports are generated by test runners (Jest, Istanbul, nyc). Linting caches are machine-local acceleration files. Both are regenerable.

### Real-World Cases

- **CI/CD pipeline**: A CI script runs tests, generates coverage in `coverage/`, uploads it as an artifact, and the directory is ignored so it doesn't pollute the repository.
- **Debugging session**: A developer enables verbose logging, generating `debug.log`; the file is ignored and never committed.
- **npm error**: An npm install fails, generating `npm-debug.log`; the file is ignored and can be shared manually if needed.

### References

- GitHub gitignore Repository: Node.gitignore — https://github.com/github/gitignore/blob/main/Node.gitignore
- Node.js Documentation: Diagnostic Reports — https://nodejs.org/api/report.html
- npm Documentation: npm-debug.log — https://docs.npmjs.com/cli/v10/using-npm/logging

## 6. Temporary Files and Swap Data

### Definitions

**Core Definition**
Temporary files and swap data are files created by text editors, development tools, and operating systems to temporarily store data during editing or processing, and which are normally deleted when the operation completes.

**Technical Definition**
Vim creates swap files (`*.swp`, `*.swo`) to recover unsaved changes after a crash. Emacs creates backup files (`*~`, `#*#`). Merge tools create `.orig` files. Generic temporary files (`*.tmp`, `*.temp`, `*.bak`) are created by various tools. These files are ephemeral, machine-local, and should never be committed.

**Beginner-Friendly Explanation**
When you edit a file, your editor might create a backup or swap file just in case something goes wrong. These files are temporary and disappear when you're done. Git should ignore them so they don't accidentally get saved.

### Purposes

- To prevent temporary editor files from being committed.
- To avoid merge conflicts from backup files.
- To keep the repository clean of ephemeral data.
- To reduce `git status` noise.
- To prevent accidental commits of incomplete or stale data.

### Syntax Rules and Structure

**Common Patterns**

| Tool | Patterns |
|------|----------|
| Vim | `*.swp`, `*.swo`, `*.swn`, `.*.swp` |
| Emacs | `*~`, `#*#`, `.#*` |
| Generic backups | `*.bak`, `*.orig`, `*.tmp`, `*.temp` |
| Patch/reject files | `*.rej`, `*.patch` (when generated) |
| Merge files | `*.orig` |

**Syntax Rules**

- Use extension patterns (`*.swp`, `*~`) to match at any depth.
- Vim swap files may start with a dot (`.*.swp`); include both patterns.
- `*~` matches Emacs and other editors' backup files.
- `*.orig` matches files created by `git merge` or `patch`.

**Constraints and Limitations**

- **Some `.orig` files may be intentional**: Rarely, `.orig` files are committed as reference; use negation if needed.
- **Editor-specific**: Different editors use different temporary file conventions.
- **Global ignore recommended**: These patterns are ideal candidates for the global ignore file (`core.excludesFile`).

### Annotated Code Examples

#### Example 1: Editor Temporary Files

```gitignore
# Temporary and swap files
*.swp
*.swo
*.swn
.*.swp
*~
#*#
.#*
*.bak
*.orig
*.tmp
*.temp
```

**Why these patterns work:** `*.swp` and `*.swo` cover Vim swap files. `.*.swp` covers dotfile variants. `*~` covers Emacs and other editors' backups. `*.orig` covers merge conflict backups. These are standard patterns found in many .gitignore files.

### Real-World Cases

- **Vim crash recovery**: A developer's Vim session crashes, leaving a `.swp` file; Git ignores it, preventing accidental commit.
- **Merge conflict backup**: A merge creates a `.orig` file; it's ignored and cleaned up by the developer.
- **Emacs auto-save**: Emacs creates `#file#` and `file~` files during editing; both are ignored.

### References

- GitHub gitignore Repository: Global/Vim.gitignore — https://github.com/github/gitignore/blob/main/Global/Vim.gitignore
- GitHub gitignore Repository: Global/Emacs.gitignore — https://github.com/github/gitignore/blob/main/Global/Emacs.gitignore
- LLVM Project: .gitignore (Temporary Files) — https://chromium.cpp.hybrid-analysis.googlesource.com/external/llvm.org/llvm/+/refs/heads/release_31/.gitignore

## 7. Environment File Templates vs. Live Configuration

### Definitions

**Core Definition**
Environment file templates are committed files that document the required environment variables with placeholder values, while live configuration files (`.env`) contain actual values and are ignored.

**Technical Definition**
Applications often use `.env` files to store environment-specific configuration (database URLs, API keys, feature flags). These files must be ignored because they contain secrets and vary between environments. A corresponding `.env.example` file (or `.env.template`, `.env.sample`) is committed to document the required variables with placeholder values. The `dotenv` library (and equivalents) reads `.env` at runtime.

**Beginner-Friendly Explanation**
Your app needs to know things like your database password and API keys. These are stored in a special file called `.env`. You don't want to share this file—it has your secrets. Instead, you create a `.env.example` file that shows your teammates what variables they need to set, without revealing the actual values. The `.env.example` file is committed; the `.env` file is ignored.

### Purposes

- To prevent secrets from being committed to the repository.
- To document required environment variables for new developers.
- To allow different developers and environments to use different values.
- To enable CI/CD systems to inject secrets securely.
- To keep the repository safe for public viewing.

### Syntax Rules and Structure

**Common Patterns**

```gitignore
# Environment files
.env
.env.*
!.env.example

# Alternative patterns
*.env
.env.local
.env.development.local
.env.test.local
.env.production.local
```

**Syntax Rules**

- Ignore `.env` and all `.env.*` variants.
- Negate `.env.example` (and optionally `.env.template`, `.env.sample`) to commit the template.
- The negation **must** come after the ignore pattern.
- In frameworks like Next.js and Vite, `.env.local` and `.env.*.local` are automatically ignored by default patterns.
- **Never** commit a file containing real secrets, even in a private repository.

**Constraints and Limitations**

- **If a `.env` is already committed**: Rotate all secrets immediately, then remove the file from tracking with `git rm --cached .env` and add it to `.gitignore`.
- **`.env.example` must stay current**: When new variables are added, the example file must be updated.
- **Framework defaults**: Some frameworks (Next.js, Vite) have built-in env handling and may not need explicit `.gitignore` entries for all variants.

### Annotated Code Examples

#### Example 1: Standard Environment File Handling

```gitignore
# Environment files
.env
.env.*
!.env.example
```

**Why these patterns work:** `.env` is the primary environment file. `.env.*` catches variants like `.env.local`, `.env.production`, `.env.development`. `!.env.example` re-includes the template file, which contains placeholder values like `API_KEY=your_key_here`. This is the recommended pattern.

#### Example 2: Framework-Specific Patterns (Next.js)

```gitignore
# dotenv environment variable files
.env
.env.development.local
.env.test.local
.env.production.local
.env.local
```

**Why these patterns work:** Next.js uses specific `.env.*.local` naming conventions. The standard Next.js `.gitignore` template includes these patterns.

### Real-World Cases

- **New developer onboarding**: A developer clones a repository, copies `.env.example` to `.env`, fills in their local database URL, and starts developing.
- **Production deployment**: A CI/CD pipeline injects production secrets as environment variables (from GitHub Secrets, AWS Secrets Manager, etc.), so `.env` is never needed in the repository.
- **Accidental commit**: A developer accidentally commits `.env`; the team rotates all secrets, removes the file from tracking, and adds it to `.gitignore`.

## 8. Secrets, API Tokens, Keystores, and Private Credentials

### Definitions

**Core Definition**
Secrets, API tokens, keystores, and private credentials are files containing authentication material—private keys, certificates, passwords, tokens, and credential stores—that grant access to systems, services, or data.

**Technical Definition**
This category includes private keys (`*.pem`, `*.key`, `id_rsa`, `id_ed25519`), keystores (`*.jks`, `*.keystore`, `*.p12`, `*.pfx`), credential files (`credentials.json`, `secrets.yml`, `auth.json`), API token files (`*.token`, `*token.json`), and environment files (covered separately). These files must **never** be committed to any repository, public or private. If committed, the secrets are compromised and must be rotated immediately.

**Beginner-Friendly Explanation**
These are the keys to your digital kingdom: passwords, API keys, and private certificates. If you accidentally save them in Git, anyone who can see the repository—now or in the future—can use them to access your systems. **Never commit secrets.** Ignore them from the start.

### Purposes

- To prevent credential leakage and unauthorised access.
- To comply with security best practices and regulations.
- To enable secret rotation without changing repository history.
- To allow secure secret injection via CI/CD systems.
- To protect both the organisation and its users.

### Syntax Rules and Structure

**Common Patterns**

| Category | Patterns |
|----------|----------|
| Private keys | `*.pem`, `*.key`, `id_rsa`, `id_dsa`, `id_ecdsa`, `id_ed25519` |
| Certificates | `*.p12`, `*.pfx`, `*.cer`, `*.crt`, `*.der`, `*.csr` |
| Keystores | `*.jks`, `*.keystore`, `*.truststore` |
| Credential files | `credentials.json`, `credentials.yaml`, `secrets.json`, `secrets.yml`, `auth.json` |
| Token files | `*.token`, `*token.json`, `*tokens.json`, `.api-key` |
| SSH files | `known_hosts`, `.ssh/` |
| Cloud credentials | `.aws/`, `.gcloud/`, `.azure/` |

**Syntax Rules**

- Use extension patterns (`*.pem`, `*.key`) to match at any depth.
- Use specific file name patterns (`credentials.json`, `secrets.yml`).
- Use wildcard patterns (`*secret*`, `*credential*`) for broad coverage, but be careful not to over-match.
- **Negate placeholder files** if needed (e.g., `!credentials.example.json`).
- Add these patterns to your **global** ignore file to protect all repositories.

**Constraints and Limitations**

- **Over-broad patterns**: `*.json` is too broad; it would ignore `package.json`. Use specific names like `credentials.json`.
- **Already committed secrets**: If a secret was committed, it remains in Git history even after deletion. **Rotate the secret immediately** and consider history rewriting (e.g., `git filter-repo`).
- **Pre-commit hooks**: Tools like `gitleaks`, `trufflehog`, and `detect-secrets` can catch secrets before they're committed.
- **Environment variables**: Prefer environment variables over files for secrets in CI/CD.

#### Example 1: Comprehensive Secrets Ignore Section

```gitignore

*.key
*.p12
*.pfx
*.cer
*.crt
*.der
*.csr
*.jks
*.keystore

```

**Why these patterns work:** This covers the most common secret file types across languages and platforms. `*.pem` and `*.key` catch private keys. `credentials.json` and `secrets.yml` catch common credential file names. The patterns are based on real-world security-focused .gitignore files.

#### Example 2: SSH and Cloud Credentials

**Why these patterns work:** SSH private keys and cloud credential directories are extremely sensitive. They should never be committed. The SSH directory and key files are ignored, as are the credential directories for major cloud providers.

### Real-World Cases

- **Accidental secret commit**: A developer commits a `.pem` file; the team rotates the key immediately, removes the file from the repository, and adds the pattern to `.gitignore`.
- **CI/CD secret injection**: A pipeline injects `API_KEY` from GitHub Secrets, so no secret file is needed in the repository.
- **Pre-commit hook**: A team installs `gitleaks` as a pre-commit hook; it blocks commits containing patterns that look like secrets.
- **Open-source project**: A contributor accidentally includes `credentials.json`; the maintainer rejects the PR and asks them to rotate the credentials.
