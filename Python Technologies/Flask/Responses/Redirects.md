## Topic Overview

### Definitions

**Core Definition:** A redirect in Flask is an HTTP response that instructs the client's browser to navigate to a different URL. It is implemented via the `redirect()` function, which returns a response with a 3xx status code and a `Location` header pointing to the target URL.

**Technical Definition:** `flask.redirect(location, code=302, Response=None)` creates a `Response` object with the specified status code (default `302 Found`) and sets the `Location` header to the target URL. The function delegates to `current_app.redirect()` when an application context is active, which in turn uses the application's `response_class`; otherwise, it falls back to `werkzeug.utils.redirect`. Supported status codes include 301, 302, 303, 305, and 307. The `url_for()` function is the recommended way to generate the target URL, as it derives URLs from endpoint names and parameters rather than hard-coded strings.

**Beginner-Friendly Explanation:** A redirect is like a receptionist saying "That office moved—go to this new address instead." When your Flask view returns `redirect(url_for("some_view"))`, the browser automatically loads the new page. You use `url_for()` to figure out the correct URL so you don't have to hard-code it.

### Key Characteristics

- **Default is 302:** `redirect()` uses `302 Found` (temporary) unless you specify `code=301`.
- **Location header:** The response includes a `Location` header with the target URL.
- **Endpoint-based generation:** `url_for()` resolves endpoint names to URLs, handling variable parts and query strings.
- **PRG pattern support:** Redirects are the foundation of the POST/Redirect/GET pattern, which prevents duplicate form submissions.
- **Open redirect risk:** Unvalidated redirect targets can be exploited for phishing; validation is essential.
- **External URL support:** `url_for(..., _external=True)` generates absolute URLs for cross-domain redirects.

### Prerequisites

- Python 3.8+ and Flask installed (`pip install flask`).
- Familiarity with Flask routing, view functions, and the `request` object.
- Basic understanding of HTTP status codes (3xx class).
- Knowledge of Python functions and decorators.

### Related Programming Areas

- **HTTP status codes:** 3xx codes are the foundation of redirects.
- **URL construction:** `url_for()` is the primary tool for generating redirect targets.
- **Form handling:** The PRG pattern is a standard practice for form submissions.
- **Security:** Open redirect vulnerabilities are a common web security issue.
- **SEO:** 301 vs. 302 redirects have different implications for search engine indexing.

### Core Concepts / Features

1. `redirect()` (Mechanics, 302 Default, Target Parameters)

## 1. `redirect()` (Mechanics, 302 Default, Target Parameters)

### Definitions

**Core Definition:** `redirect()` is a Flask helper function that creates a response object instructing the client to navigate to a different URL.

**Technical Definition:** `flask.redirect(location, code=302, Response=None)` returns a `Response` object with the specified status code and a `Location` header set to `location`. When called within an application context, it delegates to `current_app.redirect()`, which uses the application's `response_class`. The `location` parameter can be a relative path (`/login`), an absolute URL (`https://example.com`), or a URL generated by `url_for()`. The `code` parameter accepts `301`, `302`, `303`, `305`, or `307`; the default is `302`.

**Beginner-Friendly Explanation:** `redirect()` is how you tell the browser "go to this other page instead." You give it the URL you want the user to land on, and Flask sends back a special response that makes the browser load that URL.

### Purposes

- To send users to a different page after an action (login, logout, form submission).
- To redirect legacy URLs to new locations.
- To enforce HTTPS by redirecting HTTP requests.
- To implement the POST/Redirect/GET pattern.
- To redirect users who are not authenticated to a login page.

### Syntax Rules and Structure

**Complete General Syntax:**

```python
from flask import redirect, url_for

# Basic redirect (302)
return redirect(url_for("endpoint_name"))

# Permanent redirect (301)
return redirect(url_for("endpoint_name"), code=301)

# Redirect to an external URL
return redirect("https://example.com")
```

**Component Breakdown:**

| Parameter | Description |
|-----------|-------------|
| `location` | Target URL (relative, absolute, or generated by `url_for()`) |
| `code` | HTTP status code (default `302`; supports `301`, `302`, `303`, `305`, `307`) |
| `Response` | Optional custom response class (used only when no app context) |

**Syntax Rules:**

- `location` is required; it can be a relative path or an absolute URL.
- `code` defaults to `302`; use `301` for permanent redirects.
- The `Location` header is automatically set to `location`.
- Werkzeug automatically converts relative `Location` headers to absolute URLs.

**Constraints and Limitations:**

- The `code` parameter must be one of the supported 3xx codes; other values raise an error.
- Redirects do not carry a response body; the client is expected to follow the `Location` header.
- 301 redirects are cached by browsers; use with caution if the target may change.

### Annotated Code Examples

**Example 1: Basic Redirect**

```python
from flask import Flask, redirect, url_for

app = Flask(__name__)

@app.route("/")
def index():
    return "Home Page"

@app.route("/old")
def old_page():
    return redirect(url_for("index"))

if __name__ == "__main__":
    app.run(debug=True)
```

**Expected Output:**
- `GET /old` → `302 Found` redirect to `/`.

**Why this output:** `redirect(url_for("index"))` creates a response with status `302` and `Location: /`. The browser automatically navigates to the home page.

**Example 2: Permanent Redirect**

```python
@app.route("/legacy")
def legacy():
    return redirect(url_for("index"), code=301)
```

**Expected Output:**
- `GET /legacy` → `301 Moved Permanently` redirect to `/`.

**Why this output:** The `code=301` parameter makes the redirect permanent. Browsers and search engines will update their records to point to `/` instead of `/legacy`.

### Real-World Cases

- **Login redirects:** After successful login, redirect to the dashboard.
- **Logout:** Clear the session and redirect to the home page.
- **Legacy URLs:** Permanently redirect old URLs to new ones after a site restructure.
- **HTTPS enforcement:** Redirect HTTP requests to HTTPS.

## 2. `url_for()` (Generating Local and External Routing Targets)

### Definitions

**Core Definition:** `url_for()` is a Flask function that generates a URL for a given endpoint (view function name) and set of parameters, enabling reverse routing instead of hard-coded URLs.

**Technical Definition:** `flask.url_for(endpoint, **values)` delegates to `current_app.url_for()` when an application context is active. It accepts reserved keyword arguments (`_anchor`, `_method`, `_scheme`, `_external`) and arbitrary values for the endpoint's URL variables. Unknown values are appended as query parameters. When `_external=True`, an absolute URL including the scheme and domain is generated; otherwise, a relative URL is returned. Outside a request context, external URLs require `SERVER_NAME` to be configured.

**Beginner-Friendly Explanation:** `url_for()` figures out the correct URL for a view function by name. Instead of writing `/user/42` yourself, you write `url_for("profile", user_id=42)`. If you later change the route, all your links update automatically.

### Purposes

- To generate URLs dynamically without hard-coding paths.
- To build redirect targets safely and consistently.
- To handle variable URL parts and query parameters automatically.
- To generate external URLs for emails, API responses, and OAuth callbacks.
- To avoid broken links when routes change.

### Syntax Rules and Structure

**Complete General Syntax:**

```python
from flask import url_for

# Internal URL
url_for("endpoint_name", param=value)

# External URL
url_for("endpoint_name", param=value, _external=True)

# External URL with HTTPS scheme
url_for("endpoint_name", _external=True, _scheme="https")

# With query parameters (unknown keys become query params)
url_for("search", q="flask", page=2)  # /search?q=flask&page=2
```

**Component Breakdown:**

| Parameter | Description |
|-----------|-------------|
| `endpoint` | View function name (required) |
| `**values` | Values for URL variables and query parameters |
| `_external` | If `True`, generates absolute URL with scheme and domain |
| `_scheme` | Overrides the URL scheme (e.g., `"https"`); requires `_external=True` |
| `_anchor` | Appends a fragment identifier |
| `_method` | Generates URL for a specific HTTP method |

**Syntax Rules:**

- The endpoint name defaults to the view function's `__name__`.
- Unknown keyword arguments become query string parameters.
- `_external=True` includes scheme and domain; requires `SERVER_NAME` outside a request.
- `_scheme` can only be used with `_external=True`.

**Constraints and Limitations:**

- If the endpoint does not exist, a `BuildError` is raised.
- Outside a request context, external URLs require `SERVER_NAME` to be set.
- `url_for()` cannot generate URLs for endpoints not registered in the URL map.

### Annotated Code Examples

**Example 1: Internal Redirect with `url_for()`**

```python
from flask import Flask, redirect, url_for

app = Flask(__name__)

@app.route("/login")
def login():
    return "Login Page"

@app.route("/dashboard")
def dashboard():
    return "Dashboard"

@app.route("/go-to-login")
def go_to_login():
    return redirect(url_for("login"))
```

**Expected Output:**
- `GET /go-to-login` → `302 Found` redirect to `/login`.

**Why this output:** `url_for("login")` generates the URL for the `login` endpoint (`/login`). `redirect()` then creates a response that sends the browser there.

**Example 2: External URL with `_external=True`**

```python
@app.route("/callback")
def callback():
    return redirect(url_for("dashboard", _external=True, _scheme="https"))
```

**Expected Output:**
- `GET /callback` → `302 Found` redirect to `https://example.com/dashboard` (assuming `SERVER_NAME` is configured).

**Why this output:** `_external=True` generates an absolute URL, and `_scheme="https"` forces the HTTPS scheme. This is useful for OAuth callbacks and external integrations.

### Real-World Cases

- **Template links:** `{{ url_for('user_profile', username=user.name) }}` generates a link to a user's profile.
- **Form actions:** `<form action="{{ url_for('submit_form') }}">` ensures the form posts to the correct URL.
- **Email links:** Generating absolute URLs for password reset links.
- **OAuth callbacks:** Providing absolute redirect URIs to third-party providers.

## 3. Redirect After Form Submission (Mitigating Double-Submission Bugs)

### Definitions

**Core Definition:** Redirecting after form submission means returning a redirect response instead of rendering a page directly after processing a POST request, preventing the browser from re-submitting the form when the user refreshes the page.

**Technical Definition:** When a form is submitted via POST and the server responds with an HTML page, refreshing the browser re-sends the POST request, causing duplicate submissions. By returning a redirect (typically 302) after processing the POST, the browser's last request becomes a GET, so refreshing only re-fetches the result page without re-submitting the form. This is the core mechanism of the POST/Redirect/GET (PRG) pattern.

**Beginner-Friendly Explanation:** If you submit a form and then refresh the page, the browser asks "do you want to resubmit?" and you might accidentally create duplicate data. If the server redirects you after processing the form, refreshing just reloads the result page harmlessly.

### Purposes

- To prevent duplicate form submissions on page refresh.
- To avoid the browser's "confirm form resubmission" dialog.
- To provide a clean, bookmarkable URL for the result page.
- To separate the form-processing action from the result display.
- To implement the POST/Redirect/GET pattern consistently.

### Syntax Rules and Structure

**Complete General Syntax:**

```python
from flask import Flask, request, redirect, url_for, render_template

app = Flask(__name__)

@app.route("/submit", methods=["GET", "POST"])
def submit():
    if request.method == "POST":
        # Process the form data
        name = request.form.get("name")
        # Save to database, etc.
        return redirect(url_for("success", name=name))
    return render_template("form.html")

@app.route("/success")
def success():
    name = request.args.get("name", "")
    return f"Success! Name: {name}"
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| POST handler | Processes the form data |
| `redirect()` | Returns a 302 redirect after processing |
| Success view | Displays the result via GET |

**Syntax Rules:**

- The form-handling route must accept both GET (to display the form) and POST (to process it).
- After processing, always return a redirect, not a rendered template.
- The redirect target should be a GET route that displays the result.
- Pass result data via query parameters, session, or database lookup.

**Constraints and Limitations:**

- Redirects cannot carry a request body; result data must be passed via query string, session, or database.
- Very large result data should not be passed via query parameters.
- The PRG pattern does not apply to AJAX form submissions; use client-side handling instead.

### Annotated Code Examples

**Example 1: PRG Pattern for a Contact Form**

```python
from flask import Flask, request, redirect, url_for, render_template_string

app = Flask(__name__)

FORM = """
<form method="POST">
    <input name="name" placeholder="Your name">
    <button type="submit">Submit</button>
</form>
"""

@app.route("/contact", methods=["GET", "POST"])
def contact():
    if request.method == "POST":
        name = request.form.get("name", "Guest")
        # Simulate saving to database
        return redirect(url_for("thank_you", name=name))
    return render_template_string(FORM)

@app.route("/thank-you")
def thank_you():
    name = request.args.get("name", "Guest")
    return f"Thank you, {name}!"

if __name__ == "__main__":
    app.run(debug=True)
```

**Expected Output:**
- `POST /contact` with `name=Alice` → `302 Found` redirect to `/thank-you?name=Alice`, then `"Thank you, Alice!"`.
- Refreshing `/thank-you` reloads the GET page without re-submitting the form.

**Why this output:** The POST handler processes the form and returns a redirect. The browser follows the redirect with a GET request. Refreshing the browser re-sends the GET request, not the POST, preventing duplicate submissions.

### Real-World Cases

- **User registration:** After creating an account, redirect to a welcome page.
- **Order placement:** After placing an order, redirect to an order confirmation page.
- **Comment posting:** After posting a comment, redirect to the comment list.
- **Settings updates:** After saving settings, redirect to the settings page with a success message.

## 4. Permanent vs. Temporary Redirects (301 vs. 302)

### Definitions

**Core Definition:** `301 Moved Permanently` indicates that a resource has permanently moved to a new URL, while `302 Found` indicates a temporary redirect. The distinction affects browser caching and search engine indexing.

**Technical Definition:** `301 Moved Permanently` tells the client that the requested resource has been assigned a new permanent URI; future references should use the new URI. Browsers and search engines cache 301 redirects and update their records. `302 Found` indicates a temporary redirect; the original URL should continue to be used for future requests. In Flask, `redirect()` defaults to `302`; pass `code=301` for permanent redirects. Both codes are defined in RFC 9110 and are implemented by all browsers.

**Beginner-Friendly Explanation:** A 301 says "I've moved forever—update your bookmarks." A 302 says "I'm just visiting this other page for now—keep using the old address." 301 redirects are cached by browsers, so they are faster but harder to undo.

### Purposes

- **301:** To redirect legacy URLs to new ones after a permanent site restructure.
- **301:** To enforce HTTPS by permanently redirecting HTTP requests.
- **302:** To redirect users after login or form submission (temporary).
- **302:** To redirect users to a language-specific version of a page (temporary).
- **SEO:** To tell search engines which URL is canonical.

### Syntax Rules and Structure

**Complete General Syntax:**

```python
from flask import redirect, url_for

# Permanent redirect (301)
return redirect(url_for("new_page"), code=301)

# Temporary redirect (302, default)
return redirect(url_for("new_page"))
```

**Component Breakdown:**

| Code | Meaning | Browser Behavior | SEO Impact |
|------|---------|------------------|------------|
| 301 | Permanent | Caches the new URL | Transfers page rank |
| 302 | Temporary | Does not cache | Keeps original URL |

**Syntax Rules:**

- `redirect()` defaults to `302`; pass `code=301` for permanent redirects.
- 301 redirects are cached by browsers and may be difficult to reverse.
- 302 redirects are not cached, making them safer for temporary changes.

**Constraints and Limitations:**

- 301 redirects are cached indefinitely by some browsers; use with caution during development.
- Using 301 for temporary changes can cause users to be stuck on the wrong URL.
- Search engines may take time to update their indexes after a 301 redirect.

### Annotated Code Examples

**Example 1: Permanent Redirect for Legacy URL**

```python
from flask import Flask, redirect, url_for

app = Flask(__name__)

@app.route("/old-blog")
def old_blog():
    return redirect(url_for("new_blog"), code=301)

@app.route("/blog")
def new_blog():
    return "New Blog Home"

if __name__ == "__main__":
    app.run(debug=True)
```

**Expected Output:**
- `GET /old-blog` → `301 Moved Permanently` redirect to `/blog`.

**Why this output:** The `code=301` parameter makes the redirect permanent. Browsers will cache this redirect, and search engines will update their records to point to `/blog`.

**Example 2: Temporary Redirect After Login**

```python
@app.route("/login")
def login():
    return redirect(url_for("dashboard"))  # 302 default
```

**Expected Output:**
- `GET /login` → `302 Found` redirect to `/dashboard`.

**Why this output:** The default `302` code indicates a temporary redirect. Browsers will not cache this redirect, so the next visit to `/login` will hit the server again.

### Real-World Cases

- **Domain migration:** Permanently redirect `old-domain.com` to `new-domain.com` with 301.
- **URL restructure:** Permanently redirect `/products/123` to `/items/123` with 301.
- **Login redirect:** Temporarily redirect to the dashboard after login with 302.
- **Language selection:** Temporarily redirect to `/en/` or `/fr/` based on user preference with 302.

## 5. The POST/Redirect/GET (PRG) Pattern

### Definitions

**Core Definition:** The POST/Redirect/GET (PRG) pattern is a web development design pattern in which a POST request that modifies server state is followed by a redirect, forcing the browser to issue a GET request for the result page.

**Technical Definition:** The PRG pattern separates state-changing operations (POST) from result display (GET). When a form is submitted via POST, the server processes the data and returns a redirect (typically 302) to a GET endpoint that displays the result. This prevents duplicate submissions on refresh and avoids the browser's "confirm form resubmission" dialog. The pattern is a standard best practice for web forms and is recommended in the Flask documentation and by web standards bodies.

**Beginner-Friendly Explanation:** The PRG pattern means: when you submit a form, the server does the work and then tells the browser "now go look at this result page." If you refresh the result page, it's just a normal page load, not a form resubmission.

### Purposes

- To prevent duplicate form submissions on page refresh.
- To avoid the browser's "confirm form resubmission" dialog.
- To provide a clean, bookmarkable URL for the result page.
- To separate state-changing actions from result display.
- To improve user experience and data integrity.

### Syntax Rules and Structure

**Complete General Syntax:**

```python
from flask import Flask, request, redirect, url_for, render_template

app = Flask(__name__)

@app.route("/form", methods=["GET", "POST"])
def form():
    if request.method == "POST":
        # Process the form data (e.g., save to database)
        data = request.form.get("data")
        # Redirect to a GET endpoint
        return redirect(url_for("result"))
    return render_template("form.html")

@app.route("/result")
def result():
    # Fetch and display the result
    return render_template("result.html")
```

**Component Breakdown:**

| Step | Method | Action |
|------|--------|--------|
| 1 | GET | Display the form |
| 2 | POST | Process the form data |
| 3 | Redirect | Return 302 to the result page |
| 4 | GET | Display the result |

**Syntax Rules:**

- The form-handling route must accept both GET and POST.
- After processing the POST, always return a redirect, not a rendered template.
- The redirect target must be a GET-only route.
- Result data can be passed via query parameters, session, or database lookup.

**Constraints and Limitations:**

- Redirects cannot carry a request body; use query strings or sessions for small result data.
- Very large result data should be stored in a database or cache and retrieved by ID.
- The PRG pattern does not apply to AJAX form submissions.

### Annotated Code Examples

**Example 1: Complete PRG Pattern**

```python
from flask import Flask, request, redirect, url_for, render_template_string

app = Flask(__name__)

FORM = """
<form method="POST">
    <input name="title" placeholder="Title">
    <textarea name="content" placeholder="Content"></textarea>
    <button type="submit">Post</button>
</form>
"""

@app.route("/posts/new", methods=["GET", "POST"])
def new_post():
    if request.method == "POST":
        title = request.form.get("title", "Untitled")
        content = request.form.get("content", "")
        # Save to database (simulated)
        return redirect(url_for("view_post", title=title))
    return render_template_string(FORM)

@app.route("/posts/view")
def view_post():
    title = request.args.get("title", "Untitled")
    return f"Post created: {title}"

if __name__ == "__main__":
    app.run(debug=True)
```

**Expected Output:**
- `POST /posts/new` with `title=Hello` → `302 Found` redirect to `/posts/view?title=Hello`, then `"Post created: Hello"`.
- Refreshing `/posts/view` reloads the GET page without re-posting.

**Why this output:** The POST handler processes the form and redirects to a GET endpoint. The browser follows the redirect with a GET request, and refreshing only re-fetches the GET page.

### Real-World Cases

- **Blog comments:** After posting a comment, redirect to the comment list.
- **E-commerce checkout:** After placing an order, redirect to the order confirmation page.
- **User registration:** After creating an account, redirect to the welcome page.
- **Settings updates:** After saving settings, redirect to the settings page.

## 6. Open Redirect Vulnerability Mitigation

### Definitions

**Core Definition:** An open redirect vulnerability occurs when an application redirects users to a URL specified in an unvalidated parameter, allowing attackers to craft links that appear to be from the trusted site but lead to a malicious destination.

**Technical Definition:** Open redirects (CWE-601) are a class of web vulnerabilities where the application uses untrusted input (e.g., a `next` or `url` query parameter) to determine the redirect target without validation. Attackers exploit this for phishing, credential theft, and malware distribution. In Flask, mitigation involves validating redirect targets against a whitelist of allowed hosts or restricting redirects to relative paths only. The `next` parameter is a common attack vector in login flows.

**Beginner-Friendly Explanation:** If your login page has `?next=https://evil.com`, an attacker can send a victim a link that looks like your site but redirects to a phishing page. Always validate where you're redirecting.

### Purposes

- To prevent phishing attacks that abuse your domain's trust.
- To protect users from being redirected to malicious sites.
- To comply with security best practices (OWASP, CWE-601).
- To maintain the integrity of your application's redirect behavior.
- To avoid reputational damage from users being phished via your site.

### Syntax Rules and Structure

**Complete General Syntax (Validation):**

```python
from urllib.parse import urlparse, urljoin
from flask import request, redirect, url_for

def is_safe_url(target):
    """Check if the target URL is safe for redirecting."""
    ref_url = urlparse(request.host_url)
    test_url = urlparse(urljoin(request.host_url, target))
    return test_url.scheme in ('http', 'https') and ref_url.netloc == test_url.netloc

@app.route("/login")
def login():
    next_page = request.args.get("next", "")
    if next_page and is_safe_url(next_page):
        return redirect(next_page)
    return redirect(url_for("index"))
```

**Whitelist Approach:**

```python
ALLOWED_HOSTS = {"example.com", "app.example.com"}

def is_safe_redirect(target):
    parsed = urlparse(target)
    if not parsed.netloc:
        return True  # Relative path
    return parsed.netloc in ALLOWED_HOSTS

@app.route("/redirect")
def safe_redirect():
    target = request.args.get("url", "/")
    if not is_safe_redirect(target):
        target = "/"
    return redirect(target)
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `urlparse` | Parses a URL into scheme, netloc, path, etc. |
| `request.host_url` | The current request's base URL |
| `ALLOWED_HOSTS` | Whitelist of trusted domains |
| Relative path check | Ensures the target starts with `/` and not `//` |

**Syntax Rules:**

- Always validate redirect targets before passing them to `redirect()`.
- Prefer relative paths over absolute URLs for internal redirects.
- Whitelist allowed hosts for external redirects.
- Never trust user-supplied `next` or `url` parameters without validation.

**Constraints and Limitations:**

- URL parsing can be tricky; use well-tested libraries like `urllib.parse`.
- Whitelists must be maintained as domains change.
- Protocol-relative URLs (`//evil.com`) must be rejected.

### Annotated Code Examples

**Example 1: Safe Redirect After Login**

```python
from urllib.parse import urlparse, urljoin
from flask import Flask, request, redirect, url_for

app = Flask(__name__)

def is_safe_url(target):
    ref_url = urlparse(request.host_url)
    test_url = urlparse(urljoin(request.host_url, target))
    return test_url.scheme in ('http', 'https') and ref_url.netloc == test_url.netloc

@app.route("/login")
def login():
    next_page = request.args.get("next", "")
    if next_page and is_safe_url(next_page):
        return redirect(next_page)
    return redirect(url_for("index"))

@app.route("/")
def index():
    return "Home"

if __name__ == "__main__":
    app.run(debug=True)
```

**Expected Output:**
- `GET /login?next=/dashboard` → `302 Found` redirect to `/dashboard` (safe).
- `GET /login?next=https://evil.com` → `302 Found` redirect to `/` (unsafe target rejected).

**Why this output:** The `is_safe_url()` function checks that the target URL has the same host as the application. If the target is external, the redirect falls back to the home page.

**Example 2: Whitelist-Based Validation**

```python
from urllib.parse import urlparse
from flask import Flask, request, redirect

app = Flask(__name__)
ALLOWED_HOSTS = {"example.com", "app.example.com"}

def is_safe_redirect(target):
    parsed = urlparse(target)
    if not parsed.netloc:
        return True  # Relative path
    return parsed.netloc in ALLOWED_HOSTS

@app.route("/redirect")
def safe_redirect():
    target = request.args.get("url", "/")
    if not is_safe_redirect(target):
        target = "/"
    return redirect(target)
```

**Expected Output:**
- `GET /redirect?url=https://example.com/page` → redirect to `https://example.com/page`.
- `GET /redirect?url=https://evil.com` → redirect to `/`.

**Why this output:** The whitelist allows only trusted hosts. External URLs not in the whitelist are rejected, and the user is redirected to the home page instead.
