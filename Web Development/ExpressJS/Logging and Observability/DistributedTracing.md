# Distributed Tracing — Comprehensive Programming Cheat Sheet

---

## Topic Overview

### Definitions

**Core Definition:** Distributed tracing is the practice of tracking a single request as it flows through multiple services, recording the time spent in each service and the causal relationships between operations, so that operators can diagnose latency, errors, and bottlenecks across a distributed system.

**Technical Definition:** Distributed tracing instruments an application to produce **traces** — a trace is the complete journey of one request or transaction across services, identified by a `trace_id`. Within a trace, each unit of work (a function call, database query, HTTP request, or queue processing) is represented as a **span**, identified by a `span_id` and linked to its parent via a `parent_span_id`. Context (the current trace ID and active span ID) is propagated across process and network boundaries using the W3C Trace Context standard (`traceparent` header). OpenTelemetry is the vendor-neutral standard for generating, collecting, and exporting this telemetry data.

**Beginner-Friendly Explanation:** Imagine a package being shipped through multiple warehouses. Without tracking, you only know it left and arrived — not where it got stuck or delayed. Distributed tracing is like a tracking number for every request: each service stamps the package with the same number, so you can see its complete journey, how long it spent at each stop, and exactly where things went wrong.

### Key Characteristics

- **Trace ID as the unifying identifier:** Every span in a trace shares the same `trace_id`, enabling correlation across services.
- **Span hierarchy:** Spans form a tree — a root span (the inbound request) and child spans for each sub-operation.
- **Context propagation:** Trace context travels across service boundaries via HTTP headers (W3C `traceparent`), gRPC metadata, and message queue attributes.
- **Vendor-neutral instrumentation:** OpenTelemetry provides a single API and SDK that works with any backend (Jaeger, Zipkin, Tempo, Datadog, etc.).
- **Automatic and manual instrumentation:** Auto-instrumentation captures HTTP, database, and framework operations without code changes; manual instrumentation adds business-specific spans.
- **Sampling controls cost:** Head-based and tail-based sampling reduce the volume of exported traces while preserving errors and slow requests.

### Prerequisites

- **Node.js runtime** (v18 or higher).
- **OpenTelemetry packages installed:** `@opentelemetry/sdk-node`, `@opentelemetry/auto-instrumentations-node`, and an exporter package (e.g., `@opentelemetry/exporter-trace-otlp-http`).
- **A tracing backend** (Jaeger, Zipkin, Grafana Tempo, or a vendor platform).
- **Basic understanding of HTTP, microservices, and asynchronous programming.**
- **Familiarity with `AsyncLocalStorage`** for context propagation.

### Related Programming Areas

- **Metrics:** Complementary observability signal for aggregated performance data.
- **Logging:** Correlation of logs with trace IDs for request-scoped debugging.
- **APM (Application Performance Monitoring):** Commercial platforms built on tracing.
- **Service mesh:** Infrastructure-level tracing (Istio, Linkerd) that complements application-level tracing.
- **W3C Trace Context:** The standard for propagating trace context across services.

### Core Concepts

1. **Trace IDs** — unique identifiers for the full request journey.
2. **Spans** — timed units of work within a trace.
3. **Service-to-Service Tracing** — propagating context across service boundaries.
4. **OpenTelemetry Concepts** — TracerProvider, MeterProvider, context propagation.
5. **Exporters** — OTLP, Jaeger, Zipkin.
6. **Automatic vs. Manual Instrumentation** — zero-code vs. custom spans.
7. **Sampling Strategies** — head-based vs. tail-based sampling.

## Core Concept 1: Trace IDs

### Definitions

**Core Definition:** A trace ID is a globally unique 128-bit (32 hex character) identifier assigned to a request when it enters the system, and propagated to every service that handles the request so all spans can be correlated.

**Technical Definition:** In OpenTelemetry, a trace ID is a 16-byte (128-bit) value represented as 32 lowercase hexadecimal characters. The ID is generated by the first service to handle the request (or by an API gateway). Every span created during that request’s lifetime carries the same `trace_id`. The W3C Trace Context specification defines the `traceparent` header format: `00-{trace-id}-{parent-span-id}-{flags}`, where `trace-id` is the 32-hex-character trace ID, `parent-span-id` is the 16-hex-character span ID of the caller, and `flags` indicates whether the trace is sampled.

**Beginner-Friendly Explanation:** A trace ID is like a tracking number for a shipment. Every warehouse (service) that handles the package writes down the same tracking number. Later, you can search for that number and see every warehouse the package visited, how long it stayed, and whether anything went wrong.

### Purposes

- To uniquely identify a complete request across all services and all time.
- To enable correlation of logs from different services for the same request.
- To provide a searchable key in tracing backends (Jaeger, Tempo, etc.).
- To support causal analysis — understanding which service call triggered which downstream call.

### Syntax Rules and Structure

**W3C Trace Context `traceparent` header format:**
```
traceparent: 00-{trace-id}-{parent-span-id}-{trace-flags}
```

| Component | Length | Example | Description |
|-----------|--------|---------|-------------|
| Version | 2 hex | `00` | Current version. |
| Trace ID | 32 hex | `0af7651916cd43dd8448eb211c80319c` | Unique trace identifier. |
| Parent Span ID | 16 hex | `b7ad6b7169203331` | Span ID of the caller. |
| Trace Flags | 2 hex | `01` | Sampled (`01`) or not (`00`). |

**Generating a trace ID manually (Node.js):**
```js
const crypto = require('crypto');

function generateTraceId() {
  // 16 random bytes = 32 hex characters
  return crypto.randomBytes(16).toString('hex');
}

function generateSpanId() {
  // 8 random bytes = 16 hex characters
  return crypto.randomBytes(8).toString('hex');
}
```

**Rules:**
- Trace IDs must be 32 lowercase hexadecimal characters in OpenTelemetry. 
- The trace ID is generated once at the entry point and never regenerated.
- Trace IDs are globally unique — collisions are astronomically unlikely with 128-bit randomness.
- The `traceparent` header is the standard propagation mechanism. 
- Do not confuse trace IDs (32 hex) with span IDs (16 hex). 

### Annotated Code Example

```js
// trace-id-demo.js
const crypto = require('crypto');

// Generate a trace ID and span ID
const traceId = crypto.randomBytes(16).toString('hex');  // 32 hex chars
const spanId = crypto.randomBytes(8).toString('hex');     // 16 hex chars

console.log('Trace ID:', traceId);
console.log('Trace ID length:', traceId.length);  // 32
console.log('Span ID:', spanId);
console.log('Span ID length:', spanId.length);    // 16

// W3C traceparent header
const traceparent = `00-${traceId}-${spanId}-01`;
console.log('traceparent:', traceparent);
```

**Expected Output:**
```
Trace ID: 0af7651916cd43dd8448eb211c80319c
Trace ID length: 32
Span ID: b7ad6b7169203331
Span ID length: 16
traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
```

**Why this output:** The trace ID is 32 hex characters (128 bits), the span ID is 16 hex characters (64 bits). The `traceparent` header combines them with the version (`00`) and flags (`01` for sampled). This header is sent to downstream services, which extract the trace ID and continue the trace.

### Real-World Cases

- **E-commerce checkout:** A single trace ID follows the request through cart, inventory, payment, and order services.
- **API gateways:** The gateway generates the trace ID and injects it into the `traceparent` header for all downstream calls.
- **Log correlation:** Searching logs by trace ID reveals every log line from every service that handled the request.

## Core Concept 2: Spans

### Definitions

**Core Definition:** A span is a timed unit of work within a trace — it represents a single operation such as an HTTP request, database query, function call, or message processing. Each span has a start time, end time, name, and a unique span ID, and is linked to its parent span.

**Technical Definition:** An OpenTelemetry span contains: a **name** (low-cardinality label such as `http.server.request` or `db.query.users.select`), **start and end timestamps** (high-precision), a **span ID** (16 hex characters), a **trace ID** (shared with all spans in the trace), a **parent span ID** (the span that caused this one), **attributes** (key-value metadata such as `http.method`, `http.status_code`, `db.system`), **events** (timestamped logs within the span), and **status** (OK, ERROR, or UNSET).

**Beginner-Friendly Explanation:** A span is one step in the journey. If the trace is the entire road trip, each span is a leg of the trip — driving to the airport, waiting at security, boarding the plane, landing. Each leg has a start and end time, and they are nested inside each other (the whole trip contains the airport visit, which contains the security check).

### Purposes

- To measure the duration of each operation in the request path.
- To identify which operation is the bottleneck (e.g., the database query that takes 2 seconds).
- To record contextual metadata (HTTP method, status code, database table).
- To capture errors and exceptions that occur during the operation.
- To build the causal tree of the request (which operation triggered which).

### Syntax Rules and Structure

**Creating a span manually:**
```js
const { trace } = require('@opentelemetry/api');

const tracer = trace.getTracer('my-service');

async function processOrder(orderId) {
  return tracer.startActiveSpan('processOrder', async (span) => {
    span.setAttribute('order.id', orderId);

    try {
      const result = await db.query('SELECT * FROM orders WHERE id = $1', [orderId]);
      span.setAttribute('db.rows', result.rowCount);
      span.setStatus({ code: SpanStatusCode.OK });
      return result;
    } catch (err) {
      span.recordException(err);
      span.setStatus({ code: SpanStatusCode.ERROR, message: err.message });
      throw err;
    } finally {
      span.end();
    }
  });
}
```

| Span Property | Type | Example | Purpose |
|--------------|------|---------|---------|
| `name` | String | `db.query.users.select` | Identifies the operation. |
| `startTime` / `endTime` | Timestamp | — | Duration calculation. |
| `spanId` | 16 hex | `b7ad6b7169203331` | Unique within the trace. |
| `traceId` | 32 hex | `0af7651916...` | Shared across all spans. |
| `parentSpanId` | 16 hex | — | Causal parent. |
| `attributes` | Key-value | `http.method: GET` | Searchable metadata. |
| `status` | Enum | `OK`, `ERROR` | Outcome. |
| `events` | Array | `{ name: 'exception' }` | Timestamped logs. |

**Rules:**
- Span names should be low-cardinality — use `http.server.request` not `GET /users/123`.
- Always call `span.end()` to finalise the span.
- Use `span.recordException(err)` to capture errors.
- Set `span.setStatus({ code: SpanStatusCode.ERROR })` on failures.
- Use `span.setAttribute()` for searchable metadata, not for large payloads.

### Annotated Code Example

```js
// span-demo.js
const { trace, SpanStatusCode } = require('@opentelemetry/api');

const tracer = trace.getTracer('order-service');

async function processOrder(orderId) {
  // Root span — the inbound request
  return tracer.startActiveSpan('processOrder', async (span) => {
    span.setAttribute('order.id', orderId);
    span.setAttribute('service.name', 'order-service');

    try {
      // Child span — database query
      const order = await tracer.startActiveSpan('db.query.orders', async (dbSpan) => {
        dbSpan.setAttribute('db.system', 'postgresql');
        dbSpan.setAttribute('db.statement', 'SELECT * FROM orders WHERE id = $1');
        const result = { id: orderId, total: 99.99 };
        dbSpan.end();
        return result;
      });

      // Child span — payment processing
      await tracer.startActiveSpan('payment.charge', async (paySpan) => {
        paySpan.setAttribute('payment.provider', 'stripe');
        paySpan.setAttribute('payment.amount', order.total);
        paySpan.end();
      });

      span.setStatus({ code: SpanStatusCode.OK });
      return order;
    } catch (err) {
      span.recordException(err);
      span.setStatus({ code: SpanStatusCode.ERROR, message: err.message });
      throw err;
    } finally {
      span.end();
    }
  });
}

processOrder('ord_123').then(() => console.log('Order processed'));
```

**Expected Output (in tracing backend — Jaeger/Tempo):**
```
Trace: 0af7651916cd43dd8448eb211c80319c
├── processOrder (250ms)
│   ├── db.query.orders (45ms)  ← attribute: db.system=postgresql
│   └── payment.charge (180ms)  ← attribute: payment.provider=stripe
```

**Why this output:** The root span `processOrder` wraps the entire operation. Inside it, two child spans are created: `db.query.orders` and `payment.charge`. The tracing backend displays this as a tree, showing the duration of each operation. The root span’s duration (250ms) equals the sum of its children plus the time spent in the function itself.

### Real-World Cases

- **Database query optimisation:** Identifying the slowest query in a request.
- **External API calls:** Measuring the latency of third-party services.
- **Function profiling:** Understanding which internal function is the bottleneck.

## Core Concept 3: Service-to-Service Tracing

### Definitions

**Core Definition:** Service-to-service tracing is the propagation of trace context across network boundaries — HTTP, gRPC, message queues — so that spans from different services are linked into a single trace.

**Technical Definition:** OpenTelemetry uses the W3C Trace Context standard for propagation. When a service makes an outbound HTTP request, the instrumentation (or manual code) injects the `traceparent` header containing the trace ID, parent span ID, and sampling flags. The receiving service extracts the header, creates a new span with the extracted trace ID and the incoming span ID as its parent, and continues the trace. This process repeats for every service boundary, resulting in a complete end-to-end trace.

**Beginner-Friendly Explanation:** When Service A calls Service B, it passes along the trace ID and its own span ID in an HTTP header. Service B reads that header, continues the trace with the same trace ID, and records its own work as a child span. When Service B calls Service C, the process repeats. The result is a complete picture of the request across all services.

### Purposes

- To connect spans from different services into a single trace.
- To measure end-to-end latency across service boundaries.
- To identify which service in a chain is the bottleneck.
- To support distributed debugging — following a request through microservices.

### Syntax Rules and Structure

**HTTP propagation (automatic with instrumentation):**
```js
// With auto-instrumentation, propagation is automatic.
// The HTTP instrumentation injects traceparent into outbound requests
// and extracts it from inbound requests.

// Manual injection (if not using auto-instrumentation):
const { propagation, context } = require('@opentelemetry/api');

const headers = {};
propagation.inject(context.active(), headers);
// headers now contains: { traceparent: '00-{traceId}-{spanId}-01' }

await fetch('http://service-b/api/data', { headers });
```

**Message queue propagation:**
```js
// Producer: inject context into message attributes
const message = { body: '...' };
propagation.inject(context.active(), message.headers);

// Consumer: extract context from message attributes
const parentContext = propagation.extract(context.active(), message.headers);
tracer.startActiveSpan('process-message', { context: parentContext }, (span) => {
  // Continue the trace
});
```

| Transport | Propagation Mechanism |
|-----------|----------------------|
| HTTP | `traceparent` header. |
| gRPC | Metadata key `traceparent`. |
| Message queues | Message attributes/headers. |
| TCP | Custom protocol headers. |

**Rules:**
- Auto-instrumentation handles HTTP, gRPC, and many libraries automatically. 
- For custom transports (message queues, WebSockets), inject and extract manually.
- The `traceparent` header format is `00-{trace-id}-{parent-span-id}-{flags}`. 
- Ensure the receiving service extracts the context before creating any spans.

### Annotated Code Example

```js
// service-a.js
const { NodeSDK } = require('@opentelemetry/sdk-node');
const { getNodeAutoInstrumentations } = require('@opentelemetry/auto-instrumentations-node');
const { OTLPTraceExporter } = require('@opentelemetry/exporter-trace-otlp-http');

const sdk = new NodeSDK({
  serviceName: 'service-a',
  traceExporter: new OTLPTraceExporter({ url: 'http://collector:4318/v1/traces' }),
  instrumentations: [getNodeAutoInstrumentations()]
});
sdk.start();

const express = require('express');
const app = express();

app.get('/api/process', async (req, res) => {
  // Outbound call — instrumentation injects traceparent automatically
  const response = await fetch('http://service-b:3001/api/data');
  const data = await response.json();
  res.json({ from: 'service-a', data });
});

app.listen(3000, () => console.log('Service A on 3000'));
```

```js
// service-b.js
const { NodeSDK } = require('@opentelemetry/sdk-node');
const { getNodeAutoInstrumentations } = require('@opentelemetry/auto-instrumentations-node');
const { OTLPTraceExporter } = require('@opentelemetry/exporter-trace-otlp-http');

const sdk = new NodeSDK({
  serviceName: 'service-b',
  traceExporter: new OTLPTraceExporter({ url: 'http://collector:4318/v1/traces' }),
  instrumentations: [getNodeAutoInstrumentations()]
});
sdk.start();

const express = require('express');
const app = express();

app.get('/api/data', (req, res) => {
  // The traceparent header is extracted automatically
  // This span is a child of Service A's outbound span
  res.json({ data: 'from-service-b' });
});

app.listen(3001, () => console.log('Service B on 3001'));
```

**Expected Output (in tracing backend):**
```
Trace: 0af7651916cd43dd8448eb211c80319c
├── GET /api/process (service-a, 320ms)
│   └── HTTP GET http://service-b:3001/api/data (280ms)
│       └── GET /api/data (service-b, 45ms)
```

**Why this output:** Service A receives the request and creates a root span. When it calls Service B via `fetch`, the HTTP instrumentation injects the `traceparent` header. Service B extracts the header, creates a child span with the same trace ID, and the tracing backend links the two spans into a single trace.

### Real-World Cases

- **E-commerce:** A checkout request flows through cart, inventory, payment, and order services — all linked by one trace ID.
- **Banking:** A transfer touches account, fraud, and ledger services — the trace shows the complete chain.
- **SaaS platforms:** API gateway → auth service → data service → database — the trace reveals the bottleneck.

## Core Concept 4: OpenTelemetry Concepts — TracerProvider and MeterProvider

### Definitions

**Core Definition:** `TracerProvider` is the OpenTelemetry component that creates and manages tracers (for traces); `MeterProvider` creates and manages meters (for metrics). Both are registered with the global OpenTelemetry API so that instrumentation libraries can discover and use them.

**Technical Definition:** The `NodeTracerProvider` (from `@opentelemetry/sdk-trace-node`) is the entry point for tracing in Node.js. It holds the sampler (sampling decision), span processors (batch or simple), and resource (service metadata). The `MeterProvider` (from `@opentelemetry/sdk-metrics`) holds metric readers and exporters, and is used to create counters, histograms, and gauges. Both providers are configured once at application startup and registered globally via `tracerProvider.register()` and `metrics.setGlobalMeterProvider(meterProvider)`.

**Beginner-Friendly Explanation:** The TracerProvider is the factory that makes tracers. A tracer is the object you use to create spans. Similarly, the MeterProvider makes meters, which you use to create metrics. You set up both once when your application starts, and then any instrumentation library or your own code can use them.

### Purposes

- To create tracers and meters for instrumenting application code.
- To configure the sampler that decides which traces to record.
- To configure span processors that batch and export spans.
- To attach a Resource that describes the service (name, version, environment).
- To register the provider globally so instrumentation libraries can discover it.

### Syntax Rules and Structure

**Minimal setup with `NodeSDK` (recommended):**
```js
const { NodeSDK } = require('@opentelemetry/sdk-node');
const { getNodeAutoInstrumentations } = require('@opentelemetry/auto-instrumentations-node');
const { OTLPTraceExporter } = require('@opentelemetry/exporter-trace-otlp-http');

const sdk = new NodeSDK({
  serviceName: 'my-service',
  traceExporter: new OTLPTraceExporter(),
  instrumentations: [getNodeAutoInstrumentations()]
});

sdk.start();
```

**Manual TracerProvider and MeterProvider setup:**
```js
const { NodeTracerProvider } = require('@opentelemetry/sdk-trace-node');
const { MeterProvider, PeriodicExportingMetricReader } = require('@opentelemetry/sdk-metrics');
const { BatchSpanProcessor } = require('@opentelemetry/sdk-trace-base');
const { Resource } = require('@opentelemetry/resources');
const { ATTR_SERVICE_NAME } = require('@opentelemetry/semantic-conventions');

// Resource — describes the service
const resource = new Resource({
  [ATTR_SERVICE_NAME]: 'order-service',
  'service.version': '1.0.0',
  'deployment.environment': 'production'
});

// TracerProvider
const tracerProvider = new NodeTracerProvider({
  resource,
  spanProcessors: [new BatchSpanProcessor(exporter)]
});
tracerProvider.register();

// MeterProvider
const meterProvider = new MeterProvider({
  resource,
  readers: [new PeriodicExportingMetricReader({ exporter: metricExporter })]
});
```

| Component | Purpose |
|-----------|---------|
| `NodeTracerProvider` | Creates tracers; holds sampler and span processors. |
| `MeterProvider` | Creates meters; holds metric readers and exporters. |
| `Resource` | Describes the service (name, version, environment). |
| `BatchSpanProcessor` | Batches spans before exporting (efficient). |
| `SimpleSpanProcessor` | Exports spans immediately (development only). |

**Rules:**
- Call `tracerProvider.register()` to make the provider globally available. 
- Use `BatchSpanProcessor` in production — it batches spans and reduces network calls. 
- Use `SimpleSpanProcessor` only for development or debugging. 
- Set the service name via `Resource` or the `NodeSDK` constructor. 
- The provider must be configured **before** any instrumented code runs. 

### Annotated Code Example

```js
// otel-setup.js
const { NodeSDK } = require('@opentelemetry/sdk-node');
const { getNodeAutoInstrumentations } = require('@opentelemetry/auto-instrumentations-node');
const { OTLPTraceExporter } = require('@opentelemetry/exporter-trace-otlp-http');
const { OTLPMetricExporter } = require('@opentelemetry/exporter-metrics-otlp-http');
const { PeriodicExportingMetricReader } = require('@opentelemetry/sdk-metrics');
const { Resource } = require('@opentelemetry/resources');
const { ATTR_SERVICE_NAME, ATTR_SERVICE_VERSION } = require('@opentelemetry/semantic-conventions');

const resource = new Resource({
  [ATTR_SERVICE_NAME]: 'order-service',
  [ATTR_SERVICE_VERSION]: '1.0.0',
  'deployment.environment': process.env.NODE_ENV || 'development'
});

const sdk = new NodeSDK({
  resource,
  traceExporter: new OTLPTraceExporter({
    url: process.env.OTEL_EXPORTER_OTLP_ENDPOINT || 'http://localhost:4318/v1/traces'
  }),
  metricReader: new PeriodicExportingMetricReader({
    exporter: new OTLPMetricExporter(),
    exportIntervalMillis: 60000
  }),
  instrumentations: [
    getNodeAutoInstrumentations({
      '@opentelemetry/instrumentation-fs': { enabled: false }  // Optional: disable noisy instrumentations
    })
  ]
});

sdk.start();
console.log('OpenTelemetry initialized');

// Graceful shutdown
process.on('SIGTERM', () => {
  sdk.shutdown().then(() => process.exit(0));
});
```

**Expected Output:**
```
OpenTelemetry initialized
```

**Why this output:** The `NodeSDK` initialises both tracing and metrics with a single `sdk.start()` call. The `Resource` attaches the service name and version to every span and metric. The `OTLPTraceExporter` sends spans to the collector, and the `PeriodicExportingMetricReader` sends metrics every 60 seconds. The SDK is configured before the application code runs, so auto-instrumentation can patch libraries at load time.

### Real-World Cases

- **Multi-service deployments:** Each service has its own `NodeSDK` configuration with a unique service name.
- **Development:** Using `ConsoleSpanExporter` to see spans in the terminal. 
- **Production:** Using `OTLPTraceExporter` to send spans to a collector, which routes to Jaeger or Tempo.

## Core Concept 5: Exporters (OTLP, Jaeger, Zipkin)

### Definitions

**Core Definition:** An exporter is the component that sends finished spans and metrics from the OpenTelemetry SDK to an observability backend (Jaeger, Zipkin, Tempo, Datadog, etc.).

**Technical Definition:** OpenTelemetry JS provides several exporter packages. The **OTLP exporter** (`@opentelemetry/exporter-trace-otlp-http` or `@opentelemetry/exporter-trace-otlp-grpc`) sends telemetry to any OTLP-compatible endpoint, including the OpenTelemetry Collector, Jaeger (via OTLP), and commercial platforms. The **Jaeger exporter** (`@opentelemetry/exporter-jaeger`) sends spans directly to a Jaeger agent or collector. The **Zipkin exporter** (`@opentelemetry/exporter-zipkin`) sends spans to a Zipkin server. Exporters are wired into the SDK via a span processor (typically `BatchSpanProcessor` for production).

**Beginner-Friendly Explanation:** An exporter is the shipping method for your tracing data. The OTLP exporter is like a universal courier that can deliver to any address. The Jaeger and Zipkin exporters are specialised couriers for those specific backends. In most cases, you use the OTLP exporter and send data to an OpenTelemetry Collector, which then routes it to any backend you choose.

### Purposes

- To send spans and metrics to a tracing backend for storage, search, and visualisation.
- To decouple the application from the backend — switch backends by changing the exporter, not the code.
- To batch and compress telemetry for efficient network transfer.
- To support multiple backends simultaneously (e.g., Jaeger for traces, Prometheus for metrics).

### Syntax Rules and Structure

| Exporter | Package | Backend | Protocol |
|----------|---------|---------|----------|
| OTLP HTTP | `@opentelemetry/exporter-trace-otlp-http` | Collector, Jaeger, Tempo | HTTP/protobuf. |
| OTLP gRPC | `@opentelemetry/exporter-trace-otlp-grpc` | Collector, Jaeger, Tempo | gRPC. |
| Jaeger | `@opentelemetry/exporter-jaeger` | Jaeger | UDP/HTTP. |
| Zipkin | `@opentelemetry/exporter-zipkin` | Zipkin | HTTP JSON. |
| Console | `@opentelemetry/sdk-trace-base` (ConsoleSpanExporter) | Terminal | — |

**OTLP exporter setup:**
```js
const { OTLPTraceExporter } = require('@opentelemetry/exporter-trace-otlp-http');

const exporter = new OTLPTraceExporter({
  url: 'http://collector:4318/v1/traces',
  headers: {
    'Authorization': `Bearer ${process.env.TRACING_API_KEY}`
  }
});
```

**Jaeger exporter setup:**
```js
const { JaegerExporter } = require('@opentelemetry/exporter-jaeger');
const exporter = new JaegerExporter({
  endpoint: 'http://localhost:14268/api/traces'
});
```

**Zipkin exporter setup:**
```js
const { ZipkinExporter } = require('@opentelemetry/exporter-zipkin');
const exporter = new ZipkinExporter({
  url: 'http://localhost:9411/api/v2/spans'
});
```

**Rules:**
- Use `BatchSpanProcessor` with exporters in production. 
- The OTLP exporter is the recommended choice for new deployments. 
- Jaeger supports OTLP natively — you can send OTLP data directly to Jaeger without a separate exporter. 
- Store exporter credentials (API keys, tokens) in environment variables, never in code. 
- Test exporter connectivity in development before deploying.

### Annotated Code Example

```js
// exporter-otlp.js
const { NodeSDK } = require('@opentelemetry/sdk-node');
const { getNodeAutoInstrumentations } = require('@opentelemetry/auto-instrumentations-node');
const { OTLPTraceExporter } = require('@opentelemetry/exporter-trace-otlp-http');
```

```
OTLP exporter configured
```
*(Spans are batched and sent to the collector every few seconds.)*

**Why this output:** The OTLP exporter sends spans to `http://localhost:4318/v1/traces` (the standard OTLP HTTP endpoint). The `BatchSpanProcessor` accumulates spans and sends them in batches, reducing network overhead. The collector receives the spans and forwards them to Jaeger, Tempo, or any configured backend.

### Real-World Cases

- **Kubernetes:** OTLP exporter sends to a collector DaemonSet, which routes to Tempo.
- **Multi-backend:** OTLP exporter sends to a collector that fans out to Jaeger (traces) and Prometheus (metrics).
- **Vendor platforms:** OTLP exporter sends to Datadog, New Relic, or Honeycomb via their OTLP endpoints.

## Core Concept 6: Automatic vs. Manual Instrumentation

### Definitions

**Core Definition:** Automatic instrumentation (auto-instrumentation) patches Node.js libraries (HTTP, Express, PostgreSQL, Redis, etc.) to emit spans without code changes; manual instrumentation uses the OpenTelemetry API to create custom spans for business logic.

**Technical Definition:** Auto-instrumentation is provided by the `@opentelemetry/auto-instrumentations-node` package (or individual instrumentation packages), which uses Node.js module loading hooks to wrap library functions. When enabled, it automatically creates spans for inbound HTTP requests, outbound HTTP calls, database queries, and framework operations. Manual instrumentation uses `tracer.startActiveSpan()` to create spans for operations that are not covered by auto-instrumentation — typically business logic, custom protocols, or specific code paths that need detailed tracing.

**Beginner-Friendly Explanation:** Auto-instrumentation is like installing a security camera system — it records everything automatically without you doing anything. Manual instrumentation is like placing a camera in a specific spot because you know something important happens there. You use both: auto-instrumentation for the broad strokes (HTTP, database), and manual instrumentation for the details that matter to your business.

### Purposes

- To get broad coverage of standard operations (HTTP, database) without writing code.
- To add business-specific spans for operations that auto-instrumentation does not cover.
- To enrich spans with custom attributes (order ID, user ID, payment amount).
- To record exceptions and set span status for custom operations.

### Syntax Rules and Structure

**Auto-instrumentation (zero code changes):**
```js
// otel.js — preloaded with --require flag
const { NodeSDK } = require('@opentelemetry/sdk-node');
const { getNodeAutoInstrumentations } = require('@opentelemetry/auto-instrumentations-node');

const sdk = new NodeSDK({
  serviceName: 'my-service',
  instrumentations: [getNodeAutoInstrumentations()]
});
sdk.start();
```

```bash
# Run the app with the preload flag
node --require ./otel.js app.js
```

**Manual instrumentation (custom spans):**
```js
const { trace, SpanStatusCode } = require('@opentelemetry/api');
const tracer = trace.getTracer('my-service');

async function checkout(cart) {
  return tracer.startActiveSpan('checkout', async (span) => {
    span.setAttribute('cart.items', cart.items.length);
    span.setAttribute('cart.total', cart.total);

    try {
      const order = await processPayment(cart);
      span.setAttribute('order.id', order.id);
      span.setStatus({ code: SpanStatusCode.OK });
      return order;
    } catch (err) {
      span.recordException(err);
      span.setStatus({ code: SpanStatusCode.ERROR, message: err.message });
      throw err;
    } finally {
      span.end();
    }
  });
}
```

| Aspect | Auto-Instrumentation | Manual Instrumentation |
|--------|---------------------|------------------------|
| Code changes | None | Requires API calls. |
| Coverage | HTTP, DB, frameworks | Custom business logic. |
| Attributes | Standard (http.*, db.*) | Custom (order.id, user.id). |
| Setup | `getNodeAutoInstrumentations()` | `tracer.startActiveSpan()`. |
| Use case | Broad coverage. | Specific, important operations. |

**Rules:**
- Use auto-instrumentation for HTTP, database, and framework layers. 
- Use manual instrumentation for business logic, message queues, and custom protocols.
- Always call `span.end()` in a `finally` block. 
- Record exceptions with `span.recordException(err)`. 
- Set span status to ERROR on failure. 

### Annotated Code Example

```js
// app.js
const express = require('express');
const { trace, SpanStatusCode } = require('@opentelemetry/api');

const app = express();
const tracer = trace.getTracer('order-service');

// Auto-instrumentation creates a span for this HTTP request automatically
app.post('/api/orders', async (req, res) => {
  // Manual span for business logic
  return tracer.startActiveSpan('create-order', async (span) => {
    span.setAttribute('order.customer_id', req.body.customerId);
    span.setAttribute('order.item_count', req.body.items.length);

    try {
      // Database query — auto-instrumented
      const order = await db.query(
        'INSERT INTO orders (customer_id, total) VALUES ($1, $2) RETURNING *',
        [req.body.customerId, req.body.total]
      );

      span.setAttribute('order.id', order.rows[0].id);
      span.setStatus({ code: SpanStatusCode.OK });
      res.status(201).json(order.rows[0]);
    } catch (err) {
      span.recordException(err);
      span.setStatus({ code: SpanStatusCode.ERROR, message: err.message });
      res.status(500).json({ error: 'Order creation failed' });
    } finally {
      span.end();
    }
  });
});

app.listen(3000, () => console.log('Server on 3000'));
```

**Expected Output (in tracing backend):**
```
Trace: 0af7651916cd43dd8448eb211c80319c
├── POST /api/orders (auto, 120ms)
│   └── create-order (manual, 95ms)  ← attribute: order.customer_id=42
│       └── db.query.orders.insert (auto, 45ms)
```

**Why this output:** The HTTP request is auto-instrumented (`POST /api/orders`). Inside the handler, a manual span `create-order` is created with custom attributes. The database query is auto-instrumented as a child of the manual span. The result is a complete trace that includes both automatic and manual spans.

### Real-World Cases

- **E-commerce:** Auto-instrument HTTP and database; manually instrument checkout logic with `order.id` and `cart.total`.
- **Fintech:** Auto-instrument HTTP and database; manually instrument payment processing with `payment.amount` and `payment.provider`.
- **SaaS:** Auto-instrument HTTP and database; manually instrument tenant-specific operations with `tenant.id`.

## Core Concept 7: Sampling Strategies — Head-Based vs. Tail-Based

### Definitions

**Core Definition:** Sampling is the process of deciding which traces to record and export, reducing data volume and cost. Head-based sampling decides at the start of the trace; tail-based sampling decides after the trace is complete.

**Technical Definition:** **Head-based sampling** makes the sampling decision when the root span is created — typically using a probabilistic sampler (e.g., sample 10% of traces) or a parent-based sampler (follow the parent's decision). The decision is propagated to all downstream services via the `traceparent` header. **Tail-based sampling** collects all spans for a trace, then decides whether to keep or drop the trace based on complete information — such as whether the trace contains errors or exceeded a latency threshold. Tail-based sampling is implemented in the OpenTelemetry Collector, not in the application SDK.

**Beginner-Friendly Explanation:** Head-based sampling is like flipping a coin at the start of each request: “heads we record, tails we don’t.” It’s simple and cheap, but you might miss a rare error because the coin came up tails. Tail-based sampling is like recording everything first, then deciding what to keep — “keep all traces with errors, keep all slow traces, and keep 10% of the rest.” It’s more intelligent but requires more infrastructure.

### Purposes

- To reduce the volume of exported traces and control storage costs.
- To ensure errors and slow requests are always captured (tail-based).
- To maintain statistical representativeness with a configurable sample rate (head-based).
- To balance observability completeness against infrastructure cost.

### Syntax Rules and Structure

| Aspect | Head-Based Sampling | Tail-Based Sampling |
|--------|---------------------|---------------------|
| Decision time | At trace start. | After trace completes. |
| Decision location | Application SDK. | Collector. |
| Propagation | Sampling flag in `traceparent`. | All spans collected. |
| Cost | Low (no spans exported if dropped). | Higher (all spans buffered). |
| Error capture | Probabilistic — may miss errors. | Guaranteed — all errors kept. |
| Node.js support | Built into SDK. | Collector-side (no SDK change). |

**Head-based sampling in Node.js:**
```js
const { NodeTracerProvider } = require('@opentelemetry/sdk-trace-node');
const { TraceIdRatioBasedSampler, ParentBasedSampler } = require('@opentelemetry/sdk-trace-base');

const provider = new NodeTracerProvider({
  sampler: new ParentBasedSampler({
    root: new TraceIdRatioBasedSampler(0.1)  // Sample 10% of root traces
  })
});
```

**Tail-based sampling in the collector (YAML):**
```yaml
processors:
  tail_sampling:
    decision_wait: 10s
    policies:
      - name: errors
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow
        type: latency
        latency: { threshold_ms: 500 }
      - name: random
        type: probabilistic
        probabilistic: { sampling_percentage: 10 }

service:
  pipelines:
    traces:
      processors: [tail_sampling]
```

**Rules:**
- Start with head-based sampling for simplicity; add tail-based when you need guaranteed error capture. 
- Use `ParentBasedSampler` to ensure consistency across services — if the parent is sampled, all children are sampled. 
- Tail-based sampling requires buffering spans in the collector; plan for memory and latency. 
- Combine both: head-based as a first filter (e.g., 100% for critical endpoints, 10% for others), tail-based for intelligent selection. 
- Always sample errors — set tail-based policies to keep all traces with `ERROR` status. 

### Annotated Code Example

```js
// head-sampling.js
const { NodeTracerProvider } = require('@opentelemetry/sdk-trace-node');
const { BatchSpanProcessor } = require('@opentelemetry/sdk-trace-base');
const { TraceIdRatioBasedSampler, ParentBasedSampler } = require('@opentelemetry/sdk-trace-base');

// Sample 10% of root traces; follow parent decision for child spans
const sampler = new ParentBasedSampler({
  root: new TraceIdRatioBasedSampler(0.1)
});

const provider = new NodeTracerProvider({ sampler });
provider.register();

console.log('Sampling at 10% for root traces');
```

**Expected Output:**
```
Sampling at 10% for root traces
```
*(Approximately 10% of incoming requests will be traced and exported.)*

**Why this output:** The `TraceIdRatioBasedSampler(0.1)` samples 10% of root traces based on a hash of the trace ID. The `ParentBasedSampler` ensures that if a trace is sampled at the root, all child spans in downstream services are also sampled (because the sampling flag is propagated in the `traceparent` header).

### Real-World Cases

- **High-traffic APIs:** 10% head-based sampling reduces trace volume by 90% while maintaining statistical representativeness.
- **Incident response:** Tail-based sampling ensures that all traces with errors are kept, even if head-based sampling would have dropped them.
- **Critical endpoints:** Head-based sampling with 100% for `/checkout` and `/payment`, and 5% for `/search` and `/browse`.
