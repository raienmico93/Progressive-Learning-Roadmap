# Laravel Resource Routing (RESTful Conventions): A Comprehensive Cheat Sheet

---

## Topic Overview

### Definitions

**Core Definition:** Laravel Resource Routing is a declarative routing feature that automatically generates a complete set of RESTful routes for a given resource (e.g., posts, users, products) by mapping standard HTTP verbs and URIs to conventional controller actions in a single line of code.

**Technical Definition:** The `Route::resource()` method delegates to the `ResourceRegistrar` class, which registers a preset collection of routes into the `RouteCollection`. Each route maps a specific HTTP verb and URI pattern to a conventional controller method (`index`, `create`, `store`, `show`, `edit`, `update`, `destroy`). The `ResourceRegistrar` also handles parameter naming (singularising the resource name), route name generation (`resource.action`), and nested resource scoping. Variants such as `apiResource()`, `singleton()`, and partial mapping via `only()`/`except()` provide fine-grained control over which routes are registered.

**Beginner-Friendly Explanation:** Instead of manually writing seven separate route definitions for every CRUD resource (list, create form, save, view, edit form, update, delete), Laravel lets you write one line: `Route::resource('posts', PostController::class)`. Laravel generates all seven routes and names them automatically, following standard REST conventions that developers worldwide already understand.

### Key Characteristics

- **Convention Over Configuration:** Follows RESTful conventions out of the box, requiring only a resource name and controller class.
- **Automatic Parameter Naming:** Route parameters are generated by singularising the resource name (e.g., `posts` → `{post}`).
- **Automatic Route Naming:** Routes are named `resource.action` (e.g., `posts.index`, `posts.show`).
- **Attack Surface Reduction:** `only()` and `except()` allow trimming unused routes.
- **API-Ready:** `apiResource()` strips presentation-only actions (`create`, `edit`) unsuitable for JSON APIs.
- **Singleton Support:** `singleton()` handles one-of-one resources (e.g., profile, settings) without ID parameters.
- **Cache Compatible:** All resource routes are controller-based and support `php artisan route:cache`.

### Prerequisites

- **Laravel 9.42+** for singleton routes; **Laravel 8.x+** for `apiResource()` and `scopeBindings()`.
- **PHP 8.1+** (Laravel 10) or **PHP 8.2+** (Laravel 11/12).
- A resource controller generated via `php artisan make:controller PostController --resource` (or `--api` for API controllers).
- Familiarity with basic routing, controllers, and Eloquent models.

### Related Programming Areas

- **RESTful API Design:** Resource routing is the implementation of REST principles in Laravel.
- **MVC Architecture:** Resource controllers embody the Controller layer of MVC.
- **Route Model Binding:** Resource parameters automatically trigger implicit model binding.
- **Middleware Pipeline:** Resource routes can be wrapped in middleware groups for authentication and rate limiting.
- **Route Caching:** Resource routes are optimised for production route caching.

## 1. Resource Controllers

### Definitions

**Core Definition:** A resource controller is a controller class containing conventional RESTful methods (`index`, `create`, `store`, `show`, `edit`, `update`, `destroy`) that are automatically mapped to routes by `Route::resource()`.

**Technical Definition:** The `Route::resource()` method registers seven routes by default, each mapping an HTTP verb and URI pattern to a specific controller method. The `ResourceRegistrar::register()` method iterates over a predefined action map, creating `Route` instances with names in the format `{resource}.{action}` and parameters named by singularising the resource. The generated routes are assigned the `resource` metadata, enabling route inspection and cache generation.

**Beginner-Friendly Explanation:** Think of a resource controller as a pre-built template for handling everything about one type of thing—like blog posts. It has seven methods ready to go: one for listing, one for showing a create form, one for saving, one for viewing a single item, one for showing an edit form, one for updating, and one for deleting. Laravel automatically creates the seven routes that connect to these methods.

### Purposes

- To scaffold full multi-action endpoint structures with a single line of code.
- To enforce RESTful conventions consistently across an application.
- To reduce boilerplate and potential for routing errors.
- To enable rapid prototyping of CRUD applications.
- To provide predictable URLs and route names for front-end developers.

### Syntax Rules and Structure

**Complete General Syntax:**

```php
Route::resource('posts', PostController::class);
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `'posts'` | The resource name (plural, kebab-case by convention). |
| `PostController::class` | The controller class handling the resource. |

**Generated Routes:**

| Verb | URI | Action | Route Name |
|------|-----|--------|------------|
| GET | `/posts` | index | posts.index |
| GET | `/posts/create` | create | posts.create |
| POST | `/posts` | store | posts.store |
| GET | `/posts/{post}` | show | posts.show |
| GET | `/posts/{post}/edit` | edit | posts.edit |
| PUT/PATCH | `/posts/{post}` | update | posts.update |
| DELETE | `/posts/{post}` | destroy | posts.destroy |

**Complete General Syntax — Nested Resources:**

```php
Route::resource('posts.comments', CommentController::class);
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `'posts.comments'` | Dot notation creates nested routes. |
| Generated URIs | `/posts/{post}/comments`, `/posts/{post}/comments/{comment}`, etc. |

**Syntax Rules:**

- The resource name is conventionally plural and kebab-case (e.g., `blog-posts`).
- The controller must extend `App\Http\Controllers\Controller` and contain the seven conventional methods.
- Route parameters are automatically singularised: `posts` → `{post}`, `users` → `{user}`.
- Additional routes should be defined **before** `Route::resource()` to avoid being captured by the `{post}` wildcard.
- Nested resources use dot notation: `Route::resource('posts.comments', CommentController::class)`.

**Constraints and Limitations:**

- **Wildcard capture:** The `{post}` parameter in `show`, `edit`, `update`, and `destroy` routes can capture unintended URIs if additional routes are defined after the resource route.
- **Controller method requirements:** All seven methods must exist on the controller, or use `only()`/`except()` to limit routes.
- **Parameter naming:** Override the default singularised parameter name via the `parameters` option if needed.
- **No built-in shallow nesting:** Use `->shallow()` to avoid requiring parent IDs in child operations.

### Multiple Annotated Complete Code Examples

**Example 1: Basic Resource Controller with All Seven Routes**

```php
<?php
// app/Http/Controllers/PostController.php

namespace App\Http\Controllers;

use App\Models\Post;
use Illuminate\Http\Request;

class PostController extends Controller
{
    // GET /posts — list all posts
    public function index()
    {
        return Post::all();
    }

    // GET /posts/create — show creation form
    public function create()
    {
        return view('posts.create');
    }

    // POST /posts — store new post
    public function store(Request $request)
    {
        $post = Post::create($request->validated());
        return redirect()->route('posts.show', $post);
    }

    // GET /posts/{post} — show single post
    public function show(Post $post)
    {
        return view('posts.show', compact('post'));
    }

    // GET /posts/{post}/edit — show edit form
    public function edit(Post $post)
    {
        return view('posts.edit', compact('post'));
    }

    // PUT/PATCH /posts/{post} — update post
    public function update(Request $request, Post $post)
    {
        $post->update($request->validated());
        return redirect()->route('posts.show', $post);
    }

    // DELETE /posts/{post} — delete post
    public function destroy(Post $post)
    {
        $post->delete();
        return redirect()->route('posts.index');
    }
}
```

```php
<?php
// routes/web.php

use App\Http\Controllers\PostController;
use Illuminate\Support\Facades\Route;

Route::resource('posts', PostController::class);
```

**Setup:** Generate the controller via `php artisan make:controller PostController --resource`. Create a `Post` model and migration.

**Expected Output:** Visiting `/posts` lists all posts; `/posts/1` shows post 1; `/posts/create` shows the creation form. All seven routes are registered and named.

**Why:** `Route::resource()` registers the seven conventional routes. Each route uses implicit model binding: `{post}` automatically resolves to a `Post` model instance in `show`, `edit`, `update`, and `destroy`.

---

**Example 2: Nested Resource Controller**

```php
<?php
// routes/web.php

use App\Http\Controllers\CommentController;
use App\Http\Controllers\PostController;
use Illuminate\Support\Facades\Route;

// Parent resource
Route::resource('posts', PostController::class);

// Nested child resource — URIs become /posts/{post}/comments/*
Route::resource('posts.comments', CommentController::class);
```

```php
<?php
// app/Http/Controllers/CommentController.php

namespace App\Http\Controllers;

use App\Models\Comment;
use App\Models\Post;

class CommentController extends Controller
{
    // GET /posts/{post}/comments
    public function index(Post $post)
    {
        return $post->comments;
    }

    // GET /posts/{post}/comments/{comment}
    public function show(Post $post, Comment $comment)
    {
        return $comment;
    }
}
```

**Expected Output:** `GET /posts/1/comments` returns comments for post 1. `GET /posts/1/comments/5` returns comment 5 if it belongs to post 1.

**Why:** Dot notation (`'posts.comments'`) creates nested routes. Both `{post}` and `{comment}` parameters are injected into the controller methods in order.

---

**Example 3: Shallow Nesting to Simplify Child URIs**

```php
<?php
// routes/web.php

use App\Http\Controllers\CommentController;
use App\Http\Controllers\PostController;
use Illuminate\Support\Facades\Route;

Route::resource('posts', PostController::class);

// Shallow nesting: only index, create, store require parent ID
Route::resource('posts.comments', CommentController::class)->shallow();
```

**Generated Routes with Shallow Nesting:**

| Verb | URI | Action |
|------|-----|--------|
| GET | `/posts/{post}/comments` | index |
| GET | `/posts/{post}/comments/create` | create |
| POST | `/posts/{post}/comments` | store |
| GET | `/comments/{comment}` | show |
| GET | `/comments/{comment}/edit` | edit |
| PUT/PATCH | `/comments/{comment}` | update |
| DELETE | `/comments/{comment}` | destroy |

**Expected Output:** `GET /comments/5` shows comment 5 without requiring the parent post ID in the URI.

**Why:** The `->shallow()` modifier eliminates the parent parameter from routes where the child can be uniquely identified by its own ID alone.

### Real-World Cases

- **Blog Platforms:** `Route::resource('posts', PostController::class)` handles all blog post CRUD operations.
- **E-commerce:** `Route::resource('products', ProductController::class)` manages product catalogue.
- **User Management:** `Route::resource('users', UserController::class)` handles user CRUD in admin panels.
- **Nested Comments:** `Route::resource('posts.comments', CommentController::class)->shallow()` manages comments on blog posts.
- **Project Management:** `Route::resource('projects.tasks', TaskController::class)` handles tasks within projects.

## 2. Partial Resource Mapping

### Definitions

**Core Definition:** Partial resource mapping restricts which of the seven conventional resource routes are registered, using the `only()` or `except()` methods to include or exclude specific actions.

**Technical Definition:** The `only()` and `except()` methods set the `only` and `except` options on the `ResourceRegistrar`, which filters the action map before route registration. `only()` specifies an allowlist of actions to register; `except()` specifies a denylist. The result is a reduced set of routes registered in the `RouteCollection`, reducing the application's attack surface and route count.

**Beginner-Friendly Explanation:** If your application only needs to list and view posts (not create, edit, or delete), you can tell Laravel to only register the `index` and `show` routes. This keeps your route list clean and prevents accidental exposure of unused endpoints.

### Purposes

- To limit active routes to only those the application actually uses, trimming the attack surface.
- To reduce route registration overhead and route cache size.
- To prevent accidental exposure of unused CRUD endpoints.
- To clarify intent by explicitly declaring which actions are supported.
- To comply with security best practices (principle of least privilege).

### Syntax Rules and Structure

**Complete General Syntax — `only()`:**

```php
Route::resource('posts', PostController::class)->only(['index', 'show']);
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `->only(['index', 'show'])` | Array of action names to register. |
| `'index'` | List action. |
| `'show'` | Detail view action. |

**Complete General Syntax — `except()`:**

```php
Route::resource('posts', PostController::class)->except(['destroy']);
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `->except(['destroy'])` | Array of action names to exclude. |
| `'destroy'` | The delete action is not registered. |

**Complete General Syntax — `apiOnly()` (Laravel 10+):**

```php
Route::resource('posts', PostController::class)->apiOnly();
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `->apiOnly()` | Excludes `create` and `edit` (equivalent to `apiResource()`). |

**Syntax Rules:**

- `only()` and `except()` accept an array of action name strings.
- Valid action names: `index`, `create`, `store`, `show`, `edit`, `update`, `destroy`.
- `only()` and `except()` cannot be used together on the same resource.
- The `only()` method is preferred over `except()` for security: it acts as a whitelist, making it explicit which routes are exposed.

**Constraints and Limitations:**

- **Method requirements:** The controller must still contain the methods for the actions you register; unregistered actions' methods can be omitted.
- **Route naming:** Names remain `resource.action` regardless of filtering.
- **Order dependency:** Additional routes must be defined before the resource route to avoid wildcard capture.
- **Nested resources:** `only()` and `except()` apply to the child resource's actions.

### Multiple Annotated Complete Code Examples

**Example 1: `only()` for Read-Only Resources**

```php
<?php
// routes/web.php

use App\Http\Controllers\CategoryController;
use Illuminate\Support\Facades\Route;

// Only register index and show — no create, edit, or delete
Route::resource('categories', CategoryController::class)
    ->only(['index', 'show']);
```

**Expected Output:** Only `GET /categories` and `GET /categories/{category}` are registered. Attempting `POST /categories` returns 405 Method Not Allowed.

**Why:** The `only()` method acts as a whitelist, registering only the two specified actions. The `create`, `store`, `edit`, `update`, and `destroy` routes are not registered, reducing the attack surface.

---

**Example 2: `except()` to Remove Destructive Actions**

```php
<?php
// routes/web.php

use App\Http\Controllers\OrderController;
use Illuminate\Support\Facades\Route;

// Register all resource routes except destroy
Route::resource('orders', OrderController::class)
    ->except(['destroy']);
```

**Expected Output:** All routes except `DELETE /orders/{order}` are registered. Orders can be created, viewed, edited, and updated but not deleted through this route.

**Why:** The `except()` method excludes the `destroy` action, useful when orders should be archived rather than deleted.

---

**Example 3: `apiOnly()` for API-Ready Controllers**

```php
<?php
// routes/web.php

use App\Http\Controllers\ProductController;
use Illuminate\Support\Facades\Route;

// Equivalent to apiResource() — excludes create and edit
Route::resource('products', ProductController::class)->apiOnly();
```

**Expected Output:** Registers `index`, `store`, `show`, `update`, and `destroy` only. `GET /products/create` returns 404 (not registered).

**Why:** `apiOnly()` is a convenience method that excludes the two form-display actions (`create`, `edit`) that are meaningless in a JSON API context.

### Real-World Cases

- **Public Directories:** `Route::resource('listings', ListingController::class)->only(['index', 'show'])` for a read-only public directory.
- **Order Management:** `->except(['destroy'])` when orders should never be hard-deleted.
- **User Profiles:** `->only(['show', 'edit', 'update'])` for self-service profile management.
- **Admin Panels:** `->except(['show'])` when the admin uses a data table instead of a detail view.
- **Audit Logs:** `->only(['index', 'show'])` for immutable audit trail resources.

## 3. API Resource Routing

### Definitions

**Core Definition:** API resource routing generates a stateless set of five RESTful routes—excluding the form-display actions `create` and `edit`—suitable for JSON API consumption.

**Technical Definition:** The `Route::apiResource()` method calls `ResourceRegistrar::register()` with the `api` option set, which filters the default seven-action map to exclude `create` and `edit`. The resulting routes (`index`, `store`, `show`, `update`, `destroy`) map exclusively to JSON-returning controller methods. When defined in `routes/api.php`, these routes are automatically prefixed with `/api` and assigned the `api` middleware group.

**Beginner-Friendly Explanation:** A JSON API doesn't need HTML forms for creating or editing resources—the client (a mobile app, SPA, or another server) sends JSON directly. So `apiResource()` generates only the five routes that make sense for APIs, skipping the two that return HTML forms.

### Purposes

- To build pure JSON APIs without HTML form routes.
- To reduce route count and attack surface in API-first applications.
- To follow REST conventions where `create` and `edit` are client-side concerns.
- To automatically apply the `api` middleware group and `/api` prefix.
- To simplify API documentation and client SDK generation.

### Syntax Rules and Structure

**Complete General Syntax:**

```php
Route::apiResource('posts', PostController::class);
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `Route::apiResource()` | Registers five API routes (excludes `create`, `edit`). |
| `'posts'` | Resource name. |
| `PostController::class` | API controller class. |

**Generated Routes:**

| Verb | URI | Action | Route Name |
|------|-----|--------|------------|
| GET | `/api/posts` | index | posts.index |
| POST | `/api/posts` | store | posts.store |
| GET | `/api/posts/{post}` | show | posts.show |
| PUT/PATCH | `/api/posts/{post}` | update | posts.update |
| DELETE | `/api/posts/{post}` | destroy | posts.destroy |

**Complete General Syntax — Multiple API Resources:**

```php
Route::apiResources([
    'posts'    => PostController::class,
    'comments' => CommentController::class,
]);
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `apiResources([...])` | Registers multiple API resources in one call. |
| `'posts' => PostController::class` | Key-value pair of resource name → controller. |

**Syntax Rules:**

- `apiResource()` is functionally equivalent to `resource()->except(['create', 'edit'])`.
- Routes defined in `routes/api.php` receive the `/api` prefix and `api` middleware group automatically.
- API controllers should be generated with `php artisan make:controller PostController --api` to include only the five relevant methods.
- The `apiResource()` method can be chained with `->only()` and `->except()` for further filtering.

**Constraints and Limitations:**

- **No form routes:** `create` and `edit` are never registered—if you need them, use `resource()` instead.
- **Statelessness:** API routes lack session and CSRF middleware. Authentication must be handled via tokens (Sanctum, Passport) or other stateless mechanisms.
- **Prefix configuration:** The default `/api` prefix can be changed in `bootstrap/app.php` via `->withRouting(apiPrefix: 'api/v1')`.

### Multiple Annotated Complete Code Examples

**Example 1: Basic API Resource**

```php
<?php
// routes/api.php

use App\Http\Controllers\Api\PostController;
use Illuminate\Support\Facades\Route;

// Registers 5 API routes (no create/edit)
Route::apiResource('posts', PostController::class);
```

**Expected Output:**
- `GET /api/posts` → `PostController@index` (JSON list)
- `POST /api/posts` → `PostController@store` (JSON create)
- `GET /api/posts/1` → `PostController@show` (JSON detail)
- `PUT /api/posts/1` → `PostController@update` (JSON update)
- `DELETE /api/posts/1` → `PostController@destroy` (JSON delete)

**Why:** `apiResource()` registers only the five stateless routes. The `/api` prefix is automatically applied because the route is defined in `routes/api.php`.

---

**Example 2: Multiple API Resources in One Call**

```php
<?php
// routes/api.php

use App\Http\Controllers\Api\CommentController;
use App\Http\Controllers\Api\PostController;
use App\Http\Controllers\Api\UserController;
use Illuminate\Support\Facades\Route;

// Register three API resources at once
Route::apiResources([
    'posts'    => PostController::class,
    'comments' => CommentController::class,
    'users'    => UserController::class,
]);
```

**Expected Output:** Registers 15 routes total (5 per resource). All use the `/api` prefix and `api` middleware.

**Why:** `apiResources()` (plural) accepts an associative array and registers all resources in a single call, reducing boilerplate.

---

**Example 3: Nested API Resource with `only()`**

```php
<?php
// routes/api.php

use App\Http\Controllers\Api\CommentController;
use App\Http\Controllers\Api\PostController;
use Illuminate\Support\Facades\Route;

// Parent API resource
Route::apiResource('posts', PostController::class);

// Nested child — only index and store
Route::apiResource('posts.comments', CommentController::class)
    ->only(['index', 'store']);
```

**Expected Output:**
- `GET /api/posts/1/comments` → list comments for post 1.
- `POST /api/posts/1/comments` → create a comment on post 1.
- `GET /api/posts/1/comments/5` → 404 (show not registered).

**Why:** The `only()` method filters the nested API resource to just two actions, reducing the API surface for child resources that don't need full CRUD.

### Real-World Cases

- **Mobile App Backends:** `Route::apiResource('posts', PostController::class)` serves JSON to iOS/Android apps.
- **SPA Backends:** Vue/React front-ends consume API resources for CRUD operations.
- **Third-Party Integrations:** Partner systems access data through versioned API resources.
- **Microservices:** Internal services communicate via API resources scoped to specific domains.
- **Headless CMS:** Content is managed via API resources and delivered to any front-end.

## 4. Singleton Resources

### Definitions

**Core Definition:** Singleton resources are routes for resources that have exactly one instance (or zero-to-one instances) in the application, such as a user's profile or application settings, and therefore do not require an ID parameter in the URI.

**Technical Definition:** The `Route::singleton()` method registers four routes—`show`, `create`, `store`, `edit`, `update`, and `destroy`—but omits the `index` route, since there is only ever one instance. The URI contains no resource parameter (e.g., `/profile` rather than `/profiles/{profile}`). The `ResourceRegistrar::singleton()` method handles registration, and the controller is generated via `php artisan make:controller ProfileController --singleton`.

**Beginner-Friendly Explanation:** Some things only exist once per user or application—like your profile page or your account settings. You don't need `/profile/1` or `/profile/2`; you just need `/profile`. Singleton routes handle this elegantly by generating routes without ID parameters.

### Purposes

- To manage single-record routes (e.g., `/profile`, `/settings`) where an ID parameter is unnecessary.
- To enforce that only one instance of a resource exists per scope.
- To simplify URIs by removing redundant identifiers.
- To support nested singletons (e.g., `/videos/{video}/thumbnail`).
- To reduce route complexity for one-of-one resources.

### Syntax Rules and Structure

**Complete General Syntax:**

```php
Route::singleton('profile', ProfileController::class);
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `'profile'` | Singular resource name. |
| `ProfileController::class` | Controller class for the singleton. |

**Generated Routes:**

| Verb | URI | Action | Route Name |
|------|-----|--------|------------|
| GET | `/profile` | show | profile.show |
| GET | `/profile/create` | create | profile.create |
| POST | `/profile` | store | profile.store |
| GET | `/profile/edit` | edit | profile.edit |
| PUT/PATCH | `/profile` | update | profile.update |
| DELETE | `/profile` | destroy | profile.destroy |

**Complete General Syntax — Nested Singleton:**

```php
Route::singleton('videos.thumbnail', VideoThumbnailController::class);
```

**Generated Routes:**

| Verb | URI | Action |
|------|-----|--------|
| GET | `/videos/{video}/thumbnail` | show |
| GET | `/videos/{video}/thumbnail/edit` | edit |
| PUT/PATCH | `/videos/{video}/thumbnail` | update |
| DELETE | `/videos/{video}/thumbnail` | destroy |

**Complete General Syntax — Partial Singleton:**

```php
Route::singleton('profile', ProfileController::class)
    ->only(['show', 'update']);
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `->only(['show', 'update'])` | Registers only two singleton routes. |

**Syntax Rules:**

- Singleton routes have **no `index` action** because there is no collection to list.
- The resource name is **singular** (e.g., `profile`, not `profiles`).
- Nested singletons use dot notation: `Route::singleton('videos.thumbnail', ...)`.
- `only()` and `except()` work identically to standard resources.
- The `--singleton` flag generates a controller with the appropriate methods: `php artisan make:controller ProfileController --singleton`.

**Constraints and Limitations:**

- **Laravel 9.42+:** The `Route::singleton()` method was introduced in Laravel 9.42. Earlier versions require manual route definitions.
- **No index:** There is no route for listing singleton instances.
- **Parameter naming:** The URI parameter for nested singletons is the parent resource parameter (e.g., `{video}`), not the singleton itself.
- **Model binding:** Singleton routes do not automatically resolve a model instance unless you implement custom binding logic in the controller.

### Multiple Annotated Complete Code Examples

**Example 1: Basic Singleton Resource**

```php
<?php
// routes/web.php

use App\Http\Controllers\ProfileController;
use Illuminate\Support\Facades\Route;

// Singleton profile routes — no ID parameter
Route::singleton('profile', ProfileController::class);
```

```php
<?php
// app/Http/Controllers/ProfileController.php

namespace App\Http\Controllers;

use Illuminate\Http\Request;
use Illuminate\Support\Facades\Auth;

class ProfileController extends Controller
{
    // GET /profile
    public function show()
    {
        return view('profile.show', ['profile' => Auth::user()->profile]);
    }

    // PUT/PATCH /profile
    public function update(Request $request)
    {
        Auth::user()->profile->update($request->validated());
        return redirect()->route('profile.show');
    }

    // GET /profile/edit
    public function edit()
    {
        return view('profile.edit', ['profile' => Auth::user()->profile]);
    }
}
```

**Expected Output:** `GET /profile` shows the authenticated user's profile. `PUT /profile` updates it. No ID parameter is required in any URI.

**Why:** Singleton routes omit the resource parameter because there is only one profile per user. The controller resolves the profile through the authenticated user rather than a route parameter.

---

**Example 2: Nested Singleton Resource**

```php
<?php
// routes/web.php

use App\Http\Controllers\VideoThumbnailController;
use Illuminate\Support\Facades\Route;

// Nested singleton — thumbnail belongs to a specific video
Route::singleton('videos.thumbnail', VideoThumbnailController::class);
```

**Generated Routes:**
- `GET /videos/{video}/thumbnail` → show
- `GET /videos/{video}/thumbnail/edit` → edit
- `PUT/PATCH /videos/{video}/thumbnail` → update
- `DELETE /videos/{video}/thumbnail` → destroy

**Expected Output:** `GET /videos/5/thumbnail` shows the thumbnail for video 5. No `{thumbnail}` parameter is needed.

**Why:** The parent `{video}` parameter is required to scope the singleton, but the singleton itself has no ID. This is ideal for one-to-one relationships.

**Example 3: Partial Singleton with `only()`**

```php
<?php
// routes/web.php

use App\Http\Controllers\SettingsController;
use Illuminate\Support\Facades\Route;

// Only register show and update for settings
Route::singleton('settings', SettingsController::class)
    ->only(['show', 'update']);
```

**Expected Output:** Only `GET /settings` and `PUT/PATCH /settings` are registered. `GET /settings/create` and `DELETE /settings` return 405.

**Why:** The `only()` method filters the singleton to just the two actions the application needs, reducing the attack surface.

- **Application Settings:** `Route::singleton('settings', SettingsController::class)` handles global configuration.
- **User Preferences:** `Route::singleton('preferences', PreferenceController::class)` manages notification and display preferences.
- **Video Thumbnails:** `Route::singleton('videos.thumbnail', VideoThumbnailController::class)` manages a video's single thumbnail.
- **Company Logo:** `Route::singleton('company.logo', LogoController::class)` manages a company's single logo.

## 5. Route Inspection

### Definitions

**Core Definition:** Route inspection refers to the set of Artisan terminal commands that allow developers to list, diagnose, cache, and clear the application's route registrations.

**Technical Definition:** The `route:list` command invokes the `RouteListCommand`, which bootstraps the application's routing layer and iterates over the `RouteCollection`, rendering each route's HTTP verb, URI, name, action, and middleware. The `route:cache` command compiles all routes into a single `routes-v7.php` file in `bootstrap/cache`, while `route:clear` deletes this cache file. The `route:status` command (Laravel 12+) provides a summary of route registration status.

**Beginner-Friendly Explanation:** These are command-line tools that help you see what routes your application actually has, clear out cached routes when you make changes, and speed up your app in production by caching routes.

### Purposes

- To diagnose system schemas by listing all registered routes with their verbs, URIs, names, and middleware.
- To filter routes by name, path, or middleware for targeted inspection.
- To clear stale route caches after modifying route definitions.
- To create route caches for production performance optimisation.
- To verify that resource routes were registered correctly.
- To check middleware assignments for security auditing.

### Syntax Rules and Structure

**Complete General Syntax — `route:list`:**

```bash
php artisan route:list
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `php artisan` | Laravel's CLI entry point. |
| `route:list` | Lists all registered routes. |

**Complete General Syntax — Filtered `route:list`:**

```bash
php artisan route:list --path=api
php artisan route:list --name=posts
php artisan route:list --middleware=auth
php artisan route:list --except-vendor
```

**Component Breakdown:**

| Flag | Description |
|------|-------------|
| `--path=api` | Filter routes by URI path. |
| `--name=posts` | Filter routes by name. |
| `--middleware=auth` | Filter routes by middleware. |
| `--except-vendor` | Exclude vendor package routes. |
| `--only-vendor` | Show only vendor package routes. |
| `-v` | Verbose mode: show full middleware class names. |

**Complete General Syntax — Route Caching:**

```bash
php artisan route:cache    # Create route cache
php artisan route:clear    # Remove route cache
php artisan route:status   # Show route registration status (Laravel 12+)
```

**Component Breakdown:**

| Command | Description |
|---------|-------------|
| `route:cache` | Compiles all routes into a single cached file for production. |
| `route:clear` | Deletes the route cache file. |
| `route:status` | Displays a summary of route registration and cache status. |

**Syntax Rules:**

- `route:list` must be run from the application root directory.
- Routes using Closures cannot be cached. Use controller-based routes for cache compatibility.
- `route:clear` must be run after modifying route files if a route cache exists.
- The `-v` flag increases verbosity, showing full middleware class names instead of aliases.
- The `--middleware` filter accepts partial strings and matches aliases or class names.

**Constraints and Limitations:**

- **Closure limitation:** Routes using Closures prevent `route:cache` from functioning. Convert to controller-based routes for production caching.
- **Cache invalidation:** After deploying new code with changed routes, `route:clear` must be run (or `route:cache` re-run) to reflect the changes.
- **Performance:** `route:list` bootstraps the full application, which can be slow on large applications. Use filters to narrow output.
- **Laravel version:** `route:status` is available in Laravel 12+; earlier versions require `route:list` and manual inspection.

**Example 3: Route Caching Workflow**

```bash
# Step 1: Clear any existing route cache
php artisan route:clear

# Step 2: Verify routes are registered correctly
php artisan route:list --path=posts

# Step 3: Create the production route cache
php artisan route:cache

# Step 4: Verify cache status
php artisan route:status
```

**Expected Output:**
- `route:clear` → `Route cache cleared successfully.`
- `route:list` → Lists all `/posts` routes.
- `route:cache` → `Routes cached successfully!`
- `route:status` → Shows cache status summary.

**Why:** This workflow ensures that route changes are picked up (by clearing the cache), verified (by listing), and then optimised for production (by caching). The `route:status` command provides a final confirmation.

- **Debugging 404s:** `php artisan route:list --path=missing-route` quickly reveals whether a route is registered.
- **Security Auditing:** `php artisan route:list --middleware=auth` verifies that all sensitive routes are protected.
- **Production Deployment:** `php artisan route:cache` is a standard step in deployment scripts for performance.
- **API Documentation:** `php artisan route:list --path=api --json` outputs routes as JSON for documentation generation.
- **CI/CD Validation:** `php artisan route:list` is run in CI pipelines to verify that new routes are registered correctly.
