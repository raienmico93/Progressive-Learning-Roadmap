# Laravel Modern Routing Architecture & Optimization: A Comprehensive Cheat Sheet

---

## Topic Overview

### Definitions

**Core Definition:** Laravel Modern Routing Architecture & Optimization refers to the structural changes introduced in Laravel 11+ that simplify route registration, the security mechanisms (signed routes, rate limiting) that protect route endpoints, and the production optimization techniques (route caching) that maximise routing performance.

**Technical Definition:** Laravel 11 introduced a minimal application skeleton where the HTTP and Console kernels were removed, and route registration was consolidated into the `bootstrap/app.php` file via the `withRouting()` method. The `Application::configure()` fluent API now controls routing, middleware, and exception handling. Console commands are registered in `routes/console.php`, and a built-in health-check endpoint is exposed at `/up` by default. Signed routes use HMAC-SHA256 signatures generated by the `URL` facade, validated by the `ValidateSignature` middleware. Rate limiting is configured via the `RateLimiter` facade and applied through the `throttle` middleware. Route caching compiles all controller-based routes into a single serialised PHP file, reducing registration overhead from O(n) to O(1) at runtime.

**Beginner-Friendly Explanation:** Laravel 11 cleaned house. Instead of having many configuration files scattered around, it put the important settings in one place (`bootstrap/app.php`). It also added useful built-in features like a health-check URL that hosting platforms can ping, a way to create tamper-proof URLs (signed routes), a way to limit how many times someone can hit your API (rate limiting), and a way to make your app much faster in production by caching all your routes in one file.

### Key Characteristics

- **Minimal Skeleton:** Fewer default files; API, broadcasting, and console routes are opt-in.
- **Centralised Configuration:** Routing, middleware, and exceptions are configured in `bootstrap/app.php`.
- **Health-Check Built-In:** A `/up` endpoint is available out of the box for uptime monitoring.
- **Per-Second Rate Limiting:** Laravel 11 introduced per-second rate limiting granularity.
- **Signed URLs:** Cryptographically tamper-proof URLs for email verification, unsubscribe links, and more.
- **Route Caching:** Production route caching compiles routes into a single file for faster bootstrapping.
- **Closure Limitation:** Routes defined with Closures cannot be cached, requiring refactoring to controllers.

### Prerequisites

- **Laravel 11.x, 12.x, or 13.x** (this topic covers features introduced in Laravel 11+).
- **PHP 8.2+** (Laravel 11 requires PHP 8.2 minimum).
- Composer for dependency management.
- Basic understanding of HTTP routing, middleware, and Laravel's service container.

### Related Programming Areas

- **Application Bootstrapping:** The `bootstrap/app.php` file is the entry point for application configuration.
- **Middleware Pipeline:** Rate limiting and signature validation are implemented as middleware.
- **Security:** Signed routes and rate limiting protect against tampering and brute-force attacks.
- **DevOps & Deployment:** Health-check endpoints and route caching are critical for production deployments.
- **WebSocket Broadcasting:** `install:broadcasting` activates real-time features via Laravel Reverb.

## 1. Modern File Structures (Laravel 11+)

### Definitions

**Core Definition:** Laravel 11 introduced a minimal application structure that removes the HTTP and Console kernels, eliminates the default `api.php` and `channels.php` route files, and centralises routing, middleware, and exception configuration into `bootstrap/app.php`.

**Technical Definition:** The `Application::configure()` method in `bootstrap/app.php` returns an `ApplicationBuilder` instance, which provides the `withRouting()`, `withMiddleware()`, `withExceptions()`, and `withProviders()` methods. The `withRouting()` method accepts parameters for `web`, `api`, `commands`, `channels`, and `health` route files. The `install:api` Artisan command installs Laravel Sanctum and creates `routes/api.php`, while `install:broadcasting` creates `routes/channels.php` and installs Laravel Reverb.

**Beginner-Friendly Explanation:** In Laravel 10 and earlier, you had separate files like `app/Http/Kernel.php` for middleware, `app/Console/Kernel.php` for commands, and `routes/api.php` for API routes. Laravel 11 combined all of this into one file—`bootstrap/app.php`—and made the API and broadcasting route files opt-in, so you only create them if you actually need them.

### Purposes

- To provide a leaner, more modern experience while retaining familiar Laravel concepts.
- To centralise high-level application configuration in a single file.
- To reduce the default file count for applications that do not need APIs or broadcasting.
- To enable opt-in activation of API routes via `php artisan install:api`.
- To enable opt-in activation of WebSocket broadcasting via `php artisan install:broadcasting`.
- To simplify the learning curve for new Laravel developers by reducing configuration surface area.

### Syntax Rules and Structure

**Complete General Syntax — `bootstrap/app.php`:**

```php
<?php

use Illuminate\Foundation\Application;
use Illuminate\Foundation\Configuration\Exceptions;
use Illuminate\Foundation\Configuration\Middleware;

return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(
        web: __DIR__.'/../routes/web.php',
        commands: __DIR__.'/../routes/console.php',
        health: '/up',
    )
    ->withMiddleware(function (Middleware $middleware) {
        //
    })
    ->withExceptions(function (Exceptions $exceptions) {
        //
    })->create();
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `Application::configure()` | Static factory method creating the application builder. |
| `basePath: dirname(__DIR__)` | Sets the application's base path. |
| `->withRouting(web: ...)` | Registers the web route file. |
| `commands: ...` | Registers the console route file. |
| `health: '/up'` | Enables the health-check endpoint at `/up`. |
| `->withMiddleware(...)` | Configures middleware via a closure. |
| `->withExceptions(...)` | Configures exception handling via a closure. |

**Complete General Syntax — Activating API Routes:**

```bash
php artisan install:api
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `install:api` | Installs Laravel Sanctum, creates `routes/api.php`, and configures `bootstrap/app.php`. |

**Complete General Syntax — Activating Broadcasting:**

```bash
php artisan install:broadcasting
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `install:broadcasting` | Installs Laravel Reverb, creates `routes/channels.php`, and configures broadcasting. |

**Syntax Rules:**

- `bootstrap/app.php` must return the result of `Application::configure()->...->create()`.
- The `withRouting()` method can be called only once; all route files must be specified in a single call.
- The `health` parameter accepts a string URI (default `/up`) or a `false` value to disable the health route.
- After running `install:api`, the `api` parameter is automatically uncommented in `bootstrap/app.php`.
- The `install:api` command also creates a personal access tokens migration and a Sanctum configuration file.

**Constraints and Limitations:**

- **Laravel 11+ only:** The new structure is not available in Laravel 10 and earlier. Existing applications are not affected unless they opt into the new structure.
- **Kernel removal:** The `app/Http/Kernel.php` and `app/Console/Kernel.php` files are removed in Laravel 11. Middleware and commands are configured in `bootstrap/app.php` and `routes/console.php` respectively.
- **Service provider streamlining:** The `app/Providers/` directory is reduced to a single `AppServiceProvider` by default.
- **Route file creation:** `routes/api.php` and `routes/channels.php` do not exist by default; they must be created via the respective `install` commands.

**Why:** This is the default Laravel 11+ `bootstrap/app.php`. The `withRouting()` method registers only the specified route files. The `health: '/up'` parameter enables the built-in health-check route.

- **Minimal Web Applications:** Use the default structure without API or broadcasting routes for smaller applications.
- **Existing Laravel 10 Applications:** Continue using the old structure; the new structure is opt-in for new applications only.

## 2. Console & Health-Check Endpoints

### Definitions

**Core Definition:** Console routes (`routes/console.php`) define closure-based CLI commands, while the health-check endpoint (`/up`) is a built-in route that returns a 200 status when the application is running, used by uptime monitors and orchestration platforms.

**Technical Definition:** The `routes/console.php` file uses `Artisan::command()` to register closure-based console commands, each bound to a command instance with access to input/output methods. The health-check route is registered via the `health` parameter in `withRouting()` and dispatches a `DiagnosingHealth` event before returning a view. The route responds with HTTP 200 when the application is healthy and HTTP 500 when the framework fails to boot.

**Beginner-Friendly Explanation:** Console routes are like shortcuts for running PHP code from the terminal (e.g., `php artisan inspire`). The health-check endpoint is a special URL (`/up`) that you can give to services like AWS, Kubernetes, or UptimeRobot so they can automatically check if your app is alive and respond accordingly.

### Purposes

- To define closure-based console commands in a dedicated, organised file.
- To schedule recurring tasks within the console route file.
- To provide a standardised health-check endpoint for load balancers and orchestration platforms.
- To enable automated monitoring of application health without custom endpoint code.
- To integrate with container orchestration health probes (Kubernetes liveness/readiness).
- To reduce the need for custom health-check controllers.

### Syntax Rules and Structure

**Complete General Syntax — Console Route:**

```php
<?php
// routes/console.php

use Illuminate\Foundation\Inspiring;
use Illuminate\Support\Facades\Artisan;

Artisan::command('inspire', function () {
    $this->comment(Inspiring::quote());
})->purpose('Display an inspiring quote');
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `Artisan::command('inspire', ...)` | Registers a command named `inspire`. |
| `function () { ... }` | The command handler. `$this` refers to the command instance. |
| `$this->comment(...)` | Outputs a comment to the console. |
| `->purpose(...)` | Sets the command description shown in `php artisan list`. |

**Complete General Syntax — Scheduling Tasks:**

```php
<?php
// routes/console.php

use Illuminate\Support\Facades\Schedule;

Schedule::command('emails:send')->daily();
Schedule::call(function () {
    // Inline scheduled task
})->hourly();
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `Schedule::command(...)` | Schedules an Artisan command. |
| `->daily()` | Runs the command once per day. |
| `Schedule::call(...)` | Schedules an inline closure. |
| `->hourly()` | Runs the closure every hour. |

**Complete General Syntax — Health-Check Endpoint:**

```php
// In bootstrap/app.php
->withRouting(
    web: __DIR__.'/../routes/web.php',
    commands: __DIR__.'/../routes/console.php',
    health: '/up',
)
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `health: '/up'` | Registers the health-check route at `/up`. |
| Default response | HTTP 200 with `{"status":"ok"}` (JSON) or an animated "Application up" page (HTML). |

**Syntax Rules:**

- Console commands are defined using `Artisan::command()` in `routes/console.php`.
- The `$this` variable inside the closure refers to the `Command` instance, providing `$this->comment()`, `$this->info()`, `$this->error()`, etc.
- The `health` parameter accepts a string URI (e.g., `/up`, `/health`) or `false` to disable.
- The health route dispatches a `DiagnosingHealth` event, allowing listeners to perform additional checks.
- The health route returns HTTP 200 when healthy and HTTP 500 when the framework fails to boot.

**Constraints and Limitations:**

- **Console closures:** Console route commands are closure-based and cannot be cached like HTTP routes. For cacheable console commands, use dedicated `Command` classes.
- **Health route simplicity:** The built-in health route only checks that the framework boots—it does not check database connectivity, Redis, or other services. Use a package like `laravel-health` or `gavtaylor/laravel-health-route` for structured checks.
- **Middleware:** The health route uses the `web` middleware group by default. If the application uses session or CSRF middleware that could interfere, consider disabling the health route and creating a custom one.
- **Laravel version:** The health route is available in Laravel 11+. Earlier versions require manual implementation.

**Example 3: Health-Check Endpoint with Custom Response**

```php
<?php
// bootstrap/app.php

use Illuminate\Foundation\Application;

return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(
        web: __DIR__.'/../routes/web.php',
        commands: __DIR__.'/../routes/console.php',
        health: '/up',
    )
    ->withEvents(discover: [
        __DIR__.'/../app/Listeners',
    ])
    ->create();
```

```php
<?php
// app/Listeners/DiagnoseHealth.php

namespace App\Listeners;

use Illuminate\Foundation\Events\DiagnosingHealth;
use Illuminate\Support\Facades\DB;
use Illuminate\Support\Facades\Redis;

class DiagnoseHealth
{
    public function handle(DiagnosingHealth $event): void
    {
        // Check database connectivity
        try {
            DB::connection()->getPdo();
        } catch (\Exception $e) {
            abort(500, 'Database unavailable');
        }

        // Check Redis connectivity
        try {
            Redis::ping();
        } catch (\Exception $e) {
            abort(500, 'Redis unavailable');
        }
    }
}
```

**Expected Output:**
- `GET /up` → HTTP 200 `{"status":"ok"}` if database and Redis are reachable.
- `GET /up` → HTTP 500 if the database or Redis is unavailable.

**Why:** The `DiagnosingHealth` event is dispatched before the health route responds. Listeners can perform additional checks and `abort(500)` to signal unhealthy status. This provides a customisable health-check without overriding the route.

### Real-World Cases

- **Kubernetes Liveness Probes:** Configure `livenessProbe` to `GET /up` to restart unhealthy pods.
- **AWS ALB Health Checks:** Set the target group health check path to `/up`.
- **Uptime Monitoring:** Services like UptimeRobot and Pingdom ping `/up` every minute to detect downtime.
- **CLI Administrative Tasks:** Console routes provide quick commands for user management, data seeding, and maintenance.
- **Scheduled Maintenance:** The scheduler in `routes/console.php` runs backups, pruning, and report generation.

## 3. Signed Routes

### Definitions

**Core Definition:** Signed routes are URLs that include a cryptographic signature in the query string, allowing Laravel to verify that the URL has not been tampered with since it was generated.

**Technical Definition:** The `URL::signedRoute()` method generates a URL with an `signature` query parameter computed as an HMAC-SHA256 hash of the full URL (including the host, path, query string, and any expiration time). The `ValidateSignature` middleware (aliased as `signed`) recalculates the signature on the incoming request and compares it to the provided value. If they match and the URL has not expired, the request proceeds; otherwise, an `InvalidSignatureException` is thrown, resulting in a 401 or 403 response.

**Beginner-Friendly Explanation:** When you send someone a link in an email—like a password reset link—you want to make sure no one can change the URL to access someone else's account. Signed routes add a secret code to the URL that only your application can generate. If anyone tries to change the URL, the code won't match, and Laravel will reject the request.

### Purposes

- To generate tamper-proof URLs for sensitive operations like email verification and password reset.
- To protect unsubscribe links from being manipulated to unsubscribe arbitrary users.
- To secure temporary download links that expire after a set time.
- To prevent CSRF-like attacks on GET-based actions.
- To enable stateless authentication for one-time-use URLs.

### Syntax Rules and Structure

**Complete General Syntax — Generating a Signed URL:**

```php
use Illuminate\Support\Facades\URL;

$url = URL::signedRoute('unsubscribe', ['user' => 1]);
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `URL::signedRoute()` | Generates a signed URL for a named route. |
| `'unsubscribe'` | The named route to generate the URL for. |
| `['user' => 1]` | Route parameters to include. |

**Complete General Syntax — Temporary Signed URL:**

```php
$url = URL::temporarySignedRoute(
    'unsubscribe',
    now()->addMinutes(30),
    ['user' => 1]
);
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `URL::temporarySignedRoute()` | Generates a signed URL that expires. |
| `now()->addMinutes(30)` | The expiration time (30 minutes from now). |
| `['user' => 1]` | Route parameters. |

**Complete General Syntax — Verifying a Signed Route:**

```php
use Illuminate\Http\Request;

Route::get('/unsubscribe/{user}', function (Request $request) {
    if (! $request->hasValidSignature()) {
        abort(401);
    }
    // ...
})->name('unsubscribe');
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `$request->hasValidSignature()` | Checks the request's signature validity. |
| `abort(401)` | Returns a 401 Unauthorized response if invalid. |

**Complete General Syntax — ValidateSignature Middleware:**

```php
Route::get('/unsubscribe/{user}', function () {
    // ...
})->name('unsubscribe')->middleware('signed');
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `->middleware('signed')` | Applies the `ValidateSignature` middleware. |
| Automatic rejection | Returns 403 Forbidden if the signature is invalid. |

**Syntax Rules:**

- The `signedRoute()` method must be called on the `URL` facade (`Illuminate\Support\Facades\URL`).
- The `signed` middleware alias maps to `Illuminate\Routing\Middleware\ValidateSignature`.
- Temporary signed routes include an `expires` query parameter; expired URLs are rejected.
- The `absolute: false` argument excludes the domain from the signature hash, useful for load-balanced environments.
- The `ValidateSignature` middleware supports additional arguments to ignore specific query parameters.

**Constraints and Limitations:**

- **APP_KEY dependency:** Signed URLs are generated using the application's `APP_KEY`. Rotating the key invalidates all existing signed URLs.
- **Query string only:** Signed routes work through query parameters. They do not protect against POST body tampering.
- **Time sensitivity:** Temporary signed routes require accurate server time. Clock skew between servers can cause false rejections.
- **URL length:** The signature adds a query parameter, making URLs slightly longer.
- **No encryption:** Signed URLs are tamper-proof but not encrypted. Do not include sensitive data in the URL parameters.

### Multiple Annotated Complete Code Examples

**Example 1: Email Verification with Signed Route**

```php
<?php
// app/Http/Controllers/Auth/VerificationController.php

namespace App\Http\Controllers\Auth;

use App\Models\User;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\URL;

class VerificationController extends Controller
{
    /**
     * Send a verification email with a signed URL.
     */
    public function send(Request $request)
    {
        $user = $request->user();

        $verificationUrl = URL::temporarySignedRoute(
            'verification.verify',
            now()->addHours(24),
            ['user' => $user->id]
        );

        // Send email with $verificationUrl...
        return response()->json(['url' => $verificationUrl]);
    }
}
```

```php
<?php
// routes/web.php

use Illuminate\Http\Request;
use Illuminate\Support\Facades\Route;

Route::get('/email/verify/{user}', function (Request $request, string $user) {
    // The 'signed' middleware validates the signature automatically
    $user = \App\Models\User::findOrFail($user);
    $user->markEmailAsVerified();

    return 'Email verified!';
})->name('verification.verify')->middleware('signed');
```

**Expected Output:**
- The generated URL looks like `https://example.com/email/verify/1?expires=...&signature=...`.
- Visiting the URL with a valid signature verifies the email.
- Modifying the `user` parameter or the signature returns 403 Forbidden.

**Why:** The `temporarySignedRoute()` method generates a URL with an expiration and a signature. The `signed` middleware validates both the signature and the expiration before allowing the request to proceed.

**Example 2: Custom Validation Logic**

```php
<?php
// routes/web.php

use Illuminate\Http\Request;
use Illuminate\Support\Facades\URL;

Route::get('/download/{file}', function (Request $request, string $file) {
    // Manual signature validation
    if (! $request->hasValidSignature()) {
        abort(401, 'Invalid or expired download link.');
    }

    // Serve the file...
    return response()->download(storage_path("app/files/{$file}"));
})->name('download');

// Generate a signed download URL
$downloadUrl = URL::temporarySignedRoute(
    'download',
    now()->addMinutes(15),
    ['file' => 'report.pdf']
);
```

**Expected Output:** Visiting the generated URL downloads `report.pdf`. After 15 minutes, the URL returns 401. Modifying the `file` parameter returns 401.

**Why:** Manual validation via `hasValidSignature()` provides full control over the response. The `temporarySignedRoute()` method includes an `expires` parameter that is validated automatically.

**Example 3: Signed Route with Ignored Parameters**

```php
<?php
```

### Real-World Cases

- **Password Reset:** Send a temporary signed URL to the user's email; the URL expires after 30–60 minutes.
- **Email Verification:** Generate a signed URL that verifies the user's email without requiring login.
- **Unsubscribe Links:** Include a signed URL in marketing emails so recipients can unsubscribe without authentication.
- **Temporary Downloads:** Generate signed URLs for files that expire after a set time, preventing hotlinking.
- **One-Time Actions:** Use signed URLs for actions that should only be performed once (e.g., confirming a booking).

## 4. Throttle Middleware & Rate Limiting

### Definitions

**Core Definition:** The `throttle` middleware restricts the number of requests a client can make to a route within a specified time window, protecting against brute-force attacks, API abuse, and traffic spikes.

**Technical Definition:** Rate limiters are defined via the `RateLimiter::for()` method, which accepts a name and a closure returning a `Limit` instance. The `Limit` class specifies the maximum number of requests per time period and the key (user ID, IP address, etc.). The `throttle` middleware accepts the rate limiter name as a parameter (e.g., `throttle:api`) and uses Laravel's cache-backed rate limiting to track request counts. If the limit is exceeded, a 429 Too Many Requests response is returned with `Retry-After` and `X-RateLimit-*` headers.

**Beginner-Friendly Explanation:** Rate limiting is like a bouncer at a club who says "you can only come in 60 times per minute." If you try to come in more often, you're turned away with a "429 Too Many Requests" message and told to try again later. This prevents bots and attackers from overwhelming your application.

### Purposes

- To restrict brute-force traffic spikes on authentication endpoints.
- To protect API endpoints from abuse by limiting request frequency.
- To enforce fair usage policies across different user tiers (free vs. paid).
- To prevent denial-of-service (DoS) attacks by capping request rates.
- To provide per-user and per-IP rate limiting with dynamic limit calculation.
- To comply with third-party API rate limits (e.g., GitHub API).

### Syntax Rules and Structure

**Complete General Syntax — Defining a Rate Limiter:**

```php
// In AppServiceProvider::boot() or bootstrap/app.php
use Illuminate\Cache\RateLimiting\Limit;
use Illuminate\Support\Facades\RateLimiter;

RateLimiter::for('api', function (Request $request) {
    return Limit::perMinute(60)->by($request->user()?->id ?: $request->ip());
});
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `RateLimiter::for('api', ...)` | Registers a rate limiter named `api`. |
| `Limit::perMinute(60)` | Allows 60 requests per minute. |
| `->by($request->user()?->id ?: $request->ip())` | Uses user ID if authenticated, otherwise IP address. |

**Complete General Syntax — Applying to Routes:**

```php
Route::middleware(['throttle:api'])->group(function () {
    Route::get('/user', function () {
        return 'User data';
    });
});
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `->middleware(['throttle:api'])` | Applies the `api` rate limiter to the group. |
| `throttle:api` | The `api` rate limiter name. |

**Complete General Syntax — Inline Throttle:**

```php
Route::get('/profile', function () {
    return 'Profile';
})->middleware('throttle:60,1');
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `throttle:60,1` | 60 requests per 1 minute (inline configuration). |

**Complete General Syntax — Dynamic Rate Limiting:**

```php
RateLimiter::for('uploads', function (Request $request) {
    return $request->user()->isPremium()
        ? Limit::none()
        : Limit::perMinute(10)->by($request->user()->id);
});
```

**Component Breakdown:**

| Component | Description |
|-----------|-------------|
| `Limit::none()` | No limit for premium users. |
| `Limit::perMinute(10)` | 10 requests per minute for free users. |
| `->by($request->user()->id)` | Limits are tracked per user ID. |

**Syntax Rules:**

- Rate limiters must be defined in a service provider's `boot()` method (typically `AppServiceProvider`).
- The `throttle` middleware accepts either a limiter name (`throttle:api`) or inline parameters (`throttle:60,1`).
- Laravel 11+ supports per-second rate limiting (`Limit::perSecond()`).
- The `Limit` class supports `perMinute()`, `perHour()`, `perDay()`, and `perSecond()`.
- The `by()` method determines the key used for tracking; if omitted, the authenticated user ID or IP is used.

**Constraints and Limitations:**

- **Cache dependency:** Rate limiting requires a cache driver. Redis is recommended for distributed applications.
- **Middleware order:** Rate limiting should be applied before authentication middleware when limiting by IP, or after when limiting by user ID.
- **`throttle:api` vs. `throttle:60,1`:** The named limiter (`throttle:api`) is preferred for configurability; inline parameters are simpler but less flexible.
- **429 responses:** Exceeded limits return HTTP 429 with `Retry-After` and `X-RateLimit-*` headers.

### Multiple Annotated Complete Code Examples

**Example 1: API Rate Limiting with Named Limiter**

```php
<?php
// app/Providers/AppServiceProvider.php

namespace App\Providers;

use Illuminate\Cache\RateLimiting\Limit;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\RateLimiter;
use Illuminate\Support\ServiceProvider;

class AppServiceProvider extends ServiceProvider
{
    public function boot(): void
    {
        // Define the 'api' rate limiter
        RateLimiter::for('api', function (Request $request) {
            return Limit::perMinute(60)
                ->by($request->user()?->id ?: $request->ip());
        });
    }
}
```

```php
<?php
// routes/api.php

use Illuminate\Support\Facades\Route;

Route::middleware(['throttle:api'])->group(function () {
    Route::get('/user', function (Request $request) {
        return $request->user();
    });

    Route::get('/posts', function () {
        return \App\Models\Post::all();
    });
});
```

**Expected Output:**
- Authenticated users: 60 requests per minute per user ID.
- Guests: 60 requests per minute per IP address.
- 61st request: HTTP 429 with `Retry-After: 60`.

**Why:** The `RateLimiter::for('api', ...)` defines the limiter. The `throttle:api` middleware applies it to all routes in the group. The `by()` method differentiates between authenticated users and guests.

---

**Example 2: Dynamic Rate Limiting for Premium Users**

```php
<?php
// app/Providers/AppServiceProvider.php

use Illuminate\Cache\RateLimiting\Limit;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\RateLimiter;

RateLimiter::for('downloads', function (Request $request) {
    $user = $request->user();

    // Premium users: unlimited downloads
    if ($user && $user->isPremium()) {
        return Limit::none();
    }

    // Free users: 5 downloads per hour
    if ($user) {
        return Limit::perHour(5)->by($user->id);
    }

    // Guests: 1 download per hour by IP
    return Limit::perHour(1)->by($request->ip());
});
```

```php
<?php
// routes/web.php

Route::get('/download/{file}', function (string $file) {
    return response()->download(storage_path("app/files/{$file}"));
})->middleware('throttle:downloads')->name('download');
```

**Expected Output:**
- Premium user: unlimited downloads.
- Free user: 5 downloads per hour.
- Guest: 1 download per hour.
- 6th free-user download: HTTP 429.

**Why:** The rate limiter closure returns different `Limit` instances based on the user's subscription tier. `Limit::none()` disables limiting for premium users.

---

**Example 3: Per-Second Rate Limiting (Laravel 11+)**

```php
<?php
// app/Providers/AppServiceProvider.php

use Illuminate\Cache\RateLimiting\Limit;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\RateLimiter;

RateLimiter::for('high-frequency', function (Request $request) {
    // Allow 10 requests per second per IP
    return Limit::perSecond(10)->by($request->ip());
});
```

```php
<?php
// routes/api.php

Route::middleware(['throttle:high-frequency'])->group(function () {
    Route::post('/webhook', function () {
        return response()->json(['status' => 'received']);
    });
});
```

**Expected Output:** A webhook endpoint accepts up to 10 requests per second from a single IP. The 11th request in the same second returns HTTP 429.

**Why:** Laravel 11 introduced `Limit::perSecond()` for high-frequency endpoints like webhooks. The `by($request->ip())` ensures each IP is limited independently.

### Real-World Cases

- **Login Endpoints:** `throttle:5,1` (5 attempts per minute) prevents brute-force password attacks.
- **API Endpoints:** `throttle:api` with 60 requests per minute is a standard API rate limit.
- **Webhook Receivers:** Per-second rate limiting handles high-frequency webhook traffic from external services.
- **File Downloads:** Dynamic rate limiting gives premium users unlimited downloads while capping free users.
- **Password Reset:** `throttle:3,1` (3 attempts per minute) prevents abuse of password reset endpoints.

## 5. Production Route Caching

### Definitions

**Core Definition:** Route caching is a production optimization technique that compiles all controller-based routes into a single serialised PHP file, dramatically reducing the time Laravel spends registering routes on each request.

**Technical Definition:** The `php artisan route:cache` command serialises the `RouteCollection` into `bootstrap/cache/routes-v7.php`. At runtime, Laravel loads this file instead of parsing the route definition files (`web.php`, `api.php`, etc.). This reduces route registration overhead from O(n) (proportional to the number of routes) to O(1) (a single file inclusion). The command **fails** if any route uses a Closure, because Closures cannot be serialised.

**Beginner-Friendly Explanation:** Every time someone visits your Laravel app, Laravel normally reads all your route files and figures out which route matches the request. If you have hundreds of routes, this takes time. Route caching pre-computes all of this and saves it in a single file, so Laravel can just load that file instead of doing the work every time. It's like pre-sorting a deck of cards instead of shuffling them on every request.

### Purposes

- To maximise registration execution speed by eliminating repeated route parsing.
- To reduce CPU overhead per request in production environments.
- To improve response times for applications with many routes.
- To decrease memory usage during route registration.
- To prevent deployment slowdowns caused by uncached Closure routes.

### Syntax Rules and Structure

**Complete General Syntax — Route Caching:**

```bash
php artisan route:cache
```

**Component Breakdown:**

| Command | Description |
|---------|-------------|
| `php artisan route:cache` | Compiles routes into `bootstrap/cache/routes-v7.php`. |

**Complete General Syntax — Clearing Route Cache:**

```bash
php artisan route:clear
```

**Component Breakdown:**

| Command | Description |
|---------|-------------|
| `php artisan route:clear` | Deletes the route cache file. |

**Complete General Syntax — Checking Status:**

```bash
php artisan route:status
```

**Component Breakdown:**

| Command | Description |
|---------|-------------|
| `php artisan route:status` | Shows route registration and cache status (Laravel 12+). |

**Syntax Rules:**

- Route caching must be enabled **after** all routes are defined. If you add new routes, you must re-run `route:cache`.
- **Closure routes cannot be cached.** The command will fail with an error if any route uses a Closure.
- Route caching is intended for production environments only. In development, use `route:clear` after modifying routes.
- The `optimize` command (`php artisan optimize`) runs `route:cache` along with `config:cache` and `view:cache`.

**Constraints and Limitations:**

- **Closure incompatibility:** This is the most significant limitation. Any route defined as `Route::get('/path', function () { ... })` will prevent route caching. Convert all Closures to controller methods.
- **Deployment requirement:** After deploying new code, you must run `route:cache` on the production server (or in the deployment pipeline).
- **Cache invalidation:** If routes change without clearing the cache, the application will serve stale routes.
- **Vendor package routes:** Routes from vendor packages are included in the cache. Ensure all packages are installed before caching.

### Multiple Annotated Complete Code Examples

**Example 1: Basic Route Caching Workflow**

```bash
# Step 1: Clear any existing cache
php artisan route:clear

# Step 2: Verify all routes are controller-based (no Closures)
php artisan route:list

# Step 3: Create the route cache
php artisan route:cache

# Step 4: Verify the cache was created
php artisan route:status
```

**Expected Output:**
- `route:clear` → `Route cache cleared successfully.`
- `route:list` → Lists all routes.
- `route:cache` → `Routes cached successfully!`
- `route:status` → Shows cache status.

**Why:** This workflow ensures that stale caches are cleared, routes are verified, and the new cache is created. The `route:status` command confirms the cache is active.

---

**Example 2: Refactoring a Closure Route to a Controller**

```php
<?php
// BEFORE: Closure route (cannot be cached)
// routes/web.php

use Illuminate\Support\Facades\Route;

Route::get('/welcome', function () {
    return view('welcome');
});
```

```php
<?php
// AFTER: Controller route (can be cached)

// Step 1: Create the controller
// php artisan make:controller WelcomeController

// app/Http/Controllers/WelcomeController.php
namespace App\Http\Controllers;

class WelcomeController extends Controller
{
    public function __invoke()
    {
        return view('welcome');
    }
}
```

```php
<?php
// routes/web.php

use App\Http\Controllers\WelcomeController;
use Illuminate\Support\Facades\Route;

Route::get('/welcome', WelcomeController::class);
```

**Expected Output:** Running `php artisan route:cache` succeeds after refactoring. The `/welcome` route is now cacheable.

**Why:** The Closure route prevented caching. Refactoring to an invokable controller makes the route serialisable and cacheable. This is a critical step for production deployments.

For large applications, the RPS (requests per second) can increase from ~1,800 to ~3,920, with response time dropping from 5.4ms to 2.3ms.

### Real-World Cases

- **Large E-commerce Platforms:** Thousands of routes are common; route caching is essential for acceptable response times.
- **SaaS Applications:** Multi-tenant applications with many route groups benefit significantly from caching.
- **API Gateways:** High-throughput API endpoints rely on route caching to maintain low latency.
- **Deployment Pipelines:** Standard deployment scripts include `php artisan route:cache` as a post-deploy step.
- **CI/CD Validation:** `php artisan route:cache` is run in CI to verify that no Closure routes were introduced.
