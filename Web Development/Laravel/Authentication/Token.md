# Laravel Token Authentication: A Comprehensive Programming Cheat Sheet

---

## Topic Overview

### Definitions

**Core Definition**

Laravel Token Authentication is a stateless authentication mechanism where a client (mobile app, SPA, or third-party service) exchanges credentials for an opaque token, which is then sent with each subsequent request to authenticate the user. Unlike session authentication, token authentication does not rely on server-side sessions or cookies; the token itself carries the authentication state.

**Technical Definition**

Token authentication in Laravel is implemented through two primary packages: **Laravel Sanctum** (for lightweight API tokens, SPAs, and mobile apps) and **Laravel Passport** (for full OAuth2 server implementations). Sanctum stores hashed API tokens in a `personal_access_tokens` table and authenticates requests via the `Authorization: Bearer` header or stateful SPA cookies. Passport implements the OAuth2 protocol using the League OAuth2 server, issuing access tokens, refresh tokens, and supporting authorization code, password, client credentials, and other grant types.

**Beginner-Friendly Explanation**

Token authentication is like a temporary key you receive after proving who you are. You show your ID (email and password) once, and in return you get a key (token). For every future request, you show that key instead of your password. This is perfect for mobile apps and APIs because the server does not need to remember who you are between requests — the key proves it every time. Think of it as a hotel key card: you check in once at the front desk, and then your key card opens your room door without you having to go back to the front desk every time.

---

### Key Characteristics

- **Statelessness**: The server does not store session state; each request carries the token that proves identity.
- **Scalability**: Stateless authentication scales horizontally because no session affinity is required.
- **Multiple Tokens per User**: Sanctum allows each user to generate multiple API tokens, each with its own abilities and expiration.
- **Token Abilities (Scopes)**: Tokens can be granted specific abilities (e.g., `server:update`, `read`) that restrict what actions they can perform.
- **Token Revocation**: Tokens can be individually revoked or revoked in bulk without affecting other tokens.
- **SPA Support**: Sanctum supports cookie-based SPA authentication (CSRF-protected) in addition to API tokens.
- **OAuth2 Compliance**: Passport provides full OAuth2 server capabilities for third-party integrations.
- **Token Hashing**: Sanctum hashes tokens using SHA-256 before storing them in the database, so the plain-text token is only shown once at creation.

---

### Prerequisites

- **PHP 8.1 or higher** (Laravel 10+) or **PHP 8.2** (Laravel 11+).
- **A Laravel application** installed via Composer.
- **A configured database** for storing tokens.
- **Basic understanding of HTTP headers** and the `Authorization` header.
- **Familiarity with Eloquent models** and middleware.

---

### Related Programming Areas

- **Session Authentication**: Token authentication is the stateless counterpart to session authentication.
- **OAuth2**: Passport implements the OAuth2 protocol; understanding OAuth2 terminology (grant types, scopes, clients) is helpful.
- **Middleware**: Token authentication is enforced via middleware (`auth:sanctum`, `auth:api`).
- **Eloquent**: Tokens are stored in database tables and managed through Eloquent relationships.
- **API Development**: Token authentication is the standard for securing RESTful APIs.

### 1. API Tokens

#### Definitions

**Core Definition**

An API token is an opaque string that a client presents to the server to authenticate a request. The server validates the token, retrieves the associated user, and grants access based on the token's abilities.

**Technical Definition**

In Laravel Sanctum, API tokens are stored in the `personal_access_tokens` table. Each token record contains a `tokenable` morph relationship (the user), a hashed `token` value, a `name`, optional `abilities` (JSON array), and timestamps. Tokens are created via `$user->createToken($name, $abilities)`, which returns a `NewAccessToken` instance whose `plainTextToken` property contains the unhashed token. Requests are authenticated via the `Authorization: Bearer <token>` header.

**Beginner-Friendly Explanation**

An API token is a long string of characters that works like a password, but is generated by the application, not chosen by the user. You give this token to your mobile app or API client, and it sends the token with every request. Laravel checks the token against its database and, if valid, knows who you are.

#### Purposes

- To provide stateless authentication for API clients.
- To allow users to generate multiple tokens for different devices or applications.
- To enable fine-grained access control through token abilities.
- To support token revocation without affecting other tokens or the user's password.

#### Syntax Rules and Structure

**Complete General Syntax**

```php
// Issuing a token
$token = $user->createToken('token-name', ['ability1', 'ability2']);
return $token->plainTextToken;

// Using the token (client side)
// Authorization: Bearer <plainTextToken>
```

**Component Breakdown**

| Component | Description |
|-----------|-------------|
| `createToken($name, $abilities)` | Creates a new token. |
| `$name` | A human-readable label for the token. |
| `$abilities` | Array of allowed abilities (optional). |
| `plainTextToken` | The unhashed token string. |

**Syntax Rules**

- The `HasApiTokens` trait must be added to the `User` model.
- The token is hashed using SHA-256 before storage.
- `plainTextToken` is only available immediately after creation.
- Tokens are sent in the `Authorization: Bearer` header.

**Constraints and Limitations**

- The plain-text token cannot be retrieved after creation.
- Tokens should be transmitted over HTTPS only.
- Default token expiration is null (no expiration) unless configured.

#### Multiple Annotated Complete Step by Step Code Examples and Expected Outputs

**Example 1: Issuing a Basic API Token**

**User Model**

```php
<?php
// app/Models/User.php
namespace App\Models;

use Illuminate\Foundation\Auth\User as Authenticatable;
use Laravel\Sanctum\HasApiTokens;

class User extends Authenticatable
{
    use HasApiTokens;
}
```

**Controller**

```php
<?php
// app/Http/Controllers/AuthController.php
namespace App\Http\Controllers;

use App\Models\User;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Hash;

class AuthController extends Controller
{
    public function login(Request $request)
    {
        $user = User::where('email', $request->email)->first();

        if (! $user || ! Hash::check($request->password, $user->password)) {
            return response()->json(['error' => 'Invalid credentials'], 401);
        }

        $token = $user->createToken('mobile-app')->plainTextToken;

        return response()->json(['token' => $token]);
    }
}
```

**Expected Output**

```json
{"token":"1|abc123def456ghi789..."}
```

**Why This Output Occurs**

The `createToken` method generates a new token, stores its SHA-256 hash in the database, and returns the plain-text token. The client stores this token and sends it as `Authorization: Bearer 1|abc123...` in subsequent requests.

---

**Example 2: Protecting a Route with Sanctum**

**Route**

```php
// routes/api.php
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Route;

Route::middleware('auth:sanctum')->get('/user', function (Request $request) {
    return $request->user();
});
```

**Expected Output (with valid token)**

```json
{"id":1,"name":"John Doe","email":"john@example.com"}
```

**Expected Output (without token)**

```json
{"message":"Unauthenticated."}
```

**Why This Output Occurs**

The `auth:sanctum` middleware validates the Bearer token. If valid, it resolves the user and injects it into the request. If invalid or missing, it returns a 401 Unauthenticated response.

#### Real-World Cases with Explanation

**Case 1: Mobile App Authentication**

A mobile app authenticates users via email and password, receives a Sanctum token, and stores it securely on the device (e.g., Keychain on iOS, Keystore on Android). Every API request includes the token in the `Authorization` header.

**Explanation**: Token authentication is ideal for mobile apps because it is stateless and works seamlessly across app restarts.

**Case 2: Third-Party API Integration**

A SaaS platform allows customers to generate API tokens from their account settings. These tokens are used by external scripts or integrations to access the platform's API on the customer's behalf.

**Explanation**: Personal access tokens enable secure, revocable programmatic access without sharing passwords.

### 2. Sanctum

#### Definitions

**Core Definition**

Laravel Sanctum is a lightweight authentication package for SPAs, mobile applications, and simple token-based APIs. It provides API token issuance and SPA cookie authentication without the complexity of OAuth2.

**Technical Definition**

Sanctum is a first-party Laravel package that stores API tokens in a `personal_access_tokens` table and authenticates requests via the `Authorization: Bearer` header or stateful cookies. It uses the `HasApiTokens` trait on the `User` model, the `auth:sanctum` middleware, and the `Laravel\Sanctum\Sanctum` service provider. Sanctum also provides `EnsureFrontendRequestsAreStateful` middleware for SPA cookie authentication.

**Beginner-Friendly Explanation**

Sanctum is the simple way to add authentication to your API. It is perfect for your own mobile app or single-page application. If you need to let other companies build integrations with OAuth2, you would use Passport instead.

#### Purposes

- To provide simple API token authentication without OAuth2 complexity.
- To authenticate SPAs using session cookies with CSRF protection.
- To support mobile applications with long-lived personal access tokens.
- To offer token abilities for fine-grained access control.

#### Syntax Rules and Structure

**Complete General Syntax**

```bash
# Installation
php artisan install:api
```

```php
// User model
use Laravel\Sanctum\HasApiTokens;

class User extends Authenticatable
{
    use HasApiTokens;
}

// Protecting routes
Route::middleware('auth:sanctum')->get('/user', ...);
```

**Component Breakdown**

| Component | Description |
|-----------|-------------|
| `install:api` | Installs Sanctum and creates `routes/api.php`. |
| `HasApiTokens` | Trait for the `User` model. |
| `auth:sanctum` | Middleware for token/SPA authentication. |
| `personal_access_tokens` | Database table for tokens. |

**Syntax Rules**

- Sanctum is installed via `php artisan install:api` in Laravel 11+.
- The `HasApiTokens` trait must be added to the `User` model.
- The `auth:sanctum` middleware protects API routes.
- SPA authentication requires the `EnsureFrontendRequestsAreStateful` middleware and `SANCTUM_STATEFUL_DOMAINS` configuration.

**Constraints and Limitations**

- Sanctum does not support OAuth2.
- SPA authentication requires same-domain or configured stateful domains.
- Tokens have no expiration by default.

### 4. Sanctum Configuration

#### Definitions

**Core Definition**

Sanctum configuration involves setting up the `HasApiTokens` trait on the `User` model, configuring the `sanctum.php` config file, and setting up SPA stateful domains.

**Technical Definition**

The `config/sanctum.php` file contains options including `stateful` (domains for SPA authentication), `guard` (default: `web`), `expiration` (token lifetime in minutes), `token_prefix` (optional token prefix), and `middleware` (middleware for Sanctum routes). The `HasApiTokens` trait is added to the `User` model. For SPA authentication, `SANCTUM_STATEFUL_DOMAINS` must include the SPA's domain.

**Beginner-Friendly Explanation**

Configuring Sanctum means telling Laravel which domains are allowed to use SPA authentication, how long tokens should last, and adding a trait to your user model.

#### Purposes

- To enable Sanctum's API token and SPA authentication features.
- To configure token expiration and stateful domains.
- To add the necessary trait to the `User` model.
- To customize Sanctum's behaviour for the application's needs.

#### Syntax Rules and Structure

**Complete General Syntax**

```php
// config/sanctum.php
return [
    'stateful' => explode(',', env('SANCTUM_STATEFUL_DOMAINS', sprintf(
        '%s%s',
        'localhost,localhost:3000,127.0.0.1,127.0.0.1:8000,::1',
        Sanctum::currentApplicationUrlWithPort(),
    ))),
    'guard' => ['web'],
    'expiration' => null, // minutes, null = never expires
    'token_prefix' => env('SANCTUM_TOKEN_PREFIX', ''),
    'middleware' => [
        'authenticate_session' => Laravel\Sanctum\Http\Middleware\AuthenticateSession::class,
        'encrypt_cookies' => Illuminate\Cookie\Middleware\EncryptCookies::class,
        'validate_csrf_token' => Illuminate\Foundation\Http\Middleware\ValidateCsrfToken::class,
    ],
];
```

**Component Breakdown**

| Option | Description |
|--------|-------------|
| `stateful` | Domains for SPA authentication. |
| `guard` | The guard used for SPA authentication. |
| `expiration` | Token lifetime in minutes. |
| `token_prefix` | Optional prefix for tokens. |

**Syntax Rules**

- The `HasApiTokens` trait must be added to the `User` model.
- `SANCTUM_STATEFUL_DOMAINS` should include all SPA domains.
- `expiration` is null by default (tokens never expire).

**Constraints and Limitations**

- SPA authentication requires the `EnsureFrontendRequestsAreStateful` middleware.
- The `expiration` setting overrides token-specific `expires_at` values.

### 5. Sanctum Token Issuance

#### Definitions

**Core Definition**

Sanctum token issuance is the process of generating a new API token for a user, typically during login or from an account settings page.

**Technical Definition**

Tokens are issued via `$user->createToken($name, $abilities)`, which creates a `PersonalAccessToken` record with a hashed token and returns a `NewAccessToken` instance. The `plainTextToken` property contains the unhashed token, which should be displayed to the user immediately. The token is formatted as `{id}|{plainTextToken}`.

**Beginner-Friendly Explanation**

Token issuance is how you give a user their key. When they log in or click "Generate API Token," Laravel creates a new token and shows it to them once. They need to save it because they will not see it again.

#### Purposes

- To generate API tokens for users.
- To allow users to create multiple tokens for different devices.
- To assign abilities to tokens at creation time.
- To provide a secure, hashed token storage mechanism.

#### Syntax Rules and Structure

**Complete General Syntax**

```php
// Basic token
$token = $user->createToken('token-name')->plainTextToken;

// Token with abilities
$token = $user->createToken('token-name', ['read', 'write'])->plainTextToken;

// Token with expiration
$token = $user->createToken('token-name', ['*'], now()->addWeek())->plainTextToken;
```

**Component Breakdown**

| Parameter | Description |
|-----------|-------------|
| `$name` | Human-readable token label. |
| `$abilities` | Array of allowed abilities. |
| `$expiresAt` | Optional expiration timestamp. |

**Syntax Rules**

- The `createToken` method returns a `NewAccessToken` instance.
- `plainTextToken` is the unhashed token.
- Tokens are hashed with SHA-256 before storage.
- `['*']` grants all abilities.

**Constraints and Limitations**

- The plain-text token cannot be retrieved after creation.
- Tokens should be transmitted over HTTPS.

### 6. Sanctum Token Abilities

#### Definitions

**Core Definition**

Token abilities (also called "scopes") are strings that define what actions a token is permitted to perform. They enable fine-grained access control over API resources.

**Technical Definition**

Abilities are stored as a JSON array in the `abilities` column of the `personal_access_tokens` table. The `tokenCan()` and `tokenCant()` methods on the authenticated user check if the current token has a given ability. The `abilities` middleware (`Laravel\Sanctum\Http\Middleware\CheckAbilities` and `CheckForAnyAbility`) can enforce abilities at the route level.

**Beginner-Friendly Explanation**

Abilities let you say "this token can read data but not delete anything." They are like permissions attached to a specific key.

#### Purposes

- To restrict what actions a token can perform.
- To implement least-privilege access for API clients.
- To differentiate between tokens with different permission levels.
- To enforce authorization at the route level via middleware.

#### Syntax Rules and Structure

**Complete General Syntax**

```php
// Issuing with abilities
$token = $user->createToken('token', ['server:read', 'server:update'])->plainTextToken;

// Checking abilities
if ($user->tokenCan('server:update')) {
    // Allowed
}

if ($user->tokenCant('server:delete')) {
    // Denied
}
```

```php
// Route middleware
Route::middleware(['auth:sanctum', 'abilities:server:update'])->put('/server', ...);
Route::middleware(['auth:sanctum', 'ability:server:update,server:delete'])->delete('/server', ...);
```

**Component Breakdown**

| Method | Description |
|--------|-------------|
| `tokenCan($ability)` | Checks if the token has the ability. |
| `tokenCant($ability)` | Checks if the token lacks the ability. |
| `abilities:...` | Middleware requiring all listed abilities. |
| `ability:...` | Middleware requiring any listed ability. |

**Syntax Rules**

- Abilities are passed as the second argument to `createToken()`.
- `['*']` grants all abilities.
- `tokenCan()` always returns `true` for first-party SPA requests.
- Middleware aliases must be registered in `bootstrap/app.php` (Laravel 11+).

**Constraints and Limitations**

- Abilities are stored as a JSON array; very large arrays may impact performance.
- `tokenCan()` returns `false` if no token is present (e.g., session authentication).

#### Multiple Annotated Complete Step by Step Code Examples and Expected Outputs

**Example 1: Issuing a Token with Abilities**

```php

```

**Expected Output**

```
// Token granted post:read and post:create abilities
```

**Why This Output Occurs**

The abilities array is stored with the token and checked on each request.

```php
{

```

```

// If token lacks server:update → 403 {"error":"Unauthorized"}
```

**Why This Output Occurs**

`tokenCan()` checks the abilities array of the current access token.

---

**Example 3: Enforcing Abilities via Middleware**

**Route**

```php

```

**Expected Output**

```

// Token without post:create → 403 Forbidden
```

**Why This Output Occurs**

The `abilities` middleware checks if the token has all the specified abilities.

#### Real-World Cases with Explanation

**Case 1: Read-Only API Keys**

A monitoring integration needs to read data but should never modify it. A token with only the `data:read` ability is created, ensuring the integration cannot accidentally delete or update data.

**Explanation**: Token abilities enforce least-privilege access, reducing the blast radius of a compromised token.

### 7. Sanctum Token Revocation

#### Definitions

**Core Definition**

Token revocation is the process of invalidating an API token so that it can no longer be used for authentication. Revoked tokens are deleted from the database.

**Technical Definition**

Tokens are revoked by deleting their records from the `personal_access_tokens` table using the `tokens` relationship provided by the `HasApiTokens` trait. The `currentAccessToken()->delete()` method revokes the token used in the current request. The `tokens()->delete()` method revokes all of a user's tokens.

**Beginner-Friendly Explanation**

Revoking a token is like cancelling a key card. Once revoked, the token no longer works. This is useful if a device is lost or a token is compromised.

#### Purposes

- To invalidate compromised or lost tokens.
- To allow users to manage their active sessions/devices.
- To enforce token lifecycle management (e.g., logout).
- To support security incident response.

#### Syntax Rules and Structure

**Complete General Syntax**

```php
// Revoke all tokens
$user->tokens()->delete();

// Revoke current token
$request->user()->currentAccessToken()->delete();

// Revoke a specific token
$user->tokens()->where('id', $tokenId)->delete();
```

**Component Breakdown**

| Method | Description |
|--------|-------------|
| `tokens()->delete()` | Revokes all tokens for the user. |
| `currentAccessToken()->delete()` | Revokes the token used in the current request. |
| `tokens()->where('id', $id)->delete()` | Revokes a specific token. |

**Syntax Rules**

- The `tokens` relationship is provided by the `HasApiTokens` trait.
- `currentAccessToken()` returns the token used for the current request.

**Constraints and Limitations**

- Revoking all tokens logs the user out of all devices.

### 8. Passport

#### Definitions

**Core Definition**

Laravel Passport is a full OAuth2 server implementation for Laravel applications. It provides a complete OAuth2 authorization server with support for multiple grant types, access tokens, refresh tokens, and scopes.

**Technical Definition**

Passport is built on the League OAuth2 server (`league/oauth2-server`). It provides routes for OAuth2 token issuance, middleware for token validation, and Eloquent models for OAuth2 clients, access tokens, and refresh tokens. Passport supports the authorization code grant (with PKCE), password grant, client credentials grant, device authorization grant, and personal access tokens.

**Beginner-Friendly Explanation**

Passport is the full-featured OAuth2 solution. Use it when you need to let other applications access your API on behalf of users — like how "Log in with Google" works. If you just need to authenticate your own mobile app, Sanctum is simpler.

#### Purposes

- To provide full OAuth2 server capabilities.
- To support third-party integrations and API ecosystems.
- To issue access tokens and refresh tokens with scopes.
- To enable authorization code flow with PKCE.
- To support machine-to-machine authentication.

#### Syntax Rules and Structure

**Complete General Syntax**

```bash
# Installation
php artisan install:api --passport
```

```php
// User model
use Laravel\Passport\HasApiTokens;
use Laravel\Passport\Contracts\OAuthenticatable;

class User extends Authenticatable implements OAuthenticatable
{
    use HasApiTokens;
}
```

```php
// config/auth.php
'guards' => [
    'api' => [
        'driver' => 'passport',
        'provider' => 'users',
    ],
],
```

**Component Breakdown**

| Component | Description |
|-----------|-------------|
| `install:api --passport` | Installs Passport and runs migrations. |
| `HasApiTokens` | Trait for the `User` model. |
| `OAuthenticatable` | Interface for the `User` model. |
| `passport` driver | API guard driver. |

**Syntax Rules**

- Passport requires the `HasApiTokens` trait and `OAuthenticatable` interface.
- The `api` guard must use the `passport` driver.
- `passport:keys` generates encryption keys.
- Passport routes are registered automatically at `/oauth/*`.

**Constraints and Limitations**

- Passport is more complex to set up than Sanctum.
- Not recommended for simple SPAs or mobile apps (use Sanctum instead).
- Requires encryption keys for token signing.

### 10. Passport Configuration

#### Definitions

**Core Definition**

Passport configuration involves setting token lifetimes, defining scopes, configuring the `api` guard, and managing OAuth2 clients.

**Technical Definition**

Passport configuration is performed in `AuthServiceProvider` (Laravel 10 and earlier) or `AppServiceProvider` (Laravel 11+) using `Passport::tokensExpireIn()`, `Passport::refreshTokensExpireIn()`, `Passport::tokensCan()` (scopes), and `Passport::defaultScopes()`. The `api` guard is configured in `config/auth.php` with the `passport` driver.

**Beginner-Friendly Explanation**

Configuring Passport means telling Laravel how long tokens should last, what permissions (scopes) are available, and which guard to use.

#### Purposes

- To configure token and refresh token lifetimes.
- To define OAuth2 scopes for fine-grained access control.
- To set default scopes for tokens.
- To configure the API guard and client management.

#### Syntax Rules and Structure

**Complete General Syntax**

```php
// AppServiceProvider boot() method
use Laravel\Passport\Passport;

Passport::tokensExpireIn(now()->addDays(15));
Passport::refreshTokensExpireIn(now()->addDays(30));
Passport::personalAccessTokensExpireIn(now()->addMonths(6));

Passport::tokensCan([
    'check-status' => 'Check order status',
    'place-orders' => 'Place orders',
]);
```

**Component Breakdown**

| Method | Description |
|--------|-------------|
| `tokensExpireIn()` | Access token lifetime. |
| `refreshTokensExpireIn()` | Refresh token lifetime. |
| `tokensCan()` | Defines available scopes. |
| `defaultScopes()` | Default scopes for tokens. |

**Syntax Rules**

- Configuration is done in a service provider's `boot()` method.
- Token lifetimes should be balanced between security and convenience.
- Scopes must be defined before they can be assigned to tokens.

**Constraints and Limitations**

- Passport's default access token lifetime is one year.
- Refresh token lifetime should be longer than access token lifetime.

#### Multiple Annotated Complete Step by Step Code Examples and Expected Outputs

### 11. Passport OAuth2 Flows

#### Definitions

**Core Definition**

OAuth2 flows (or grant types) are the different mechanisms by which an OAuth2 client can obtain an access token. Passport supports authorization code, password, client credentials, device authorization, and personal access token grants.

**Technical Definition**

Each grant type is designed for a specific use case: **Authorization Code** (with PKCE) for server-side and SPA clients; **Password** for first-party mobile apps; **Client Credentials** for machine-to-machine authentication; **Device Authorization** for devices with limited input capabilities; **Personal Access Tokens** for user-generated tokens. The `/oauth/token` endpoint is used for token issuance.

**Beginner-Friendly Explanation**

OAuth2 flows are different ways to get a token depending on who is asking. A website uses one flow, a mobile app uses another, and a server talking to another server uses a third.

#### Purposes

- To provide the appropriate OAuth2 flow for each client type.
- To enable secure delegation of API access.
- To support third-party integrations with user consent.
- To handle machine-to-machine authentication.

#### Syntax Rules and Structure

**Complete General Syntax**

```bash
# Creating a password grant client
php artisan passport:client --password

# Creating a client credentials client
php artisan passport:client --client

# Creating an authorization code client
php artisan passport:client
```

```php
// Requesting a password grant token
$response = Http::asForm()->post('http://passport-app.test/oauth/token', [
    'grant_type' => 'password',
    'client_id' => 'client-id',
    'client_secret' => 'client-secret',
    'username' => 'taylor@laravel.com',
    'password' => 'my-password',
    'scope' => '',
]);
```

**Component Breakdown**

| Grant Type | Use Case |
|------------|----------|
| Authorization Code | Web apps, SPAs (with PKCE) |
| Password | First-party mobile apps |
| Client Credentials | Machine-to-machine |
| Device Authorization | Smart TVs, IoT devices |
| Personal Access Tokens | User-generated tokens |

**Syntax Rules**

- Each grant type requires a corresponding client.
- The `/oauth/token` endpoint accepts grant-type-specific parameters.
- Scopes are requested in the `scope` parameter.
- Refresh tokens are issued with authorization code and password grants.

**Constraints and Limitations**

- The password grant is not recommended for third-party clients.
- Authorization code flow requires a redirect URI.
- Client credentials grant has no user context.

### 12. Token Best Practices

#### Definitions

**Core Definition**

Token best practices are the recommended guidelines for securely issuing, storing, transmitting, and revoking API tokens.

**Technical Definition**

Best practices encompass token hashing, HTTPS enforcement, token expiration, ability scoping, rate limiting, secure storage, revocation strategies, and choosing the right authentication mechanism (Sanctum vs. Passport).

**Beginner-Friendly Explanation**

Best practices are the security rules that keep your tokens safe from attackers.

#### Key Best Practices

1. **Always Use HTTPS**: Tokens must be transmitted over TLS/SSL to prevent interception.

2. **Choose the Right Tool**: Use Sanctum for SPAs, mobile apps, and first-party APIs. Use Passport only when OAuth2 is required for third-party integrations.

3. **Set Token Expiration**: Configure `expiration` in `config/sanctum.php` or `Passport::tokensExpireIn()`. Tokens should not live forever.

4. **Use Token Abilities**: Assign only the abilities a token needs. Avoid `['*']` unless absolutely necessary.

5. **Hash Tokens at Rest**: Sanctum already hashes tokens with SHA-256. Never store plain-text tokens.

6. **Never Log Tokens**: Exclude tokens from logs and error reports.

7. **Revoke Tokens on Logout**: Implement logout endpoints that revoke the current token.

8. **Rate Limit Authentication Endpoints**: Apply `throttle` middleware to login and token issuance routes.

9. **Use Separate Tokens per Device**: Each device or integration should have its own token for granular revocation.

10. **Rotate Encryption Keys**: For Passport, periodically rotate the RSA key pair and invalidate old tokens.

11. **Monitor Token Usage**: Track token usage and revoke tokens that appear compromised.

12. **Test Token Authentication**: Write tests for token issuance, ability checks, and revocation.

#### Multiple Annotated Complete Step by Step Code Examples and Expected Outputs

**Example 1: Secure Token Issuance with Rate Limiting**

```php
Route::middleware('throttle:5,1')->post('/login', [AuthController::class, 'login']);
```

**Expected Output**

```
// After 5 failed login attempts, the client is blocked for 1 minute
```

**Why This Output Occurs**

The `throttle:5,1` middleware limits login attempts to prevent brute-force attacks.

---

**Example 2: Token Expiration Configuration**

```php
// config/sanctum.php
'expiration' => 60 * 24 * 30, // 30 days
```

**Expected Output**

```
// Tokens expire after 30 days
```

**Why This Output Occurs**

The `expiration` value is in minutes; setting it to `43200` (30 days) ensures tokens are automatically invalidated.

---

#### Real-World Cases with Explanation

**Case 1: Financial API Security**

A financial API uses short-lived access tokens (15 minutes), refresh tokens (30 days), token abilities, HTTPS, and rate limiting to protect sensitive data.

**Explanation**: High-security APIs require multiple layers of token protection.
