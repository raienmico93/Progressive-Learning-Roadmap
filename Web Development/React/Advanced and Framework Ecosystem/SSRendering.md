# Server-Side Rendering (SSR) & Streaming: A Comprehensive Programming Cheat Sheet

---

## Topic Overview

### Definitions

**Core Definition:** Server-Side Rendering (SSR) is the process of rendering React components to HTML on the server and sending that HTML to the browser, where React then "hydrates" it by attaching event handlers and taking over the DOM. Streaming SSR extends this by sending HTML in progressive chunks over a single HTTP connection, allowing users to see and interact with parts of the page before the entire render completes.

**Technical Definition:** SSR in React involves two coordinated phases. On the server, `renderToPipeableStream` (Node.js) or `renderToReadableStream` (Web Streams) renders the React tree to an HTML stream. The server sends the document shell immediately and streams Suspense boundary content as it resolves. On the client, `hydrateRoot` attaches React to the server-rendered HTML, reconciling the server's output with the client's virtual DOM. React 18+ introduced concurrent rendering features — streaming SSR and selective hydration — that are deeply integrated with `<Suspense>`. Streaming sends HTML in progressive chunks with inline `<script>` tags that swap fallback content for real content as it arrives. Selective hydration allows React to prioritize hydrating the parts of the page the user interacts with first, even before the full JavaScript bundle has loaded.

**Beginner-Friendly Explanation:** Normally, when you visit a React app, the browser downloads a bunch of JavaScript, runs it, and then finally shows you something. That's slow. With SSR, the server builds the HTML first and sends it to the browser, so you see content almost immediately. Then React "wakes up" that HTML by attaching all the click handlers and interactive behaviour — that's called hydration. Streaming SSR takes it further: instead of waiting for the entire page to be ready, the server sends it in pieces, so you see the header and main content while the slower parts (like reviews or recommendations) are still being prepared. Selective hydration means if you click on a section before it's ready, React prioritizes making that section interactive first.

### Key Characteristics

- **Two-Phase Rendering:** SSR involves a server render phase (producing HTML) and a client hydration phase (attaching interactivity). The two outputs must match; mismatches are bugs.
- **Progressive Delivery:** Streaming SSR sends the document shell first, then streams Suspense boundary content as it resolves. The browser can paint and parse progressively.
- **Interaction-Aware Hydration:** Selective hydration prioritizes hydrating components the user is interacting with, rather than hydrating top-down in order.
- **Suspense as the Boundary:** `<Suspense>` boundaries define both streaming chunks on the server and independent hydration units on the client.
- **Performance Trade-offs:** SSR improves First Contentful Paint (FCP) and Interaction to Next Paint (INP) but can increase Time to First Byte (TTFB) because the server must generate HTML before responding.

### Prerequisites

- Solid understanding of React components, Hooks, and JSX.
- Familiarity with Node.js streams and HTTP fundamentals.
- Basic understanding of client-side rendering (CSR) and the virtual DOM.
- Knowledge of React Suspense and lazy loading.
- Experience with a build tool that supports SSR (Vite, Next.js, or a custom Express setup).

### Related Programming Areas

- **Hydration:** The client-side process of attaching React to server-rendered HTML.
- **React Server Components (RSC):** Components that run only on the server and ship no JavaScript.
- **Code-Splitting:** Loading JavaScript chunks on demand to reduce initial bundle size.
- **Web Performance:** Core Web Vitals (TTFB, FCP, INP, TBT) and perceived performance.
- **Edge Rendering:** Running SSR at the edge for lower latency.

## Core Concept 1: Hydration Fundamentals

### Definitions

**Core Definition:** Hydration is the client-side process where React attaches event handlers and internal state to server-rendered HTML, "bringing it to life" without re-creating the DOM from scratch.

**Technical Definition:** `hydrateRoot(domNode, reactNode)` attaches React to existing HTML that was generated by `react-dom/server`. During hydration, React walks the server-rendered DOM and the client's virtual DOM in parallel, reusing existing DOM nodes and attaching event listeners. React expects the server-rendered HTML to be **identical** to what the client would render on the first pass. If the two outputs differ, React raises a **hydration mismatch error**. In development, React warns with the mismatching content and a component stack; in production, it may silently fall back to client rendering for the affected subtree, discarding the server HTML and re-rendering on the client. React 19 consolidated hydration errors and improved the developer experience, but the core principle remains: mismatches should be treated as bugs and fixed, not suppressed. Common causes include browser-only APIs accessed during render (`window`, `localStorage`), non-deterministic values (`Date.now()`, `Math.random()`), locale-dependent formatting, invalid HTML nesting, and browser extensions that mutate the DOM before hydration.

**Beginner-Friendly Explanation:** Hydration is like putting batteries into a toy that's already assembled. The server sends you the fully built toy (HTML), and React just needs to add the batteries (event handlers) to make it work. But React is very picky: the toy it builds in the browser must look exactly like the one the server sent. If there's even a tiny difference — like a timestamp that says 10:00 on the server and 10:01 in the browser — React gets confused and throws a hydration error. The fix is to make sure the server and the browser produce the same output, or to delay rendering browser-specific content until after hydration.

### Purposes

- To attach event handlers and React state to server-rendered HTML without re-creating the DOM.
- To preserve the fast initial paint provided by SSR while enabling client-side interactivity.
- To reuse the server's rendering work, avoiding a full client-side re-render on initial load.
- To enable selective and progressive hydration strategies that prioritize critical interactivity.
- To detect and surface mismatches between server and client rendering as actionable bugs.
- To support the two-pass rendering pattern for genuinely client-dependent content.

### Syntax Rules and Structure

**General Syntax for `hydrateRoot`:**

```tsx
import { hydrateRoot } from 'react-dom/client';

const domNode = document.getElementById('root');
hydrateRoot(domNode, <App />);
```

**Component Breakdown:**
- `domNode`: The DOM element that was rendered as the root on the server (e.g., `<div id="root">`).
- `<App />`: The React node used to render the existing HTML. This must be the **same** component tree that was rendered on the server.
- `hydrateRoot` returns a root object with `render` and `unmount` methods.

**General Syntax for Server-Side Rendering with `renderToPipeableStream`:**

```tsx
import { renderToPipeableStream } from 'react-dom/server';
import express from 'express';

const app = express();

app.get('/', (req, res) => {
  const { pipe, abort } = renderToPipeableStream(<App />, {
    bootstrapScripts: ['/client.js'],
    onShellReady() {
      res.setHeader('Content-Type', 'text/html');
      pipe(res);
    },
    onShellError(error) {
      res.statusCode = 500;
      res.send('<h1>Server error</h1>');
    },
    onError(error) {
      console.error(error);
    },
  });

  setTimeout(abort, 10000);
});
```

**Component Breakdown:**
- `renderToPipeableStream(<App />, options)`: Renders the React tree to a Node.js stream.
- `bootstrapScripts`: The client-side JavaScript bundles to load.
- `onShellReady`: Called when the initial HTML shell (outside Suspense) is ready. The stream is piped to the response.
- `onShellError`: Called if the shell itself fails to render.
- `onError`: Called for any error during rendering.
- `pipe(res)`: Streams the HTML to the client.
- `abort()`: Aborts the stream if it takes too long.

**Common Hydration Mismatch Causes and Fixes:**

| Cause | Wrong | Correct |
|-------|-------|---------|
| **Date/Time** | `<span>{new Date().toLocaleTimeString()}</span>` | Two-pass: `useState(null)` + `useEffect` to set time after mount |
| **Random values** | `Math.random()` during render | Use `useId()` or a server-provided stable seed |
| **Locale formatting** | `amount.toLocaleString(undefined, ...)` | Pass explicit `locale` prop from server |
| **Browser APIs** | `window.innerWidth` during render | Read in `useEffect` or use a client-only component |
| **Invalid HTML nesting** | `<p><p>Nested</p></p>` | Use `<div>` for block-level nesting |
| **Auth state** | Server renders logged-out UI, client renders logged-in | Read cookies on server and pass as props, or use `suppressHydrationWarning` |

**Syntax Rules:**
- The component tree passed to `hydrateRoot` must be the **same** as the one rendered on the server.
- Never access browser-only APIs (`window`, `document`, `localStorage`) during render. Use `useEffect` or a client-only wrapper.
- Never use non-deterministic values (`Date.now()`, `Math.random()`) during render.
- Pass explicit locale and timezone information from the server to the client.
- Validate HTML nesting to avoid browser auto-correction.
- Use `suppressHydrationWarning` only for unavoidable mismatches (e.g., timestamps), and only on the specific element.
- In React 19, `onRecoverableError` can be used to log hydration mismatches in production.

**Constraints and Limitations:**
- Hydration mismatches in production are often silent; React may fall back to client rendering, losing SSR benefits.
- `hydrateRoot` does not support client-rendered apps with no server HTML; use `createRoot` instead.
- Hydration is CPU-intensive; a large tree can block the main thread and delay interactivity.
- `suppressHydrationWarning` only suppresses the warning for text content and attributes on the specific element; it does not fix underlying bugs.

### Annotated Code Examples

**Example 1: Two-Pass Rendering for Client-Only Content**

```tsx
import { useState, useEffect } from 'react';

function Timestamp() {
  // First pass: both server and client render "Loading..."
  const [time, setTime] = useState<string | null>(null);

  // Second pass: only on the client, after hydration
  useEffect(() => {
    setTime(new Date().toLocaleTimeString());
  }, []);

  if (!time) return <span>Loading...</span>;
  return <span>{time}</span>;
}
```

**Expected Output:** The server renders `<span>Loading...</span>`. The client hydrates with the same output. After hydration, `useEffect` fires, `setTime` updates the state, and the component re-renders with the actual time.

**Why This Output Occurs:** The first render (on both server and client) produces identical output (`Loading...`), so hydration succeeds. The `useEffect` runs only on the client after hydration, where `new Date().toLocaleTimeString()` is safe to call. This two-pass pattern is the recommended fix for any content that must differ between server and client.

**Example 2: Explicit Locale from Server**

```tsx
function Price({ amount, locale }: { amount: number; locale: string }) {
  return (
    <span>
      {amount.toLocaleString(locale, { style: 'currency', currency: 'USD' })}
    </span>
  );
}
```

**Expected Output:** The server passes the user's locale (from a cookie or header) to the component. Both server and client format the price using the same locale, producing identical output and avoiding hydration mismatches.

**Why This Output Occurs:** Without an explicit locale, the server might format `1234.56` as `$1,234.56` (en-US) while the client's browser (e.g., de-DE) formats it as `1.234,56 €`. By passing the locale from the server, both environments use the same formatting rules.

### Real-World Cases

- **E-commerce:** Rendering product prices with the user's locale to avoid currency formatting mismatches.
- **Dashboards:** Displaying timestamps and relative dates ("2 minutes ago") using two-pass rendering.
- **Authentication:** Passing server-read user session data as props to avoid logged-in vs. logged-out mismatches.
- **Content platforms:** Rendering user-generated HTML (from a CMS) with validated nesting to prevent browser auto-correction.
- **Any SSR app:** Validating that components do not access `window` or `localStorage` during render.

## Core Concept 2: Streaming SSR

### Definitions

**Core Definition:** Streaming SSR is the technique of sending HTML from the server to the browser in progressive chunks over a single HTTP connection, allowing the browser to paint content before the entire page has finished rendering.

**Technical Definition:** Streaming SSR uses `renderToPipeableStream` (Node.js) or `renderToReadableStream` (Web Streams) to render a React tree to an HTML stream. The server sends the **document shell** — everything outside Suspense boundaries — immediately in the `onShellReady` callback. Suspense boundary content is streamed as it resolves, with inline `<script>` tags that replace fallback content in the DOM with the real content. The client hydrates the streamed HTML with `hydrateRoot`. React 18+ integrates streaming with `<Suspense>`: each Suspense boundary is a streaming chunk. This is the recommended API for server-side rendering in Node.js environments with full support for Suspense, streaming, and selective hydration.

**Beginner-Friendly Explanation:** Imagine you're ordering food at a restaurant. With traditional SSR, the kitchen makes everything before the waiter brings you anything. With streaming SSR, the waiter brings you the bread and drinks immediately, then brings the appetizer when it's ready, then the main course, and so on. You start eating right away instead of staring at an empty table. In React, the "bread and drinks" are the page shell (header, layout), and the "main course" is the slow-loading content (reviews, recommendations) that streams in later.

### Purposes

- To reduce Time to First Byte (TTFB) by sending the document shell immediately.
- To improve First Contentful Paint (FCP) by allowing the browser to paint content before the full render completes.
- To improve perceived performance by showing users content progressively rather than all at once.
- To allow slow-loading sections (data-heavy widgets, third-party content) to stream in without blocking the rest of the page.
- To integrate with Suspense boundaries as natural streaming chunks.
- To enable selective hydration on the client, where each streamed chunk can hydrate independently.

### Syntax Rules and Structure

**General Syntax for Streaming SSR (Node.js/Express):**

```tsx
import express from 'express';
import { renderToPipeableStream } from 'react-dom/server';
import App from './App';

const app = express();

app.get('/', (req, res) => {
  const { pipe, abort } = renderToPipeableStream(<App />, {
    bootstrapScripts: ['/client.js'],
    onShellReady() {
      res.setHeader('Content-Type', 'text/html');
      res.setHeader('Transfer-Encoding', 'chunked');
      pipe(res);
    },
    onShellError(error) {
      res.statusCode = 500;
      res.send('<h1>Server error</h1>');
    },
    onError(error) {
      console.error(error);
    },
  });

  setTimeout(abort, 10000);
});

app.listen(3000);
```

**Component Breakdown:**
- `renderToPipeableStream(<App />, options)`: Creates a streaming render.
- `onShellReady`: Fires when the shell (content outside Suspense) is ready. This is where you pipe the stream to the response.
- `onShellError`: Fires if the shell itself fails.
- `onError`: Fires for any rendering error.
- `abort()`: Aborts the render after a timeout.
- The stream is piped to `res`, which is a Node.js `Writable` stream.

**General Syntax for Streaming with Suspense Boundaries:**

```tsx
import { Suspense } from 'react';

function App() {
  return (
    <html>
      <body>
        <Header />
        <Suspense fallback={<p>Loading products...</p>}>
          <ProductList />
        </Suspense>
        <Suspense fallback={<p>Loading reviews...</p>}>
          <Reviews />
        </Suspense>
        <Footer />
      </body>
    </html>
  );
}
```

**Component Breakdown:**
- `<Header />` and `<Footer />` are part of the shell and stream immediately.
- `<ProductList />` is wrapped in Suspense. If it suspends (e.g., waiting for data), the fallback streams first, then the real content streams when ready.
- `<Reviews />` is a separate Suspense boundary, streaming independently.
- Each Suspense boundary is a separate chunk in the stream.

**Syntax Rules:**
- Use `renderToPipeableStream` for Node.js environments. For edge/Web Streams, use `renderToReadableStream`.
- The `onShellReady` callback is the correct place to pipe the response.
- Wrap independently loading sections in `<Suspense>` boundaries to create streaming chunks.
- Use `onAllReady` if you want to wait for all Suspense content before streaming (less optimal for perceived performance).
- Set `Content-Type: text/html` and `Transfer-Encoding: chunked` headers.
- Use `abort()` with a timeout to prevent hangs.

**Constraints and Limitations:**
- Streaming requires a server runtime that supports streams (Node.js 16+, Deno, Bun, edge runtimes).
- `renderToString` is synchronous and non-streaming; it should not be used for new SSR implementations.
- Streaming SSR cannot be used with `ReactDOM.render`; it requires `hydrateRoot`.
- If the client bundle fails to load, the streamed HTML remains visible but not interactive.
- Errors in Suspense boundaries are handled by the nearest Error Boundary on the server; if none exists, the stream may be aborted.

### Annotated Code Examples

**Example 1: Basic Streaming SSR with Express**

```tsx
// server.tsx
import express from 'express';
import { renderToPipeableStream } from 'react-dom/server';
import React, { Suspense } from 'react';

function App() {
  return (
    <html>
      <head><title>Streaming SSR</title></head>
      <body>
        <h1>Streaming SSR Demo</h1>
        <p>This content streams immediately.</p>
        <Suspense fallback={<p>Loading slow content...</p>}>
          <SlowComponent />
        </Suspense>
        <script src="/client.js" defer></script>
      </body>
    </html>
  );
}

function SlowComponent() {
  // Simulate a slow data fetch
  return new Promise((resolve) => {
    setTimeout(() => resolve(<p>Slow content loaded!</p>), 2000);
  });
}

const server = express();

server.get('/', (req, res) => {
  const { pipe, abort } = renderToPipeableStream(<App />, {
    onShellReady() {
      res.setHeader('Content-Type', 'text/html');
      pipe(res);
    },
    onShellError(error) {
      res.statusCode = 500;
      res.send('<h1>Something went wrong</h1>');
    },
    onError(error) {
      console.error(error);
    },
  });

  setTimeout(abort, 10000);
});

server.listen(3000, () => console.log('Server on http://localhost:3000'));
```

**Expected Output:** The browser receives the shell HTML (the `<h1>`, the immediate `<p>`, and the Suspense fallback "Loading slow content...") almost immediately. After 2 seconds, the slow content ("Slow content loaded!") streams in and replaces the fallback.

**Why This Output Occurs:** `renderToPipeableStream` renders the shell first and calls `onShellReady`. The `pipe(res)` call streams the shell HTML to the browser. The `<SlowComponent />` suspends (it returns a Promise), so React streams the fallback. When the Promise resolves, React streams the real content along with an inline `<script>` tag that replaces the fallback in the DOM.

### Real-World Cases

- **E-commerce product pages:** Streaming the product header and images immediately while reviews and recommendations stream in later.
- **News sites:** Streaming the article content while comments and related articles load progressively.
- **Dashboards:** Streaming the dashboard shell while individual widgets stream in as their data resolves.
- **SaaS applications:** Streaming the page layout while analytics charts and data tables stream in independently.
- **Content platforms:** Streaming the article body while the author bio and social sharing buttons load.

## Core Concept 3: Selective Hydration

### Definitions

**Core Definition:** Selective hydration is React's ability to prioritize hydrating parts of the page based on user interaction, making the components the user is trying to use interactive first, even before the full JavaScript bundle has loaded.

**Technical Definition:** Selective hydration, introduced in React 18, leverages Suspense boundaries as independent hydration units. Instead of hydrating the entire page top-down in a single pass, React can hydrate each Suspense boundary independently. When a user interacts with a component that has not yet hydrated (e.g., clicks a button in the reviews section), React **prioritizes hydrating that component immediately**, even if other parts of the page are still loading. React records the interaction and replays it after hydration, ensuring the user's click is not lost. This is possible because concurrent rendering allows React to interrupt, pause, and resume hydration work. Selective hydration works with `hydrateRoot` and Suspense boundaries; components not wrapped in Suspense are hydrated immediately as part of the shell.

**Beginner-Friendly Explanation:** Normally, when a page hydrates, React starts at the top and works its way down, making everything interactive in order. If the user clicks on a button near the bottom of the page before React gets there, nothing happens — the click is lost. Selective hydration fixes this: if the user clicks on a section that hasn't hydrated yet, React immediately jumps to that section and hydrates it first. It's like a smart waiter who notices you're trying to get their attention and comes to your table first, even if other tables were seated before you.

### Purposes

- To make critical interactive components responsive immediately, even before the full bundle loads.
- To prevent lost user interactions during hydration (clicks on unhydrated components).
- To improve Interaction to Next Paint (INP) by prioritizing hydration of components the user is engaging with.
- To allow independent hydration of Suspense boundaries, so a slow section does not block a fast one.
- To reduce the perceived time to interactivity for above-the-fold content.
- To work seamlessly with streaming SSR, where each streamed chunk can hydrate independently.

### Syntax Rules and Structure

**General Syntax for Selective Hydration with Suspense:**

```tsx
import { Suspense } from 'react';
import { hydrateRoot } from 'react-dom/client';

function App() {
  return (
    <div>
      <Header /> {/* Hydrates immediately (not in Suspense) */}
      <Suspense fallback={<CartSkeleton />}>
        <ShoppingCart /> {/* Hydrates when code loads */}
      </Suspense>
      <Suspense fallback={<ProductListSkeleton />}>
        <ProductList /> {/* Hydrates independently */}
      </Suspense>
      <Suspense fallback={<FooterSkeleton />}>
        <Footer /> {/* Low priority */}
      </Suspense>
    </div>
  );
}

hydrateRoot(document.getElementById('root'), <App />);
```

**Component Breakdown:**
- `<Header />` is not wrapped in Suspense, so it hydrates as part of the initial shell.
- Each `<Suspense>` boundary hydrates independently when its JavaScript code loads.
- If the user clicks on `<ProductList />` before it hydrates, React prioritizes hydrating that boundary first.
- The fallback is shown until the boundary's code loads and hydration completes.

**General Syntax for Selective Hydration with Error Boundaries:**

```tsx
import { Suspense } from 'react';
import { ErrorBoundary } from 'react-error-boundary';

function ProductPage({ productId }) {
  return (
    <main>
      <ProductHeader productId={productId} />
      <Suspense fallback={<DetailsSkeleton />}>
        <ErrorBoundary fallback={<div>Details unavailable</div>}>
          <ProductDetails productId={productId} />
        </ErrorBoundary>
      </Suspense>
      <Suspense fallback={<ReviewsSkeleton />}>
        <ErrorBoundary fallback={<div>Reviews unavailable</div>}>
          <ProductReviews productId={productId} />
        </ErrorBoundary>
      </Suspense>
    </main>
  );
}
```

**Component Breakdown:**
- Each Suspense boundary has its own Error Boundary, so a failure in one section does not affect others.
- Hydration of each section is independent.
- If the user interacts with a section, React prioritizes hydrating it.

**Syntax Rules:**
- Use `<Suspense>` boundaries to define hydration boundaries.
- Components not wrapped in Suspense hydrate as part of the initial shell.
- Wrap independent sections in their own Suspense boundaries for maximum selectivity.
- Use Error Boundaries inside Suspense boundaries to contain failures.
- Selective hydration requires `hydrateRoot` (not `createRoot`).
- Components that use `React.lazy` or Suspense-enabled data fetching will suspend and benefit from selective hydration.

**Constraints and Limitations:**
- Selective hydration is automatic; no additional configuration is required beyond using `hydrateRoot` and Suspense.
- The shell (content outside Suspense) always hydrates first.
- If a component is not wrapped in Suspense, it cannot be selectively hydrated.
- Selective hydration works best with code-splitting (e.g., `React.lazy`), so each boundary's code loads independently.
- Interactions on unhydrated components are recorded and replayed, but this may cause a brief delay if the component's code takes long to load.

### Annotated Code Examples

**Example 1: E-Commerce Product Page with Selective Hydration**

```tsx
import { Suspense, lazy } from 'react';
import { hydrateRoot } from 'react-dom/client';
import { ErrorBoundary } from 'react-error-boundary';

const Reviews = lazy(() => import('./Reviews'));
const RecommendedProducts = lazy(() => import('./RecommendedProducts'));
const Footer = lazy(() => import('./Footer'));

function ProductPage({ productId }) {
  return (
    <div>
      {/* Critical above-the-fold content hydrates immediately */}
      <ProductHeader productId={productId} />
      <ProductImages productId={productId} />
      <AddToCartButton productId={productId} />

      {/* Medium priority — user might scroll to quickly */}
      <Suspense fallback={<div className="h-32 animate-pulse bg-gray-100" />}>
        <ErrorBoundary fallback={<div>Product details unavailable</div>}>
          <ProductDetails productId={productId} />
        </ErrorBoundary>
      </Suspense>

      {/* Lower priority — typically below the fold */}
      <Suspense fallback={<div className="h-64 animate-pulse bg-gray-50" />}>
        <ErrorBoundary fallback={<div>Reviews temporarily unavailable</div>}>
          <Reviews productId={productId} />
        </ErrorBoundary>
      </Suspense>

      <Suspense fallback={<div className="h-48 animate-pulse bg-gray-50" />}>
        <ErrorBoundary fallback={<div>Recommendations unavailable</div>}>
          <RecommendedProducts categoryId={productId} />
        </ErrorBoundary>
      </Suspense>

      <Suspense fallback={<div className="h-24 animate-pulse bg-gray-100" />}>
        <ErrorBoundary fallback={<div>Footer unavailable</div>}>
          <Footer />
        </ErrorBoundary>
      </Suspense>
    </div>
  );
}

hydrateRoot(document.getElementById('root'), <ProductPage productId="123" />);
```

**Expected Output:** The header, images, and add-to-cart button hydrate immediately. The details, reviews, recommendations, and footer each hydrate independently as their code loads. If the user clicks on a review before it has hydrated, React prioritizes hydrating the reviews section first.

**Why This Output Occurs:** Each Suspense boundary is an independent hydration unit. The header and add-to-cart button are outside Suspense, so they hydrate as part of the shell. The lazy-loaded sections hydrate when their code chunks load. If the user interacts with a section that hasn't hydrated, React records the interaction and prioritizes that boundary's hydration.

### Real-World Cases

- **E-commerce:** Prioritizing hydration of the "Add to Cart" button and product details when the user interacts with them.
- **SaaS dashboards:** Prioritizing hydration of the chart or table the user clicks on.
- **Social media:** Prioritizing hydration of the post or comment the user interacts with in a feed.
- **News sites:** Prioritizing hydration of the comment section when the user clicks to expand it.
- **Documentation sites:** Prioritizing hydration of the search box when the user focuses it.

## Core Concept 4: Rendering Trade-offs

### Definitions

**Core Definition:** Rendering trade-offs are the performance balances between Time to First Byte (TTFB), First Contentful Paint (FCP), and Interaction to Next Paint (INP) that determine the perceived speed and responsiveness of a web application.

**Technical Definition:** Each rendering strategy optimises for different performance metrics. **Time to First Byte (TTFB)** measures the time from navigation to the first byte of the response. **First Contentful Paint (FCP)** measures when the first content (text, image) becomes visible. **Interaction to Next Paint (INP)** measures the responsiveness of the page to user input throughout its lifecycle. **Server-Side Rendering (SSR)** produces fast FCP (HTML arrives complete) but can increase TTFB (server compute time delays the response). **Streaming SSR** improves TTFB (shell sends immediately) and FCP (content paints progressively), while reducing Total Blocking Time (TBT) and INP by limiting client-side JavaScript execution. **Client-Side Rendering (CSR)** has fast TTFB (static shell) but slow FCP (requires JavaScript to render content) and poor INP (main thread is blocked during initial render). **Static Site Generation (SSG)** has fast TTFB and FCP but requires rebuilds for content changes. The optimal strategy depends on the application: content-heavy sites benefit from SSR/SSG, while interactive applications benefit from streaming SSR with selective hydration.

**Beginner-Friendly Explanation:** When you visit a website, three things matter: how fast the server responds (TTFB), how fast you see something on screen (FCP), and how fast the page responds when you click or type (INP). Different rendering strategies are good at different things. SSR shows you content fast but the server takes longer to respond. Streaming SSR is a good balance: the server responds quickly with the page shell, you see content progressively, and the page stays responsive because not all JavaScript runs at once. CSR is fast to respond but slow to show content, and the page can feel sluggish until all JavaScript loads. There's no perfect strategy — you pick the one that best fits your application's needs.

### Purposes

- To understand which rendering strategy best fits a given application's performance requirements.
- To balance the trade-off between fast server response (TTFB) and fast content display (FCP).
- To improve perceived performance by choosing strategies that show content quickly.
- To reduce Total Blocking Time (TBT) and improve INP by limiting client-side JavaScript execution.
- To make informed architecture decisions about SSR, SSG, CSR, and streaming based on product needs.
- To measure and monitor Core Web Vitals to ensure the chosen strategy meets performance goals.

### Syntax Rules and Structure

**Performance Metrics Definitions:**

| Metric | Definition | Target |
|--------|-----------|--------|
| **TTFB** | Time from navigation to the first byte of the response | < 800ms |
| **FCP** | Time from navigation to when the first content is painted | < 1.8s |
| **INP** | Responsiveness to user input (representative) | < 200ms |
| **TBT** | Total time the main thread is blocked during load | < 200ms |

**Rendering Strategy Comparison:**

| Strategy | TTFB | FCP | INP | Best For |
|----------|------|-----|-----|----------|
| **CSR** | Fast | Slow | Poor | Highly interactive apps (dashboards, editors) |
| **SSR** | Slow (server compute) | Fast | Good | Content sites, e-commerce, SEO-critical pages |
| **Streaming SSR** | Fast (shell) | Fast | Good | Content sites with independent sections |
| **SSG** | Fast (CDN) | Fast | Good | Static content, blogs, marketing pages |
| **Streaming + Selective Hydration** | Fast | Fast | Best | Large applications with critical interactivity |

**Syntax Rules:**
- Use SSR/streaming when FCP and SEO are priorities.
- Use CSR when the application is highly interactive and SEO is not critical.
- Use SSG when content changes infrequently and fast TTFB is important.
- Use streaming SSR when the page has independent sections that can load at different speeds.
- Use selective hydration when critical interactive components must be responsive before the full bundle loads.
- Measure TTFB, FCP, and INP with tools like Lighthouse, WebPageTest, and Chrome UX Report.

**Constraints and Limitations:**
- No single strategy is optimal for all metrics; trade-offs are inevitable.
- SSR increases TTFB due to server compute time; streaming mitigates this by sending the shell early.
- CSR has poor FCP and INP because the browser must download and execute JavaScript before rendering.
- Streaming SSR requires a server runtime that supports streams.
- Selective hydration requires Suspense boundaries and code-splitting to be effective.

### Annotated Code Examples

**Example 1: Measuring Performance Impact of Streaming SSR**

```tsx
// server.tsx — Streaming SSR with Suspense
import express from 'express';
import { renderToPipeableStream } from 'react-dom/server';
import { Suspense } from 'react';

const app = express();

app.get('/', (req, res) => {
  const { pipe } = renderToPipeableStream(
    <html>
      <body>
        <Header />
        <Suspense fallback={<p>Loading products...</p>}>
          <ProductList />
        </Suspense>
        <Suspense fallback={<p>Loading reviews...</p>}>
          <Reviews />
        </Suspense>
        <Footer />
      </body>
    </html>,
    {
      onShellReady() {
        res.setHeader('Content-Type', 'text/html');
        pipe(res);
      },
    }
  );
});
```

**Expected Output:** TTFB is low (shell sends immediately), FCP is fast (header and footer paint immediately), and INP is good because JavaScript execution is spread across progressive chunks rather than blocking the main thread with a single large bundle.

**Why This Output Occurs:** The shell (header, footer, and Suspense fallbacks) streams immediately, so TTFB is low and FCP is fast. The Suspense boundaries stream as their data resolves, so the browser can paint content progressively. The client-side JavaScript for each boundary loads independently, reducing the initial main-thread blocking time and improving INP.

### Real-World Cases

- **E-commerce:** Streaming SSR for product pages to show the product header and images immediately while reviews and recommendations stream in.
- **News sites:** SSG for article pages with streaming SSR for comments and related articles.
- **SaaS dashboards:** CSR for highly interactive dashboards, with streaming SSR for the initial shell.
- **Marketing sites:** SSG for fast TTFB and FCP, with selective hydration for interactive forms.
- **Large applications:** Streaming SSR with selective hydration for the best balance of TTFB, FCP, and INP.
