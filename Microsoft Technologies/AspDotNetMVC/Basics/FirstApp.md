# Your First ASP.NET Core MVC Application: A Comprehensive Cheat Sheet

> **Version Scope & Compatibility Note**
> This cheat sheet targets **ASP.NET Core MVC** using the **minimal hosting model** (default since .NET 6, including .NET 8/9/10/11). The legacy `Startup.cs` pattern is covered for historical context and migration awareness. Project creation instructions reference both **Visual Studio** and the **.NET CLI** (`dotnet new mvc`). All code examples assume **top-level statements** are enabled (the default in current templates). The default route and MVC conventions described here are stable across modern ASP.NET Core versions.

---

## Topic Overview

### Definitions

| Type | Definition |
|------|------------|
| **Core Definition** | A "first ASP.NET Core MVC application" is the **initial project** generated by the official MVC template, which provides a working web application with a home page, basic routing, and the standard folder structure for controllers, views, and models. |
| **Technical Definition** | The project is scaffolded from the `Microsoft.AspNetCore.Mvc` template, which configures the **generic host** (or minimal hosting model), registers MVC services via `AddControllersWithViews()`, enables endpoint routing with a default conventional route (`{controller=Home}/{action=Index}/{id?}`), and includes a `HomeController` with `Index`, `Privacy`, and `Error` actions alongside Razor views. The template produces a runnable application that demonstrates the **Model-View-Controller** pattern and serves as a foundation for adding features. |
| **Beginner‑Friendly Explanation** | Your first ASP.NET Core MVC app is like a **starter home** for a website. It already has the essential rooms (controllers, views, models), a front door (routing), and basic furniture (a home page). You can move in immediately—run it and see a working website—and then renovate room by room as you learn. |

### Key Characteristics

- **Runnable immediately** – The template produces a working app without any code changes.
- **Convention‑based** – Controllers live in `Controllers`, views in `Views`, and models in `Models`; the framework discovers them automatically.
- **Minimal hosting** – `Program.cs` is the single entry point; there is no `Startup.cs` in modern templates.
- **Default routing** – A conventional route maps URLs to `{controller}/{action}/{id?}` with defaults `Home`/`Index`.
- **View‑oriented** – The template includes shared layouts, a home page, and a privacy page, demonstrating Razor view rendering.
- **Cross‑platform** – The same project runs on Windows, Linux, and macOS via the .NET SDK.

### Prerequisites

- **.NET SDK** (version 6.0 or later; the tutorial in the official docs uses .NET 9/10).
- **An IDE or editor**: Visual Studio 2022+ (with the ASP.NET and web development workload) or Visual Studio Code with the C# extension.
- **Basic familiarity with C#** and the command line (for the CLI approach).
- **No prior ASP.NET experience required** – the template is designed for beginners.

### Related Programming Areas

- **Routing** – The default route is the first routing concept encountered.
- **Razor Views** – The template includes `.cshtml` files that mix HTML and C#.
- **Dependency Injection** – MVC services are registered in `Program.cs`; controllers receive dependencies via constructor injection.
- **Static Files** – The `wwwroot` folder serves CSS, JavaScript, and images.
- **Configuration** – `appsettings.json` holds application settings.

1. **Project Creation** – Scaffolding the project via Visual Studio or the .NET CLI.

5. **Controllers** – Classes that handle HTTP requests and return views.

## 2. Project Structure

### Definitions

| Type | Definition |
|------|------------|
| **Core Definition** | The project structure is the **default folder and file layout** produced by the MVC template, which organises controllers, views, models, static assets, and configuration files according to MVC conventions. |
| **Technical Definition** | The structure follows **convention‑over‑configuration**: `Controllers/` contains `*Controller` classes; `Views/` contains `.cshtml` files grouped by controller name with a `Shared/` subfolder; `Models/` contains data classes; `wwwroot/` contains static files served by `UseStaticFiles`; `appsettings.json` holds configuration; `Program.cs` is the entry point. The `.csproj` file defines the target framework and package references. The framework discovers controllers and views based on these folder locations, reducing explicit configuration. |
| **Beginner‑Friendly Explanation** | The project structure is the **floor plan of your starter home**. There’s a room for controllers (the “traffic directors”), a room for views (the “HTML templates”), a room for models (the “data blueprints”), and a public area (`wwwroot`) for things like CSS and images. Everything has its place, so you can find what you need quickly and the framework knows where to look. |

### Purposes (each begins with “To”)

- **To** provide a predictable location for each type of file, enabling automatic discovery by the framework.
- **To** separate concerns (presentation, logic, data) into distinct folders for maintainability.
- **To** keep static assets isolated in `wwwroot` so they can be served efficiently.
- **To** centralise configuration in `appsettings.json` and `Program.cs`.
- **To** offer a scalable foundation that can grow with additional folders (`Services`, `Data`, `Filters`) as the application matures.

### Syntax Rules and Structure

#### Default Folder Layout

```
MvcMovie/
├── Controllers/          # Controller classes
├── Models/               # Data and view model classes
├── Views/                # Razor views (.cshtml)
│   ├── Home/            # Views for HomeController
│   ├── Shared/          # Shared layouts and partials
│   ├── _ViewStart.cshtml
│   └── _ViewImports.cshtml
├── wwwroot/             # Static files (CSS, JS, images)
├── appsettings.json     # Configuration
├── Program.cs           # Entry point
└── MvcMovie.csproj      # Project file
```

#### Component Breakdown

| Folder/File | Purpose |
|-------------|---------|
| `Controllers/` | Contains controller classes; convention is `*Controller` suffix. |
| `Models/` | Contains data models and view models. |
| `Views/` | Contains Razor views; subfolders match controller names. |
| `Views/Shared/` | Layouts (`_Layout.cshtml`), partials, error views. |
| `wwwroot/` | Static assets served directly to clients. |
| `appsettings.json` | Application configuration (connection strings, logging). |
| `Program.cs` | Application startup and middleware configuration. |
| `_ViewStart.cshtml` | Sets the default layout for all views. |
| `_ViewImports.cshtml` | Shared `@using` directives and Tag Helper registrations. |

#### Syntax Rules

- **Controllers must be in `Controllers/`** (or discovered via assembly scanning).
- **Views must be in `Views/`** or a subfolder matching the controller name.
- **Models are conventionally in `Models/`** but can reside elsewhere; the folder name is not enforced by the framework.
- **`wwwroot` is the web root** for static files; files outside it are not served directly.

#### Constraints and Limitations

- **Razor Pages mix** – Modern templates may include a `Pages/` folder for Razor Pages; MVC and Razor Pages can coexist but use different routing mechanisms.
- **Folder names can be customised** – The framework’s conventions can be overridden, but beginners should stick to defaults.

## 3. `Program.cs`

### Definitions

| Type | Definition |
|------|------------|
| **Core Definition** | `Program.cs` is the **entry point** of an ASP.NET Core application, responsible for creating the web application builder, registering services, configuring the middleware pipeline, and starting the server. |
| **Technical Definition** | In the **minimal hosting model** (.NET 6+), `Program.cs` uses top‑level statements to call `WebApplication.CreateBuilder(args)`, which initialises a `WebApplicationBuilder`. Services are registered on `builder.Services`, and the application pipeline is configured on `builder.Build()`. Middleware is added via `app.Use...()` methods, and routing is configured with `app.MapControllerRoute()` or `app.MapDefaultControllerRoute()`. The file replaces the legacy `Startup.cs` and `Main` method combination. |
| **Beginner‑Friendly Explanation** | `Program.cs` is the **control room** of your app. It’s the first file that runs when the application starts. It says: “Set up the web server, register the services my app needs (like MVC), configure the request pipeline (routing, static files, error handling), and then start listening for requests.” |

### Purposes (each begins with “To”)

- **To** create and configure the web application host.
- **To** register all services required by MVC and the application (dependency injection).
- **To** define the order of middleware in the HTTP request pipeline.
- **To** set up routing so that incoming URLs are mapped to controllers and actions.
- **To** configure environment‑specific behaviour (e.g., developer exception page vs. production error handling).
- **To** start the web server and begin listening for requests.

### Syntax Rules and Structure

#### General Syntax (Minimal Template)

```csharp
var builder = WebApplication.CreateBuilder(args);

// Register services
builder.Services.AddControllersWithViews();

var app = builder.Build();

// Configure middleware pipeline
if (!app.Environment.IsDevelopment())
{
    app.UseExceptionHandler("/Home/Error");
    app.UseHsts();
}

app.UseHttpsRedirection();
app.UseStaticFiles();
app.UseRouting();
app.UseAuthorization();

// Configure routing
app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

app.Run();
```

**Component breakdown:**

| Component | Description |
|-----------|-------------|
| `WebApplication.CreateBuilder(args)` | Creates a builder with default configuration (appsettings, environment variables, logging). |
| `builder.Services.AddControllersWithViews()` | Registers MVC services (controllers, views, Tag Helpers, etc.). |
| `builder.Build()` | Creates the configured `WebApplication`. |
| `app.Use...()` | Adds middleware to the pipeline in order. |
| `app.MapControllerRoute(...)` | Defines the default conventional route. |
| `app.Run()` | Starts the server and blocks until shutdown. |

#### Syntax Rules

- **Order matters** – Middleware executes in the order it is added. `UseRouting` should come before `UseAuthorization` and `MapControllerRoute`.
- **Environment check** – `app.Environment.IsDevelopment()` enables developer‑friendly error pages; production uses exception handling and HSTS.
- **Top‑level statements** – The file does not require a `Main` method or a class definition.
- **No `Startup.cs`** – In .NET 6+, all configuration is in `Program.cs`; the legacy `Startup` class is optional and not generated by templates.

#### Constraints and Limitations

- **Single file can grow large** – As the app scales, `Program.cs` can become cluttered; extension methods are recommended to keep it clean.
- **Legacy compatibility** – The minimal hosting model can still call a `Startup` class if needed, but new projects should use `Program.cs` directly.

### Multiple Annotated Complete Step‑by‑Step Code Examples

#### Example 1: The Default `Program.cs` from the Template

```csharp

// Add services to the container.
builder.Services.AddControllersWithViews();

var app = builder.Build();

// Configure the HTTP request pipeline.

{
    app.UseExceptionHandler("/Home/Error");
    app.UseHsts();
}

app.UseHttpsRedirection();

app.UseRouting();
app.UseAuthorization();

    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

app.Run();
```

**Step‑by‑step explanation:**

1. The builder is created with command‑line arguments.
2. MVC services are registered.
3. In non‑development environments, a global exception handler and HSTS are enabled.
4. HTTPS redirection, static files, routing, and authorization middleware are added in the correct order.
5. The default conventional route is mapped.
6. The application starts.

**Expected Output:** The app runs and serves the home page at `/`.

**Why this output?** The default route maps `/` to `HomeController.Index`, which returns the `Index` view.

## 4. `Startup.cs` (Legacy)

### Definitions

| Type | Definition |
|------|------------|
| **Core Definition** | `Startup.cs` is the **legacy configuration class** used in ASP.NET Core 2.x–5.x (and optionally in .NET 6+) to separate service registration (`ConfigureServices`) from middleware configuration (`Configure`). |
| **Technical Definition** | The `Startup` class contains a `ConfigureServices(IServiceCollection services)` method for DI registration and a `Configure(IApplicationBuilder app, IWebHostEnvironment env)` method for pipeline configuration. It was the default pattern before .NET 6's minimal hosting model, where `Program.cs` uses `WebApplication.CreateBuilder`. Modern templates no longer generate `Startup.cs`, but the pattern is still supported for backward compatibility. |
| **Beginner‑Friendly Explanation** | `Startup.cs` was the **old control room** of an ASP.NET Core app. It had two main jobs: register services (like MVC) and set up the request pipeline (routing, error handling). Since .NET 6, these jobs moved into `Program.cs`, so you won’t see `Startup.cs` in new projects—but older tutorials and codebases still use it. |

### Purposes (each begins with “To”)

- **To** separate service configuration from middleware configuration in older ASP.NET Core versions.
- **To** provide a clear, testable startup class in applications built before .NET 6.
- **To** allow migration‑era projects to continue using the familiar pattern while adopting newer .NET versions.
- **To** serve as a reference for understanding legacy codebases and tutorials.

### Syntax Rules and Structure

#### General Syntax

```csharp
public class Startup
{
    public Startup(IConfiguration configuration)
    {
        Configuration = configuration;
    }

    public IConfiguration Configuration { get; }

    public void ConfigureServices(IServiceCollection services)
    {
        services.AddControllersWithViews();
    }

    public void Configure(IApplicationBuilder app, IWebHostEnvironment env)
    {
        if (env.IsDevelopment())
        {
            app.UseDeveloperExceptionPage();
        }
        else
        {
            app.UseExceptionHandler("/Home/Error");
            app.UseHsts();
        }

        app.UseHttpsRedirection();
        app.UseStaticFiles();
        app.UseRouting();
        app.UseAuthorization();

        app.UseEndpoints(endpoints =>
        {
            endpoints.MapControllerRoute(
                name: "default",
                pattern: "{controller=Home}/{action=Index}/{id?}");
        });
    }
}
```

#### Component Breakdown

| Method | Purpose |
|--------|---------|
| `ConfigureServices` | Registers services with the DI container. |
| `Configure` | Configures the middleware pipeline. |
| Constructor | Receives `IConfiguration` for use in services. |

#### Syntax Rules

- **`Program.cs` calls `CreateHostBuilder`** (or `CreateWebHostBuilder`) to use `Startup`.
- **`ConfigureServices`** is optional; **`Configure`** is required.
- **`UseEndpoints`** is required for endpoint routing in ASP.NET Core 3.0+; in earlier versions, `UseMvc` was used.

#### Constraints and Limitations

- **Not generated in new projects** – Since .NET 6, templates use the minimal hosting model; `Startup.cs` is absent.
- **Still supported** – Existing projects can continue using `Startup`; migration is not mandatory unless simplification is desired.
- **May be confusing for beginners** – Modern tutorials assume `Program.cs`; encountering `Startup.cs` in older resources can cause confusion.

## 5. Controllers

### Definitions

| Type | Definition |
|------|------------|
| **Core Definition** | Controllers are classes that **handle HTTP requests**, coordinate application logic, and return responses (views, JSON, redirects, etc.). |
| **Technical Definition** | A controller inherits from `Controller` (for MVC with views) and contains **action methods**—public methods that are mapped to routes. In the default template, `HomeController` provides `Index()`, `Privacy()`, and `Error()` actions. Controllers are discovered automatically from the `Controllers` folder; no registration is required. Action methods use **model binding** to populate parameters and return `IActionResult` implementations such as `View()`. |
| **Beginner‑Friendly Explanation** | Controllers are the **traffic directors** of your app. When a request comes in for `/Home/Privacy`, the `HomeController` handles it. The `Privacy` action method runs and decides what to send back—usually a view (HTML page). The template gives you a `HomeController` with a few basic actions to get started. |

### Purposes (each begins with “To”)

- **To** receive HTTP requests and route them to the appropriate application logic.
- **To** coordinate between models (data) and views (presentation).
- **To** return the correct response type (HTML view, JSON, file, redirect).
- **To** keep controllers **thin** by delegating business logic to services (as the app grows).
- **To** provide a clear entry point for each user interaction in the application.

### Syntax Rules and Structure

#### General Syntax (Template `HomeController`)

```csharp
public class HomeController : Controller
{
    public IActionResult Index()
    {
        return View();
    }

    public IActionResult Privacy()
    {
        return View();
    }

    [ResponseCache(Duration = 0, Location = ResponseCacheLocation.None, NoStore = true)]
    public IActionResult Error()
    {
        return View(new ErrorViewModel { RequestId = Activity.Current?.Id ?? HttpContext.TraceIdentifier });
    }
}
```

#### Component Breakdown

| Component | Description |
|-----------|-------------|
| `Controller` base class | Provides view helpers (`View()`, `RedirectToAction()`, `Json()`). |
| Action methods | Public methods returning `IActionResult`. |
| `View()` | Returns the view matching the action name (`Views/Home/Index.cshtml`). |
| `[ResponseCache]` | Prevents caching of error responses. |

#### Syntax Rules

- **Folder:** Controllers reside in `Controllers/`.
- **Naming:** Class names end with `Controller` (e.g., `HomeController`).
- **Discovery:** Automatically discovered; no explicit registration needed.

## 6. Views

### Definitions

| Type | Definition |
|------|------------|
| **Core Definition** | Views are **Razor template files** (`.cshtml`) that render HTML, combining static markup with server‑side C# to display data from the controller. |
| **Technical Definition** | Views are discovered by the **RazorViewEngine** using the search order: `/Views/{Controller}/{Action}.cshtml`, then `/Views/Shared/{Action}.cshtml`. The template includes `Views/Home/Index.cshtml`, `Privacy.cshtml`, `Views/Shared/_Layout.cshtml`, `_ViewStart.cshtml`, and `_ViewImports.cshtml`. Views receive data via the **`@model`** directive (strongly typed) or `ViewData`/`ViewBag`. Layouts provide shared structure; `_ViewStart` sets the default layout. |
| **Beginner‑Friendly Explanation** | Views are the **HTML templates** of your app—what the user actually sees in the browser. The controller passes data to a view, and the view uses Razor syntax (mixing HTML and C#) to produce the final page. The template gives you a home page, a privacy page, and a shared layout with a navigation bar and footer. |

### Purposes (each begins with “To”)

- **To** separate the presentation layer (HTML) from business logic, following the **separation of concerns** principle.
- **To** render dynamic data passed from the controller using Razor syntax.
- **To** provide reusable UI structure through layouts and partial views.
- **To** enable strongly typed views that benefit from IntelliSense and compile‑time checking.
- **To** keep markup consistent across the application via shared layouts and Tag Helpers.

### Syntax Rules and Structure

#### View Discovery Order

```
1. /Views/{ControllerName}/{ActionName}.cshtml
2. /Views/Shared/{ActionName}.cshtml
```

#### Template Views

| File | Purpose |
|------|---------|
| `Views/Home/Index.cshtml` | Home page content. |
| `Views/Home/Privacy.cshtml` | Privacy page content. |
| `Views/Shared/_Layout.cshtml` | Shared layout with `<header>`, navigation, and `<footer>`. |
| `Views/_ViewStart.cshtml` | Sets `Layout = "_Layout"`. |
| `Views/_ViewImports.cshtml` | Imports Tag Helpers and shared namespaces. |

#### Syntax Rules

- **`@model`** declares the model type; the view becomes strongly typed.
- **`@`** introduces Razor code; `@{ ... }` for code blocks, `@Model.Property` for output.
- **`_ViewStart.cshtml`** executes before each view and sets the default layout.
- **`_ViewImports.cshtml`** is **not** inherited by area views; each area needs its own.

#### Constraints and Limitations

- **Views are not strongly typed by default** – use `@model` for compile‑time safety.
- **`ViewBag`/`ViewData` are dynamic** – prefer strongly typed models for maintainability.

## 8. Routing

### Definitions

| Type | Definition |
|------|------------|
| **Core Definition** | Routing is the mechanism that **maps incoming URLs to controller actions** based on URL patterns (route templates). |
| **Technical Definition** | The default conventional route in `Program.cs` is `{controller=Home}/{action=Index}/{id?}`. It tokenises the URL path: the first segment maps to the controller name, the second to the action name, and the optional third to an `id` parameter. Default values (`Home`, `Index`) apply when segments are missing. The `?` makes `id` optional. Routing middleware (`UseRouting`) selects the endpoint; `MapControllerRoute` registers the route. |
| **Beginner‑Friendly Explanation** | Routing is the **address system** of your app. It says: “When someone visits `/Home/Privacy`, run the `Privacy` action on `HomeController`.” The default rule is simple: first part of the URL = controller, second part = action, and an optional third part = ID. If you visit `/`, it defaults to `HomeController.Index`. |

### Purposes (each begins with “To”)

- **To** map clean, readable URLs to controller actions without exposing file names.
- **To** provide default values so that the application root (`/`) works without a specific URL.
- **To** support optional parameters (`id`) for detail/edit/delete actions.
- **To** enable URL generation for links within views using Tag Helpers.
- **To** serve as the foundation for adding attribute routing and areas later.

### Syntax Rules and Structure

#### Default Route

```csharp
app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");
```

#### Route Template Breakdown

| Token | Meaning |
|-------|---------|
| `{controller=Home}` | Controller name; defaults to `Home`. |
| `{action=Index}` | Action name; defaults to `Index`. |
| `{id?}` | Optional `id` parameter; no value if absent. |

#### URL Matching Examples

| URL | Controller | Action | Route Values |
|-----|------------|--------|--------------|
| `/` | `Home` | `Index` | `{}` |
| `/Home` | `Home` | `Index` | `{controller="Home"}` |
| `/Home/Privacy` | `Home` | `Privacy` | `{controller="Home", action="Privacy"}` |
| `/Products/Details/5` | `Products` | `Details` | `{controller="Products", action="Details", id="5"}` |

#### Syntax Rules

- **Routing middleware order:** `UseRouting()` before `UseAuthorization()` and `MapControllerRoute()`.
- **`MapDefaultControllerRoute()`** is a shortcut for the default route.
- **Route parameters are case‑insensitive** during matching.

#### Constraints and Limitations

- **Default route is broad** – It matches most three‑segment URLs; more specific routes must be registered before it.
- **Attribute routing for APIs** – REST APIs should use attribute routing instead of conventional routing.

### Multiple Annotated Complete Step‑by‑Step Code Examples

#### Example 1: Default Route in Action

```csharp
app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");
```

**Step‑by‑step explanation:**

1. A request to `/` matches the route with defaults `Home`/`Index`.
2. A request to `/Home/Privacy` matches with `controller = "Home"`, `action = "Privacy"`.
3. A request to `/Products/Details/5` matches with `id = "5"`.

**Expected Output:** The corresponding controller actions are invoked, and their views are rendered.

**Why this output?** The routing middleware tokenises the URL and uses the route template to determine the controller and action.

---

#### Example 2: Generating Links with Tag Helpers

```cshtml

```

**Expected Output:** Renders `<a href="/Home/Privacy">Privacy</a>`.

**Why this output?** The Anchor Tag Helper uses the default route to generate the URL from the controller and action names.

### Real‑World Cases

- **Home page:** `/` routes to `HomeController.Index`.
- **Privacy policy:** `/Home/Privacy` routes to `HomeController.Privacy`.
- **Detail pages:** `/Products/Details/5` routes to `ProductsController.Details(5)`.

## 10. First Application Best Practices

### Definitions

| Type | Definition |
|------|------------|
| **Core Definition** | First‑application best practices are guidelines for building on the template foundation in a way that remains maintainable, secure, and scalable as the application grows. |
| **Technical Definition** | Best practices encompass **thin controllers** (delegating business logic to services), **strongly typed views** (using `@model` instead of `ViewBag`), **convention adherence** (keeping files in their designated folders), **configuration externalisation** (using `appsettings.json`), **routing awareness** (understanding the default route and its limitations), and **incremental architecture** (adding folders like `Services/` and `Data/` only when needed). |
| **Beginner‑Friendly Explanation** | Best practices are the **rules of thumb** that keep your first app from becoming messy as you add features. For example: keep controllers small, use the standard folders, don’t hard‑code settings, and understand that the default route is a starting point—not the final routing strategy. |

### Purposes (each begins with “To”)

- **To** establish a clean foundation that can scale without major refactoring.
- **To** avoid common beginner pitfalls such as fat controllers and magic strings.
- **To** maintain consistency with the framework’s conventions, reducing friction.
- **To** keep the application secure by externalising configuration and using built‑in security middleware.
- **To** make the codebase understandable for future team members.

### Guideline Checklist

| Guideline | Rationale | Example |
|-----------|-----------|---------|
| **Keep controllers thin** | Business logic belongs in services; thin controllers are easier to test and maintain. | Controller calls `_service.GetAllAsync()` and returns `View(result)`. |
| **Use strongly typed views** | `@model` provides compile‑time checking and IntelliSense. | `@model IEnumerable<Movie>` instead of `ViewBag.Movies`. |
| **Adhere to folder conventions** | The framework discovers controllers and views by location. | Keep controllers in `Controllers/`, views in `Views/`. |
| **Externalise configuration** | Never hard‑code connection strings or secrets. | Use `appsettings.json` and `IOptions<T>`. |
| **Understand the default route** | It is broad and may need refinement as the app grows. | Add attribute routes or specific conventional routes before the default. |
| **Use HTTPS redirection and HSTS** | The template includes these in production; keep them enabled. | `app.UseHttpsRedirection(); app.UseHsts();` |
| **Avoid `ViewBag`/`ViewData` for structured data** | They are dynamic and lack compile‑time safety. | Use a ViewModel. |
| **Add folders incrementally** | Don’t over‑architect a first app; add `Services/`, `Data/`, etc., as needed. | Start with the template; introduce `Services/` when business logic grows. |
| **Follow the Explicit Dependencies Principle** | Controllers should declare their dependencies via constructor injection. | `public HomeController(IProductService service)` |
| **Use filters for cross‑cutting concerns** | Reduces duplication in controllers. | Validation filters, exception filters. |

#### Constraints and Limitations

- **Over‑engineering** – Applying advanced patterns (Clean Architecture, repositories) to a first app can cause unnecessary complexity.
- **Ignoring conventions** – Renaming `Views` or `Controllers` breaks discovery unless custom conventions are configured.

### Multiple Annotated Complete Step‑by‑Step Code Examples

#### Example 1: Thin Controller with a Service (Incremental Improvement)

```csharp
// Before (fat controller – not recommended)
public IActionResult Index()
{
    var movies = _db.Movies.ToList();
    return View(movies);
}

// After (thin controller with a service)
public class HomeController : Controller
{
    private readonly IMovieService _movieService;

    public HomeController(IMovieService movieService) => _movieService = movieService;

    public async Task<IActionResult> Index()
    {
        var movies = await _movieService.GetAllAsync();
        return View(movies);
    }
}
```

**Expected Output:** The controller delegates data access to the service, remaining focused on HTTP concerns.

**Why this output?** Thin controllers are easier to test and maintain as the application grows.

---

#### Example 2: Strongly Typed View

```cshtml
@model IEnumerable<Movie>

<h2>Movies</h2>
<ul>
@foreach (var movie in Model)
{
    <li>@movie.Title (@movie.ReleaseDate.Year)</li>
}
</ul>
```

**Expected Output:** The view renders a list of movies with compile‑time checking.

**Why this output?** `@model` provides type safety, unlike `ViewBag` which is dynamic.

### Real-World Cases

- **E‑commerce:** Thin `ProductsController` delegating to `IProductService`; strongly typed `ProductListViewModel`.
- **Blog:** `PostsController` using `IPostService`; views with `@model PostListViewModel`.
- **API:** Attribute routing for JSON endpoints, conventional routing for HTML views.
