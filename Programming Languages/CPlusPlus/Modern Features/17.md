# C++17 Features — Comprehensive Programming Cheat Sheet

---

## Topic Overview

### Definitions

**Core Definition**
C++17 (ISO/IEC 14882:2017, published December 2017) is a major revision of the C++ standard that introduced many long-awaited language and library features, including structured bindings, `if constexpr`, fold expressions, class template argument deduction, `std::optional`, `std::variant`, `std::string_view`, and the filesystem library, while also removing several deprecated features (notably `std::auto_ptr`, `std::random_shuffle`, and the old `std::bind` placeholders).

**Technical Definition**
C++17 is the fifth major version of the ISO C++ standard. It is a large release that combines features from several Technical Specifications (Library Fundamentals TS, File System TS, Parallelism TS) and adds significant core-language facilities: structured binding declarations (P0217R3), `if constexpr` (P0292R2), fold expressions (N4295), class template argument deduction (P0091R3), guaranteed copy elision (P0135R1), inline variables (N4659), and many library components. The standard also adopts `[[nodiscard]]`, `[[maybe_unused]]`, and `[[fallthrough]]` as standard attributes.

**Beginner-Friendly Explanation**
C++17 is the “big practical” release. It made everyday C++ much more expressive: you can unpack tuples and structs into named variables (structured bindings), write compile-time `if` statements (`if constexpr`), let the compiler deduce template arguments for class templates (`std::pair p{1, 2}`), use type-safe unions (`std::variant`), optional values (`std::optional`), non-owning string views (`std::string_view`), and portable filesystem operations (`std::filesystem`). It also filled in many smaller conveniences like `std::clamp`, `std::gcd`, and `std::size`.

### Key Characteristics

- **Expressive unpacking** – structured bindings let you destructure pairs, tuples, arrays, and structs into named variables.
- **Compile-time branching** – `if constexpr` discards the non-taken branch entirely, enabling template code that would otherwise not compile.
- **Variadic simplification** – fold expressions reduce parameter packs without recursion.
- **Deduction everywhere** – CTAD lets you omit template arguments when constructing objects.
- **Vocabulary types** – `std::optional`, `std::variant`, and `std::any` provide standard, type-safe ways to represent absence, choice, and any-value.
- **Non-owning views** – `std::string_view` provides a cheap read-only window onto string data.
- **Standard filesystem** – `std::filesystem` offers portable path manipulation and file/directory operations.
- **Zero-cost abstractions** – guaranteed copy elision eliminates copies even for non-copyable types.
- **Parallelism** – execution policies let standard algorithms run in parallel with a single argument.

### Prerequisites

- Solid understanding of C++11/14 (especially `auto`, lambdas, move semantics, and `constexpr`).
- Familiarity with templates and template argument deduction.
- Knowledge of the standard library containers, iterators, and algorithms.
- Basic understanding of concurrency and filesystem concepts (for those sections).

### Related Programming Areas

- **Generic programming** – `if constexpr`, fold expressions, CTAD, and variable templates.
- **Type-safe data modelling** – `std::optional`, `std::variant`, `std::any`.
- **Performance** – guaranteed copy elision, parallel algorithms, `std::string_view`.
- **Systems programming** – `std::filesystem`, `std::byte`, `std::scoped_lock`, `std::shared_mutex`.
- **Functional programming** – `std::invoke`, `std::apply`, `std::not_fn`.

## 1. Structured Bindings

### Definitions

**Core Definition**
A structured binding declaration unpacks an object—such as a `std::pair`, `std::tuple`, `std::array`, or aggregate struct—into a list of named variables in a single declaration.

**Technical Definition**
A structured binding declaration has the form `attr(optional) cv-auto ref-operator(optional) [identifier-list] = expression;` (since C++17). The declaration first introduces a uniquely named variable `e` to hold the initializer, then binds the identifiers in the list to subobjects or elements of `e`. The binding follows one of three protocols: array binding (if `E` is an array type), tuple-like binding (if `std::tuple_size<E>` is complete), or member binding (binding to public data members of a non-union class).

**Beginner-Friendly Explanation**
Structured bindings let you “unpack” a multi-part value into separate named variables in one line. Instead of writing `auto p = get_point(); int x = p.first; int y = p.second;`, you write `auto [x, y] = get_point();`.

### Purposes

- To unpack pairs, tuples, arrays, and structs into named variables.
- To make range-based `for` loops over maps cleaner (`for (const auto& [key, value] : map)`).
- To reduce boilerplate when returning multiple values.
- To improve readability of code that works with tuple-like types.

### Syntax Rules and Structure

**General Syntax**
```cpp
auto [a, b, c] = expression;
const auto& [x, y] = pair_value;
```

**Component Breakdown**

| Component | Description |
|-----------|-------------|
| `auto` | Placeholder for the hidden variable `e`. |
| `[a, b, c]` | Identifier list (the structured bindings). |
| `expression` | The object to unpack (array, tuple-like, or aggregate). |

**Syntax Rules**
- The number of identifiers must match the number of elements.
- `auto&` binds by reference to the elements; `auto` copies.
- Structured bindings are declarations, not expressions; they cannot be nested.

**Constraints and Limitations**
- Cannot be used in constant expressions before C++20.
- Cannot be captured by lambdas before C++20 (workaround: capture the underlying object).
- The hidden variable `e` is not directly accessible.

### Annotated Code Examples

**Example 1: Unpacking a pair**

```cpp
#include <iostream>
#include <utility>

int main() {
    std::pair<int, std::string> p = {42, "answer"};
    auto [number, text] = p;
    std::cout << number << ' ' << text << '\n';
}
```

**Expected Output**
```
42 answer
```

**Why this output?**  
The structured binding `[number, text]` binds `number` to `p.first` and `text` to `p.second`.

**Example 2: Iterating a map**

```cpp
#include <iostream>
#include <map>
#include <string>

int main() {
    std::map<std::string, int> ages = {{"Alice", 30}, {"Bob", 25}};
    for (const auto& [name, age] : ages)
        std::cout << name << ": " << age << '\n';
}
```

**Expected Output**
```
Alice: 30
Bob: 25
```

**Why this output?**  
The structured binding unpacks each `std::pair<const std::string, int>` into `name` and `age`.

### Real-World Cases

- **Returning multiple values** – `auto [ok, value] = try_parse(input);`.
- **Map iteration** – the canonical way to iterate key-value pairs.
- **Aggregate decomposition** – unpacking `struct Point { int x, y; }`.

## 2. `if constexpr`

### Definitions

**Core Definition**
`if constexpr` is a compile-time conditional statement that evaluates a constant expression and **discards** the branch not taken, meaning the discarded branch is not instantiated and need not even compile for the current template arguments.

**Technical Definition**
`if constexpr (condition)` requires `condition` to be a contextually converted constant expression of type `bool`. When the condition is `true`, the `statement-true` is kept and the `statement-false` (if any) is discarded; when `false`, the reverse happens. The discarded statement is not instantiated for the current specialization, which allows template code to contain expressions that are only valid for certain types. Unlike a regular `if`, both branches of a regular `if` must compile for every instantiation.

**Beginner-Friendly Explanation**
`if constexpr` is an `if` statement that the compiler evaluates **at compile time**. The branch that is not taken is completely thrown away—the compiler does not even try to compile it. This lets you write template functions that use type-specific operations without causing compile errors for other types.

### Purposes

- To select code branches at compile time based on type traits or constant values.
- To write template functions that handle different types differently.
- To avoid recursion and tag dispatch for simple type-based branching.
- To enable code that would be ill-formed for some instantiations.

### Syntax Rules and Structure

**General Syntax**
```cpp
if constexpr (constant_expression) {
    // compiled only if true
} else if constexpr (another_condition) {
    // compiled only if the first is false and this is true
} else {
    // compiled otherwise
}
```

**Component Breakdown**

| Component | Description |
|-----------|-------------|
| `constexpr` | Keyword marking compile-time evaluation. |
| `condition` | A constant expression convertible to `bool`. |
| Discarded branch | Not instantiated, not type-checked for dependent expressions. |

**Syntax Rules**
- The condition must be a constant expression.
- The discarded branch is not instantiated, but it must still be syntactically valid.
- `if constexpr` can be nested.

**Constraints and Limitations**
- The condition cannot depend on runtime values.
- The discarded branch cannot contain syntax errors, only semantic errors that depend on template parameters are tolerated.

### Annotated Code Example

```cpp
#include <iostream>
#include <string>
#include <type_traits>

template <typename T>
std::string describe(const T& value) {
    if constexpr (std::is_integral_v<T>) {
        return "integral: " + std::to_string(value);
    } else if constexpr (std::is_floating_point_v<T>) {
        return "floating: " + std::to_string(value);
    } else {
        return std::string(value);
    }
}

int main() {
    std::cout << describe(42) << '\n';
    std::cout << describe(3.14) << '\n';
    std::cout << describe("hello") << '\n';
}
```

**Expected Output**
```
integral: 42
floating: 3.140000
hello
```

**Why this output?**  
For `int`, only the integral branch is instantiated; for `double`, only the floating branch; for `const char*`, only the string branch. The other branches are discarded at compile time and never cause errors.

### Real-World Cases

- **Generic serialization** – handling different types differently.
- **Type traits dispatch** – replacing SFINAE and tag dispatch for simple cases.
- **Compile-time configuration** – selecting algorithms based on platform or type properties.

## 3. `if` with Initializer / `switch` with Initializer

### Definitions

**Core Definition**
C++17 allows `if` and `switch` statements to include an initializer statement before the condition, keeping the scope of the introduced variable tight and limited to the `if`/`switch` statement.

**Technical Definition**
The syntax is `if ( init-statement condition )` and `switch ( init-statement condition )`. The `init-statement` is executed first, and any variables it declares are in scope for the condition, the `then`/`else` branches, and the `switch` body, but not beyond the statement.

**Beginner-Friendly Explanation**
You can now declare a variable inside the parentheses of an `if` or `switch`, and it lives only within that statement. This is great for locking mutexes, getting a status code, or performing a lookup that you only need inside the condition.

### Purposes

- To keep the scope of helper variables as tight as possible.
- To avoid polluting the surrounding scope with temporary variables.
- To combine resource acquisition (e.g., `lock_guard`) with a condition check.
- To make code more readable and less error-prone.

### Syntax Rules and Structure

**General Syntax**
```cpp
if (init-statement; condition) { /* ... */ }
switch (init-statement; condition) { /* ... */ }
```

**Component Breakdown**

| Component | Description |
|-----------|-------------|
| `init-statement` | A statement (declaration, expression, etc.) executed once. |
| `condition` | The condition or switch expression. |

**Syntax Rules**
- The semicolon separates the initializer from the condition.
- The initializer can declare one or more variables.
- The scope of the initializer extends to the entire `if`/`switch` statement.

**Constraints and Limitations**
- The initializer cannot be a declaration without an initializer in some contexts.

### Annotated Code Example

```cpp
#include <iostream>
#include <map>
#include <string>

int main() {
    std::map<std::string, int> ages = {{"Alice", 30}};

    if (auto it = ages.find("Alice"); it != ages.end()) {
        std::cout << "Found: " << it->second << '\n';
    } else {
        std::cout << "Not found\n";
    }

    switch (auto x = 2; x) {
        case 1: std::cout << "one\n"; break;
        case 2: std::cout << "two\n"; break;
    }
}
```

**Expected Output**
```
Found: 30
two
```

**Why this output?**  
The `if` initializer performs the lookup and binds `it` only within the `if` statement. The `switch` initializer declares `x` and uses it in the cases.

### Real-World Cases

- **Mutex locking** – `if (std::lock_guard lk(mtx); !container.empty())`.
- **Status codes** – `if (auto status = do_work(); status != ok)`.
- **Map lookups** – keeping the iterator scoped to the `if`.

## 4. Fold Expressions

### Definitions

**Core Definition**
A fold expression reduces a parameter pack over a binary operator, producing a single result without recursion.

**Technical Definition**
C++17 introduces four forms of fold expressions: unary right fold `(pack op ...)`, unary left fold `(... op pack)`, binary right fold `(pack op ... op init)`, and binary left fold `(init op ... op pack)`. The operator can be any of 32 binary operators. When a unary fold is used with an empty pack, only `&&` (value `true`), `||` (value `false`), and `,` (value `void()`) are allowed.

**Beginner-Friendly Explanation**
A fold expression is a compact way to apply an operation across all arguments in a parameter pack. Instead of writing a recursive template to sum `1 + 2 + 3 + ...`, you write `(args + ...)`.

### Purposes

- To reduce parameter packs without recursion.
- To write variadic functions concisely.
- To perform compile-time checks over all template arguments.
- To simplify metaprogramming.

### Syntax Rules and Structure

**General Syntax**
```cpp
(pack op ...)              // unary right fold
(... op pack)              // unary left fold
(pack op ... op init)      // binary right fold
(init op ... op pack)      // binary left fold
```

**Component Breakdown**

| Form | Expansion (conceptual) |
|------|------------------------|
| `(E op ...)` | `E1 op (E2 op (... op EN))` |
| `(... op E)` | `((E1 op E2) op ...) op EN` |
| `(E op ... op I)` | `E1 op (... op (EN op I))` |
| `(I op ... op E)` | `((I op E1) op ...) op EN` |

**Syntax Rules**
- The parentheses are part of the fold expression.
- In a binary fold, both operators must be the same.
- The initializer `I` must not contain an unexpanded pack.

**Constraints and Limitations**
- An empty pack is only valid for `&&`, `||`, and `,`.

### Annotated Code Example

```cpp
#include <iostream>

template <typename... Args>
auto sum(Args... args) {
    return (args + ...);           // unary right fold
}

template <typename... Args>
bool all_true(Args... args) {
    return (... && args);          // unary left fold
}

int main() {
    std::cout << sum(1, 2, 3, 4) << '\n';        // 10
    std::cout << std::boolalpha << all_true(true, true, false) << '\n'; // false
}
```

**Expected Output**
```
10
false
```

**Why this output?**  
`sum(1, 2, 3, 4)` expands to `1 + (2 + (3 + 4)) = 10`. `all_true` expands to `(true && true) && false = false`.

### Real-World Cases

- **Variadic logging** – printing all arguments.
- **Type trait conjunction** – `(std::is_integral_v<Args> && ...)`.
- **Building tuples** – constructing from a pack.

## 5. Class Template Argument Deduction (CTAD)

### Definitions

**Core Definition**
Class template argument deduction (CTAD) allows the compiler to deduce template arguments for class templates from the types of their constructor arguments, so you can write `std::pair p{1, 2.5};` instead of `std::pair<int, double> p{1, 2.5};`.

**Technical Definition**
CTAD (since C++17) applies in variable declarations and functional-style casts where the type specifier names a primary class template without an explicit template argument list. The compiler forms a set of hypothetical function templates from the constructors and uses template argument deduction and overload resolution to select the best specialization. Deduction guides can be user-provided to extend or override the implicit guides.

**Beginner-Friendly Explanation**
CTAD means you can let the compiler figure out the template parameters for class templates from the arguments you give to the constructor. You no longer need to spell out `std::pair<int, double>`—just `std::pair p{1, 2.5}` and the compiler works it out.

### Purposes

- To reduce verbosity when creating class template objects.
- To make code more readable and maintainable.
- To allow class templates to be used like function templates with respect to deduction.
- To simplify factory functions and generic code.

### Syntax Rules and Structure

**General Syntax**
```cpp
std::pair p{1, 2.5};           // deduces std::pair<int, double>
std::vector v{1, 2, 3};        // deduces std::vector<int>
std::lock_guard lk(mtx);       // deduces std::lock_guard<std::mutex>
```

**Component Breakdown**

| Component | Description |
|-----------|-------------|
| Class template name without `<...>` | The type specifier. |
| Constructor arguments | Used for deduction. |
| Deduction guides | Optional user-defined rules. |

**Syntax Rules**
- CTAD only applies in variable declarations and functional-style casts.
- The class template must have accessible constructors.
- Deduction guides can be explicitly provided.

**Constraints and Limitations**
- CTAD does not apply to partial specializations in the same way.
- Aggregate deduction has limitations before C++20.

### Annotated Code Example

```cpp
#include <iostream>
#include <vector>
#include <utility>
#include <string>

int main() {
    std::pair p{42, std::string("answer")};   // pair<int, string>
    std::vector v{1, 2, 3};                   // vector<int>

    std::cout << p.first << ' ' << p.second << '\n';
    std::cout << v.size() << '\n';
}
```

**Expected Output**
```
42 answer
3
```

**Why this output?**  
The compiler deduces `std::pair<int, std::string>` from the arguments `42` and `"answer"`, and `std::vector<int>` from the initializer list `{1, 2, 3}`.

### Real-World Cases

- **Factory functions** – `return std::pair{status, value};`.
- **Container creation** – `std::vector v{1, 2, 3};`.
- **Lock guards** – `std::lock_guard lk(mtx);`.

## 6. `std::optional`

### Definitions

**Core Definition**
`std::optional<T>` is a vocabulary type that either contains a value of type `T` or is empty (disengaged), providing a type-safe way to represent a value that may be absent.

**Technical Definition**
Defined in `<optional>` since C++17, `std::optional<T>` manages an optional contained value. A default-constructed `optional` is empty; it can be constructed from a `T` to become engaged. The contained value is stored inline (no dynamic allocation). Access is via `operator*`, `->`, `value()`, or `value_or()`. `std::nullopt` represents the empty state.

**Beginner-Friendly Explanation**
`std::optional` is a box that may or may not contain a value. It replaces error-prone patterns like returning `-1` or `nullptr` to mean “no result.”

### Purposes

- To represent a value that may be absent without using pointers or sentinel values.
- To return a value from a function that may fail.
- To store optional members in classes.
- To avoid dynamic allocation for optional values.

### Syntax Rules and Structure

**General Syntax**
```cpp
std::optional<T> opt;                  // empty
std::optional<T> opt = value;          // engaged
opt = std::nullopt;                    // reset to empty
if (opt) { /* has value */ }
T v = opt.value();                     // throws if empty
T v = opt.value_or(default);           // safe
```

**Component Breakdown**

| Operation | Description |
|-----------|-------------|
| `has_value()` / `operator bool` | Checks engagement. |
| `value()` | Returns the value; throws `std::bad_optional_access` if empty. |
| `operator*` | Unchecked access. |
| `value_or(default)` | Returns the value or a default. |
| `reset()` | Disengages. |

**Syntax Rules**
- `optional` is not a pointer; the contained object lives inside the optional.
- `std::nullopt` represents the empty state.

**Constraints and Limitations**
- No optional references (use `std::reference_wrapper` as a workaround).
- Slight space overhead for the boolean flag.

### Annotated Code Example

```cpp
#include <iostream>
#include <optional>
#include <string>

std::optional<int> parse_positive(int x) {
    if (x > 0) return x;
    return std::nullopt;
}

int main() {
    auto r1 = parse_positive(5);
    if (r1) std::cout << "Value: " << *r1 << '\n';

    auto r2 = parse_positive(-1);
    std::cout << "Default: " << r2.value_or(0) << '\n';
}
```

**Expected Output**
```
Value: 5
Default: 0
```

**Why this output?**  
The first call returns an engaged optional; the second returns an empty optional, and `value_or(0)` yields `0`.

### Real-World Cases

- **Parsing** – returning `optional<T>` from parsing functions.
- **Configuration** – optional settings that may be omitted.
- **Lookup** – returning `optional` from map-like lookups.

## 7. `std::variant`

### Definitions

**Core Definition**
`std::variant<Types...>` is a type-safe union that holds exactly one value from a fixed set of types at any time.

**Technical Definition**
Defined in `<variant>` since C++17, `std::variant` is a sum type. It tracks which alternative is active and prevents type-punning. Access is via `std::get<T>` (throws on mismatch), `std::get_if<T>` (returns `nullptr` on mismatch), or `std::visit` (dispatches to a visitor). `std::monostate` can be used as a first alternative to make the variant default-constructible.

**Beginner-Friendly Explanation**
`std::variant` is a safe union: it can hold one of several types, and it always knows which type it currently holds. You can visit it to process the contained value.

### Purposes

- To represent a value that can be one of several types.
- To replace unsafe C unions.
- To implement state machines and tagged unions.
- To support type-safe visitation.

### Syntax Rules and Structure

**General Syntax**
```cpp
std::variant<int, double, std::string> v = 42;
v = "hello";
std::visit([](auto&& x){ /* ... */ }, v);
```

**Component Breakdown**

| Operation | Description |
|-----------|-------------|
| `index()` | Active alternative index. |
| `holds_alternative<T>` | Checks active type. |
| `get<T>` / `get<I>` | Accesses the value (throws on mismatch). |
| `get_if<T>` | Pointer access (nullptr on mismatch). |
| `visit` | Calls a visitor with the active value. |

**Syntax Rules**
- Must have at least one alternative (use `std::monostate` for empty).
- Alternatives must be destructible and not references/arrays/`void`.

**Constraints and Limitations**
- `valueless_by_exception` is a rare error state.

### Annotated Code Example

```cpp
#include <iostream>
#include <variant>
#include <string>

int main() {
    std::variant<int, std::string> v = 42;
    std::cout << std::get<int>(v) << '\n';

    v = "hello";
    std::visit([](auto&& x) { std::cout << x << '\n'; }, v);
}
```

**Expected Output**
```
42
hello
```

**Why this output?**  
`v` first holds an `int`; after assignment it holds a `std::string`. `std::visit` calls the generic lambda with the active value.

### Real-World Cases

- **Parsers** – a token can be an identifier, number, or operator.
- **State machines** – states as variant alternatives.
- **Error handling** – `variant<T, Error>` as a result type.

## 8. `std::any`

### Definitions

**Core Definition**
`std::any` is a type-safe container for a single value of any copy-constructible type.

**Technical Definition**
Defined in `<any>` since C++17, `std::any` stores an instance of any type that satisfies the constructor requirements, or is empty. Access is via `std::any_cast<T>`, which throws `std::bad_any_cast` on type mismatch. `has_value()` checks emptiness; `type()` returns the `type_info` of the contained value.

**Beginner-Friendly Explanation**
`std::any` is a box that can hold a value of literally any type—like a type-safe `void*`.

### Purposes

- To store values of any type in a type-safe way.
- To implement dynamic typing or heterogeneous collections.
- To pass values through interfaces that cannot be templated.
- To replace `void*` with a safer alternative.

### Syntax Rules and Structure

**General Syntax**
```cpp
std::any a = 42;
a = std::string("hello");
int i = std::any_cast<int>(a);         // throws on mismatch
auto* p = std::any_cast<int>(&a);       // nullptr on mismatch
```

**Component Breakdown**

| Operation | Description |
|-----------|-------------|
| `has_value()` | Checks if a value is stored. |
| `type()` | Returns `typeid` of the contained value. |
| `any_cast<T>` | Type-safe access; throws on failure. |
| `reset()` | Makes the `any` empty. |

**Syntax Rules**
- `any` can hold any `CopyConstructible` type.
- `any_cast<T>` requires exact type matching.

**Constraints and Limitations**
- Requires `CopyConstructible`; move-only types are not supported.
- Potential dynamic allocation for large types.

### Annotated Code Example

```cpp
#include <iostream>
#include <any>
#include <string>

int main() {
    std::any a = 42;
    std::cout << std::any_cast<int>(a) << '\n';

    a = std::string("hello");
    std::cout << std::any_cast<std::string>(a) << '\n';

    try {
        std::cout << std::any_cast<double>(a) << '\n';
    } catch (const std::bad_any_cast& e) {
        std::cout << "Bad cast: " << e.what() << '\n';
    }
}
```

**Expected Output**
```
42
hello
Bad cast: bad any_cast
```

**Why this output?**  
`any_cast` succeeds when the type matches and throws when it does not.

### Real-World Cases

- **Property systems** – storing arbitrary property values.
- **Scripting bridges** – passing values between typed and dynamic code.
- **Event systems** – carrying arbitrary event payloads.

## 9. `std::string_view`

### Definitions

**Core Definition**
`std::string_view` is a non-owning, read-only view over a contiguous sequence of characters.

**Technical Definition**
Defined in `<string_view>` since C++17, `std::basic_string_view<CharT>` holds a pointer to character data and a length. It makes no copies and does not assume null termination. It is implicitly convertible from `std::string` and string literals. The caller must ensure the underlying data outlives the view.

**Beginner-Friendly Explanation**
`std::string_view` is a “window” onto a string. It lets you read the characters without copying them, but you must ensure the original string stays alive.

### Purposes

- To pass strings to functions without copying.
- To provide a lightweight, read-only view over string data.
- To avoid `const std::string&` when ownership is not needed.
- To serve as a building block for parsing and tokenization.

### Syntax Rules and Structure

**General Syntax**
```cpp
std::string_view sv = "hello";
sv.substr(1, 3);                      // "ell"
sv.data();                            // pointer to data
sv.size();                            // length
```

**Component Breakdown**

| Operation | Description |
|-----------|-------------|
| `data()` | Pointer to the first character. |
| `size()` | Number of characters. |
| `substr(pos, count)` | Returns a sub-view. |
| `remove_prefix(n)` / `remove_suffix(n)` | Shrinks the view. |

**Syntax Rules**
- Does not own its data; must not outlive the underlying string.
- Implicit conversion from `std::string` and string literals.

**Constraints and Limitations**
- Dangling views are undefined behaviour.
- No null-termination guarantee.

### Annotated Code Example

```cpp
#include <iostream>
#include <string_view>
#include <string>

void print(std::string_view sv) {
    std::cout << sv << '\n';
}

int main() {
    print("literal");
    std::string s = "string";
    print(s);
}
```

**Expected Output**
```
literal
string
```

**Why this output?**  
`string_view` accepts both a string literal and a `std::string` without copying.

### Real-World Cases

- **Parsing** – tokenizing without allocations.
- **API parameters** – accepting `string_view` instead of `const std::string&`.
- **Logging** – formatting without copying.

## 11. `std::byte`

**Technical Definition**
Defined in `<cstddef>` since C++17, `std::byte` is declared as `enum class byte : unsigned char {};`. It supports bitwise operations (`|`, `&`, `^`, `~`, `<<`, `>>`) but not arithmetic. Conversion to and from integers requires explicit `std::to_integer<T>(b)` or `std::byte{value}`.

- To force deliberate conversions when interacting with integers.
- To improve type safety in memory manipulation code.

## 12. Inline Variables

### Definitions

**Core Definition**
An inline variable is a variable that can be defined in multiple translation units (typically in a header) with a single shared instance, just as inline functions can be defined in multiple translation units.

**Technical Definition**
The `inline` specifier can be applied to variables (since C++17). A variable declared `inline` has the same linkage semantics as an inline function: it may be defined in multiple translation units, provided all definitions are identical, and the linker merges them into a single entity. Static data members can be declared `inline` and defined inside the class definition.

**Beginner-Friendly Explanation**
Before C++17, defining a global variable in a header caused linker errors if the header was included in multiple source files. `inline` variables solve this: you can define them in a header, and all translation units share the same variable.

### Purposes

- To define variables in headers without linker errors.
- To define static data members inside the class definition.
- To replace the “function returning a static local” idiom for header-only constants.
- To simplify header-only libraries.

### Syntax Rules and Structure

**General Syntax**
```cpp
inline int global_counter = 0;
struct S {
    static inline int count = 0;
};
```

**Component Breakdown**

| Component | Description |
|-----------|-------------|
| `inline` | Specifier indicating inline variable. |
| Initializer | Required (except for static data members with default member initializers). |

**Syntax Rules**
- The `inline` specifier must be present in every declaration.
- All definitions must be identical.
- Inline variables have external linkage by default.

**Constraints and Limitations**
- Inline variables are not `const` by default.
- They can be used in constant expressions if `constexpr` as well.

### Annotated Code Example

```cpp
// header.h
#pragma once
inline int shared_value = 42;

// main.cpp
#include "header.h"
#include "other.cpp"   // also includes header.h
#include <iostream>

int main() {
    std::cout << shared_value << '\n';
}
```

**Expected Output**
```
42
```

**Why this output?**  
The inline variable `shared_value` is defined in the header and merged across translation units, so there is exactly one instance.

### Real-World Cases

- **Header-only libraries** – defining global constants and configuration variables.
- **Class static members** – defining counters or shared state inside the class.
- **Logging** – global loggers defined in headers.

## 14. `[[nodiscard]]`, `[[maybe_unused]]`, `[[fallthrough]]`

### Definitions

**Core Definition**
C++17 standardised three attributes: `[[nodiscard]]` warns if a function’s return value is discarded, `[[maybe_unused]]` suppresses warnings for intentionally unused entities, and `[[fallthrough]]` indicates that falling through a `switch` case is intentional.

**Technical Definition**
- `[[nodiscard]]` can be applied to functions, classes, and enums. When a `[[nodiscard]]` function’s return value is discarded, the compiler is encouraged to issue a warning.
- `[[maybe_unused]]` can be applied to variables, functions, parameters, and types; it suppresses unused-entity warnings.
- `[[fallthrough]]` can be applied to a statement in a `switch` case to indicate intentional fallthrough, suppressing compiler warnings.

**Beginner-Friendly Explanation**
These attributes are notes to the compiler: `[[nodiscard]]` says “warn if the return value is ignored”; `[[maybe_unused]]` says “this is intentionally unused, don’t warn”; `[[fallthrough]]` says “I meant to fall through to the next case.”

### Purposes

- To catch ignored return values that matter (`[[nodiscard]]`).
- To avoid noisy warnings for intentionally unused variables (`[[maybe_unused]]`).
- To document intentional fallthrough in `switch` statements (`[[fallthrough]]`).
- To improve code safety and clarity.

### Syntax Rules and Structure

**General Syntax**
```cpp
[[nodiscard]] int compute();
[[maybe_unused]] int unused = 0;
switch (x) {
    case 1:
        do_something();
        [[fallthrough]];
    case 2:
        do_more();
}
```

**Component Breakdown**

| Attribute | Applies To | Effect |
|-----------|------------|--------|
| `[[nodiscard]]` | Functions, classes, enums | Warn if return value ignored. |
| `[[maybe_unused]]` | Variables, functions, parameters, types | Suppress unused warnings. |
| `[[fallthrough]]` | Statements in `switch` | Suppress fallthrough warnings. |

**Syntax Rules**
- Attributes appear in double square brackets.
- `[[nodiscard]]` can take a reason string (C++20).
- `[[fallthrough]]` must be followed by a semicolon.

**Constraints and Limitations**
- Compiler support varies; unknown attributes are ignored.

### Annotated Code Example

```cpp
#include <iostream>

[[nodiscard]] int important() { return 42; }

int main() {
    important();                        // warning: return value ignored

    [[maybe_unused]] int x = 10;       // no warning

    switch (2) {
        case 1:
            std::cout << "one\n";
            [[fallthrough]];
        case 2:
            std::cout << "two\n";
            break;
    }
}
```

**Expected Output** (warning for ignored return value is compiler-dependent)
```
two
```

**Why this output?**  
The `[[nodiscard]]` function triggers a warning when its result is discarded; `[[maybe_unused]]` suppresses the unused-variable warning; `[[fallthrough]]` documents the intentional fallthrough.

### Real-World Cases

- **Error codes** – `[[nodiscard]]` on functions returning status codes.
- **Test code** – `[[maybe_unused]]` for variables used only in assertions.
- **State machines** – `[[fallthrough]]` in switch-based state transitions.

## 15. Guaranteed Copy Elision

### Definitions

**Core Definition**
Guaranteed copy elision means that when an object is initialised from a prvalue of the same type, the compiler must construct the object directly in the target location, with no copy or move constructor call, even if the constructor has side effects.

**Technical Definition**
Since C++17, when a prvalue of class type is used to initialise an object of the same type (ignoring cv-qualification), the prvalue directly initialises the object; no temporary is materialised and no copy/move constructor is called. The copy/move constructor need not be accessible or present. This applies in return statements, variable initialisation, and function arguments.

**Beginner-Friendly Explanation**
Guaranteed copy elision means the compiler must skip the copy or move when constructing an object from a temporary of the same type. This allows returning non-copyable, non-movable types by value and eliminates unnecessary constructor calls.

### Purposes

- To allow returning non-copyable, non-movable types by value.
- To eliminate unnecessary copy/move constructor calls.
- To improve performance and simplify code.
- To make value semantics more predictable.

### Syntax Rules and Structure

**General Syntax**
```cpp
T create() { return T(); }             // no copy/move
T obj = create();                     // no copy/move
```

**Component Breakdown**

| Context | Guarantee |
|---------|-----------|
| `return T();` | Constructs directly in return slot. |
| `T obj = T();` | Constructs directly in `obj`. |
| Function argument `f(T())` | Constructs directly in parameter. |

**Syntax Rules**
- The prvalue must have the same type as the target (ignoring cv-qualification).
- The copy/move constructor does not need to be accessible.

**Constraints and Limitations**
- Only applies to prvalues of the same type; named objects (lvalues) still require copies/moves.

### Annotated Code Example

```cpp
#include <iostream>

struct NonCopyable {
    NonCopyable() { std::cout << "Constructed\n"; }
    NonCopyable(const NonCopyable&) = delete;
    NonCopyable(NonCopyable&&) = delete;
};

NonCopyable create() {
    return NonCopyable();              // guaranteed elision
}

int main() {
    NonCopyable obj = create();        // no copy/move
    std::cout << "Done\n";
}
```

**Expected Output**
```
Constructed
Done
```

**Why this output?**  
`NonCopyable` has deleted copy and move constructors, yet the code compiles because C++17 guarantees the prvalue is constructed directly in `obj`.

### Real-World Cases

- **Factory functions** – returning non-copyable types by value.
- **`std::lock_guard`** – returning lock guards from helper functions.
- **Immutable types** – types that intentionally disable copying.

## 16. Parallel Algorithms

### Definitions

**Core Definition**
C++17 allows standard algorithms to be executed in parallel by passing an execution policy as the first argument.

**Technical Definition**
The header `<execution>` defines execution policy objects: `std::execution::seq` (sequential), `std::execution::par` (parallel), `std::execution::par_unseq` (parallel + vectorised). Algorithms that accept execution policies include `std::sort`, `std::for_each`, `std::transform`, `std::reduce`, and many others. With `par` or `par_unseq`, the user-provided callables must not cause data races.

**Beginner-Friendly Explanation**
Parallel algorithms let you speed up standard algorithms by adding a single argument. The compiler and runtime handle the threading.

### Purposes

- To parallelise standard algorithms with minimal code changes.
- To exploit multi-core processors.
- To simplify parallel programming compared with manual threading.
- To provide a standard, portable parallelism mechanism.

### Syntax Rules and Structure

**General Syntax**
```cpp
std::sort(std::execution::par, v.begin(), v.end());
std::for_each(std::execution::par, v.begin(), v.end(), f);
```

**Component Breakdown**

| Policy | Meaning |
|--------|---------|
| `seq` | Sequential (default). |
| `par` | Parallel (multiple threads). |
| `par_unseq` | Parallel and vectorised. |

**Syntax Rules**
- Include `<execution>` and the algorithm header.
- The policy is the first argument to the algorithm.
- Callables must be thread-safe under `par`/`par_unseq`.

**Constraints and Limitations**
- Requires linking with a parallel backend (e.g., `-ltbb` for GCC/Clang).
- Not all algorithms support execution policies.

### Annotated Code Example

```cpp
#include <algorithm>
#include <execution>
#include <vector>
#include <iostream>

int main() {
    std::vector<int> v(1'000'000, 1);
    std::for_each(std::execution::par, v.begin(), v.end(),
                  [](int& x) { x *= 2; });
    std::cout << v[0] << '\n';
}
```

**Expected Output**
```
2
```

**Why this output?**  
The parallel `for_each` doubles every element; `v[0]` becomes `2`.

### Real-World Cases

- **Data processing** – parallel sorting, transforming large datasets.
- **Numerical computation** – parallel `reduce` and `transform_reduce`.
- **Image processing** – parallel pixel operations.

## 17. `std::scoped_lock`, `std::shared_mutex`

### Definitions

**Core Definition**
`std::scoped_lock` is a RAII lock guard that can lock multiple mutexes simultaneously without deadlock; `std::shared_mutex` is a reader-writer mutex that allows multiple readers or one writer.

**Technical Definition**
`std::scoped_lock` (C++17) is a variadic lock guard that uses a deadlock-avoidance algorithm to lock zero or more mutexes. `std::shared_mutex` (C++17) provides `lock()`/`unlock()` for exclusive ownership and `lock_shared()`/`unlock_shared()` for shared ownership; `std::shared_lock` is the RAII wrapper for shared ownership.

**Beginner-Friendly Explanation**
`std::scoped_lock` lets you lock several mutexes at once safely. `std::shared_mutex` lets many readers read at the same time, while a writer gets exclusive access.

### Purposes

- To lock multiple mutexes without deadlock (`scoped_lock`).
- To implement reader-writer locks (`shared_mutex`).
- To protect data that is read frequently and written rarely.
- To simplify multi-mutex locking code.

### Syntax Rules and Structure

**General Syntax**
```cpp
std::scoped_lock lock(mtx1, mtx2);    // locks both
std::shared_lock read_lock(sh_mtx);   // shared ownership
std::unique_lock write_lock(sh_mtx);  // exclusive ownership
```

**Component Breakdown**

| Component | Description |
|-----------|-------------|
| `scoped_lock` | Locks one or more mutexes (deadlock-avoiding). |
| `shared_mutex` | Reader-writer mutex. |
| `shared_lock` | RAII shared ownership. |

**Syntax Rules**
- `scoped_lock` can lock zero or more mutexes.
- `shared_mutex` supports both shared and exclusive locking.

**Constraints and Limitations**
- Reader-writer locks have more overhead than plain mutexes.

### Annotated Code Example

```cpp
#include <iostream>
#include <mutex>
#include <shared_mutex>
#include <thread>

std::shared_mutex sh_mtx;
int data = 0;

void reader() {
    std::shared_lock lock(sh_mtx);
    std::cout << "Read: " << data << '\n';
}

void writer() {
    std::unique_lock lock(sh_mtx);
    ++data;
}

int main() {
    std::thread w(writer);
    w.join();
    std::thread r1(reader), r2(reader);
    r1.join();
    r2.join();
}
```

**Expected Output**
```
Read: 1
Read: 1
```

**Why this output?**  
The writer increments `data` under exclusive lock; both readers acquire shared locks and see the updated value.

### Real-World Cases

- **Caches** – many readers, occasional updates.
- **Configuration data** – read by many threads, reloaded rarely.
- **Bank accounts** – transferring between accounts with `scoped_lock`.

## 18. `std::apply`, `std::invoke`, `std::not_fn`, `std::as_const`

`std::apply` lets you call a function with a tuple’s elements as arguments; `std::invoke` lets you call anything callable in a uniform way; `std::not_fn` negates a predicate; `std::as_const` gives you a const view of a variable.

### Purposes

- To unpack tuples into function calls (`apply`).
- To write generic code that works with any callable (`invoke`).
- To negate predicates without writing a lambda (`not_fn`).
- To force const overload selection (`as_const`).

### Syntax Rules and Structure

**General Syntax**
```cpp
std::apply(f, tuple);
std::invoke(f, args...);
std::not_fn(predicate);
std::as_const(obj);
```

**Component Breakdown**

| Utility | Purpose |
|---------|---------|
| `apply` | Unpack tuple into arguments. |
| `invoke` | Uniform callable invocation. |
| `not_fn` | Negate a callable. |
| `as_const` | Add `const` to an lvalue. |

**Syntax Rules**
- `apply` works with any tuple-like type.
- `invoke` supports member pointers.
- `not_fn` returns an unspecified callable.

**Constraints and Limitations**
- `not_fn` replaces the deprecated `std::not1`/`std::not2`.

### Annotated Code Example

```cpp
#include <iostream>
#include <tuple>
#include <functional>

int add(int a, int b) { return a + b; }

int main() {

    const auto& cs = std::as_const(s);
    std::cout << cs.size() << '\n';                         // 5
}
```

**Expected Output**
```
3
true
5
```

**Why this output?**  
`apply` unpacks the pair into `add(1, 2)`; `not_fn` negates `is_even`; `as_const` provides a const reference.

### Real-World Cases

- **Generic invocation** – writing wrappers that work with any callable.
- **Tuple processing** – applying functions to tuple elements.
- **Predicate composition** – negating predicates in algorithms.

## 19. `std::clamp`, `std::gcd`, `std::lcm`, `std::hypot`

### Definitions

**Core Definition**
C++17 added several mathematical utilities: `std::clamp` constrains a value to a range, `std::gcd` and `std::lcm` compute greatest common divisor and least common multiple, and `std::hypot` computes the hypotenuse (with a three-argument overload for 3D).

**Technical Definition**
- `std::clamp(v, lo, hi)` returns `lo` if `v < lo`, `hi` if `hi < v`, otherwise `v`.
- `std::gcd(m, n)` returns the greatest common divisor; `std::lcm(m, n)` returns the least common multiple.
- `std::hypot(x, y)` and `std::hypot(x, y, z)` compute `sqrt(x² + y²)` and `sqrt(x² + y² + z²)` without undue overflow/underflow.

**Beginner-Friendly Explanation**
These are handy math functions that save you from writing common algorithms: clamping a value between bounds, finding the GCD/LCM of two numbers, and computing distances.

### Purposes

- To constrain values to a range (`clamp`).
- To compute GCD and LCM (`gcd`, `lcm`).
- To compute Euclidean distances safely (`hypot`).
- To avoid reinventing common mathematical operations.

### Syntax Rules and Structure

**General Syntax**
```cpp
std::clamp(value, low, high);
std::gcd(m, n);
std::lcm(m, n);
std::hypot(x, y);
std::hypot(x, y, z);
```

**Component Breakdown**

| Function | Header | Purpose |
|----------|--------|---------|
| `clamp` | `<algorithm>` | Constrain to range. |
| `gcd` | `<numeric>` | Greatest common divisor. |
| `lcm` | `<numeric>` | Least common multiple. |
| `hypot` | `<cmath>` | Euclidean distance. |

**Syntax Rules**
- `clamp` returns a reference to one of its arguments.
- `gcd`/`lcm` require integer types.
- `hypot` has two- and three-argument overloads (the three-argument version since C++17).

**Constraints and Limitations**
- `clamp` requires `lo <= hi`.

### Annotated Code Example

```cpp
#include <iostream>
#include <algorithm>
#include <numeric>
#include <cmath>

int main() {
    std::cout << std::clamp(15, 0, 10) << '\n';   // 10
    std::cout << std::gcd(12, 18) << '\n';         // 6
    std::cout << std::lcm(4, 6) << '\n';           // 12
    std::cout << std::hypot(3, 4) << '\n';         // 5
}
```

**Expected Output**
```
10
6
12
5
```

**Why this output?**  
`clamp(15, 0, 10)` returns `10` because 15 exceeds the upper bound; `gcd(12, 18)` is 6; `lcm(4, 6)` is 12; `hypot(3, 4)` is 5.

### Real-World Cases

- **Graphics** – clamping colour values, computing distances.
- **Number theory** – simplifying fractions.
- **Physics** – Euclidean distances in 2D/3D.

## 20. `std::size`, `std::data`, `std::empty`

### Definitions

**Core Definition**
C++17 added free-function versions of `size`, `data`, and `empty` that work uniformly with containers, C arrays, and `std::initializer_list`.

**Technical Definition**
Defined in `<iterator>` (and `<array>`, `<string>`, etc.) since C++17:
- `std::size(c)` returns the number of elements.
- `std::data(c)` returns a pointer to the underlying array.
- `std::empty(c)` returns `true` if the range is empty.
These functions work with any type that provides `size()`, `data()`, or `empty()`, as well as with C arrays.

**Beginner-Friendly Explanation**
These functions let you write generic code that works with both containers and C arrays without special-casing.

### Purposes

- To unify access to `size`, `data`, and `empty` across containers and C arrays.
- To simplify generic code.
- To avoid writing `sizeof(arr)/sizeof(arr[0])` for C arrays.
- To enable uniform treatment of different sequence types.

### Syntax Rules and Structure

**General Syntax**
```cpp
std::size(container);
std::data(container);
std::empty(container);
```

**Component Breakdown**

| Function | Returns | Works With |
|----------|---------|------------|
| `size` | `std::size_t` | Containers, arrays, initializer_list |
| `data` | Pointer | Containers, arrays |
| `empty` | `bool` | Containers, arrays |

**Syntax Rules**
- Requires `<iterator>` (and the container header).
- Works with any type that provides the corresponding member or is a C array.

**Constraints and Limitations**
- `data` requires contiguous storage.

### Annotated Code Example

```cpp
#include <iostream>
#include <vector>
#include <iterator>

int main() {
    std::vector<int> v = {1, 2, 3};
    int arr[] = {4, 5, 6};

    std::cout << std::size(v) << ' ' << std::size(arr) << '\n';
    std::cout << std::boolalpha << std::empty(v) << '\n';
    std::cout << *std::data(v) << '\n';
}
```

**Expected Output**
```
3 3
false
1
```

**Why this output?**  
`std::size` works for both the vector and the array; `std::empty` returns `false` for a non-empty vector; `std::data` returns a pointer to the first element.

### Real-World Cases

- **Generic algorithms** – writing functions that accept containers or arrays.
- **C interoperability** – using `std::data` to obtain pointers.
- **Serialization** – getting size and data uniformly.

## 21. `std::bool_constant`

### Definitions

**Core Definition**
`std::bool_constant<B>` is an alias template for `std::integral_constant<bool, B>`, providing a convenient way to represent compile-time boolean constants.

**Technical Definition**
Defined in `<type_traits>` since C++17, `std::bool_constant` is an alias template: `template<bool B> using bool_constant = integral_constant<bool, B>;`. It is commonly used in template metaprogramming to pass boolean values as type parameters.

**Beginner-Friendly Explanation**
`std::bool_constant<true>` is a type that represents the compile-time value `true`. It is a shorthand for `std::integral_constant<bool, true>`.

### Purposes

- To represent compile-time boolean values as types.
- To simplify template metaprogramming.
- To pass boolean flags to template functions.
- To replace verbose `std::integral_constant<bool, B>`.

### Syntax Rules and Structure

**General Syntax**
```cpp
template <bool B>
using bool_constant = std::integral_constant<bool, B>;
```

**Component Breakdown**

| Component | Description |
|-----------|-------------|
| `B` | The boolean value. |
| `value` | Static member constant equal to `B`. |
| `value_type` | `bool`. |

**Syntax Rules**
- `bool_constant` is an alias template.
- It inherits from `integral_constant<bool, B>`.

**Constraints and Limitations**
- Only for boolean values; use `integral_constant` for other integral types.

### Annotated Code Example

```cpp
#include <iostream>
#include <type_traits>

template <bool B>
void check(std::bool_constant<B>) {
    std::cout << std::boolalpha << B << '\n';
}

int main() {
    check(std::bool_constant<true>{});
    check(std::bool_constant<false>{});
}
```

**Expected Output**
```
true
false
```

**Why this output?**  
`std::bool_constant<B>` provides a type whose `value` is `B`; the function template deduces `B` and prints it.

### Real-World Cases

- **Template metaprogramming** – passing compile-time booleans.
- **Type traits** – implementing traits that return boolean types.
- **Tag dispatch** – using boolean constants as tags.
