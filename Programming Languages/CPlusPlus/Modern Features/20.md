# C++20 Features — Comprehensive Programming Cheat Sheet

## Topic Overview

### Definitions

**Core Definition**
C++20 (ISO/IEC 14882:2020, published December 2020) is the sixth major version of the ISO C++ standard, introducing four “big” language features—**concepts, ranges, coroutines, and modules**—alongside many smaller language and library improvements that fundamentally changed how modern C++ is written.

**Technical Definition**
C++20 is a major revision of the C++ standard. Its headline language features are constraints and concepts (P0734R0), the ranges library (P0896R4), coroutines (P0912R5), and modules (P1103R3). It also added the three-way comparison operator `<=>` (P0515R3), designated initialisers (P0329R4), `consteval` and `constinit` (P1073R3, P1143R2), further relaxed `constexpr` rules, `char8_t`, `[[no_unique_address]]`, `[[likely]]`, and `[[unlikely]]`. On the library side it introduced `<span>`, `<format>`, `<bit>`, `<numbers>`, `<syncstream>`, `<semaphore>`, `<latch>`, `<barrier>`, `<stop_token>`, `<source_location>`, `<concepts>`, `<ranges>`, and `<compare>`, along with numerous utilities such as `std::bit_cast`, `std::ssize`, `std::midpoint`, `std::lerp`, `std::to_array`, `std::erase`/`std::erase_if`, `std::atomic_ref`, `std::jthread`, and the `std::cmp_*` family.

**Beginner-Friendly Explanation**
C++20 is the “modern modern C++” release. It is the version that finally made templates produce readable error messages (concepts), let you write expressive data pipelines without copying (ranges), brought async/await-style programming to C++ (coroutines), and replaced the ancient `#include` system with something faster and cleaner (modules). It also added dozens of small conveniences that you will reach for every day.

### Key Characteristics

- **Compile-time constraints** – concepts let you express and enforce template requirements, producing clear diagnostics.
- **Composable data pipelines** – ranges and views enable lazy, lazy, allocation-free transformations.
- **Resumable functions** – coroutines allow functions to suspend and resume without blocking a thread.
- **Component-based compilation** – modules replace textual `#include` with importable, isolated translation units.
- **Strong ordering** – `<=>` generates all six relational operators from one declaration.
- **Immediate functions and guaranteed initialisation** – `consteval` forces compile-time evaluation; `constinit` forces compile-time initialisation.
- **Type-safe formatting** – `std::format` replaces `printf` with compile-time-checked format strings.
- **Standardised bit manipulation** – `std::bit_cast` and the `<bit>` header.
- **Safer concurrency** – `std::jthread`, stop tokens, latches, barriers, and semaphores.
- **Zero-cost source diagnostics** – `std::source_location` replaces `__FILE__` and `__LINE__`.

### Prerequisites

- Solid understanding of C++11/14/17 (especially `auto`, lambdas, move semantics, `constexpr`, templates, and the standard library).
- Familiarity with template metaprogramming and SFINAE (to appreciate concepts).
- Basic knowledge of iterators and STL algorithms (for ranges).
- Understanding of concurrency primitives (for jthread, latch, barrier, semaphore).
- A C++20-compliant compiler (GCC 10+, Clang 12+, MSVC 19.29+ for most features).

### Related Programming Areas

- **Generic programming** – concepts, abbreviated function templates, `requires` expressions.
- **Data processing** – ranges, views, adaptors, and pipelines.
- **Asynchronous programming** – coroutines for cooperative multitasking.
- **Build systems and modularity** – modules for faster, cleaner builds.
- **Low-level programming** – `std::bit_cast`, `std::endian`, `std::assume_aligned`.
- **Concurrency** – `std::jthread`, stop tokens, latches, barriers, semaphores, `std::atomic_ref`.

## 1. Concepts

### Definitions

**Core Definition**
A concept is a named set of compile-time requirements on template parameters, used to constrain templates and select the most appropriate overload.

**Technical Definition**
Concepts are named sets of requirements. Each concept is a predicate evaluated at compile time and becomes part of the interface of a template where it is used as a constraint. Concepts can be defined with the `concept` keyword and a `requires` expression, and can be applied via `template<Concept T>`, `requires Concept<T>`, or a trailing `requires` clause. Violations are detected at compile time, early in the instantiation process, producing clear diagnostics.

**Beginner-Friendly Explanation**
A concept is a label that describes what a type must be able to do. Instead of letting the compiler produce a wall of errors when a template is used with the wrong type, you say “this template only accepts types that satisfy this concept,” and the compiler tells you immediately and clearly if the requirement is not met.

### Purposes

- To express template requirements declaratively and readably.
- To produce clear, early compile-time diagnostics.
- To enable overload selection based on semantic properties.
- To replace SFINAE and tag dispatch in many cases.
- To model semantic categories (Number, Range, RegularFunction) rather than syntactic restrictions.

### Syntax Rules and Structure

**General Syntax**
```cpp
template<typename T>
concept ConceptName = requires(T a) {
    { expression } -> std::convertible_to<Type>;
    // ...
};

template<ConceptName T>
void function(T value);

// Alternative forms:
template<typename T> requires ConceptName<T>
void function(T value);

void function(ConceptName auto value);
```

**Component Breakdown**

| Component | Description |
|-----------|-------------|
| `concept` | Keyword introducing a concept definition. |
| `requires` expression | Specifies the required operations and their result types. |
| `template<Concept T>` | Constrained template parameter. |
| `requires` clause | Applies a constraint to a template. |
| `Concept auto` | Abbreviated function template form. |

**Syntax Rules**
- Concepts must be defined at namespace scope.
- A concept cannot be explicitly instantiated, specialised, or partially specialised.
- Concepts can be combined with `&&` and `||`.
- The `requires` expression is an unevaluated operand.

**Constraints and Limitations**
- Concepts model semantic categories, not just syntactic capabilities; avoid concepts without meaningful semantics (Core Guideline T.20).
- Concepts do not replace all uses of SFINAE; some advanced scenarios still require `enable_if`.

### Annotated Code Examples

**Example 1: Defining and using a concept**

```cpp
#include <concepts>
#include <iostream>
#include <string>

template<typename T>
concept Hashable = requires(T a) {
    { std::hash<T>{}(a) } -> std::convertible_to<std::size_t>;
};

template<Hashable T>
void print_hash(const T& value) {
    std::cout << std::hash<T>{}(value) << '\n';
}

int main() {
    print_hash(std::string("hello"));   // OK: string satisfies Hashable
    // print_hash(42);                   // OK: int is hashable
    // print_hash(std::vector<int>{});   // error: vector is not hashable
}
```

**Expected Output** (hash value is implementation-dependent)
```
...
```

**Why this output?**  
`std::string` satisfies the `Hashable` concept because `std::hash<std::string>` is valid and returns a type convertible to `size_t`. The constrained template accepts it.

**Example 2: Constrained overload selection**

```cpp
#include <concepts>
#include <iostream>

void process(std::integral auto x) {
    std::cout << "integral: " << x << '\n';
}

void process(std::floating_point auto x) {
    std::cout << "floating: " << x << '\n';
}

int main() {
    process(42);       // integral
    process(3.14);     // floating
}
```

**Expected Output**
```
integral: 42
floating: 3.14
```

**Why this output?**  
The abbreviated function templates use concepts to constrain each overload; overload resolution selects the correct one based on the argument type.

### Real-World Cases

- **Standard library** – `<concepts>` provides `std::integral`, `std::floating_point`, `std::same_as`, `std::convertible_to`, and many more.
- **Library API design** – constraining public templates with meaningful concepts.
- **Error message quality** – replacing hundreds of lines of template errors with a single constraint failure message.

## 2. Ranges

### Definitions

**Core Definition**
The ranges library is an extension and generalisation of the algorithms and iterator libraries that makes them composable and less error-prone, introducing lightweight *views* that indirectly represent iterable sequences.

**Technical Definition**
The `<ranges>` header defines the namespace `std::ranges` and the namespace alias `std::views`. Ranges are an abstraction over iterator pairs, counted sequences, conditionally terminated sequences, and unbounded sequences. The library provides range algorithms (applied eagerly to ranges) and range adaptors (applied lazily to views). Adaptors compose into pipelines, and the work is performed as the view is iterated.

**Beginner-Friendly Explanation**
Ranges let you write data processing pipelines without loops and without intermediate containers. You say “take these numbers, keep the even ones, square them, and take the first five,” and C++ does the rest lazily.

### Purposes

- To simplify algorithm calls by accepting ranges instead of iterator pairs.
- To enable lazy, composable data transformations.
- To avoid intermediate containers and unnecessary copies.
- To provide clearer, more readable data-processing code.

### Syntax Rules and Structure

**General Syntax**
```cpp
#include <ranges>
#include <vector>

std::vector<int> v = {1, 2, 3, 4, 5};
auto result = v
    | std::views::filter([](int x){ return x % 2 == 0; })
    | std::views::transform([](int x){ return x * x; })
    | std::views::take(3);
```

**Component Breakdown**

| Component | Description |
|-----------|-------------|
| `std::views::filter` | View of elements satisfying a predicate. |
| `std::views::transform` | View of elements transformed by a function. |
| `std::views::take` | View of the first `n` elements. |
| `std::views::iota` | Generator view (bounded or unbounded). |
| `\|` | Pipeline operator. |

**Syntax Rules**
- Views are lazy; no work is done until the view is iterated.
- Adaptors are in `std::views` (alias for `std::ranges::views`).
- Range algorithms are in `std::ranges` and are eager.

**Constraints and Limitations**
- The underlying range must outlive the view.
- Infinite ranges must be truncated before full consumption.

### Annotated Code Example

```cpp
#include <ranges>
#include <vector>
#include <iostream>

int main() {
    std::vector<int> v = {1, 2, 3, 4, 5, 6, 7, 8};

    auto result = v
        | std::views::filter([](int x){ return x % 2 == 0; })
        | std::views::transform([](int x){ return x * 10; })
        | std::views::take(3);

    for (int x : result) std::cout << x << ' ';
}
```

**Expected Output**
```
20 40 60
```

**Why this output?**  
The pipeline keeps evens (`2, 4, 6, 8`), multiplies by 10 (`20, 40, 60, 80`), and takes the first three (`20, 40, 60`). All operations are lazy and composed via `|`.

### Real-World Cases

- **Data filtering and transformation** – processing large datasets without temporary allocations.
- **Pagination** – `data | views::drop(page * size) | views::take(size)`.
- **Infinite sequences** – `views::iota(0) | views::take(10)`.

## 3. Coroutines

### Definitions

**Core Definition**
A coroutine is a function that can suspend its execution and later resume it, preserving its local state across suspensions.

**Technical Definition**
C++20 coroutines are functions that use `co_await` (to suspend until resumed), `co_yield` (to suspend and return a value), or `co_return` (to return a final value). A function becomes a coroutine if its body contains any of these keywords. The compiler transforms the function into a state machine that interacts with a *promise type* supplied by the return type.

**Beginner-Friendly Explanation**
A coroutine is a function that can pause in the middle and later continue where it left off. This is the foundation for asynchronous code that reads like synchronous code.

### Purposes

- To write asynchronous code without callback hell.
- To implement generators and lazy sequences.
- To enable cooperative multitasking.
- To simplify state machines.

### Syntax Rules and Structure

**General Syntax**
```cpp
Task coroutine_function() {
    co_await async_operation();
    co_yield some_value;
    co_return final_value;
}
```

**Component Breakdown**

| Keyword | Effect |
|---------|--------|
| `co_await expr` | Suspends until the awaited operation completes. |
| `co_yield expr` | Suspends and produces a value. |
| `co_return expr` | Returns a final value and terminates the coroutine. |

**Syntax Rules**
- A function is a coroutine if its body contains `co_await`, `co_yield`, or `co_return`.
- The return type must define a promise type with the required customization points.
- Coroutines cannot be `constexpr` or `consteval`.

**Constraints and Limitations**
- The standard library does not provide ready-made coroutine types (as of C++20); `std::generator` arrives in C++23.
- Writing custom coroutine machinery is complex.

### Annotated Code Example

```cpp
#include <coroutine>
#include <iostream>

struct Generator {
    struct promise_type {
        int current_value;
        Generator get_return_object() { return Generator{this}; }
        std::suspend_always initial_suspend() { return {}; }
        std::suspend_always final_suspend() noexcept { return {}; }
        std::suspend_always yield_value(int value) {
            current_value = value;
            return {};
        }
        void return_void() {}
        void unhandled_exception() {}
    };

    promise_type* p;
    explicit Generator(promise_type* p) : p(p) {}

    bool move_next() {
        p->resume();
        return !p->done();
    }
    int current_value() const { return p->current_value; }
};

Generator count_to(int n) {
    for (int i = 1; i <= n; ++i)
        co_yield i;
}

int main() {
    auto g = count_to(3);
    while (g.move_next())
        std::cout << g.current_value() << ' ';
}
```

**Expected Output**
```
1 2 3
```

**Why this output?**  
`count_to` is a coroutine that `co_yield`s each number. The generator resumes it step by step, printing each yielded value.

### Real-World Cases

- **Asynchronous I/O** – reading sockets or files without blocking threads.
- **Generators** – lazily producing sequences.
- **Game loops** – scripting and behaviour trees.
- **State machines** – expressing states as coroutine frames.

## 4. Modules

### Definitions

**Core Definition**
A module is a language feature for sharing declarations and definitions across translation units, replacing textual `#include` with importable, isolated units.

**Technical Definition**
A module unit is a translation unit that has a module declaration (`export module name;`). Modules export declarations via `export` and import other modules via `import`. Module interface units export their declarations; implementation units do not. Modules are orthogonal to namespaces and provide isolation, faster compilation, and macro hygiene.

**Beginner-Friendly Explanation**
Modules are a modern replacement for `#include`. Instead of copying header text into every source file, you import a module and get only its exported declarations—faster builds, no include guards, no macro leakage.

### Purposes

- To replace textual inclusion with semantic import.
- To improve compilation speed.
- To isolate macros and implementation details.
- To provide a cleaner, more reliable component model.

### Syntax Rules and Structure

**General Syntax**
```cpp
// helloworld.cpp
export module helloworld;
import <iostream>;
export void hello() {
    std::cout << "Hello world!\n";
}

// main.cpp
import helloworld;
int main() { hello(); }
```

**Component Breakdown**

| Declaration | Meaning |
|-------------|---------|
| `export module name;` | Module declaration and interface unit. |
| `module name;` | Implementation unit (not exported). |
| `export declaration;` | Export a declaration. |
| `import module-name;` | Import a module. |

**Syntax Rules**
- The module declaration must be the first declaration in the translation unit (after the global module fragment).
- Module names can contain dots for hierarchy.
- There must be exactly one primary module interface unit per named module.

**Constraints and Limitations**
- Compiler and build-system support varies.
- Modules do not replace namespaces; both are used together.
- The global module fragment (`module;`) is needed for legacy `#include` directives.

### Annotated Code Example

```cpp
// math.cpp
export module math;
export int add(int a, int b) { return a + b; }

// main.cpp
import math;
#include <iostream>
int main() {
    std::cout << add(2, 3) << '\n';    // 5
}
```

**Expected Output**
```
5
```

**Why this output?**  
`add` is exported from the `math` module and imported into `main.cpp`; no header or macro is involved.

### Real-World Cases

- **Large codebases** – faster incremental builds.
- **Library distribution** – exporting a clean API without headers.
- **Macro isolation** – preventing macro leakage between components.

## 5. Three-Way Comparison (`<=>`)

### Definitions

**Core Definition**
The three-way comparison operator `<=>` (the “spaceship” operator) compares two values and returns an ordering type that encodes less-than, equal, or greater-than in a single result.

**Technical Definition**
`a <=> b` returns a comparison category object: `std::strong_ordering`, `std::weak_ordering`, or `std::partial_ordering`. When `<=>` is defaulted, the compiler generates all six relational operators (`<`, `<=`, `>`, `>=`, `==`, `!=`) automatically. `std::compare_three_way` is a function object that performs the comparison and returns the result.

**Beginner-Friendly Explanation**
`<=>` compares two values and tells you whether the left is less, equal, or greater in one operation. If you define it, C++ generates all the other comparison operators for you.

### Purposes

- To reduce the boilerplate of defining six comparison operators.
- To provide a single, consistent comparison primitive.
- To express ordering semantics precisely (`strong`, `weak`, `partial`).
- To simplify generic comparison code.

### Syntax Rules and Structure

**General Syntax**
```cpp
struct Point {
    int x, y;
    auto operator<=>(const Point&) const = default;
};
```

**Component Breakdown**

| Ordering Type | Meaning |
|---------------|---------|
| `std::strong_ordering` | Total order; substitutability. |
| `std::weak_ordering` | Total order; equivalence classes. |
| `std::partial_ordering` | Not all values are comparable (e.g., NaN). |

**Syntax Rules**
- `<=>` can be defaulted with `= default`.
- The return type is deduced unless explicitly specified.
- `operator==` must also be defaulted or defined separately for `std::three_way_comparable`.

**Constraints and Limitations**
- Defaulted `<=>` compares members in declaration order.
- Floating-point types produce `partial_ordering`.

### Annotated Code Example

```cpp
#include <compare>
#include <iostream>

struct Version {
    int major, minor;
    auto operator<=>(const Version&) const = default;
};

int main() {
    Version a{1, 2}, b{1, 3};
    std::cout << std::boolalpha;
    std::cout << (a < b) << '\n';        // true
    std::cout << (a == b) << '\n';       // false
    std::cout << (a >= b) << '\n';       // false
}
```

**Expected Output**
```
true
false
false
```

**Why this output?**  
The defaulted `<=>` compares `major` first, then `minor`. `a < b` is true; `a == b` is false; `a >= b` is false.

### Real-World Cases

- **Value types** – structs and classes with multiple members.
- **Standard library** – `std::pair`, `std::tuple`, and `std::string` use `<=>`.
- **Generic comparison** – algorithms that need a single comparison primitive.

## 6. Designated Initializers

### Definitions

**Core Definition**
Designated initializers allow aggregate members to be initialised by name in a braced initialiser list, e.g., `Point p{.x = 1, .y = 2}`.

**Technical Definition**
Designated initializers (P0329R4) allow the initialisation of aggregate members by name. Each designator must name a direct non-static data member, and designators must appear in declaration order. Members not explicitly initialised are value-initialised.

**Beginner-Friendly Explanation**
Designated initializers let you specify which struct member you are initialising by name, making aggregate initialisation clearer and more robust.

### Purposes

- To make aggregate initialisation self-documenting.
- To avoid positional initialisation mistakes.
- To initialise only the members you care about.
- To improve readability of configuration structs.

### Syntax Rules and Structure

**General Syntax**
```cpp
struct Point { int x; int y; int z; };
Point p{.x = 1, .z = 2};        // y is value-initialised to 0
```

**Component Breakdown**

| Component | Description |
|-----------|-------------|
| `.designator` | Names a direct non-static data member. |
| `= value` or `{value}` | The initialiser. |

**Syntax Rules**
- Designators must appear in declaration order.
- Out-of-order, nested, and mixed designated/regular initialisation are not allowed in C++ (unlike C).
- Designated initialisers cannot be used with arrays in C++.

**Constraints and Limitations**
- Only for aggregate types.
- Cannot mix designated and positional initialisers.

### Annotated Code Example

```cpp
#include <iostream>

struct Config {
    int width = 800;
    int height = 600;
    bool fullscreen = false;
};

int main() {
    Config c{.width = 1920, .fullscreen = true};
    std::cout << c.width << ' ' << c.height << ' ' << c.fullscreen << '\n';
}
```

**Expected Output**
```
1920 600 1
```

**Why this output?**  
`width` is set to 1920, `fullscreen` to true, and `height` retains its default value 600.

### Real-World Cases

- **Configuration structs** – setting only the non-default fields.
- **Test data** – constructing aggregates with named fields.
- **API design** – making aggregate initialisation readable.

## 7. `constexpr` Improvements

### Definitions

**Core Definition**
C++20 further relaxed the rules for `constexpr` functions and variables, allowing more dynamic operations at compile time.

**Technical Definition**
C++20 extends `constexpr` to allow `try`/`catch` blocks, `dynamic_cast`, `typeid` on polymorphic types, and `std::vector` and `std::string` in constant expressions (with restrictions). It also allows `constexpr` virtual functions and `constexpr` coroutines (with limitations). The rules for what can appear in a `constexpr` function body were further relaxed compared to C++14.

**Beginner-Friendly Explanation**
C++20 makes `constexpr` even more powerful: you can now use exceptions, dynamic allocation, and virtual functions in compile-time code, as long as the evaluation stays within the permitted subset.

### Purposes

- To move more complex computations to compile time.
- To allow `constexpr` containers and strings.
- To simplify compile-time programming.

### Syntax Rules and Structure

**General Syntax**
```cpp
constexpr auto compute() {
    std::vector<int> v{1, 2, 3};       // allowed in C++20
    return v[0] + v[1];
}
```

**Component Breakdown**

| Feature | C++17 | C++20 |
|---------|-------|-------|
| `try`/`catch` in `constexpr` | No | Yes (with restrictions) |
| `dynamic_cast` | No | Yes (with restrictions) |
| `std::vector` / `std::string` | No | Yes (with restrictions) |
| Virtual functions | No | Yes |

**Syntax Rules**
- Memory allocated during constant evaluation must be deallocated before the evaluation ends.
- The evaluation must not invoke undefined behaviour.

**Constraints and Limitations**
- Not all operations are allowed; the constant evaluation subset is still restricted.
- Transient allocation is allowed but must not escape.

### Annotated Code Example

```cpp
#include <iostream>
#include <vector>

constexpr int sum_first_three() {
    std::vector<int> v{10, 20, 30, 40};
    return v[0] + v[1] + v[2];
}

int main() {
    constexpr int result = sum_first_three();  // compile-time
    std::cout << result << '\n';
}
```

**Expected Output**
```
60
```

**Why this output?**  
C++20 allows `std::vector` in constant evaluation; the allocation is transient and deallocated before the function returns.

### Real-World Cases

- **Compile-time tables** – generating lookup tables with `std::vector`.
- **Compile-time parsing** – parsing strings at compile time.
- **Metaprogramming** – simplifying complex `constexpr` computations.

## 8. `consteval`

### Definitions

**Core Definition**
`consteval` declares an *immediate function*: every call to it must produce a compile-time constant.

**Technical Definition**
A function declared `consteval` (P1073R3) is an immediate function. Every potentially-evaluated call must directly or indirectly produce a constant expression. `consteval` implies `inline` and is a stricter form of `constexpr`. Calling a `consteval` function with a non-constant argument is ill-formed.

**Beginner-Friendly Explanation**
`consteval` means “this function must run at compile time, always.” You cannot call it with runtime values.

### Purposes

- To enforce compile-time evaluation.
- To guarantee that certain computations are always done at compile time.
- To catch errors at compile time.

### Syntax Rules and Structure

**General Syntax**
```cpp
consteval int square(int x) { return x * x; }
constexpr int r = square(5);        // OK
// int y = square(runtime_value);    // error
```

**Component Breakdown**

| Specifier | Guarantee |
|-----------|-----------|
| `consteval` | Every call must be a constant expression. |
| `constexpr` | Can be evaluated at compile time or runtime. |

**Syntax Rules**
- `consteval` cannot be combined with `constexpr`.
- All redeclarations must also be `consteval`.
- Cannot be applied to destructors, allocation functions, or deallocation functions.

**Constraints and Limitations**
- Cannot be called with runtime arguments.
- Pointers/references to immediate functions cannot escape constant evaluation.

### Annotated Code Example

```cpp
#include <iostream>

consteval int factorial(int n) {
    int result = 1;
    for (int i = 2; i <= n; ++i) result *= i;
    return result;
}

int main() {
    constexpr int f5 = factorial(5);
    std::cout << f5 << '\n';           // 120
    // factorial(5);                   // error if used as runtime call in some contexts
}
```

**Expected Output**
```
120
```

**Why this output?**  
`factorial(5)` is a constant expression and is evaluated at compile time; `f5` is a compile-time constant.

### Real-World Cases

- **Compile-time validation** – ensuring constants are computed at compile time.


**Component Breakdown**

| Operation | Description |
|-----------|-------------|

## 22. `std::latch`

### Definitions

**Core Definition**
`std::latch` is a single-use thread synchronisation primitive that blocks threads until a counter reaches zero.

**Technical Definition**
`std::latch` (C++20) is a downward counter. Threads can decrement the counter via `count_down()` and wait until it reaches zero via `wait()` or `arrive_and_wait()`. Once the counter reaches zero, all waiting threads are released, and the latch cannot be reused.

**Beginner-Friendly Explanation**
A latch is like a starting gate: it stays closed until a set number of arrivals have occurred, then opens for everyone.

### Purposes

- To synchronise a fixed number of tasks.
- To implement one-time barriers.
- To coordinate startup and shutdown.

### Syntax Rules and Structure

**General Syntax**
```cpp
#include <latch>
std::latch latch(n);
latch.count_down();
latch.wait();
latch.arrive_and_wait();
```

**Component Breakdown**

| Operation | Description |
|-----------|-------------|
| `count_down()` | Decrements the counter. |
| `wait()` | Blocks until the counter is zero. |
| `arrive_and_wait()` | Decrements and waits. |

**Syntax Rules**
- The counter is initialised at construction.
- Once zero, the latch stays open.

**Constraints and Limitations**
- Single-use; cannot be reset.

### Annotated Code Example

```cpp
#include <latch>
#include <thread>
#include <iostream>
#include <vector>

std::latch latch(3);

void worker(int id) {
    std::cout << "Worker " << id << " ready\n";
    latch.arrive_and_wait();
    std::cout << "Worker " << id << " running\n";
}

int main() {
    std::vector<std::thread> threads;
    for (int i = 0; i < 3; ++i)
        threads.emplace_back(worker, i);
    for (auto& t : threads) t.join();
}
```

**Expected Output** (order may vary)
```
Worker 0 ready
Worker 1 ready
Worker 2 ready
Worker 0 running
Worker 1 running
Worker 2 running
```

**Why this output?**  
All three workers call `arrive_and_wait()`; the latch releases them only after all three have arrived.

### Real-World Cases

- **Startup synchronisation** – waiting for all subsystems to initialise.
- **Parallel test setup** – ensuring all fixtures are ready.
- **One-shot barriers** – releasing threads after a fixed count.

## 23. `std::barrier`

### Definitions

**Core Definition**
`std::barrier` is a reusable thread synchronisation primitive that blocks a set of threads at a common point until all have arrived.

**Technical Definition**
`std::barrier` (C++20) is a reusable barrier. Threads arrive via `arrive_and_wait()` (or `arrive()` and `wait()`), and when the required number of threads have arrived, the barrier resets for the next phase. A completion function can be invoked at the end of each phase.

**Beginner-Friendly Explanation**
A barrier is like a meeting point: everyone must arrive before the group can proceed, and it can be used again for the next stage.

### Purposes

- To synchronise iterative parallel algorithms.
- To implement multi-phase computations.
- To coordinate repeated rendezvous points.

### Syntax Rules and Structure

**General Syntax**

**Component Breakdown**

| Operation | Description |
|-----------|-------------|
| `arrive()` | Signals arrival without waiting. |
| `wait()` | Waits for the current phase to complete. |
| `arrive_and_wait()` | Arrives and waits. |

**Syntax Rules**
- The barrier is reusable.
- A completion function can be supplied.

**Constraints and Limitations**
- The number of participating threads is fixed.

### Annotated Code Example

```cpp
#include <barrier>
```

```
Worker 1 phase 0
Worker 2 phase 0
Worker 0 phase 1
Worker 1 phase 1
Worker 2 phase 1
```

**Why this output?**  
All workers synchronise at the barrier between phases; no worker can enter phase 1 until all have completed phase 0.

### Real-World Cases

- **Iterative solvers** – synchronising phases of a numerical algorithm.
- **Simulation steps** – advancing time steps in lockstep.
- **Parallel pipelines** – stage-by-stage synchronisation.

This makes the intent of the interface clearer to both the compiler and the programmer.

**Beginner-Friendly Explanation**
`[[nodiscard("reason")]]` tells the compiler: “If the caller ignores my return value, warn them, and include this explanation.”

### Purposes

- To warn about ignored return values with a custom message.
- To express the intent of an interface clearly.
- To improve code safety.

### Syntax Rules and Structure

**General Syntax**
```cpp
[[nodiscard("error code must be checked")]]
int risky_operation();
```

**Component Breakdown**

| Component | Description |
|-----------|-------------|
| `[[nodiscard("reason")]]` | Attribute with a reason string. |
| Function declaration | The function whose return value must not be ignored. |

**Syntax Rules**
- The message is a string literal.
- The attribute can be applied to functions, classes, and enums.

**Constraints and Limitations**
- The message is a compiler extension in some implementations; it is standard in C++20.

### Annotated Code Example

```cpp
#include <iostream>

[[nodiscard("check the result, it may fail")]]
int try_parse(const char* s) {
    return s ? 1 : 0;
}

int main() {
    try_parse("hello");                  // warning with message
    int r = try_parse("hello");          // no warning
    std::cout << r << '\n';
}
```

**Expected Output** (warning is compiler-dependent)
```
1
```

**Why this output?**  
The first call discards the return value and triggers a warning with the custom message; the second call uses the result.

### Real-World Cases

- **Error codes** – forcing callers to check status.
- **Resource-returning functions** – preventing leaks.
- **API design** – documenting why the result matters.
