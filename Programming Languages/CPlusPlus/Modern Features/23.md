# C++23 Features — Comprehensive Programming Cheat Sheet

## Topic Overview

### Definitions

**Core Definition**
C++23 (ISO/IEC 14882:2024) is the seventh edition of the ISO C++ standard, published in October 2024. It follows C++20 and focuses on completing, refining, and polishing the “big four” features introduced in C++20—modules, coroutines, ranges, and concepts—while adding a substantial set of practical library and language utilities that significantly improve day-to-day C++ programming.

**Technical Definition**
C++23 is formally known as ISO/IEC 14882:2024. The final WG21 working draft is N4950, and technical work was completed in February 2023. It is a “polish and completion” release relative to C++20, fixing many inconveniences and adding highly practical features such as `std::expected`, `std::print`/`std::println`, `std::mdspan`, `std::flat_map`/`std::flat_set`, `std::generator`, deducing `this`, `if consteval`, multidimensional subscript operators, static `operator()`/`operator[]`, and many smaller utilities (`std::to_underlying`, `std::unreachable`, `std::byteswap`, `std::stacktrace`, string `contains`, `resize_and_overwrite`).

**Beginner-Friendly Explanation**
C++23 is the “quality of life” release after the massive C++20 overhaul. If C++20 was a “big bang” (modules, coroutines, concepts, ranges), C++23 is the “smooth and polish” release—it fixes the rough edges C++20 left behind and adds a batch of features you will reach for every single day, like `std::print`, `std::expected`, `std::mdspan`, and a standard stack trace.

### Key Characteristics

- **Error handling without exceptions** – `std::expected` provides a type-safe result-or-error vocabulary type, with monadic chaining (`and_then`, `transform`, `or_else`, `transform_error`) that mirrors `std::optional`’s C++23 monadic operations.
- **Type-safe formatted output** – `std::print` and `std::println` combine `std::format`’s type safety with direct stream output, eliminating the need for `printf` or `cout << format(...)`.
- **Multidimensional views** – `std::mdspan` provides a non-owning N-dimensional view over contiguous memory, decoupling storage from shape and layout.
- **Flat container adaptors** – `std::flat_map` and `std::flat_set` store elements contiguously, improving cache locality at the cost of insertion/erasure performance.
- **Standard stack traces** – `std::stacktrace` provides a portable, standardised way to capture and print the call stack at runtime.
- **Compile-time branching** – `if consteval` makes it possible to write code that behaves differently during constant evaluation, without the awkward `std::is_constant_evaluated()` dance.
- **Multidimensional subscripting** – `operator[]` can now accept multiple arguments (`a[i, j, k]`), eliminating nested `operator[]` calls for multidimensional containers.
- **Static call and subscript operators** – `static operator()` and `static operator[]` allow stateless callables to be invoked without an object, supporting new generic patterns.
- **Standard library modules** – `import std;` imports the entire standard library as a single module, replacing hundreds of `#include` directives.
- **Portable assumptions** – `[[assume(expr)]]` tells the compiler that an expression is always true at a specific point, enabling optimisations without runtime checks.
- **Deducing `this`** – member functions can accept an explicit object parameter (`this auto&& self`), eliminating the need for CRTP in many patterns and enabling recursive lambdas.

### Prerequisites

- Solid understanding of C++20 (concepts, ranges, coroutines, modules, `constexpr`, `std::format`).
- Familiarity with C++17 vocabulary types (`std::optional`, `std::variant`, `std::any`, `std::string_view`).
- Knowledge of templates, move semantics, and exception handling.
- A C++23-compliant compiler (GCC 13+, Clang 17+, MSVC 19.35+ for most features; some library features require newer versions).

### Related Programming Areas

- **Error handling** – `std::expected`, monadic operations, `std::optional` chaining.
- **Data visualisation and numerics** – `std::mdspan`, multidimensional subscripting.
- **Logging and diagnostics** – `std::print`, `std::println`, `std::stacktrace`, `std::source_location`.
- **High-performance containers** – `std::flat_map`, `std::flat_set`.
- **Coroutines** – `std::generator`.
- **Low-level programming** – `std::byteswap`, `std::to_underlying`, `std::unreachable`, `[[assume]]`.
- **Generic programming** – deducing `this`, static operators, `if consteval`.

## 1. `std::expected`

### Definitions

**Core Definition**
`std::expected<T, E>` is a vocabulary type that holds either a value of type `T` (success) or an error of type `E` (failure); it is never valueless.

**Technical Definition**
Defined in `<expected>` since C++23, `std::expected` provides a way to represent either an expected value or an unexpected error. It supports monadic operations (`and_then`, `transform`, `or_else`, `transform_error`) that allow chaining without explicit error checks at every step. It is designed for expected failures—situations where failure is a normal, recoverable outcome rather than an exceptional condition.

**Beginner-Friendly Explanation**
`std::expected` is a box that contains either the answer or the reason it couldn’t produce the answer. You can chain operations on the box, and if an error occurs at any step, the remaining steps are skipped automatically. It is the modern replacement for error codes and nullable returns.

### Purposes

- To return a value or an error from a function in a single, type-safe return type.
- To avoid the overhead and control-flow disruption of exceptions for common, expected failures (e.g., “file not found”, “parse error”).
- To provide monadic chaining for clean, composable error handling.
- To serve as a vocabulary type for functions that commonly fail.

### Syntax Rules and Structure

**General Syntax**
```cpp
#include <expected>

std::expected<int, ParseError> parse_int(std::string_view s) {
    if (s.empty()) return std::unexpected(ParseError::empty_input);
    return 42;
}

auto result = parse_int("123");
if (result) {
    use(*result);
} else {
    handle(result.error());
}
```

**Component Breakdown**

| Member | Description |
|--------|-------------|
| `has_value()` / `operator bool` | Checks whether a value is present. |
| `value()` | Returns the value; throws `std::bad_expected_access` if absent. |
| `operator*` / `operator->` | Unchecked access. |
| `error()` | Returns the error value. |
| `value_or(default)` | Returns the value or a default. |
| `and_then(f)` | Chains a function returning another `expected` (flat-map). |
| `transform(f)` | Maps the value (wraps result in `expected`). |
| `or_else(f)` | Handles the error if present. |
| `transform_error(f)` | Maps the error. |

**Syntax Rules**
- `T` must be `void` or `Destructible`; `E` must be `Destructible`.
- `std::unexpected(error)` constructs the error state.
- Monadic operations short-circuit on error.

**Constraints and Limitations**
- Requires C++23 support (GCC 13+, Clang 17+, MSVC 19.35+).
- `operator*` on an error state is undefined behaviour.

### Annotated Code Example

```cpp
#include <expected>
#include <iostream>
#include <string>

enum class ParseError { empty_input, invalid_format };

std::expected<int, ParseError> parse_int(std::string_view s) {
    if (s.empty()) return std::unexpected(ParseError::empty_input);
    try {
        return std::stoi(std::string(s));
    } catch (...) {
        return std::unexpected(ParseError::invalid_format);
    }
}

int main() {
    auto r1 = parse_int("42");
    if (r1) std::cout << "Value: " << *r1 << '\n';

    auto r2 = parse_int("abc");
    if (!r2) std::cout << "Error code: "
                       << static_cast<int>(r2.error()) << '\n';
}
```

**Expected Output**
```
Value: 42
Error code: 1
```

**Why this output?**  
`parse_int("42")` succeeds and holds the value `42`. `parse_int("abc")` fails with `ParseError::invalid_format` (value `1`), and `!r2` is `true`.

### Real-World Cases

- **Parsing** – returning `expected<T, ParseError>` from parsers.
- **File I/O** – `expected<string, FileError>` for reading files.
- **Configuration loading** – `expected<Config, Error>` with monadic chaining.

## 2. `std::optional` Monadic Operations

### Definitions

**Core Definition**
C++23 adds three monadic operations to `std::optional`—`and_then`, `transform`, and `or_else`—allowing operations that may fail to be chained without nested `if (opt.has_value())` checks.

**Technical Definition**
- `transform(f)`: If engaged, applies `f` to the value and wraps the result in `optional<U>`; if empty, returns empty `optional<U>`.
- `and_then(f)`: If engaged, applies `f` (which returns an `optional`) and returns its result; if empty, returns empty. Flat-maps to avoid `optional<optional<U>>`.
- `or_else(f)`: If engaged, returns `*this`; if empty, calls `f()` and returns its result.

**Beginner-Friendly Explanation**
These three operations let you build clean pipelines on `optional` values. Each step either threads the value forward or short-circuits to empty, so you avoid pyramids of null-checks.

### Purposes

- To chain operations that might fail without nested `if` checks.
- To write flat, readable pipelines instead of pyramids of null-checks.
- To bring functional-programming composition to `std::optional`.
- To mirror the monadic operations on `std::expected`.

### Syntax Rules and Structure

**General Syntax**
```cpp
std::optional<std::string> username = get_user(id);

auto result = username
    .and_then(find_profile)          // optional<Profile>
    .transform(get_avatar_url)       // optional<string>
    .or_else([] { return std::optional<std::string>{"default.png"}; });
```

**Component Breakdown**

| Operation | Signature (simplified) | Behaviour |
|-----------|------------------------|-----------|
| `transform(f)` | `optional<T> -> (T->U) -> optional<U>` | Maps the value if engaged. |
| `and_then(f)` | `optional<T> -> (T->optional<U>) -> optional<U>` | Flat-maps if engaged. |
| `or_else(f)` | `optional<T> -> (()->optional<T>) -> optional<T>` | Fallback if empty. |

**Syntax Rules**
- All three operations short-circuit on empty.
- `and_then` avoids nested optionals.
- `or_else` is the only operation that runs when the optional is empty.

**Constraints and Limitations**
- Requires C++23 library support.

### Annotated Code Example

```cpp
#include <optional>
#include <iostream>
#include <string>

std::optional<int> parse_int(const std::string& s) {
    try { return std::stoi(s); }
    catch (...) { return std::nullopt; }
}

std::optional<double> safe_sqrt(int n) {
    if (n < 0) return std::nullopt;
    return std::sqrt(static_cast<double>(n));
}

int main() {
    std::optional<std::string> input = "49";

    auto result = input
        .and_then(parse_int)          // optional<int>
        .and_then(safe_sqrt)           // optional<double>
        .transform([](double d) { return std::to_string(d); })
        .or_else([] { return std::optional<std::string>{"error"}; });

    if (result) std::cout << *result << '\n';
}
```

**Expected Output**
```
7.000000
```

**Why this output?**  
`"49"` parses to `49`, `safe_sqrt(49)` yields `7.0`, and `transform` converts it to a string. If any step had produced `nullopt`, `or_else` would have supplied `"error"`.

### Real-World Cases

- **Configuration parsing** – chain lookups and transformations.
- **User input validation** – parse, validate, and transform in a single pipeline.
- **Fallback handling** – `or_else` provides defaults when any step fails.

## 3. `std::mdspan`

### Definitions

**Core Definition**
`std::mdspan<T, Extents, LayoutPolicy, AccessorPolicy>` is a non-owning, multidimensional view over a contiguous range of elements—an N-dimensional generalization of `std::span`.

**Technical Definition**
Defined in `<mdspan>` since C++23, `mdspan` decouples storage from shape: the same flat buffer can be viewed as a 2×3 matrix, a 6-element vector, or a column-major 3×2 matrix through different `mdspan` objects pointing at identical memory. Template parameters include `ElementType`, `Extents` (a mix of static and dynamic dimensions), `LayoutPolicy` (default `layout_right`, row-major), and `AccessorPolicy`.

**Beginner-Friendly Explanation**
`mdspan` lets you treat a flat array or vector as a multidimensional grid without copying or reshaping the data. You give it a pointer and dimensions, and you can access elements with row/column indices using the new multidimensional `operator[]`.

### Purposes

- To provide a multidimensional view over contiguous memory without owning it.
- To decouple storage layout from logical shape.
- To support row-major and column-major layouts for interoperability with BLAS/NumPy.
- To enable safe, index-based access to multidimensional data.

### Syntax Rules and Structure

**General Syntax**
```cpp
#include <mdspan>
#include <vector>

std::vector<int> data = {1, 2, 3, 4, 5, 6};
std::mdspan<int, std::extents<int, 2, 3>> m(data.data());

std::cout << m[0, 0] << '\n';      // 1
std::cout << m[1, 2] << '\n';      // 6

std::mdspan<int, std::dextents<int, 2>> dyn(data.data(), 2, 3);
std::cout << dyn[1, 1] << '\n';    // 5
```

**Component Breakdown**

| Parameter | Purpose | Default |
|-----------|---------|---------|
| `ElementType` | Type of elements (e.g., `double`). | — (required) |
| `Extents` | Logical dimensions (static and dynamic). | — (required) |
| `LayoutPolicy` | Memory ordering. | `layout_right` (row-major) |
| `AccessorPolicy` | How elements are read/written. | `default_accessor<ElementType>` |

**Syntax Rules**
- Static extents are encoded in the type; dynamic extents use `std::dextents`.
- `layout_right` is row-major (C/C++ default); `layout_left` is column-major (Fortran/BLAS).
- The multidimensional `operator[]` is a C++23 language feature.

**Constraints and Limitations**
- `mdspan` does not own its data; the underlying buffer must outlive the view.
- Requires `<mdspan>` and C++23 support.

### Annotated Code Example

```cpp
#include <mdspan>
#include <iostream>
#include <vector>

int main() {
    std::vector<int> data = {1, 2, 3, 4, 5, 6};

    // Static extents: 2 rows × 3 columns, row-major
    std::mdspan<int, std::extents<int, 2, 3>> m(data.data());
    std::cout << m[0, 0] << '\n';      // 1
    std::cout << m[1, 2] << '\n';      // 6

    // Dynamic extents
    std::mdspan<int, std::dextents<int, 2>> dyn(data.data(), 2, 3);
    std::cout << dyn[1, 1] << '\n';    // 5
}
```

**Expected Output**
```
1
6
5
```

**Why this output?**  
The 2×3 row-major view maps logical `[0,0]` to `data[0]`, `[1,2]` to `data[5]`, and `[1,1]` to `data[4]`.

### Real-World Cases

- **Numerical computing** – interfacing with BLAS/LAPACK and NumPy arrays.
- **Image processing** – viewing flat pixel buffers as 2D/3D grids.
- **Scientific simulation** – multidimensional data without copying.

## 4. `std::flat_map` / `std::flat_set`

### Definitions

**Core Definition**
`std::flat_map` and `std::flat_set` are container adaptors introduced in C++23 that store elements in a sorted, contiguous container (typically `std::vector`), improving cache locality compared to node-based `std::map`/`std::set`.

**Technical Definition**
Defined in `<flat_map>` and `<flat_set>`, these adaptors keep their elements sorted and contiguous. Lookup is O(log n) via binary search, insertion/erasure is O(n) due to shifting, and iteration is cache-friendly. They also come in `flat_multimap` and `flat_multiset` variants.

**Beginner-Friendly Explanation**
`flat_map` and `flat_set` behave like `map` and `set`, but they store their elements side-by-side in a contiguous block instead of in separately allocated tree nodes. This makes lookups and iteration much faster in practice because the CPU cache loves contiguous memory, but insertion and deletion are slower because elements must shift.

### Purposes

- To provide sorted associative containers with better cache locality than node-based containers.
- To speed up lookups and iteration for read-heavy workloads.
- To reduce memory overhead compared to red-black trees.
- To offer a drop-in replacement for `std::map`/`std::set` when insertion/erasure is infrequent.

### Syntax Rules and Structure

**General Syntax**
```cpp
#include <flat_map>
#include <flat_set>

std::flat_map<int, std::string> fm;
fm[1] = "one";

std::flat_set<int> fs = {3, 1, 2};   // sorted: 1, 2, 3
```

**Component Breakdown**

| Container | Stores | Lookup | Insert/Erase |
|-----------|--------|--------|--------------|
| `flat_map` | key-value pairs | O(log n) | O(n) |
| `flat_set` | keys | O(log n) | O(n) |
| `flat_multimap` | duplicate keys allowed | O(log n) | O(n) |
| `flat_multiset` | duplicate keys allowed | O(log n) | O(n) |

**Syntax Rules**
- Elements are kept sorted at all times.
- The underlying container is typically `std::vector`.
- Many functions are `constexpr` (as of C++23 proposals).

**Constraints and Limitations**
- Insertion and erasure are O(n), unlike O(log n) for `std::map`/`std::set`.
- Requires `<flat_map>`/`<flat_set>` and C++23 support (GCC 15+, newer Clang/MSVC).

### Annotated Code Example

```cpp
#include <flat_map>
#include <iostream>
#include <string>

int main() {
    std::flat_map<int, std::string> fm;
    fm[3] = "three";
    fm[1] = "one";
    fm[2] = "two";

    for (const auto& [k, v] : fm)
        std::cout << k << ": " << v << '\n';
}
```

**Expected Output**
```
1: one
2: two
3: three
```

**Why this output?**  
`flat_map` keeps its elements sorted by key, so iteration visits `1, 2, 3` in order.

### Real-World Cases

- **Read-heavy lookup tables** – configuration maps, symbol tables.
- **Cache-sensitive applications** – game engines, real-time systems.
- **Small-to-medium datasets** – where O(n) insertion cost is acceptable.

## 5. `std::stacktrace`

### Definitions

**Core Definition**
`std::stacktrace` is a standardised class for capturing and inspecting the current call stack at runtime, providing a portable alternative to platform-specific backtrace APIs.

**Technical Definition**
Defined in `<stacktrace>` since C++23, `std::stacktrace::current()` captures the call stack as a sequence of `stacktrace_entry` objects. Each entry provides `description()`, `source_file()`, and `source_line()` (when debug symbols are available). The entire trace can be streamed directly to an output stream.

**Beginner-Friendly Explanation**
`std::stacktrace` lets you capture the “call history” that led to a particular point in your program—useful for logging, assertions, and exception diagnostics—without writing platform-specific code for Linux, Windows, and macOS separately.

### Purposes

- To capture the current call stack portably.
- To log stack traces alongside error messages.
- To embed stack traces in exception types for post-mortem analysis.
- To replace platform-specific `backtrace()` / `CaptureStackBackTrace()` calls.

### Syntax Rules and Structure

**General Syntax**
```cpp
#include <stacktrace>
#include <iostream>

void log_error(const std::string& msg) {
    auto trace = std::stacktrace::current();
    std::cerr << "ERROR: " << msg << "\n"
              << "Stack trace:\n" << trace << "\n";
}
```

**Component Breakdown**

| Member | Description |
|--------|-------------|
| `current()` | Captures the current stack trace. |
| `size()` | Number of frames. |
| `operator[]` | Accesses a specific frame. |
| `description()` | Function name (if available). |
| `source_file()` | Source file name (if available). |
| `source_line()` | Source line number (if available). |

**Syntax Rules**
- `current()` is a static function.
- The trace can be streamed directly to `std::ostream`.
- Debug symbols improve the quality of the output.

**Constraints and Limitations**
- Requires debug symbols for full function/file/line information.
- May require linking with `-lstacktrace` or similar (implementation-dependent).
- Requires C++23 support.

### Annotated Code Example

```cpp
#include <stacktrace>
#include <iostream>
#include <string>

void inner_function() {
    auto trace = std::stacktrace::current();
    std::cout << "Stack trace:\n" << trace << "\n";
}

void outer_function() { inner_function(); }

int main() { outer_function(); }
```

**Expected Output** (with debug symbols)
```
Stack trace:
 0# inner_function() at main.cpp:5
 1# outer_function() at main.cpp:10
 2# main at main.cpp:12
```

**Why this output?**  
`std::stacktrace::current()` captures the call chain from `main` → `outer_function` → `inner_function`, and the stream operator prints each frame with its function name and source location.

### Real-World Cases

- **Error logging** – attaching a stack trace to error messages.
- **Custom assertions** – printing the call stack on assertion failure.
- **Exception diagnostics** – embedding a trace in exception objects at the throw site.

## 6. `std::print` / `std::println`

### Definitions

**Core Definition**
`std::print` and `std::println` are type-safe, formatted output functions that write directly to a stream (default: stdout) without creating an intermediate string.

**Technical Definition**
Defined in `<print>` since C++23, these functions combine the type safety of `std::format` with direct stream output. `std::print(fmt, args...)` writes formatted output without a trailing newline; `std::println(fmt, args...)` appends a newline. Both support the same format specifications as `std::format` and can write to a specified stream (e.g., `stderr`).

**Beginner-Friendly Explanation**
`std::print` and `std::println` are the modern replacement for `printf` and `std::cout`. You write `std::println("Hello, {}!", name)` and get type-safe, readable, fast output in one line.

### Purposes

- To replace `printf` with type-safe formatting.
- To replace verbose `std::cout << ... << std::endl` chains.
- To provide compile-time-checked format strings.
- To improve performance by avoiding intermediate strings.

### Syntax Rules and Structure

**General Syntax**
```cpp
#include <print>

std::print("x = {}, y = {}\n", x, y);
std::println("Hello, {}!", name);
std::println(stderr, "Error: {}", msg);
```

**Component Breakdown**

| Function | Behaviour |
|----------|-----------|
| `std::print(fmt, args...)` | Writes formatted output without newline. |
| `std::println(fmt, args...)` | Writes formatted output with newline. |
| `std::print(stream, fmt, args...)` | Writes to a specific stream. |

**Syntax Rules**
- Format strings use `{}` placeholders (same as `std::format`).
- Format strings are checked at compile time.
- Unicode (UTF-8) is handled correctly.

**Constraints and Limitations**
- Requires C++23 `<print>` support (GCC 14+, Clang 18+, MSVC 19.37+).

### Annotated Code Example

```cpp
#include <print>
#include <string>

int main() {
    std::println("Hello, {}!", "world");
    std::println("x = {}, pi = {:.2f}", 42, 3.14159);
    std::print("No newline here. ");
    std::println("But here.");

    std::println("|{:<10}|{:>10}|{:^10}|", "left", "right", "center");
    std::println("dec={0} hex={0:#x} bin={0:#b}", 255);
}
```

**Expected Output**
```
Hello, world!
x = 42, pi = 3.14
No newline here. But here.
|left      |     right|  center  |
dec=255 hex=0xff bin=0b11111111
```

**Why this output?**  
`{}` inserts the argument; `{:.2f}` formats to two decimals; alignment specifiers control width and fill; `{0:#x}` reuses the first argument in hex format.

### Real-World Cases

- **Logging** – structured, type-safe log messages.
- **Command-line tools** – fast, readable output.
- **Replacing `printf`** – eliminating format-string vulnerabilities.

## 7. `std::format` Improvements

### Definitions

**Core Definition**
C++23 extends `std::format` with additional formatting capabilities, including range formatting and improved support for custom types.

**Technical Definition**
C++23 adds `__cpp_lib_format_ranges` (P2585R1), enabling formatting of ranges and tuples. It also improves support for formatting `volatile`-qualified types (P1147R1) and adds other refinements to the formatting library.

**Beginner-Friendly Explanation**
`std::format` gets even better in C++23—you can now format entire ranges and tuples directly, and some previously awkward types are handled more smoothly.

### Purposes

- To format ranges and tuples directly.
- To improve the expressiveness of `std::format`.
- To support more types out of the box.

### Syntax Rules and Structure

**General Syntax**
```cpp
#include <format>
#include <vector>

std::vector<int> v = {1, 2, 3};
std::string s = std::format("{}", v);   // formatted range
```

**Component Breakdown**

| Improvement | Description |
|-------------|-------------|
| Range formatting | Ranges can be formatted directly. |
| Tuple formatting | Tuples can be formatted directly. |
| `volatile` support | Improved handling of `volatile` types. |

**Syntax Rules**
- Requires `<format>` and C++23 support.

**Constraints and Limitations**
- Requires updated standard library support.

### Annotated Code Example

```cpp
#include <format>
#include <iostream>
#include <vector>

int main() {
    std::vector<int> v = {1, 2, 3};
    std::cout << std::format("Range: {}\n", v);
}
```

**Expected Output**
```
Range: [1, 2, 3]
```

**Why this output?**  
C++23’s range formatting support allows a `std::vector` to be formatted directly.

### Real-World Cases

- **Logging ranges** – printing collections without manual loops.
- **Debugging** – quickly inspecting container contents.

## 8. `if consteval`

### Definitions

**Core Definition**
`if consteval` is a compile-time conditional statement that executes one branch during constant evaluation and another at runtime, without requiring `std::is_constant_evaluated()`.

**Technical Definition**
Introduced in C++23, `if consteval { ... } else { ... }` evaluates the first branch if the enclosing function is being evaluated in a constant expression, and the `else` branch otherwise. It replaces the awkward `if (std::is_constant_evaluated())` pattern and is more readable and less error-prone.

**Beginner-Friendly Explanation**
`if consteval` lets a function ask “am I running at compile time?” and choose a different code path accordingly, with clean syntax.

### Purposes

- To provide a clean syntax for compile-time vs. runtime branching.
- To replace `std::is_constant_evaluated()`.
- To write functions that behave differently during constant evaluation.

### Syntax Rules and Structure

**General Syntax**
```cpp
constexpr int f(int x) {
    if consteval {
        return x * 2;          // compile-time path
    } else {
        return x * 3;          // runtime path
    }
}
```

**Component Breakdown**

| Branch | Executed When |
|--------|---------------|
| `if consteval { ... }` | Constant evaluation. |
| `else { ... }` | Runtime evaluation. |

**Syntax Rules**
- `if consteval` can only appear inside a function.
- The condition is implicit (no expression).
- `if !consteval` is also supported (C++23).

**Constraints and Limitations**
- Requires C++23 support.

### Annotated Code Example

```cpp
#include <iostream>

    if consteval {
        return x * 2;
    } else {
        return x * 3;
    }
}

int main() {
    constexpr int a = compute(5);   // compile-time: 10
    int b = compute(5);             // runtime: 15
    std::cout << a << ' ' << b << '\n';
}
```

**Expected Output**
```
10 15
```

**Why this output?**  
The compile-time call takes the first branch (`5 * 2 = 10`); the runtime call takes the second (`5 * 3 = 15`).

### Real-World Cases

- **Compile-time optimisations** – using faster algorithms when evaluated at compile time.
- **Constant-evaluation safety** – avoiding runtime-only operations in `constexpr` functions.

## 20. Deducing `this`

### Definitions

**Core Definition**
Deducing `this` (explicit object parameter) allows a member function to declare its object parameter explicitly as `this auto&& self`, enabling the compiler to deduce the actual type of the object—including derived types—without CRTP.

**Technical Definition**
Introduced in C++23 (P0847R7), deducing `this` makes the implicit `this` pointer explicit. The explicit object parameter must be the first parameter and is written as `this auto&& self` (or `this T& self`). It eliminates the need for the Curiously Recurring Template Pattern (CRTP) in many cases and enables recursive lambdas.

**Beginner-Friendly Explanation**
Deducing `this` lets a member function know the exact type of the object it is called on, including derived types, without complicated template tricks. It also lets you write recursive lambdas more easily.

### Purposes

- To eliminate CRTP in many common patterns.
- To enable recursive lambdas.
- To simplify generic member functions.
- To provide a cleaner way to write mixins and policy-based designs.

### Syntax Rules and Structure

**General Syntax**
```cpp
struct Base {
    void name(this auto&& self) {
        self.impl();
    }
};
```

**Component Breakdown**

| Component | Description |
|-----------|-------------|
| `this auto&& self` | Explicit object parameter. |
| `self` | The deduced object (preserves value category). |

**Syntax Rules**
- The explicit object parameter must be the first parameter.
- It can be `auto&&`, `auto&`, or a concrete type.
- It replaces the implicit `this`.

**Constraints and Limitations**
- Requires C++23 support.

### Annotated Code Example

```cpp
#include <iostream>

struct Base {
    void name(this auto&& self) {
        self.impl();
    }
};

struct Derived : Base {
    void impl() { std::cout << "Derived::impl\n"; }
};

int main() {
    Derived d;
    d.name();       // calls Derived::impl
}
```

**Expected Output**
```
Derived::impl
```

**Why this output?**  
`name` deduces `self` as `Derived&`, so `self.impl()` calls `Derived::impl`—no CRTP required.

### Real-World Cases

- **Mixin classes** – injecting behaviour without CRTP.
- **Recursive lambdas** – writing self-referential lambdas cleanly.
- **Generic libraries** – simplifying member function templates.

## 21. `constexpr` Improvements

### Definitions

**Core Definition**
C++23 further relaxes the rules for `constexpr` functions and variables, allowing more code to be evaluated at compile time.

**Technical Definition**
C++23 (P2242R3, P2647R1) permits non-literal variables, labels, and `goto` statements in `constexpr` functions as long as they are not evaluated during constant evaluation. It also allows `static` and `thread_local` variables usable in constant expressions inside `constexpr` functions, and permits a function to be declared `constexpr` even if no invocation satisfies the constant-expression requirements.

**Beginner-Friendly Explanation**
C++23 makes `constexpr` even more permissive: you can now use `goto`, labels, and non-literal variables in `constexpr` functions, as long as the compile-time evaluation never actually reaches them.

### Purposes

- To allow more natural code in `constexpr` functions.
- To remove arbitrary restrictions that made `constexpr` programming awkward.
- To support compile-time evaluation of a wider range of programs.

### Syntax Rules and Structure

**General Syntax**
```cpp
constexpr int f(int x) {
    if (std::is_constant_evaluated()) {
        goto label;        // OK in C++23 if not reached at compile time
    }
    return x;
label:
    return -1;
}
```

**Component Breakdown**

| Relaxation | Description |
|------------|-------------|
| Non-literal variables | Allowed if not evaluated at compile time. |
| Labels and `goto` | Allowed if not evaluated at compile time. |
| `static` / `thread_local` | Allowed if usable in constant expressions. |
| Non-satisfying `constexpr` | A function can be `constexpr` even if no invocation is constant. |

**Syntax Rules**
- The restrictions apply only to the constant-evaluation path.
- The function must still be valid C++.

**Constraints and Limitations**
- Requires C++23 support.

### Annotated Code Example

```cpp
#include <iostream>

constexpr int f(int x) {
    if (x > 0) return x * 2;
    goto skip;
    return x;
skip:
    return -1;
}

int main() {
    constexpr int a = f(5);        // compile-time: 10
    int b = f(-5);                 // runtime: -1
    std::cout << a << ' ' << b << '\n';
}
```

**Expected Output**
```
10 -1
```

**Why this output?**  
The compile-time path takes the `x > 0` branch and never reaches the `goto`; the runtime path reaches the label and returns `-1`.

### Real-World Cases

- **Compile-time parsing** – more natural control flow in `constexpr` code.
- **Generic libraries** – relaxing unnecessary restrictions.
