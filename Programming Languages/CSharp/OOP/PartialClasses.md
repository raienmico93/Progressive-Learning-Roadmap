# C# Partial Classes — Comprehensive Programming Cheat Sheet

---

## Topic Overview

### Definitions

**Core Definition**
A **partial class** is a class whose definition is split across **two or more source files**. Each file contains a section of the class—fields, methods, properties, events, or nested types—and the C# compiler **combines all parts into a single type at compile time**. The `partial` keyword is the mechanism that enables this splitting. Partial classes are the foundation for **tool-generated code** (designers, source generators) and for **team collaboration** on large types, because one file can be machine-generated while another is hand-written without either overwriting the other.

**Technical Definition**
The `partial` keyword modifier indicates that other parts of the class, struct, or interface can be defined in the namespace. All parts must use the `partial` keyword, must be available at compile time, and must have the same accessibility. If any part is declared `abstract`, the whole type is abstract; if any part is `sealed`, the whole type is sealed; if any part declares a base class, the whole type inherits that class. Members declared in any partial part are available to all other parts. Partial **methods** allow a declaring declaration (without body) and an implementing declaration (with body) to be separated across parts; if no implementing declaration exists for an *optional* partial method, the compiler removes both the declaration and all its invocations. **Source generators** (Roslyn `IIncrementalGenerator`) are the modern tool that generates partial-class members at compile time, enabling patterns such as `[GeneratedRegex]` and `[LoggerMessage]`.

**Beginner-Friendly Explanation**
A partial class is a **class split across multiple files**. Imagine writing a book with chapters in separate documents—each file holds part of the story, and when you compile, C# binds them into one complete book. This is essential when one part of the class is **generated by a tool** (like a visual designer or a source generator) and another part is **written by you**. You put your custom code in your file, the tool puts its generated code in its file, and neither overwrites the other. Partial **methods** work like **optional hooks**: one file declares “this hook exists,” and another file may or may not provide the implementation. If nobody implements the hook, the compiler quietly removes it—zero cost.

---

### Key Characteristics

- **Multi-file type definition** — A class, struct, or interface can be split across multiple source files, all marked `partial`.
- **Compile-time merging** — All parts must be available at compile time and are combined into one type.
- **Uniform accessibility** — All parts must have the same accessibility (e.g., all `public` or all `internal`).
- **Attribute merging** — Attributes on partial type definitions are merged in unspecified order; duplicates are not removed.
- **Base class and interface union** — Parts can specify different base interfaces; the final type implements all of them. Base-class specifications must agree.
- **Partial methods** — Allow a declaring declaration (no body) and an implementing declaration (with body) to live in separate parts; optional partial methods are removed if unimplemented.
- **Source-generator integration** — Partial types and members are the primary surface through which Roslyn source generators add code.
- **Version evolution** — C# 9 added required partial methods (non-void, with access modifiers); C# 13 added partial properties and indexers; C# 14 adds partial constructors and events.

- Knowledge of attributes and assembly-level compilation.
- Awareness of source generators and the Roslyn compiler platform (for the source-generator section).
- Understanding of `void` return types and `out` parameters (for partial method rules).

### Related Programming Areas

- **Tool-generated code** — Windows Forms designers, WPF `InitializeComponent`, and source generators all rely on partial classes.
- **Source generators** — Roslyn incremental generators emit partial-class members at compile time.
- **Team collaboration** — Multiple developers can work on different parts of the same type.
- **Code organisation** — Large types can be split into focused files by responsibility.
- **Interceptors and code weaving** — Partial methods provide hooks that generated code can implement.

## 1. Partial Classes (Overarching Concept)

### Definitions

**Core Definition**
A partial class is a class whose definition is divided across multiple source files, each marked with the `partial` keyword, and merged by the compiler into a single type.

**Technical Definition**
It is possible to split the definition of a class, a struct, an interface, or a member over two or more source files. Each source file contains a section of the type or member definition, and all parts are combined when the application is compiled. The `partial` keyword indicates that other parts of the class, struct, or interface can be defined in the namespace. All parts must use the `partial` keyword and must be available at compile time to form the final type.

**Beginner-Friendly Explanation**
A partial class is a **class written in pieces**. Each piece lives in its own file, and the compiler glues them together.

---

### Purposes

- To enable **multiple developers** to work on the same class simultaneously.
- To separate **tool-generated code** from **hand-written code** without one overwriting the other.
- To let **source generators** add members to a class declared by the developer.
- To organise **large classes** into manageable files by responsibility.
- To support **designer-generated code** (Windows Forms, Web services) alongside custom logic.

---

### Syntax Rules and Structure

```
// File 1: Employee_Part1.cs
public partial class Employee
{
    public void DoWork() { /* ... */ }
}

// File 2: Employee_Part2.cs
public partial class Employee
{
    public void GoToLunch() { /* ... */ }
}
```

**Component breakdown**

- `partial` — The modifier indicating the class is split.
- `class` / `struct` / `interface` — The kind of type being split.
- `Employee` — The type name; must be identical across all parts.
- Each part contains a subset of the type’s members.

#### Syntax Rules

- All parts must use the `partial` keyword.
- All parts must be available at compile time.
- All parts must have the same accessibility (e.g., all `public` or all `internal`).
- If any part is `abstract`, the whole type is abstract; if any part is `sealed`, the whole type is sealed.
- If any part declares a base class, the whole type inherits that class; base-class specifications must agree.
- Parts can specify different base interfaces; the final type implements all of them.
- Members declared in any part are available to all other parts.
- The `partial` modifier is not available on delegate or enumeration declarations.
- Nested types can be partial even if the containing type is not partial.
- Attributes of partial-type definitions are merged.

#### Constraints and Limitations

- All parts must be in the same assembly and module.
- Type name and generic type parameters must match exactly across parts.
- The compiler does not enforce that partial parts are in separate files; they can be in the same file (though this defeats the purpose).

---

### Annotated Code Examples and Expected Outputs

#### Example 1: Splitting a Class Across Two Files

```csharp
// File: Employee_Part1.cs
using System;

public partial class Employee
{
    public void DoWork() => Console.WriteLine("Employee is working.");
}

// File: Employee_Part2.cs
public partial class Employee
{
    public void GoToLunch() => Console.WriteLine("Employee is at lunch.");
}

// File: Program.cs
class Program
{
    static void Main()
    {
        Employee emp = new Employee();
        emp.DoWork();      // Employee is working.
        emp.GoToLunch();   // Employee is at lunch.
    }
}
```

**Expected Output**

```
Employee is working.
Employee is at lunch.
```

**Why this output occurs**

- The compiler merges `Employee_Part1.cs` and `Employee_Part2.cs` into a single `Employee` type. Both methods are available on the merged type.

---

#### Example 2: Merging Attributes and Interfaces

```csharp
// File A
[Serializable]
public partial class Document : IComparable
{
    public int CompareTo(object obj) => 0;
}

// File B
[Obsolete("Use NewDocument")]
public partial class Document : IDisposable
{
    public void Dispose() { }
}

class Program
{
    static void Main()
    {
        var doc = new Document();
        // The merged type has both [Serializable] and [Obsolete], and implements both
        // IComparable and IDisposable.
    }
}
```

**Expected Output**

```
(no output; compiles successfully)
```

**Why this output occurs**

- Attributes from all parts are merged, and the final type implements the union of all base interfaces.

### Real-World Cases

- **Windows Forms** — `Form1.cs` (your code) and `Form1.Designer.cs` (generated designer code) are partial parts of the same form class.
- **ASP.NET Razor** — Generated Razor code and code-behind files are partial parts of the same page class.
- **Source generators** — `[GeneratedRegex]` generates a partial method implementation in a separate file.
- **Large domain entities** — Splitting a large entity into `Customer.cs`, `Customer.Validation.cs`, `Customer.Mapping.cs`, etc.

## 2. `partial` Keyword

### Definitions

**Core Definition**
The `partial` keyword is a contextual modifier that signals to the compiler that the type (or member) being declared is one part of a multi-file definition.

**Technical Definition**
The `partial` modifier can only appear immediately before the keywords `class`, `struct`, or `interface` (and, since C# 13, before `record` and `record struct`; since C# 14, before `event` and instance constructors). It is a **contextual keyword**—it is only a keyword in the context of a type or member declaration. All parts of the same type must use the `partial` keyword.

**Beginner-Friendly Explanation**
`partial` is the **“this is one piece”** marker. You put it before `class`, `struct`, or `interface` to tell the compiler “another file also contributes to this type.”

---

### Purposes

- To mark a type declaration as one part of a multi-file type.
- To enable the compiler to merge parts into a single type.
- To distinguish partial declarations from ordinary declarations.

---

### Syntax Rules and Structure

```
partial class ClassName { ... }
partial struct StructName { ... }
partial interface IInterfaceName { ... }
partial record RecordName(...) { ... }
```

**Component breakdown**

- `partial` — The contextual modifier.
- `class` / `struct` / `interface` / `record` — The type kind.
- `Name` — The type identifier.

#### Syntax Rules

- The `partial` modifier can appear immediately before `class`, `struct`, or `interface`.
- All parts of the same type must use `partial`.
- Nested partial types are allowed.
- The modifier is not available on delegate or enumeration declarations.

#### Constraints and Limitations

- `partial` cannot be used on constructors, finalizers, overloaded operators, property declarations, or event declarations **prior to C# 13/14** (properties and indexers were added in C# 13; constructors and events in C# 14).

---

### Annotated Code Examples and Expected Outputs

#### Example: Partial Keyword on Class and Struct

```csharp
using System;

partial class Outer
{
    partial struct Inner   // nested partial struct is allowed
    {
        public int Value;
    }
}

partial class Outer
{
    public void UseInner()
    {
        var inner = new Inner { Value = 42 };
        Console.WriteLine(inner.Value);   // 42
    }
}

class Program
{
    static void Main()
    {
        new Outer().UseInner();   // 42
    }
}
```

**Expected Output**

```
42
```

**Why this output occurs**

- The nested `Inner` struct is partial and is merged; `Outer` uses it across parts.

---

### Real-World Cases

- **Every partial type declaration** — The keyword is mandatory for multi-file types.

## 3. Partial Methods (Optional and Required)

### Definitions

**Core Definition**
A **partial method** is a method whose declaration and implementation can be split across different parts of a partial type. If the implementing declaration is missing for an **optional** partial method, the compiler removes the declaration and all its invocations.

**Technical Definition**
There are two variations of partial methods: **required** and **optional**. A **required** partial method (§15.6.9.3) includes one or more explicit access modifiers; both the defining and implementing declarations **must exist**. An **optional** partial method (§15.6.9.2) has no explicit access modifiers, is implicitly `private`, and **does not require an implementing declaration**. Only a defining partial method participates in overload resolution. If an implementing declaration exists, invocations are retained; if not, the compiler removes the declaring declaration and all invocations at compile time.

**Beginner-Friendly Explanation**
A partial method is an **optional hook**. One part of the class says “this hook exists.” Another part may provide the implementation. If nobody implements it, the compiler quietly removes the hook—zero cost, no runtime overhead.

---

### Purposes

- To allow **generated code** to call methods that may or may not be implemented by the developer.
- To provide **extension hooks** without forcing implementation.
- To enable **source generators** to emit calls to optional customisation methods.
- To support **code weaving** and interception patterns.
- To keep generated code decoupled from hand-written code.

---

### Syntax Rules and Structure

```
// Defining declaration (no body)
partial void OnNameChanging(string newName);

// Implementing declaration (with body)
partial void OnNameChanging(string newName) { /* ... */ }
```

**Component breakdown**

- `partial` — The modifier.
- `void` — Optional partial methods must return `void`.
- `OnNameChanging` — The method name.
- `(string newName)` — Parameters; no `out` parameters allowed for optional partial methods.

#### Syntax Rules

- **Optional partial methods** must:
  - Have no access modifiers (implicitly `private`).
  - Return `void`.
  - Have no `out` parameters.
  - Have no `virtual`, `override`, `sealed`, `new`, or `extern` modifiers.
  - Have zero or one implementing declaration.
- **Required partial methods** have explicit access modifiers and must have both defining and implementing declarations.
- The `partial` keyword is not allowed on static constructors, finalizers, or overloaded operators.
- Parameter names in defining and implementing declarations do not need to match, but this can cause surprising behaviour with named arguments.
- Attributes from both declarations are combined (duplicates not removed); default arguments in the implementing declaration are removed.

#### Constraints and Limitations

- Optional partial methods are removed entirely if unimplemented—no IL is emitted.
- Required partial methods force implementation and cannot be omitted.
- Partial methods cannot be `async` prior to C# 9 (async partial methods are allowed in C# 9+).

---

### Annotated Code Examples and Expected Outputs

#### Example 1: Optional Partial Method (Unimplemented)

```csharp
using System;

partial class Customer
{
    private string _name;

    public string Name
    {
        get => _name;
        set
        {
            OnNameChanging(value);
            _name = value;
            OnNameChanged();
        }
    }

    partial void OnNameChanging(string newName);
    partial void OnNameChanged();
}

class Program
{
    static void Main()
    {
        var c = new Customer { Name = "Alice" };
        Console.WriteLine(c.Name);   // Alice
    }
}
```

**Expected Output**

```
Alice
```

**Why this output occurs**

- No implementing declaration exists for the partial methods; the compiler removes the declarations and their invocations. The setter is equivalent to a plain assignment.

---

#### Example 2: Optional Partial Method (Implemented)

```csharp
using System;

partial class Customer
{
    private string _name;

    public string Name
    {
        get => _name;
        set
        {
            OnNameChanging(value);
            _name = value;
            OnNameChanged();
        }
    }

    partial void OnNameChanging(string newName);
    partial void OnNameChanged();
}

partial class Customer
{
    partial void OnNameChanging(string newName) =>
        Console.WriteLine($"Changing {_name} to {newName}");

    partial void OnNameChanged() =>
        Console.WriteLine($"Changed to {_name}");
}

class Program
{
    static void Main()
    {
        var c = new Customer { Name = "Alice" };
        // Output:
        // Changing  to Alice
        // Changed to Alice
    }
}
```

**Expected Output**

```
Changing  to Alice
Changed to Alice
```

**Why this output occurs**

- The implementing declarations are present, so the invocations are retained and the hooks run.

---

#### Example 3: Required Partial Method

```csharp
using System;

partial class Calculator
{
    public partial int Add(int a, int b);   // required: public, returns int
}

partial class Calculator
{
    public partial int Add(int a, int b) => a + b;
}

class Program
{
    static void Main()
    {
        var calc = new Calculator();
        Console.WriteLine(calc.Add(3, 4));   // 7
    }
}
```

**Expected Output**

```
7
```

**Why this output occurs**

- The method has an explicit access modifier (`public`) and a non-`void` return type, making it a **required** partial method; both declarations must exist.

---

- **Source generators** — `[GeneratedRegex]` generates the implementing declaration of a partial method.
- **Logging** — `[LoggerMessage]` generates a partial method implementation that writes structured logs.
- **Designer hooks** — Generated code calls partial methods that developers may implement.
- **ORMs and serializers** — Generated code provides partial method hooks for customisation.

## 4. Source Generators (Roslyn `IIncrementalGenerator`)

### Definitions

**Core Definition**
A **source generator** is a Roslyn component that runs during compilation and **generates C# source code** that is added to the compilation. Source generators commonly emit **partial-class members** that complement developer-written partial declarations, such as `[GeneratedRegex]` implementations, `[LoggerMessage]` logging methods, and serialization metadata.

**Technical Definition**
Source generators are implementations of `Microsoft.CodeAnalysis.IIncrementalGenerator` (the modern, cache-aware API that replaces the legacy `ISourceGenerator`, which is **deprecated**). An incremental generator implements `Initialize(IncrementalGeneratorInitializationContext)`, sets up a pipeline of **syntax providers**, **transform providers**, and **code generators**, and emits source via `context.AddSource(...)`. Incremental generators are **cache-aware and only re-run when inputs change**, making them significantly faster in IDE scenarios. Source generators integrate with partial classes because the generator can emit a partial part that implements members declared in the developer’s partial part.

**Beginner-Friendly Explanation**
A source generator is a **code-writing robot that runs during compilation**. You declare a partial class or partial method with a special attribute, and the generator writes the other half for you. For example, you write `[GeneratedRegex("cat|dog")] private static partial Regex CatOrDog();` and the generator writes the actual regex implementation in a separate file.

---

### Purposes

- To eliminate repetitive boilerplate (regex implementations, logging, serialization).
- To generate code at compile time without runtime reflection overhead.
- To integrate with partial classes and partial methods for a seamless developer experience.
- To enable high-performance, AOT-friendly patterns.
- To provide compile-time diagnostics and error reporting.

---

### Syntax Rules and Structure (Generator Shape)

```
[Generator]
public class MyGenerator : IIncrementalGenerator
{
    public void Initialize(IncrementalGeneratorInitializationContext context)
    {
        // 1. Syntax provider: find candidate nodes
        var candidates = context.SyntaxProvider
            .ForAttributeWithMetadataName(
                "MyAttribute",
                predicate: (node, _) => node is ClassDeclarationSyntax,
                transform: (ctx, _) => /* extract data */);

        // 2. Register source output
        context.RegisterSourceOutput(candidates, (spc, data) =>
        {
            spc.AddSource("GeneratedFile.g.cs", "// generated code");
        });
    }
}
```

**Component breakdown**

- `[Generator]` — Marks the class as a source generator.
- `IIncrementalGenerator` — The modern generator interface (preferred over `ISourceGenerator`).
- `Initialize` — Called once by the host to set up the pipeline.
- `SyntaxProvider` — Discovers candidate syntax nodes.
- `RegisterSourceOutput` — Emits generated source.

#### Syntax Rules

- Generators must be declared in a separate assembly, typically targeting `netstandard2.0`.
- The generator project references `Microsoft.CodeAnalysis.CSharp`.
- `IIncrementalGenerator` is the recommended API; `ISourceGenerator` is deprecated.
- Generated code is added as **partial-class members** when the target type is partial.
- Generated files typically use the `.g.cs` suffix.

#### Constraints and Limitations

- Generators cannot modify existing code; they can only **add** new source.
- Generated code cannot access private members of developer code unless declared in the same partial type.
- Incremental generators must be **deterministic** and **cache-friendly** to avoid IDE performance regressions.

---

### Annotated Code Examples and Expected Outputs

#### Example 1: `[GeneratedRegex]` (Built-in Source Generator)

```csharp
using System;
using System.Text.RegularExpressions;

public partial class RegexExample
{
    [GeneratedRegex("cat|dog", RegexOptions.IgnoreCase)]
    private static partial Regex CatOrDog();

    public static void Main()
    {
        Console.WriteLine(CatOrDog().IsMatch("dog"));   // True
        Console.WriteLine(CatOrDog().IsMatch("bird"));  // False
    }
}
```

**Expected Output**

```
True
False
```

**Why this output occurs**

- The `[GeneratedRegex]` source generator emits the implementing declaration of `CatOrDog()` as a partial method. The developer only writes the declaration; the generator writes the body.

---

#### Example 2: A Minimal Incremental Generator (Skeleton)

```csharp
// Generator project (separate assembly)
using Microsoft.CodeAnalysis;

[Generator]
public class HelloGenerator : IIncrementalGenerator
{
    public void Initialize(IncrementalGeneratorInitializationContext context)
    {
        context.RegisterPostInitializationOutput(ctx =>
            ctx.AddSource("Hello.g.cs", """
                namespace Generated;
                public static class Hello
                {
                    public static string Greet() => "Hello from the generator!";
                }
                """));
    }
}

// Consumer code
using Generated;

class Program
{
    static void Main() => System.Console.WriteLine(Hello.Greet());
}
```

**Expected Output**

```
Hello from the generator!
```

**Why this output occurs**

- The generator emits a `Hello` class into the compilation; the consumer can use it directly.

## 5. Partial Class Best Practices

### Definitions

**Core Definition**
Partial class best practices are the design guidelines that ensure partial classes are used **for the right reasons**, keep generated and hand-written code **separate**, and avoid the fragmentation and confusion that overuse can cause.

**Technical Definition**
Best practices for partial classes derive from the C# documentation and community guidance. Key recommendations include: **use partial classes primarily to separate generated code from hand-written code**; **keep hand-written partial parts in files clearly named** (e.g., `Customer.cs`, `Customer.Generated.cs`); **avoid splitting a class across many files without a clear organisational purpose**; **use partial methods for optional hooks rather than events or virtual methods**; **ensure all partial parts share the same accessibility and base-class specifications**; and **prefer source generators over manual code generation** for modern projects. Microsoft guidance explicitly lists the situations where splitting is desirable: multiple programmers working simultaneously, adding code without recreating generated files, and source generators adding functionality.

**Beginner-Friendly Explanation**
Best practices for partial classes are simple: **use them to separate generated code from your code**, **name files clearly**, and **do not split a class just for the sake of it**. If a class is small enough to fit in one file, keep it in one file.

---

### Purposes

- To prevent fragmentation and confusion from over-splitting types.
- To keep generated and hand-written code clearly separated.
- To ensure partial parts are consistent (accessibility, base classes, attributes).
- To choose the right mechanism (partial methods vs. events vs. virtual methods).
- To align with tooling and source-generator workflows.

---

### Guidelines and Structure

#### General Guidelines

```
// Use partial classes to separate generated and hand-written code
// File: Customer.cs (hand-written)
public partial class Customer
{
    public string Name { get; set; }
}

// File: Customer.Generated.cs (generated)
// <auto-generated />
public partial class Customer
{
    public int Id { get; set; }
}

// Keep partial parts consistent
// - Same accessibility
// - Same base-class specification (if any)
// - Attributes merged

// Use partial methods for optional hooks
partial void OnNameChanging(string newName);

// Prefer source generators over manual code generation
```

**Component breakdown**

- **Separation** — Generated code in its own file (e.g., `.Generated.cs`).
- **Naming** — Clear file names indicating the part’s role.
- **Consistency** — Accessibility and base classes must match.
- **Partial methods** — Optional hooks with zero cost when unimplemented.
- **Source generators** — Modern replacement for manual code generation.

#### Rules and Constraints

- **Do** use partial classes to separate generated and hand-written code.
- **Do** keep partial parts in separate files with clear names.
- **Do** use partial methods for optional hooks.
- **Do** ensure all parts share the same accessibility and base-class specifications.
- **Do not** split a class across many files without a clear organisational purpose.
- **Do not** use partial classes as a substitute for proper decomposition (prefer smaller classes or separate types).
- **Do not** mix generated and hand-written code in the same file.

---

### Annotated Code Examples and Expected Outputs

#### Example: Clean Separation of Generated and Hand-Written Code

```csharp
// File: Customer.cs (hand-written)
using System;

public partial class Customer
{
    public string Name { get; set; }

    partial void OnNameChanged();

    public void SetName(string name)
    {
        Name = name;
        OnNameChanged();
    }
}

// File: Customer.Generated.cs (generated)
// <auto-generated />
partial class Customer
{
    partial void OnNameChanged() =>
        Console.WriteLine($"Name changed to {Name}");
}

class Program
{
    static void Main()
    {
        var c = new Customer();
        c.SetName("Alice");   // Name changed to Alice
    }
}
```

**Expected Output**

```
Name changed to Alice
```

**Why this output occurs**

- The hand-written part declares the optional partial method and calls it; the generated part implements it. If the generated part were removed, the call would be elided at compile time.

## Deprecated, Unsafe, Implementation-Dependent, and Version-Specific Notes

| Feature | Status / Note |
|---------|---------------|
| Partial classes / structs / interfaces | Core since **C# 2.0**; stable. |
| Optional partial methods | Core since **C# 3.0**; implicitly private, must return `void`, no `out` parameters. |
| Required partial methods (C# 9) | Introduced in **C# 9**; allow non-`void` returns and explicit access modifiers. |
| Partial properties and indexers | Introduced in **C# 13**; version-specific. |
| Partial constructors and events | Introduced in **C# 14**; version-specific. |
| `ISourceGenerator` (legacy) | **Deprecated**; use `IIncrementalGenerator`. |
| Partial methods on constructors, finalizers, operators, events | **Not allowed** prior to C# 14 (constructors/events added in C# 14). |
| Generated code without `partial` | **Cannot merge**; all parts must use `partial`. |
