# Comprehensive Programming Cheat Sheet: SQL UUID Type

## Topic Overview

### Definitions

**Core Definition**
The `UUID` (Universally Unique Identifier) type is a PostgreSQL data type that stores 128-bit globally unique identifiers, designed to guarantee uniqueness across distributed systems without coordination between nodes.

**Technical Definition**
PostgreSQL's `uuid` type stores Universally Unique Identifiers as defined by RFC 9562 (and previously RFC 4122), ISO/IEC 9834-8:2005, and related standards. A UUID is a **128-bit quantity** generated by an algorithm chosen to make it extremely unlikely that the same identifier will be generated by anyone else in the known universe using the same algorithm. PostgreSQL stores UUIDs natively as **16 bytes**, and they are written as a sequence of lower-case hexadecimal digits in the standard **8-4-4-4-12** format, totalling 32 hexadecimal digits that represent the 128 bits. PostgreSQL provides native support for generating UUIDs using the **UUIDv4** (random) and **UUIDv7** (time-ordered) algorithms, the latter introduced in PostgreSQL 18. For other UUID versions (v1, v3, v5), the `uuid-ossp` extension provides additional functions.

**Beginner-Friendly Explanation**
A UUID is a very long, random-looking string that is almost guaranteed to be unique anywhere in the world—even if millions of computers generate UUIDs at the same time without talking to each other. PostgreSQL stores UUIDs in a compact 16-byte binary format and provides built-in functions to generate them. You can use a UUID as a primary key when you need IDs that are globally unique, hard to guess, and safe to generate on the client side without asking the database first.

### Key Characteristics

- **128-bit storage, fixed size**: A `uuid` value always occupies **16 bytes**, regardless of its textual representation. Storing UUIDs as `text` or `varchar(36)` wastes 20+ bytes per value and degrades query performance.
- **Globally unique without coordination**: Unlike sequence generators, which are only unique within a single database, UUIDs provide a better uniqueness guarantee for distributed systems.
- **Versioned algorithms**: UUIDs embed a version number that identifies the generation algorithm—v4 (random), v7 (time-ordered), and v1/v3/v5 (legacy/name-based via extensions).
- **Flexible input, canonical output**: PostgreSQL accepts upper-case digits, braces, omitted hyphens, and extra hyphens as input, but always outputs the standard lower-case 8-4-4-4-12 format.
- **Index fragmentation is the central performance concern**: Random UUIDv4 values land at unpredictable positions in a B-tree index, causing page splits, write amplification, and poor cache locality; time-ordered UUIDv7 values largely eliminate this problem.

### Prerequisites

- A running PostgreSQL instance (version 13 or later for built-in `gen_random_uuid()`; version 18 or later for native `uuidv7()`).
- For `uuid-ossp`: the extension must be installed (`CREATE EXTENSION "uuid-ossp"`); it is considered “trusted” and can be installed by non-superusers with `CREATE` privilege on the database.
- For legacy `pgcrypto` usage: the extension may be installed, though `gen_random_uuid()` has been part of core PostgreSQL since version 13.
- Awareness of the trade-offs between UUIDs and integer keys, and between UUIDv4 and UUIDv7, before choosing a primary key strategy.

### Related Programming Areas

- Data Definition Language (DDL) – column type declarations, default expressions, and primary keys.
- Data Manipulation Language (DML) – inserting, querying, and comparing UUID values.
- Indexing and query performance – B-tree fragmentation, index size, and sequential vs. random insertion.
- Distributed systems – client-side ID generation, multi-region writes, and merge-friendly identifiers.
- Security and privacy – opaque public identifiers that do not leak row counts or creation order.

## Core Concepts and Features

### 1. `UUID`

#### Definitions

**Core Definition**
`UUID` is a PostgreSQL data type that stores a 128-bit universally unique identifier as a fixed-size binary value.

**Technical Definition**
PostgreSQL's `uuid` type stores UUIDs in **16 bytes** of binary storage. Input accepts the standard hyphenated form, upper-case digits, braces, omitted hyphens, and extra hyphens, but output is always the canonical lower-case 8-4-4-4-12 format. PostgreSQL provides the usual comparison operators for UUIDs, so they can be sorted, indexed, and used in joins and `WHERE` clauses. Two extraction functions are available: `uuid_extract_version()` returns the version number (e.g., `4` for `gen_random_uuid()`), and `uuid_extract_timestamp()` returns the timestamp embedded in v1 or v7 UUIDs.

**Beginner-Friendly Explanation**
`UUID` is PostgreSQL's native container for a 128-bit unique identifier. You can store a UUID in 16 bytes—much smaller than the 36-character string it looks like—and PostgreSQL will handle comparisons, sorting, and indexing efficiently.

#### Purposes

- To provide globally unique identifiers for distributed systems where sequence coordination is impractical.
- To expose opaque public identifiers that do not leak row counts or insertion order.
- To serve as a primary key or unique identifier for tables that must merge data from multiple sources.
- To avoid the range limitations and coordination requirements of integer sequence keys.

#### Syntax Rules and Structure

**Column definition:**

```sql
column_name UUID
```

**Literal input:**

```sql
SELECT 'a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11'::uuid;
```

**Alternative input forms (all valid):**

```sql
'A0EEBC99-9C0B-4EF8-BB6D-6BB9BD380A11'::uuid
'{a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11}'::uuid
'a0eebc999c0b4ef8bb6d6bb9bd380a11'::uuid
'a0ee-bc99-9c0b-4ef8-bb6d-6bb9-bd38-0a11'::uuid
```

**Component breakdown:**

| Component | Description |
|-----------|-------------|
| `UUID` | 16-byte binary type for 128-bit identifiers. |
| `8-4-4-4-12` | Canonical textual format: 8 hex digits, three groups of 4, then 12. |
| `uuid_extract_version()` | Returns the UUID version (e.g., 4, 7). |
| `uuid_extract_timestamp()` | Returns the embedded timestamp for v1/v7 UUIDs (or `NULL` for other versions). |

**Syntax rules:**

- Output is always in the standard lower-case hyphenated form, regardless of the input format.
- UUIDs support equality (`=`), ordering (`<`, `>`), and indexing.
- `uuid_extract_timestamp()` returns `NULL` for UUID versions that do not embed a timestamp.

**Constraints and limitations:**

- `UUID` is 16 bytes—twice the size of a `bigint`—so indexes are larger and less cache-efficient than integer indexes.
- Random UUIDv4 values cause B-tree index fragmentation; UUIDv7 is preferred for high-write tables.
- Storing UUIDs as `text` or `varchar(36)` wastes space and degrades performance; always use the native `uuid` type.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Create a table with a UUID primary key and inspect its version

```sql
-- Step 1: Create a table with a UUID primary key.
CREATE TABLE documents (
    document_id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    title       text NOT NULL,
    body        text
);

-- Step 2: Insert a row; the UUID is generated automatically.
INSERT INTO documents (title, body)
VALUES ('Design Notes', 'Content of the document')
RETURNING document_id;

-- Step 3: Inspect the UUID version and timestamp (if applicable).
SELECT document_id,
       uuid_extract_version(document_id) AS version,
       uuid_extract_timestamp(document_id) AS embedded_ts
FROM documents;
```

**Expected output:**

```text
CREATE TABLE
            document_id
--------------------------------------
 5b30857f-0bfa-48b5-ac0b-5c64e28078d1
(1 row)

            document_id             | version | embedded_ts
------------------------------------+---------+-------------
 5b30857f-0bfa-48b5-ac0b-5c64e28078d1 |       4 | 
(1 row)
```

**Why this output appears**: `gen_random_uuid()` generates a version 4 UUID, which is random and contains no timestamp. `uuid_extract_version()` returns `4`, and `uuid_extract_timestamp()` returns `NULL` because v4 does not embed a timestamp.

##### Example 2: PostgreSQL – Accept alternative input forms and normalize output

```sql
-- Step 1: Insert UUIDs using different input formats.
INSERT INTO documents (document_id, title)
VALUES
    ('A0EEBC99-9C0B-4EF8-BB6D-6BB9BD380A11', 'Upper-case'),
    ('{a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11}', 'Braced'),
    ('a0eebc999c0b4ef8bb6d6bb9bd380a11', 'No hyphens');

-- Step 2: Query the stored values.
SELECT document_id, title FROM documents ORDER BY title;
```

**Expected output:**

```text
            document_id             |    title
------------------------------------+-------------
 a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11 | Braced
 a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11 | No hyphens
 a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11 | Upper-case
(3 rows)
```

**Why this output appears**: PostgreSQL normalizes all alternative input forms to the canonical lower-case hyphenated format on output. All three rows store the same UUID value.

#### Real-World Cases

- **Public API identifiers**: A `users` table uses a `uuid` column as its public-facing ID, so API responses expose an opaque identifier rather than a sequential integer that reveals user count.
- **Distributed event logs**: Multiple services write events to a shared table using UUIDs as primary keys, avoiding coordination on a central sequence.
- **Merge-friendly data**: When two databases are merged, UUID primary keys prevent collisions that would occur with independently generated integer sequences.

### 2. UUID Generation

#### Definitions

**Core Definition**
UUID generation is the process of producing a new UUID value using a specific algorithm—random (v4), time-ordered (v7), or name-based (v3/v5)—either in the database or on the client.

**Technical Definition**
PostgreSQL provides multiple mechanisms for UUID generation. **Native functions** (PostgreSQL 13+): `gen_random_uuid()` and `uuidv4()` generate version 4 (random) UUIDs; `uuidv7()` (PostgreSQL 18+) generates version 7 (time-ordered) UUIDs. **Extensions**: `uuid-ossp` provides `uuid_generate_v1()`, `uuid_generate_v1mc()`, `uuid_generate_v3()`, `uuid_generate_v4()`, and `uuid_generate_v5()`, implementing the algorithms defined in RFC 4122; `pgcrypto` historically provided `gen_random_uuid()` before it was moved into core PostgreSQL in version 13, and its version is now a deprecated wrapper for the core function. Generation can occur as a column default, in a `SELECT` expression, or on the client side before the value is sent to the database.

**Beginner-Friendly Explanation**
There are several ways to make a UUID. PostgreSQL has built-in functions: `gen_random_uuid()` makes a random v4 UUID, and (in newer versions) `uuidv7()` makes a time-ordered v7 UUID. If you need older algorithms like v1 or v5, you install the `uuid-ossp` extension. Before PostgreSQL 13, `gen_random_uuid()` came from `pgcrypto`, but now it is built in and you do not need the extension for v4 UUIDs.

#### Purposes

- To generate unique identifiers without coordinating with a central sequence.
- To produce time-ordered UUIDs (v7) for better index locality in high-write tables.
- To generate name-based UUIDs (v3/v5) that are deterministic for a given namespace and name.
- To create UUIDs on the client side for offline or distributed applications.

#### Syntax Rules and Structure

**Native generation functions:**

```sql
-- Version 4 (random) – PostgreSQL 13+
SELECT gen_random_uuid();
SELECT uuidv4();

-- Version 7 (time-ordered) – PostgreSQL 18+
SELECT uuidv7();
SELECT uuidv7(interval '1 hour');  -- shift the timestamp
```

**uuid-ossp generation functions:**

```sql
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";

SELECT uuid_generate_v1();      -- MAC address + timestamp
SELECT uuid_generate_v1mc();    -- random multicast MAC + timestamp
SELECT uuid_generate_v3(uuid_ns_dns(), 'example.com');  -- MD5 name-based
SELECT uuid_generate_v4();      -- random
SELECT uuid_generate_v5(uuid_ns_dns(), 'example.com');  -- SHA-1 name-based
```

**Column default:**

```sql
CREATE TABLE t (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid()
);
```

**Component breakdown:**

| Function | Version | Algorithm | Availability |
|----------|---------|-----------|--------------|
| `gen_random_uuid()` | 4 | Random | PostgreSQL 13+ (core) |
| `uuidv4()` | 4 | Random | PostgreSQL 18+ |
| `uuidv7()` | 7 | Time-ordered + random | PostgreSQL 18+ |
| `uuid_generate_v4()` | 4 | Random | `uuid-ossp` extension |
| `uuid_generate_v1()` | 1 | MAC address + timestamp | `uuid-ossp` extension |
| `uuid_generate_v1mc()` | 1 | Random multicast MAC + timestamp | `uuid-ossp` extension |
| `uuid_generate_v3()` | 3 | MD5 name-based | `uuid-ossp` extension |
| `uuid_generate_v5()` | 5 | SHA-1 name-based | `uuid-ossp` extension |

**Syntax rules:**

- `uuidv7([shift interval])` accepts an optional interval to shift the embedded timestamp; infinite intervals are rejected, and the shifted timestamp must fall within the supported range (1970-01-01 UTC to approximately year 10889).
- `uuid_generate_v3()` and `uuid_generate_v5()` require a namespace UUID and a name.
- All generation functions return a `uuid` value that can be used directly in `INSERT` statements or as a column default.

**Constraints and limitations:**

- `uuidv7()` is only available in PostgreSQL 18 and later; on earlier versions, use an extension such as `pg_uuidv7` or a hand-rolled function.
- `uuid_generate_v1()` embeds the MAC address, which may be a privacy concern.
- `gen_random_uuid()` requires the `pgcrypto` extension before PostgreSQL 13; in PostgreSQL 13+, it is built in.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Generate v4 and v7 UUIDs and compare their structure

```sql
-- Step 1: Generate a v4 UUID.
SELECT gen_random_uuid() AS v4_uuid;

-- Step 2: Generate a v7 UUID (PostgreSQL 18+).
SELECT uuidv7() AS v7_uuid;

-- Step 3: Extract the version and timestamp from both.
SELECT gen_random_uuid() AS v4,
       uuid_extract_version(gen_random_uuid()) AS v4_version;

SELECT uuidv7() AS v7,
       uuid_extract_version(uuidv7()) AS v7_version,
       uuid_extract_timestamp(uuidv7()) AS v7_timestamp;
```

**Expected output:**

```text
              v4_uuid
--------------------------------------
 5b30857f-0bfa-48b5-ac0b-5c64e28078d1
(1 row)

              v7_uuid
--------------------------------------
 019535d9-3df7-79fb-b466-fa907fa17f9e
(1 row)

                 v4                 | v4_version
------------------------------------+------------
 41db1265-8bc1-4ab3-992f-e85799a4af1d |          4
(1 row)

                 v7                 | v7_version |        v7_timestamp
------------------------------------+------------+----------------------------
 019535d9-3df7-79fb-b466-fa907fa17f9e |          7 | 2025-02-23 21:46:24.503-05
(1 row)
```

**Why this output appears**: `gen_random_uuid()` produces a v4 UUID with version number 4 and no embedded timestamp. `uuidv7()` produces a v7 UUID with version number 7 and an embedded millisecond-precision timestamp that can be extracted with `uuid_extract_timestamp()`.

##### Example 2: PostgreSQL – Use uuid-ossp for name-based UUIDs

```sql
-- Step 1: Enable the uuid-ossp extension.
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";

-- Step 2: Generate a v5 (SHA-1 name-based) UUID for a well-known name.
SELECT uuid_generate_v5(uuid_ns_dns(), 'example.com') AS v5_uuid;

-- Step 3: Verify the version.
SELECT uuid_extract_version(uuid_generate_v5(uuid_ns_dns(), 'example.com')) AS version;
```

**Expected output:**

```text
CREATE EXTENSION
               v5_uuid
--------------------------------------
 cfab8b3c-4a4b-5b8f-9b2a-4f9c7b1a2d3e
(1 row)

 version
---------
       5
(1 row)
```

**Why this output appears**: `uuid_generate_v5()` applies SHA-1 to the namespace UUID and the name, producing a deterministic v5 UUID. The same namespace and name always produce the same UUID, and `uuid_extract_version()` confirms version 5.

#### Real-World Cases

- **Client-side ID generation**: A mobile app generates UUIDv7 values locally and sends them to the server, avoiding a round-trip to obtain an ID before saving related records.
- **Idempotent APIs**: A server uses the client-supplied UUID as an idempotency key, ensuring that retried requests do not create duplicate rows.
- **Data migration**: Name-based UUIDs (`uuid_generate_v5()`) are used to derive stable identifiers from legacy natural keys during a migration.

### 3. `gen_random_uuid()`

#### Definitions

**Core Definition**
`gen_random_uuid()` is the standard PostgreSQL function for generating a version 4 (random) UUID.

**Technical Definition**
`gen_random_uuid()` returns a **version 4 (random) UUID** using a cryptographically strong random number generator. It has been part of core PostgreSQL since version 13; before that, it was provided by the `pgcrypto` extension. In modern PostgreSQL, `pgcrypto`'s version is a deprecated wrapper for the core function. The function takes no arguments and returns a `uuid` value. A common pattern is to use `gen_random_uuid()` as the default value for a primary key column.

**Beginner-Friendly Explanation**
`gen_random_uuid()` is the simplest way to make a random UUID in PostgreSQL. It has been built in since PostgreSQL 13, so you do not need any extension. Just call it and you get a new unique identifier.

#### Purposes

- To generate random unique identifiers for primary keys and unique columns.
- To create UUIDs as column defaults so that inserts automatically receive an ID.
- To provide a simple, extension-free way to obtain v4 UUIDs in PostgreSQL 13+.
- To serve as the foundation for client-side and server-side ID generation.

#### Syntax Rules and Structure

**General syntax:**

```sql
gen_random_uuid() → uuid
```

**Column default:**

```sql
CREATE TABLE t (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid()
);
```

**Component breakdown:**

| Component | Description |
|-----------|-------------|
| `gen_random_uuid()` | No-argument function returning a v4 UUID. |

**Syntax rules:**

- The function can be called in `SELECT`, `INSERT ... VALUES`, or a column `DEFAULT` expression.
- It returns a value of type `uuid`, which can be stored in a `uuid` column.
- `uuidv4()` is an equivalent function available in PostgreSQL 18+.

**Constraints and limitations:**

- Version 4 UUIDs are random, so their insertion order does not correlate with key order, causing B-tree index fragmentation on high-write tables.
- Before PostgreSQL 13, `pgcrypto` must be installed to use `gen_random_uuid()`.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Use gen_random_uuid() as a column default

```sql
-- Step 1: Create a table with a UUID default.
CREATE TABLE api_keys (
    key_id     uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id    int NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);

-- Step 2: Insert without specifying the UUID.
INSERT INTO api_keys (user_id) VALUES (42) RETURNING key_id;

-- Step 3: Insert another row and observe a different UUID.
INSERT INTO api_keys (user_id) VALUES (42) RETURNING key_id;
```

**Expected output:**

```text
CREATE TABLE
                key_id
--------------------------------------
 5b30857f-0bfa-48b5-ac0b-5c64e28078d1
(1 row)
                key_id
--------------------------------------
 b42410ee-132f-42ee-9e4f-09a6485c95b8
(1 row)
```

**Why this output appears**: Each insert calls `gen_random_uuid()` implicitly through the column default, producing a new random v4 UUID. The two values are different, as expected from a random generator.

#### Real-World Cases

- **API keys**: An `api_keys` table uses `gen_random_uuid()` to generate opaque, unguessable key identifiers.
- **Session identifiers**: A `sessions` table uses UUIDs generated by `gen_random_uuid()` to identify user sessions without exposing sequential IDs.

### 4. `uuid-ossp` Extension

#### Definitions

**Core Definition**
`uuid-ossp` is a PostgreSQL extension that provides functions for generating UUIDs using several standard algorithms beyond the native v4 and v7 support, including v1 (MAC address + timestamp), v3 (MD5 name-based), and v5 (SHA-1 name-based).

**Technical Definition**
The `uuid-ossp` module provides functions to generate universally unique identifiers using one of several standard algorithms, along with functions to produce certain special UUID constants. It depends on the **OSSP UUID library**. The extension is considered **“trusted”**, meaning it can be installed by non-superusers who have `CREATE` privilege on the current database. It provides `uuid_generate_v1()`, `uuid_generate_v1mc()`, `uuid_generate_v3()`, `uuid_generate_v4()`, and `uuid_generate_v5()`, as well as namespace constants such as `uuid_ns_dns()`, `uuid_ns_url()`, `uuid_ns_oid()`, and `uuid_ns_x500()`.

**Beginner-Friendly Explanation**
`uuid-ossp` is an add-on that gives PostgreSQL more UUID generation options. If you need a v1 UUID (based on your network card's MAC address and the current time), a v3 or v5 UUID (based on a name and a namespace), or a v4 UUID from an extension rather than the built-in function, `uuid-ossp` is the tool. It is trusted, so you can install it without being a superuser.

#### Purposes

- To generate version 1 UUIDs that embed the MAC address and timestamp.
- To generate deterministic name-based UUIDs (v3 with MD5, v5 with SHA-1) for stable identifiers derived from names.
- To provide v4 UUID generation on PostgreSQL versions before 13 (though `pgcrypto` is a simpler alternative).
- To access namespace constants for name-based UUID generation.

#### Syntax Rules and Structure

**Enable the extension:**

```sql
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
```

**Generation functions:**

```sql
SELECT uuid_generate_v1();      -- v1: MAC address + timestamp
SELECT uuid_generate_v1mc();    -- v1: random multicast MAC + timestamp
SELECT uuid_generate_v3(uuid_ns_dns(), 'example.com');  -- v3: MD5
SELECT uuid_generate_v4();      -- v4: random
SELECT uuid_generate_v5(uuid_ns_dns(), 'example.com');  -- v5: SHA-1
```

**Component breakdown:**

| Function | Version | Algorithm | Deterministic? |
|----------|---------|-----------|-----------------|
| `uuid_generate_v1()` | 1 | MAC address + timestamp | No (timestamp varies) |
| `uuid_generate_v1mc()` | 1 | Random multicast MAC + timestamp | No |
| `uuid_generate_v3(ns, name)` | 3 | MD5(namespace + name) | Yes |
| `uuid_generate_v4()` | 4 | Random | No |
| `uuid_generate_v5(ns, name)` | 5 | SHA-1(namespace + name) | Yes |

**Syntax rules:**

- The extension must be created before its functions can be used.
- Name-based functions require a namespace UUID (e.g., `uuid_ns_dns()`) and a name string.
- The same namespace and name always produce the same UUID for v3 and v5.

**Constraints and limitations:**

- `uuid-ossp` depends on the OSSP UUID library, which may not be available on all platforms or may require additional packages.
- Version 1 UUIDs embed the MAC address, which can be a privacy and security concern.
- The extension is not needed for v4 UUIDs on PostgreSQL 13+, because `gen_random_uuid()` is built in.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Name-based UUIDs with uuid_generate_v5()

```sql
-- Step 1: Enable the extension.
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";

-- Step 2: Generate a deterministic v5 UUID from a DNS name.
SELECT uuid_generate_v5(uuid_ns_dns(), 'www.example.com') AS v5_uuid;

-- Step 3: Generate the same UUID again to confirm determinism.
SELECT uuid_generate_v5(uuid_ns_dns(), 'www.example.com') AS v5_uuid;
```

**Expected output:**

```text
CREATE EXTENSION
               v5_uuid
--------------------------------------
 2ed6657d-e927-568b-95e1-2665a8aea6a2
(1 row)
               v5_uuid
--------------------------------------
 2ed6657d-e927-568b-95e1-2665a8aea6a2
(1 row)
```

**Why this output appears**: `uuid_generate_v5()` applies SHA-1 to the namespace UUID and the name `'www.example.com'`. Because both inputs are fixed, the output is deterministic and identical across calls.

#### Real-World Cases

- **Stable identifiers for external resources**: A system derives v5 UUIDs from URLs or domain names to create stable identifiers for external resources.
- **Legacy v1 compatibility**: An application that must interoperate with a legacy system using v1 UUIDs uses `uuid_generate_v1mc()` to avoid MAC-address privacy issues.

### 5. `pgcrypto` Extension

#### Definitions

**Core Definition**
`pgcrypto` is a PostgreSQL extension that provides cryptographic functions, including the historical `gen_random_uuid()` function for generating version 4 UUIDs.

**Technical Definition**
`pgcrypto` provides `gen_random_bytes(count integer)` for cryptographically strong random bytes (up to 1,024 bytes per call) and `gen_random_uuid()` for version 4 (random) UUIDs. Before PostgreSQL 13, `gen_random_uuid()` was only available through `pgcrypto`; since PostgreSQL 13, it is part of core PostgreSQL, and `pgcrypto`'s version is a deprecated wrapper. `pgcrypto` also provides hashing, encryption, and PGP functions, and its capabilities depend on whether it is compiled with OpenSSL.

**Beginner-Friendly Explanation**
`pgcrypto` used to be the go-to extension for generating UUIDs in PostgreSQL. Since PostgreSQL 13, you do not need it for that purpose because `gen_random_uuid()` is built in. However, `pgcrypto` still provides other useful cryptographic functions, such as random byte generation and encryption.

#### Purposes

- To generate v4 UUIDs on PostgreSQL versions before 13.
- To generate cryptographically strong random bytes for salts, tokens, and keys.
- To provide hashing and encryption functions alongside UUID generation.
- To serve as a fallback for environments where the core function is unavailable.

#### Syntax Rules and Structure

**Enable the extension:**

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;
```

**UUID generation:**

```sql
SELECT gen_random_uuid();
```

**Random bytes:**

```sql
SELECT gen_random_bytes(16);
```

**Component breakdown:**

| Function | Return type | Description |
|----------|-------------|-------------|
| `gen_random_uuid()` | `uuid` | Version 4 (random) UUID |
| `gen_random_bytes(count)` | `bytea` | Cryptographically strong random bytes (max 1,024) |

**Syntax rules:**

- `gen_random_bytes(count)` returns at most 1,024 bytes per call to avoid draining the randomness generator pool.
- In PostgreSQL 13+, `pgcrypto`'s `gen_random_uuid()` is a wrapper for the core function.

**Constraints and limitations:**

- `pgcrypto` is no longer required for UUID generation on PostgreSQL 13+.
- The extension's encryption capabilities depend on how PostgreSQL was compiled (with or without OpenSSL).

#### Multiple Annotated Complete Step-by-Step Code Examples

```text
(1 row)
```

**Why this output appears**: `gen_random_uuid()` returns a v4 UUID, and `gen_random_bytes(16)` returns 16 cryptographically strong random bytes. Both functions come from the `pgcrypto` extension.

#### Real-World Cases

- **Pre-13 compatibility**: An application running on PostgreSQL 12 uses `pgcrypto` to generate UUIDs for primary keys.
- **Token generation**: A system generates random tokens for password resets using `gen_random_bytes()` alongside UUIDs.

### 6. UUID Best Practices

#### Definitions

**Core Definition**
UUID best practices are the guidelines for choosing, generating, indexing, and storing UUIDs to balance uniqueness, performance, storage, and security.

**Technical Definition**
Best practices include: (1) **use the native `uuid` type**, never `text` or `varchar(36)`—a UUID PK on a 100M-row table costs ~6 GB just for the PK index, and storing as text adds 20+ bytes per value; (2) **prefer UUIDv7 for high-write tables**—v4 values are random and cause B-tree fragmentation, while v7 values are time-ordered and behave like a `bigint` in the index; (3) **use UUIDs only when needed**—distributed ID generation, public-facing opaque identifiers, and merge-friendly data are the right reasons, not “modernity”; (4) **consider the hybrid pattern**—use a `bigint` internal primary key for joins and a UUID public identifier for external exposure; (5) **generate IDs on the client when appropriate** to avoid round-trips, but ensure the server validates uniqueness; and (6) **be aware of timestamp leakage**—v7 UUIDs expose creation time, which may be undesirable in adversarial settings.

**Beginner-Friendly Explanation**
UUID best practices are about not shooting yourself in the foot. Use the native UUID type instead of storing 36-character strings. Use time-ordered UUIDv7 for tables that get lots of inserts, because random UUIDv4 makes indexes slow. Do not use UUIDs just because they sound modern—use them when you actually need distributed, opaque, or merge-friendly IDs. If you need both fast internal joins and opaque public IDs, use a `bigint` internally and a UUID externally.

#### Purposes

- To avoid the storage waste and performance degradation of string-based UUID storage.
- To minimise B-tree index fragmentation and write amplification on high-write tables.
- To choose the right UUID version for the workload (random vs. time-ordered).
- To balance internal performance with external opacity and distributed uniqueness.

#### Syntax Rules and Structure

**Best-practice schema patterns:**

```sql
-- Anti-pattern: storing UUIDs as text or varchar(36).
CREATE TABLE bad_example (
    id varchar(36) PRIMARY KEY  -- wastes ~20 bytes per value; slower comparisons
);

-- Good: native uuid type with UUIDv4 default.
CREATE TABLE good_v4 (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid()
);

-- Better for high-write: time-ordered UUIDv7 (PostgreSQL 18+).
CREATE TABLE good_v7 (
    id uuid PRIMARY KEY DEFAULT uuidv7()
);

-- Hybrid: bigint internal PK + UUID public ID.
CREATE TABLE customer (
    customer_no bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id   uuid NOT NULL DEFAULT gen_random_uuid() UNIQUE
);
```

**Component breakdown:**

| Practice | Implementation |
|----------|----------------|
| Native type | `uuid` column, not `text`/`varchar(36)` |
| Time-ordered | `uuidv7()` or a v7 extension for high-write tables |
| Purpose-fit | Use UUIDs for distributed, opaque, or merge-friendly IDs |
| Hybrid pattern | `bigint` internal PK + `uuid` public ID |
| Client generation | Generate UUIDs on the client for offline/distributed use |

**Syntax rules:**

- Always use the `uuid` type for storage; convert to text only for display or external APIs.
- Use `uuidv7()` (PostgreSQL 18+) or a v7 extension for tables with high insert rates and range-scan workloads.
- Use a `UNIQUE` constraint on the public UUID column in the hybrid pattern.

**Constraints and limitations:**

- UUIDv7 is not available natively before PostgreSQL 18; use `pg_uuidv7` or a hand-rolled function.
- UUID indexes are larger than `bigint` indexes; a UUID PK on a 100M-row table costs ~6 GB, versus ~3 GB for a `bigint` PK.
- Timestamp leakage in v7 UUIDs may be a privacy concern in some applications.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Hybrid pattern with bigint internal key and UUID public ID

```sql
-- Step 1: Create a table with both an internal bigint PK and a public UUID.
CREATE TABLE customers (
    customer_no bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id   uuid NOT NULL DEFAULT gen_random_uuid() UNIQUE,
    name        text NOT NULL
);

-- Step 2: Insert a customer; both IDs are generated automatically.
INSERT INTO customers (name) VALUES ('Acme Corp') RETURNING customer_no, public_id;

-- Step 3: Query by the internal key (fast).
SELECT name FROM customers WHERE customer_no = 1;

-- Step 4: Query by the public UUID (external API).
SELECT name FROM customers WHERE public_id = (SELECT public_id FROM customers WHERE customer_no = 1);
```

**Expected output:**

```text
CREATE TABLE
 customer_no |              public_id
-------------+--------------------------------------
           1 | 5b30857f-0bfa-48b5-ac0b-5c64e28078d1
(1 row)
    name
------------
 Acme Corp
(1 row)
    name
------------
 Acme Corp
(1 row)
```

**Why this output appears**: The `customer_no` column is a compact, sequential `bigint` used for internal joins and fast lookups. The `public_id` column is a random UUID exposed to external clients. Both queries return the same customer, but the internal query uses the smaller, more efficient `bigint` index.

##### Example 2: PostgreSQL – Comparing UUIDv4 and UUIDv7 index behaviour (conceptual)

```sql
-- Step 1: Create two tables, one with v4 UUIDs and one with v7 UUIDs.
CREATE TABLE t_v4 (id uuid PRIMARY KEY DEFAULT gen_random_uuid(), payload text);
CREATE TABLE t_v7 (id uuid PRIMARY KEY DEFAULT uuidv7(), payload text);

-- Step 2: Insert many rows into each.
INSERT INTO t_v4 (payload) SELECT md5(random()::text) FROM generate_series(1, 1000000);
INSERT INTO t_v7 (payload) SELECT md5(random()::text) FROM generate_series(1, 1000000);

-- Step 3: Compare index sizes and fragmentation (conceptual; actual sizes vary).
SELECT pg_size_pretty(pg_relation_size('t_v4_pkey')) AS v4_index_size,
       pg_size_pretty(pg_relation_size('t_v7_pkey')) AS v7_index_size;
```

**Expected output (illustrative):**

```text
 v4_index_size | v7_index_size
---------------+---------------
 42 MB         | 38 MB
(1 row)
```

**Why this output appears**: The v4 index is larger and more fragmented because random UUIDs insert at unpredictable positions, causing page splits. The v7 index is more compact and sequential because time-ordered UUIDs insert near the rightmost leaf of the B-tree, reducing fragmentation and improving cache locality.

#### Real-World Cases

- **Multi-region SaaS**: A `customers` table uses a `bigint` internal primary key and a UUID `public_id` for API responses, combining fast internal joins with opaque external identifiers.
- **High-write event tables**: An `events` table uses UUIDv7 primary keys to keep index inserts sequential and avoid the fragmentation caused by random UUIDv4.
- **Distributed mobile clients**: A mobile app generates UUIDv7 values offline and syncs them to the server, using the UUID as both the primary key and an idempotency key.
