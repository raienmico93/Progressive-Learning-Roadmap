# Comprehensive Programming Cheat Sheet: Execution Plan Analysis

## Topic Overview

### Definitions

**Core Definition**
Execution plan analysis is the practice of inspecting the query plan produced by a relational database management system (RDBMS) to understand how a SQL statement will be—or has been—executed, and to diagnose and improve query performance.

**Technical Definition**
An execution plan is a tree of physical operators generated by the query optimizer, describing the algorithms and data access methods used to evaluate a SQL statement. Each node in the plan represents an operation (scan, join, sort, aggregate, etc.) with associated estimated costs, row counts, and—when `ANALYZE` is used—actual runtime statistics. Execution plan analysis involves reading this tree to identify performance bottlenecks such as sequential scans on large tables, disk-spilling sorts, inefficient join strategies, and cardinality estimation errors. The core tools are `EXPLAIN` (plan only), `EXPLAIN ANALYZE` (plan plus actual execution), `EXPLAIN (ANALYZE, BUFFERS)` (adds I/O statistics), and vendor equivalents (MySQL `EXPLAIN ANALYZE`, SQL Server estimated vs. actual execution plans). Plan analysis is fundamental to query tuning, index design, and database performance engineering.

**Beginner-Friendly Explanation**
When you ask the database to run a query, it does not just dive in. It first makes a **plan**—a step-by-step strategy for finding the data, like a recipe. Execution plan analysis is reading that recipe to see whether the database is doing something silly, such as reading an entire million-row table when a simple index lookup would do, or sorting a huge dataset on disk instead of in memory. By reading the plan, you can fix the recipe and make your query much faster.

### Key Characteristics

- **Declarative input, procedural output**: You write a declarative SQL query; the plan is a procedural tree of physical operations chosen by the optimizer.
- **Cost-based optimization**: The optimizer assigns estimated costs to alternative plans and chooses the cheapest; costs are relative and engine-specific.
- **Two modes**: Estimated plans (no execution; estimates only) and actual plans (query executed; actual rows, times, and buffer usage recorded).
- **Operator tree structure**: Plans are trees; each node consumes rows from its children and produces rows for its parent. The root returns the final result.
- **Cardinality estimation is central**: Estimated row counts drive join order, algorithm selection, and memory grants. Errors in estimates are the most common root cause of bad plans.
- **Buffer statistics reveal I/O**: `BUFFERS` shows cache hits vs. disk reads, exposing whether the working set fits in memory.
- **`loops` multiplies everything**: In actual plans, `actual time` and `rows` are per-loop; multiply by `loops` to get the total contribution of a node.

### Prerequisites

- Understanding of `SELECT`, `WHERE`, `JOIN`, `GROUP BY`, `ORDER BY`, and subqueries.
- Familiarity with indexes (B-tree, composite, covering) and their purpose.
- Basic knowledge of database statistics and the `ANALYZE`/`VACUUM` maintenance process.
- Awareness of the target engine’s `EXPLAIN` syntax and output format.

### Related Programming Areas

- Query optimization and index design.
- Database performance tuning and capacity planning.
- Data warehousing and analytical query engineering.
- Database administration and maintenance (statistics, `work_mem`, memory grants).
- Application performance engineering (ORM query analysis).

## Core Concepts and Features

### 1. `EXPLAIN`

#### Definitions

**Core Definition**
`EXPLAIN` displays the execution plan that the query optimizer would use for a given statement, without actually executing the statement.

**Technical Definition**
`EXPLAIN` parses, rewrites, and plans the statement, then outputs the chosen plan tree. In PostgreSQL, the default output is a text-formatted tree with estimated startup cost, total cost, estimated rows, and estimated row width for each node. Optional parameters control verbosity (`VERBOSE`), cost display (`COSTS`), buffer reporting (`BUFFERS`), output format (`FORMAT`), and more. In MySQL, `EXPLAIN` produces a tabular or tree-formatted plan showing access type, possible keys, key used, estimated rows, and extra information. In SQL Server, an estimated execution plan is generated without running the query (e.g., via SSMS `Ctrl+L`), showing estimated row counts and operator costs.

**Beginner-Friendly Explanation**
`EXPLAIN` is the “preview” button. It shows you the recipe the database *would* follow if you ran the query, but it does not actually cook the meal—so it is safe to run on `INSERT`, `UPDATE`, or `DELETE` without changing data.

#### Purposes

- To inspect the optimizer’s chosen plan without executing the statement.
- To compare alternative plans after adding indexes or rewriting queries.
- To identify potential performance problems before deploying a query.
- To understand join order, access methods, and estimated costs.

#### Syntax Rules and Structure

**PostgreSQL** (official) :

```sql
EXPLAIN [ ( option [, ...] ) ] statement

-- Options include:
-- ANALYZE [ boolean ] | VERBOSE [ boolean ] | COSTS [ boolean ]
-- BUFFERS [ boolean ] | FORMAT { TEXT | XML | JSON | YAML }
```

**MySQL**:

```sql
EXPLAIN [FORMAT = {TRADITIONAL | JSON | TREE}] statement;
```

**SQL Server** (SSMS estimated plan): No T-SQL keyword; use the “Display Estimated Execution Plan” button or `SET SHOWPLAN_ALL ON`.

**Component breakdown**

| Component | Description |
|-----------|-------------|
| `EXPLAIN` | Command keyword. |
| `option` | Output modifiers (PostgreSQL). |
| `statement` | The SQL statement to be planned (not executed). |

**Syntax rules**

- `EXPLAIN` does **not** execute the statement (unless `ANALYZE` is specified).
- The statement can be `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `CREATE TABLE AS`, or `EXECUTE` (PostgreSQL).
- Costs are relative, dimensionless units; only compare plans for the same query.
- The first cost number is startup cost (before first row); the second is total cost.

**Constraints and limitations**

- Estimated plans may differ from actual plans due to parameter values, stale statistics, or runtime conditions.
- `EXPLAIN` output format and available options vary by engine and version.
- `EXPLAIN` alone cannot reveal actual row counts or timing; use `EXPLAIN ANALYZE` for that.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Basic `EXPLAIN`

```sql
EXPLAIN
SELECT * FROM orders WHERE customer_id = 42;
```

**Expected output** (illustrative):

```text
 Index Scan using idx_orders_customer on orders
   (cost=0.43..8.45 rows=3 width=72)
   Index Cond: (customer_id = 42)
```

**Why this output appears**: The planner chose an `Index Scan` because `customer_id = 42` is selective and an index exists on `customer_id`. The startup cost is `0.43`, total cost `8.45`, estimated rows `3`, estimated row width `72` bytes.

##### Example 2: MySQL – `EXPLAIN FORMAT=TREE`

```sql
EXPLAIN FORMAT=TREE
SELECT o.id, c.email
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'pending';
```

**Expected output** (illustrative):

```text
-> Nested loop inner join  (cost=12.5 rows=10)
    -> Filter: (o.status = 'pending')  (cost=5.0 rows=10)
        -> Table scan on o  (cost=5.0 rows=100)
    -> Single-row index lookup on c using PRIMARY (id=o.customer_id)  (cost=0.75 rows=1)
```

**Why this output appears**: MySQL chose a nested loop join, scanning `orders` and using the primary key on `customers` for each matching row.

#### Real-World Cases

- **Pre-deployment review**: Running `EXPLAIN` on new queries before they reach production.
- **Index validation**: Confirming that a new index is actually used by the optimizer.
- **Query refactoring**: Comparing plans before and after rewriting a subquery as a join.

### 2. `EXPLAIN ANALYZE`

#### Definitions

**Core Definition**
`EXPLAIN ANALYZE` executes the statement and displays both the optimizer’s estimates and the actual runtime statistics for each plan node.

**Technical Definition**
`EXPLAIN ANALYZE` runs the statement to completion, discarding any result rows (for `SELECT`), and annotates each plan node with actual startup time, total time, actual row count, and actual number of loops. In PostgreSQL, `ANALYZE` can be combined with `BUFFERS` to report buffer usage and with `TIMING` to control clock overhead. In MySQL 8.0.18+, `EXPLAIN ANALYZE` outputs a tree with per-node `actual time=start..end`, `rows=N`, and `loops=L` measurements. In SQL Server, the actual execution plan (SSMS `Ctrl+M` then run) records actual row counts, elapsed times, and spill information.

**Beginner-Friendly Explanation**
`EXPLAIN ANALYZE` is the “test run” button. It actually executes the query, measures how long each step took and how many rows each step really processed, and shows these real numbers next to the optimizer’s guesses. It is the most reliable way to find out where a query is spending its time.

> ⚠️ **Warning**: `EXPLAIN ANALYZE` executes the statement. For `INSERT`, `UPDATE`, `DELETE`, or `MERGE`, wrap it in a transaction and roll back:
> ```sql
> BEGIN;
> EXPLAIN ANALYZE DELETE FROM ...;
> ROLLBACK;
> ```

#### Purposes

- To compare estimated row counts with actual row counts and detect cardinality estimation errors.
- To measure the real time spent in each plan node.
- To reveal disk-spilling sorts, hash batches, and buffer cache behavior.
- To validate that the optimizer’s assumptions match reality.

#### Syntax Rules and Structure

**PostgreSQL** (official) :

```sql
EXPLAIN ANALYZE statement;
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS) statement;
```

**MySQL 8.0.18+**:

```sql
EXPLAIN ANALYZE select_statement;
```

**Component breakdown**

| Component | Description |
|-----------|-------------|
| `ANALYZE` | Executes the statement and records actual statistics. |
| `actual time=start..end` | Time to first row and time to last row, per loop (milliseconds). |
| `rows=N` | Actual rows returned by the node (per loop). |
| `loops=L` | Number of times the node was executed. |
| `Buffers: shared hit/read` | Buffer cache hits and disk reads (PostgreSQL with `BUFFERS`). |

**Syntax rules**

- `ANALYZE` can be combined with other `EXPLAIN` options in PostgreSQL: `EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)`.
- `EXPLAIN ANALYZE` cannot be used with `GENERIC_PLAN`.
- `TIMING OFF` can reduce clock overhead when only row counts are needed.
- In MySQL, `EXPLAIN ANALYZE` supports only `SELECT` statements and outputs `TREE` format by default.

**Constraints and limitations**

- Running the statement has side effects (data modification, triggers, etc.); use a transaction rollback for DML.
- `actual time` includes the time of child nodes, so parent nodes may appear expensive even if their own work is trivial.
- `loops` multiplies actual rows and times; a nested loop inner node with `loops=1000` processes 1000× its per-loop rows.
- MySQL `EXPLAIN ANALYZE` reports estimated cost but not actual cost.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – `EXPLAIN (ANALYZE, BUFFERS)`

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, c.email
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'pending'
ORDER BY o.created_at DESC
LIMIT 50;
```

**Expected output** (illustrative):

```text
 Limit  (cost=... rows=50) (actual time=0.050..0.120 rows=50 loops=1)
   Buffers: shared hit=25 read=2
   ->  Nested Loop  (cost=... rows=50) (actual time=0.045..0.110 rows=50 loops=1)
         ->  Index Scan using idx_orders_status on orders o
               (cost=... rows=50) (actual time=0.030..0.060 rows=50 loops=1)
               Index Cond: (status = 'pending')
               Buffers: shared hit=10 read=1
         ->  Index Scan using customers_pkey on customers c
               (cost=... rows=1) (actual time=0.001..0.001 rows=1 loops=50)
               Index Cond: (id = o.customer_id)
               Buffers: shared hit=15 read=1
```

**Why this output appears**: The plan shows a nested loop join with an index scan on `orders` (filtered by status) and an index lookup on `customers` for each matching order. `loops=50` on the inner index scan means it was executed 50 times, once per outer row. Buffer statistics show most pages came from cache (`shared hit`) with only a few disk reads (`shared read`).

##### Example 2: MySQL 8.0.18+ – `EXPLAIN ANALYZE` tree output

```sql
EXPLAIN ANALYZE
SELECT first_name, last_name, SUM(amount) AS total
FROM staff
INNER JOIN payment ON staff.staff_id = payment.staff_id
WHERE payment.payment_date LIKE '2005-08%'
GROUP BY staff.staff_id;
```

**Expected output** (illustrative):

```text
-> Table scan on <temporary>  (actual time=0.030..0.040 rows=2 loops=1)
    -> Aggregate using temporary table  (actual time=0.025..0.030 rows=2 loops=1)
        -> Nested loop inner join  (cost=117.43 rows=894) (actual time=0.020..0.025 rows=2 loops=1)
            -> Filter: (payment.payment_date like '2005-08%')  (cost=... rows=894) (actual time=0.010..0.015 rows=2 loops=1)
                -> Table scan on payment  (cost=... rows=1000) (actual time=0.005..0.010 rows=1000 loops=1)
            -> Single-row index lookup on staff using PRIMARY (staff_id=payment.staff_id)  (cost=... rows=1) (actual time=0.001..0.001 rows=1 loops=2)
```

**Why this output appears**: MySQL scanned `payment`, filtered by the `LIKE` predicate, then performed a single-row primary key lookup on `staff` for each matching payment. The aggregation used a temporary table. `loops=2` on the inner lookup reflects the two matching payments.

#### Real-World Cases

- **Slow query diagnosis**: Identifying which node in a plan consumes the most actual time.
- **Estimation error detection**: Spotting cases where `estimated rows` is 1 but `actual rows` is 100,000, indicating stale statistics.
- **Sort spill detection**: Seeing `Sort Method: external merge Disk: 45MB` and increasing `work_mem`.
- **Index validation**: Confirming that a newly created index actually reduces buffer reads and runtime.

### 3. Query-Plan Operators

#### Definitions

**Core Definition**
Query-plan operators are the individual nodes in an execution plan tree, each representing a specific physical operation such as a table scan, index scan, join, sort, or aggregation.

**Technical Definition**
Each operator in a plan consumes zero or more child operators’ output and produces rows for its parent. Operators are classified by their role: **access methods** (sequential scan, index scan, index-only scan, bitmap scan), **join operators** (nested loop, hash join, merge join), **sort operators** (sort, incremental sort), **aggregation operators** (hash aggregate, group aggregate, stream aggregate), and **other** (limit, gather, materialize, memoize). The optimizer selects a combination of operators that minimizes estimated cost. Reading a plan means understanding what each operator does, how it consumes rows, and what its cost and row-count profile indicates.

**Beginner-Friendly Explanation**
Operators are the individual steps in the recipe. One step might say “read the whole table,” another “look up matching rows in an index,” another “combine two lists,” and another “sort the result.” Each step has a name (e.g., `Seq Scan`, `Hash Join`) and a cost, and reading the plan means following the steps from the bottom up to see how the final result is built.

#### Purposes

- To identify the access method used for each table.
- To understand how tables are combined (join strategy).
- To spot expensive operations such as disk sorts or hash spills.
- To map optimizer choices back to indexes, statistics, and query structure.

#### Syntax Rules and Structure

**Common operators**:

| Category | PostgreSQL | MySQL | SQL Server |
|----------|------------|-------|------------|
| Table access | `Seq Scan` | `Table scan` | `Table Scan` |
| Index access | `Index Scan`, `Index Only Scan` | `Index lookup`, `Index range scan` | `Index Seek`, `Index Scan` |
| Bitmap access | `Bitmap Index Scan` + `Bitmap Heap Scan` | — | — |
| Join | `Nested Loop`, `Hash Join`, `Merge Join` | `Nested loop inner join`, `Hash join` | `Nested Loops`, `Hash Match`, `Merge Join` |
| Sort | `Sort`, `Incremental Sort` | `Sort` | `Sort` |
| Aggregate | `HashAggregate`, `GroupAggregate` | `Aggregate using temporary table` | `Stream Aggregate`, `Hash Match (Aggregate)` |
| Limit | `Limit` | `Limit` | `Top` |

**Component breakdown**

| Component | Description |
|-----------|-------------|
| `->` | Indicates a child node in the plan tree. |
| `(cost=startup..total rows=N width=W)` | Estimated startup cost, total cost, rows, and row width. |
| `(actual time=start..end rows=N loops=L)` | Actual timing, rows, and loop count (when `ANALYZE` is used). |
| `Filter:`, `Index Cond:`, `Hash Cond:` | Predicates applied at this node. |

**Syntax rules**

- Plans are read from the innermost (most indented) nodes outward; the root node returns the final result.
- Operators that appear at the same indentation level are siblings; the first sibling is typically the outer or build input, depending on the operator.
- `loops` on an inner node means the node was executed once per outer row; actual time and rows are per loop.

**Constraints and limitations**

- Operator names and behaviors differ across engines and versions.
- The same logical operation may be implemented by different physical operators depending on data size, indexes, and cost estimates.
- Parallel plans introduce additional operators (`Gather`, `Exchange`, `Parallel Hash`) that complicate interpretation.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Reading an operator tree

```sql
EXPLAIN ANALYZE
SELECT c.name, SUM(o.total) AS total_spent
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE c.status = 'active'
GROUP BY c.name
ORDER BY total_spent DESC;
```

**Expected output** (illustrative):

```text
 Sort  (cost=... rows=100) (actual time=2.500..2.510 rows=100 loops=1)
   Sort Key: (sum(o.total)) DESC
   Sort Method: quicksort  Memory: 25kB
   ->  HashAggregate  (cost=... rows=100) (actual time=2.400..2.450 rows=100 loops=1)
         Group Key: c.name
         ->  Hash Join  (cost=... rows=1000) (actual time=0.500..2.000 rows=5000 loops=1)
               Hash Cond: (o.customer_id = c.id)
               ->  Seq Scan on orders o  (cost=... rows=10000) (actual time=0.010..0.500 rows=10000 loops=1)
               ->  Hash  (cost=... rows=100) (actual time=0.200..0.200 rows=100 loops=1)
                     Buckets: 1024  Batches: 1  Memory Usage: 12kB
                     ->  Seq Scan on customers c  (cost=... rows=100) (actual time=0.010..0.050 rows=100 loops=1)
                           Filter: (status = 'active')
```

**Why this output appears**: The plan reads `orders` and `customers` sequentially, builds a hash table on `customers` (filtered by active status), probes it with `orders` rows, aggregates by `c.name`, and sorts the result. The `Hash` node shows `Batches: 1`, meaning the hash table fit in memory.

#### Real-World Cases

- **Access method review**: Checking whether a large table is being sequentially scanned unnecessarily.
- **Join strategy audit**: Confirming that a nested loop is not being used when a hash join would be better.
- **Spill detection**: Looking for `Batches > 1` (hash spill) or `Sort Method: external merge Disk` (sort spill).

### 4. Estimated versus Actual Rows

#### Definitions

**Core Definition**
Estimated rows are the optimizer’s prediction of how many rows a plan node will produce; actual rows are the number of rows the node actually produced during execution.

**Technical Definition**
Estimated row counts are derived from statistics stored in system catalogs (e.g., PostgreSQL `pg_statistic`/`pg_stats`, SQL Server statistics objects). The planner computes selectivity from histograms, most-common-value (MCV) lists, and distinct-value counts, then multiplies by table cardinality. Actual row counts are recorded by `EXPLAIN ANALYZE` (or actual execution plans) when the query runs. Large discrepancies between estimated and actual rows—particularly when estimates are much lower than actuals—are the most common cause of poor plan choices, because the optimizer chooses join algorithms and memory allocations based on estimated cardinality.

**Beginner-Friendly Explanation**
The optimizer guesses how many rows each step will produce. Those guesses drive decisions like “should I sort this or hash it?” and “how much memory should I reserve?” When the guess is wildly wrong—say, guessing 10 rows when there are actually 100,000—the database may pick a strategy that works well for 10 rows but is disastrous for 100,000. Comparing estimated and actual rows in `EXPLAIN ANALYZE` is how you catch these mistakes.

#### Purposes

- To detect cardinality estimation errors that lead to bad plan choices.
- To decide when to refresh statistics (`ANALYZE`, `UPDATE STATISTICS`).
- To diagnose memory-grant problems (SQL Server) and hash/sort spills.
- To understand why the optimizer chose an unexpected join order or algorithm.

#### Syntax Rules and Structure

**Comparing estimates and actuals**:

```sql
EXPLAIN ANALYZE SELECT ...;
-- Output shows both:
-- (cost=... rows=ESTIMATED width=...) (actual time=... rows=ACTUAL loops=...)
```

**Component breakdown**

| Field | Meaning |
|-------|---------|
| `rows=N` inside `(cost=...)` | Estimated rows. |
| `rows=N` inside `(actual ...)` | Actual rows (per loop). |
| `loops=L` | Number of executions; actual total rows = `rows × loops`. |

**Syntax rules**

- Estimated rows are computed at plan time from statistics; actual rows are measured at runtime.
- A node may be executed multiple times (`loops > 1`); compare estimated per-loop rows with actual per-loop rows, or multiply both by loops.
- Estimation errors propagate upward: a bad estimate at a scan node can cause bad join and aggregation choices higher in the plan.

**Constraints and limitations**

- Estimates may differ due to parameter values, correlated columns, expressions, or stale statistics.
- SQL Server’s memory grant is based on estimated rows; underestimates cause spills, overestimates waste memory.
- PostgreSQL does not have a memory grant mechanism; `work_mem` is per-operator and fixed, so underestimates can also cause disk spills.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Large estimation error

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE status = 'pending';
```

**Expected output** (illustrative, problematic):

```text
 Seq Scan on orders  (cost=0.00..1834.00 rows=10 width=72)
                     (actual time=0.020..150.500 rows=120000 loops=1)
   Filter: (status = 'pending')
   Rows Removed by Filter: 880000
```

**Why this output appears**: The planner estimated only 10 pending orders but actually found 120,000. This 12,000× underestimate likely caused the optimizer to choose a sequential scan (or a plan suitable for a tiny result set), when an index scan or a different join strategy would have been better. The root cause is usually stale statistics or a non-uniform data distribution not captured by the histogram.

##### Example 2: SQL Server – Memory grant and spill

```sql
-- Actual execution plan shows:
-- Estimated Rows: 100
-- Actual Rows: 2,000,000
-- Operator: Sort
-- Warning: Sort spilled to tempdb (GrantedMemory too small)
```

**Why this output appears**: SQL Server reserved memory based on an estimate of 100 rows, but the sort actually processed 2 million rows. The memory grant was insufficient, causing the sort to spill to `tempdb`. The fix is to update statistics or rewrite the query so the optimizer can produce a better estimate.

#### Real-World Cases

- **Stale statistics**: After a large data load, estimates are wildly off; running `ANALYZE` or `UPDATE STATISTICS` fixes the plan.
- **Parameter sniffing**: A cached plan optimized for one parameter value performs poorly for another; actual plan analysis reveals the mismatch.
- **Correlated predicates**: The optimizer assumes independence between columns, underestimating the result of `WHERE city = 'X' AND country = 'Y'`; extended statistics or query rewrites help.

### 5. Sequential Scans

#### Definitions

**Core Definition**
A sequential scan (PostgreSQL `Seq Scan`, MySQL `Table scan`, SQL Server `Table Scan`) reads every row (or every page) of a table from start to finish, evaluating the query’s filter on each row.

**Technical Definition**
A sequential scan is the fallback access method when no usable index exists, or when the optimizer estimates that reading the entire table is cheaper than using an index. It reads all pages of the table’s heap (or clustered index) in physical order. On large tables, sequential scans are expensive because they touch every page, even if few rows satisfy the predicate. However, for small tables, low-selectivity predicates (returning a large fraction of the table), or queries that need most columns, sequential scans can be the optimal choice.

**Beginner-Friendly Explanation**
A sequential scan is like reading a book from cover to cover to find every mention of a word, instead of using the index at the back. It is fine for a short book, but slow for a large encyclopedia.

#### Purposes

- To read all rows when no index can satisfy the query.
- To efficiently retrieve a large fraction of a table (low selectivity).
- To avoid random I/O when the table is small enough to fit in memory.
- To serve as a baseline against which index scans are compared.

#### Syntax Rules and Structure

**Plan node appearance**:

```text
Seq Scan on table_name  (cost=0.00..N rows=M width=W)
  Filter: (condition)
  Rows Removed by Filter: K
```

**Component breakdown**

| Field | Meaning |
|-------|---------|
| `Seq Scan` / `Table scan` | Operator name. |
| `Filter:` | Predicate applied to each row. |
| `Rows Removed by Filter:` | Rows read but discarded (PostgreSQL). |
| `cost=0.00..N` | Startup cost 0 (no setup); total cost proportional to table size. |

**Syntax rules**

- A sequential scan has zero startup cost because it can return the first row immediately.
- The total cost is roughly proportional to the number of pages in the table.
- `Rows Removed by Filter` is a key indicator: a high number relative to rows returned suggests an index would be beneficial.

**Constraints and limitations**

- Sequential scans always read the entire table, even if the filter matches only a few rows.
- They can be optimal for small tables or low-selectivity predicates; do not assume every `Seq Scan` is a problem.
- In PostgreSQL, the visibility map and `VACUUM` affect sequential scan performance.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Sequential scan on a large table

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE status = 'pending';
```

**Expected output** (problematic):

```text
 Seq Scan on orders  (cost=0.00..1834.00 rows=10 width=72)
                     (actual time=0.020..150.500 rows=120000 loops=1)
   Filter: (status = 'pending')
   Rows Removed by Filter: 880000
```

**Why this output appears**: The table has 1,000,000 rows, and the filter matches 120,000. The planner chose a sequential scan (possibly due to stale statistics estimating only 10 matches). The `Rows Removed by Filter: 880000` shows that 880,000 rows were read and discarded—strong evidence that an index on `status` would help.

##### Example 2: PostgreSQL – Sequential scan is optimal for a small table

```sql
EXPLAIN ANALYZE
SELECT * FROM lookup_codes WHERE code = 'ABC';
```

**Expected output** (healthy):

```text
 Seq Scan on lookup_codes  (cost=0.00..1.10 rows=1 width=20)
                            (actual time=0.005..0.005 rows=1 loops=1)
   Filter: (code = 'ABC'::text)
   Rows Removed by Filter: 9
```

**Why this output appears**: The table has only 10 rows and fits in a single page. A sequential scan reads the page once; an index scan would require extra I/O. The planner correctly chose the cheaper sequential scan.

#### Real-World Cases

- **Missing index**: A sequential scan on a million-row table with a selective filter indicates a missing index.
- **Low selectivity**: A filter matching 40% of a table may be faster with a sequential scan than an index scan (which would require many random heap fetches).
- **Small dimension tables**: Sequential scans on small lookup tables are normal and efficient.

### 6. Index Scans

#### Definitions

**Core Definition**
An index scan uses an index to locate rows matching a predicate, rather than reading the entire table; variants include index scan, index-only scan, and bitmap index scan.

**Technical Definition**
An index scan traverses a B-tree (or other index structure) to find entries matching the predicate, then fetches the corresponding heap rows (unless the index is covering and an index-only scan is possible). The cost model weighs index traversal cost plus heap fetch cost against sequential scan cost. Index scans are efficient for selective predicates (returning a small fraction of rows) because they avoid reading irrelevant pages. Bitmap index scans build a bitmap of matching row locations from one or more indexes, then fetch heap rows in physical order, reducing random I/O.

**Beginner-Friendly Explanation**
An index scan is like using the index at the back of a book to jump directly to the pages that mention a topic, instead of reading every page. It is fast when you are looking for a small number of rows. A bitmap scan is like collecting all the page numbers first, sorting them, and then reading the pages in order to minimize back-and-forth.

#### Purposes

- To efficiently retrieve a small number of rows matching a selective predicate.
- To avoid reading irrelevant pages in large tables.
- To support range queries, equality lookups, and ordering.
- To provide an alternative to sequential scans when selectivity is high.

#### Syntax Rules and Structure

**Plan node appearance** (PostgreSQL):

```text
Index Scan using index_name on table_name
  (cost=startup..total rows=N width=W)
  Index Cond: (column = value)
  Filter: (additional_condition)
```

```text
Index Only Scan using index_name on table_name
  (cost=... rows=N width=W)
  Index Cond: (column = value)
  Heap Fetches: 0
```

```text
Bitmap Heap Scan on table_name
  (cost=... rows=N width=W)
  Recheck Cond: (condition)
  ->  Bitmap Index Scan on index_name
        (cost=... rows=N width=0)
        Index Cond: (condition)
```

**Component breakdown**

| Node | Meaning |
|------|---------|
| `Index Scan` | Traverses index, then fetches heap rows. |
| `Index Only Scan` | Answers entirely from the index; no heap fetch if visibility map is current. |
| `Bitmap Index Scan` | Builds a bitmap of matching row locations. |
| `Bitmap Heap Scan` | Fetches heap pages in physical order using the bitmap. |
| `Index Cond` | Predicate applied during index traversal. |
| `Filter` | Predicate applied after heap fetch (not indexable). |
| `Heap Fetches` | Number of heap row fetches needed by an index-only scan (should be low). |

**Syntax rules**

- Index scans are chosen when the optimizer estimates that index access + heap fetch is cheaper than a sequential scan.
- Index-only scans require that all referenced columns are in the index (covering index).
- Bitmap scans are chosen for moderately selective predicates or when combining multiple indexes (e.g., `OR` conditions).
- The `Index Cond` is applied during index traversal; the `Filter` is applied afterward and cannot use the index.

**Constraints and limitations**

- Index scans can be slower than sequential scans for low-selectivity predicates because of random heap I/O.
- Index-only scans require an up-to-date visibility map (PostgreSQL); otherwise, heap fetches occur.
- Bitmap scans have setup overhead and are less effective for very small result sets.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Index scan for a selective query

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 42;
```

**Expected output**:

```text

  (cost=0.43..8.45 rows=3 width=72)
  (actual time=0.021..0.031 rows=3 loops=1)
  Index Cond: (customer_id = 42)
```

**Why this output appears**: The predicate `customer_id = 42` is highly selective, and an index exists. The index scan traverses the B-tree, finds the three matching entries, and fetches the corresponding heap rows. The cost is low because only a few pages are touched.

##### Example 2: PostgreSQL – Bitmap heap scan for a moderately selective query

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE status = 'pending' OR priority = 'high';
```

**Expected output** (illustrative):

```text

  (actual time=5.000..12.000 rows=4800 loops=1)

  ->  BitmapOr  (cost=... rows=5000 width=0)

              (cost=... rows=3000 width=0)
```

#### Real-World Cases

- **Point lookups**: `WHERE id = 123` uses a unique index scan.
- **Range queries**: `WHERE created_at >= '2025-01-01'` uses an index range scan.
- **Covering indexes**: Adding `INCLUDE` columns to avoid heap fetches.
- **OR predicates**: Bitmap scans combine multiple indexes efficiently.

### 7. Sort Operations

#### Definitions

**Core Definition**
A sort operation orders rows according to one or more sort keys; it may be performed in memory or spilled to disk when the data exceeds available memory.

**Technical Definition**
A `Sort` node reads all input rows, sorts them according to the specified `Sort Key`, and emits them in order. In PostgreSQL, the `Sort Method` line reports whether the sort was performed in memory (`quicksort`, `top-N heapsort`) or spilled to disk (`external merge Disk: NkB`). SQL Server sorts similarly and may spill to `tempdb` if the memory grant is insufficient. Sorts are required for `ORDER BY`, merge joins, grouping (unless hash aggregation is used), and window functions with `ORDER BY`. Sorts are blocking operations: they must consume all input before producing the first output row, which increases startup latency.

**Beginner-Friendly Explanation**
A sort puts rows in order. If the data fits in memory, it is fast. If the data is too large, the database writes chunks to disk and merges them, which is much slower. Seeing `external merge Disk` in a plan means the sort ran out of memory and spilled to disk.

#### Purposes

- To satisfy `ORDER BY` clauses.
- To prepare sorted input for merge joins.
- To group rows for aggregation (when hash aggregation is not used).
- To support window functions that require ordered input.

#### Syntax Rules and Structure

**Plan node appearance**:

```text
Sort  (cost=... rows=N width=W)
  Sort Key: column1, column2 DESC
  Sort Method: quicksort  Memory: 25kB
  ->  child_node
```

**Disk-spilling sort**:

```text
Sort  (cost=... rows=N width=W)
  Sort Key: ...
  Sort Method: external merge  Disk: 45MB
```

**Component breakdown**

| Field | Meaning |
|-------|---------|
| `Sort Key` | Columns and direction used for ordering. |
| `Sort Method` | `quicksort` (in-memory), `top-N heapsort` (bounded), `external merge` (disk spill). |
| `Memory: NkB` | Memory used for in-memory sort. |
| `Disk: NkB` | Disk space used for spilled sort. |

**Syntax rules**

- Sorts are blocking; total cost includes reading all input before the first output row.
- `work_mem` (PostgreSQL) or memory grant (SQL Server) controls how much memory a sort can use before spilling.
- `top-N heapsort` is used when a `LIMIT` is present, allowing the sort to discard rows beyond the top N.
- Incremental sort (PostgreSQL) can exploit presorted prefixes, reducing cost.

**Constraints and limitations**

- Disk-spilling sorts are dramatically slower than in-memory sorts.
- Increasing `work_mem` too high can cause memory pressure if many concurrent sorts run.
- Sorts cannot be avoided if the query requires ordered output and no index provides that order.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – In-memory sort

```sql
EXPLAIN ANALYZE
SELECT * FROM orders ORDER BY created_at DESC LIMIT 100;
```

**Expected output** (healthy):

```text
 Limit  (cost=... rows=100) (actual time=1.200..1.250 rows=100 loops=1)
   ->  Sort  (cost=... rows=10000 width=72) (actual time=1.100..1.150 rows=100 loops=1)
         Sort Key: created_at DESC
         Sort Method: top-N heapsort  Memory: 35kB
         ->  Seq Scan on orders  (cost=... rows=10000) (actual time=0.010..0.500 rows=10000 loops=1)
```

**Why this output appears**: The `LIMIT 100` allows the sort to use `top-N heapsort`, which keeps only the top 100 rows in memory. The sort is fast and does not spill to disk.

##### Example 2: PostgreSQL – Disk-spilling sort

```sql
EXPLAIN ANALYZE
SELECT * FROM orders ORDER BY total DESC;
```

**Expected output** (problematic):

```text
 Sort  (cost=... rows=1000000 width=72)
  (actual time=5000.000..5500.000 rows=1000000 loops=1)
   Sort Key: total DESC
   Sort Method: external merge  Disk: 102400kB
   ->  Seq Scan on orders  (cost=... rows=1000000) (actual time=0.010..800.000 rows=1000000 loops=1)
```

**Why this output appears**: The table has 1,000,000 rows, and the sort exceeded `work_mem`, spilling approximately 100 MB to disk. The runtime jumped to several seconds. The fix is to increase `work_mem` for this query or create an index on `total` to avoid the sort entirely.

##### Example 3: SQL Server – Sort spill warning

```sql
-- Actual execution plan shows:
-- Sort operator
-- Estimated Rows: 1000
-- Actual Rows: 500000
-- Warning: Sort spilled to tempdb
```

**Why this output appears**: The memory grant was based on an estimate of 1,000 rows, but the sort processed 500,000 rows. The grant was insufficient, causing a spill to `tempdb`. Updating statistics to improve the estimate or increasing the memory grant (via Resource Governor) resolves the issue.

#### Real-World Cases

- **ORDER BY without index**: A query sorting a large result set spills to disk; adding an index on the sort key eliminates the sort.
- **Merge join preparation**: Sorts feeding a merge join may spill; ensuring indexes match the join keys avoids the sorts.
- **Window functions**: Window functions with `ORDER BY` may require a sort; indexes can provide the required order.

### 8. Aggregation Operations

#### Definitions

**Core Definition**
An aggregation operation groups rows by one or more keys and computes aggregate values (SUM, COUNT, AVG, MIN, MAX) for each group; the two main strategies are hash aggregation and sort-based (group) aggregation.

**Technical Definition**
Hash aggregation builds a hash table keyed by the grouping columns, accumulating aggregate state as rows arrive; it does not require sorted input and is often faster for unsorted data, but it can spill to disk if the hash table exceeds memory (`Batches > 1` in PostgreSQL). Group aggregation (sort-based) sorts the input by the grouping keys, then scans the sorted rows and accumulates aggregates for each group; it requires a sort but can be efficient when the input is already sorted or when an index provides the order. SQL Server uses `Hash Match (Aggregate)` for hash aggregation and `Stream Aggregate` for sorted aggregation; `Stream Aggregate` requires ordered input and is often paired with a `Sort` operator.

**Beginner-Friendly Explanation**
Aggregation is how you compute totals, counts, and averages per group. The database can do this in two main ways: build a hash table of groups (hash aggregation) or sort the rows by group and then walk through them (sort-based aggregation). Hash aggregation is like using a dictionary to keep a running total for each key; sort-based aggregation is like alphabetizing the list first and then adding up consecutive entries.

#### Purposes

- To compute grouped aggregates for `GROUP BY` queries.
- To support `HAVING` filters on aggregate results.
- To feed aggregated results into window functions or further joins.
- To choose between hash and sort strategies based on data size and ordering.

#### Syntax Rules and Structure

**Plan node appearance** (PostgreSQL):

```text
HashAggregate  (cost=... rows=N width=W)
  Group Key: column1, column2
  Batches: 1  Memory Usage: 12kB
  ->  child_node
```

```text
GroupAggregate  (cost=... rows=N width=W)
  Group Key: column1, column2
  ->  Sort  (cost=... rows=N width=W)
        Sort Key: column1, column2
        ->  child_node
```

**Component breakdown**

| Node | Strategy | Requires sorted input? | Spill risk |
|------|----------|------------------------|------------|
| `HashAggregate` / `Hash Match (Aggregate)` | Hash table | No | Yes (`Batches > 1`) |
| `GroupAggregate` / `Stream Aggregate` | Sort-based | Yes | Sort may spill |

**Syntax rules**

- Hash aggregation is generally chosen when the input is large and unsorted, and memory is sufficient.
- Sort-based aggregation is chosen when the input is already sorted (e.g., by an index) or when the optimizer estimates hash aggregation would be more expensive.
- `Batches > 1` in a `HashAggregate` node indicates the hash table spilled to disk.
- `Stream Aggregate` in SQL Server requires sorted input; if the input is not sorted, a `Sort` operator precedes it.

**Constraints and limitations**

- Hash aggregation can spill to disk, degrading performance.
- Sort-based aggregation adds sort cost unless the input is already ordered.
- `COUNT(DISTINCT ...)` is often implemented with sort-based aggregation or a separate hash, and may be expensive.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – HashAggregate

```sql
EXPLAIN ANALYZE
SELECT customer_id, SUM(total) AS total_spent
FROM orders
GROUP BY customer_id;
```

**Expected output** (healthy):

```text
 HashAggregate  (cost=... rows=1000 width=16)
  (actual time=50.000..60.000 rows=1000 loops=1)
   Group Key: customer_id
   Batches: 1  Memory Usage: 120kB
   ->  Seq Scan on orders  (cost=... rows=100000) (actual time=0.010..20.000 rows=100000 loops=1)
```

**Why this output appears**: The optimizer chose hash aggregation because the input is not sorted and the hash table fits in memory (`Batches: 1`). The aggregation is efficient and does not spill.

##### Example 2: PostgreSQL – GroupAggregate with sort

```sql
EXPLAIN ANALYZE
SELECT customer_id, SUM(total) AS total_spent
FROM orders
GROUP BY customer_id
ORDER BY customer_id;
```

**Expected output** (illustrative):

```text
 GroupAggregate  (cost=... rows=1000 width=16)
  (actual time=200.000..220.000 rows=1000 loops=1)
   Group Key: customer_id
   ->  Sort  (cost=... rows=100000 width=12)
        (actual time=150.000..170.000 rows=100000 loops=1)
         Sort Key: customer_id
         Sort Method: quicksort  Memory: 10240kB
         ->  Seq Scan on orders  (cost=... rows=100000) (actual time=0.010..20.000 rows=100000 loops=1)
```

**Why this output appears**: The `ORDER BY customer_id` requires sorted output, and the optimizer chose `GroupAggregate` (which also requires sorted input) instead of hash aggregation followed by a sort. The sort is performed in memory (`quicksort Memory: 10240kB`).

#### Real-World Cases

- **High-cardinality grouping**: Hash aggregation is often faster for many distinct groups.
- **Pre-sorted input**: If an index provides the grouping order, `GroupAggregate`/`Stream Aggregate` avoids an explicit sort.
- **Hash spill**: `Batches > 1` indicates the hash table exceeded `work_mem`; increasing `work_mem` or reducing the number of groups helps.

### 9. Join Strategies

#### Definitions

**Core Definition**
A join strategy is the algorithm used to combine rows from two or more tables; the three primary strategies are nested loop, hash join, and merge join.

**Technical Definition**
**Nested loop join** iterates over the outer input and, for each row, scans or seeks the inner input for matching rows; it is efficient when the outer input is small and the inner input has an index on the join key. **Hash join** builds a hash table on the smaller input (the build side) and probes it with rows from the larger input (the probe side); it is efficient for equi-joins on large unsorted inputs and does not require indexes, but it is memory-intensive and may spill (`Batches > 1`). **Merge join** sorts both inputs on the join keys (or uses existing sorted indexes) and merges them in a single pass; it is efficient for large inputs that are already sorted or can be cheaply sorted, and it is often used when the query also requires ordered output.

**Beginner-Friendly Explanation**
A join strategy is how the database combines two tables. A nested loop is like taking each row from the first table and searching the second table for matches—great if the first table is small and the second has an index. A hash join is like building a lookup dictionary from the smaller table and then scanning the larger table, checking each row against the dictionary—great for large tables without useful indexes. A merge join is like sorting both lists and then walking through them side by side—great when both lists are already sorted or when you need sorted output anyway.

#### Purposes

- To choose the most efficient algorithm for combining tables based on data size, indexes, and sort order.
- To diagnose why a join is slow (e.g., nested loop with a large outer input, hash join spilling to disk).
- To design indexes that enable efficient join strategies.
- To understand how join order and algorithm selection interact.

#### Syntax Rules and Structure

**Plan node appearance**:

```text
Nested Loop  (cost=... rows=N width=W)
  ->  outer_input
  ->  inner_input  (executed once per outer row; loops=outer_rows)

Hash Join  (cost=... rows=N width=W)
  Hash Cond: (outer.key = inner.key)
  ->  probe_input
  ->  Hash  (cost=... rows=N width=W)
        Buckets: 1024  Batches: 1  Memory Usage: 12kB
        ->  build_input
```

```text
Merge Join  (cost=... rows=N width=W)
  Merge Cond: (outer.key = inner.key)
  ->  outer_input  (sorted by key)
  ->  inner_input  (sorted by key)
```

**Component breakdown**

| Strategy | Requires index? | Requires sort? | Spill risk | Best for |
|----------|----------------|----------------|------------|----------|
| Nested Loop | Inner side index (or small inner) | No | No | Small outer set + indexed inner lookup |
| Hash Join | No | No | Yes (`Batches > 1`) | Large unsorted equi-joins |
| Merge Join | No (but indexes help) | Yes, unless presorted | Sort may spill | Large presorted inputs or ordered output |

**Syntax rules**

- Nested loop: inner side is executed once per outer row; `loops` equals the number of outer rows.
- Hash join: the build side is the smaller input (shown as the child of the `Hash` node); the probe side is the other child.
- Merge join: both inputs must be sorted on the join keys; sorts may be explicit (`Sort` nodes) or provided by indexes.
- The optimizer chooses based on estimated cardinality, available indexes, and cost.

**Constraints and limitations**

- Nested loop with a large outer input and no inner index can be disastrously slow.
- Hash join can spill to disk if the hash table exceeds `work_mem` (PostgreSQL) or memory grant (SQL Server).
- Merge join requires sorted inputs; if sorts are needed, the total cost may exceed a hash join.
- SQL Server `Hash Match` can also perform aggregation; in a join context, it is the hash join operator.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Nested loop join with index lookup

```sql
EXPLAIN ANALYZE
SELECT o.id, c.email
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.customer_id = 42;
```

**Expected output**:

```text
 Nested Loop  (cost=0.43..16.50 rows=3 width=40)
  (actual time=0.030..0.045 rows=3 loops=1)
   ->  Index Scan using idx_orders_customer on orders o
         (cost=0.43..8.45 rows=3 width=8)
         (actual time=0.021..0.031 rows=3 loops=1)
         Index Cond: (customer_id = 42)
   ->  Index Scan using customers_pkey on customers c
         (cost=0.29..8.31 rows=1 width=32)
         (actual time=0.003..0.004 rows=1 loops=3)
         Index Cond: (id = o.customer_id)
```

**Why this output appears**: The outer input (`orders` filtered by `customer_id = 42`) produces only 3 rows. For each of those 3 rows, the inner `customers` table is accessed via primary key index lookup (`loops=3`). The nested loop is efficient because the outer set is tiny and the inner side is indexed.

##### Example 2: PostgreSQL – Hash join

```sql
EXPLAIN ANALYZE
SELECT c.name, SUM(o.total) AS total_spent
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE c.status = 'active'
GROUP BY c.name;
```

**Expected output** (illustrative):

```text
 HashAggregate  (cost=... rows=100 width=...)
   Group Key: c.name
   ->  Hash Join  (cost=... rows=5000 width=...)
         Hash Cond: (o.customer_id = c.id)
         ->  Seq Scan on orders o  (cost=... rows=100000 width=...)
         ->  Hash  (cost=... rows=100 width=...)
               Buckets: 1024  Batches: 1  Memory Usage: 12kB
               ->  Seq Scan on customers c  (cost=... rows=100 width=...)
                     Filter: (status = 'active')
```

**Why this output appears**: The optimizer chose a hash join because both inputs are relatively large and neither has a useful index for the join. It builds a hash table on the filtered `customers` result (the smaller side) and probes it with `orders`. `Batches: 1` indicates the hash table fit in memory.

##### Example 3: SQL Server – Nested Loops vs Hash Match vs Merge Join

```sql
-- Nested Loops (good for small outer input)
SELECT ... FROM SmallOuter o JOIN LargeInner i ON o.key = i.key;

-- Hash Match (good for large unsorted inputs)
SELECT ... FROM LargeTableA a JOIN LargeTableB b ON a.key = b.key;

-- Merge Join (good for presorted inputs)
SELECT ... FROM SortedA a JOIN SortedB b ON a.key = b.key;
```

**Why this output appears**: SQL Server’s optimizer chooses the join operator based on estimated cardinality and the presence of sorted indexes. Nested Loops is efficient when the outer input is small; Hash Match handles large unsorted inputs; Merge Join leverages presorted inputs and can avoid explicit sorts.

#### Real-World Cases

- **OLTP point lookups**: Nested loop with index seeks is ideal for small result sets.
- **Analytical joins**: Hash joins handle large fact-to-dimension joins without requiring indexes on every foreign key.
- **Ordered reporting**: Merge joins can satisfy `ORDER BY` without an additional sort.
- **Hash spill**: `Batches > 1` indicates the hash table exceeded `work_mem`; increasing it or adding an index to enable a nested loop can help.

### 10. Buffers

#### Definitions

**Core Definition**
Buffer statistics report how many database pages were served from the shared buffer cache (`shared hit`) versus read from disk (`shared read`), providing insight into the I/O efficiency of a query.

**Technical Definition**
In PostgreSQL, `EXPLAIN (ANALYZE, BUFFERS)` reports buffer usage per node: `shared hit` (pages found in the shared buffer cache, avoiding a read), `shared read` (pages read from disk or the OS cache into the shared buffer cache), `shared dirtied` (previously unmodified pages changed by the query), `shared written` (previously dirtied pages evicted from cache), `local` blocks (temporary tables/indexes), and `temp` blocks (short-term working data for sorts, hashes, materialize nodes). A high `shared hit` ratio indicates good cache utilization; a high `shared read` count indicates disk I/O. Buffer counts for an upper-level node include those of all its child nodes. When `ANALYZE` is used, `BUFFERS` is included by default in PostgreSQL 18+ (previously required explicit `BUFFERS`).

**Beginner-Friendly Explanation**
Buffers tell you whether the database found the data it needed in memory (`hit`) or had to fetch it from disk (`read`). Reading from disk is 100–1000× slower than reading from memory, so a plan with many `shared read` pages is a sign that the query is I/O-bound and might benefit from more memory or a better index.

#### Purposes

- To determine whether a query is I/O-bound or CPU-bound.
- To evaluate cache efficiency and the impact of `shared_buffers` sizing.
- To detect disk-spilling sorts and hash joins (`temp` blocks).
- To compare alternative plans by their actual I/O footprint, not just estimated cost.

#### Syntax Rules and Structure

**PostgreSQL**:

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
```

**Output fields**:

```text
Buffers: shared hit=25 read=2
Buffers: shared hit=100 read=5000 dirtied=10 written=5
Buffers: local hit=0 read=0
Buffers: temp read=1024 written=512
```

**Component breakdown**

| Field | Meaning |
|-------|---------|
| `shared hit` | Pages served from the shared buffer cache (RAM). Fast. |
| `shared read` | Pages read from disk (or OS cache) into shared buffers. Slow. |
| `shared dirtied` | Pages modified by the query. |
| `shared written` | Previously dirtied pages written out during query execution. |
| `local hit/read` | Pages for temporary tables/indexes (session-local). |
| `temp read/written` | Short-term working data for sorts, hashes, materialize nodes. |

**Syntax rules**

- `BUFFERS` can be used alone (planning-phase buffer usage only) or with `ANALYZE` (execution-phase usage).
- In PostgreSQL 18+, `BUFFERS` is included automatically when `ANALYZE` is used.
- Buffer counts are cumulative for the node and all its children.
- In text format, only non-zero values are printed.

**Constraints and limitations**

- `shared hit` vs `shared read` depends on cache state; a plan that shows many reads on a cold cache may show hits on a warm cache.
- Buffer statistics do not directly translate to wall-clock time unless `track_io_timing` is enabled.
- High `shared hit` counts can still be expensive if the query touches many pages; hits are cheaper than reads but not free.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Cache-friendly plan

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE customer_id = 42;
```

**Expected output**:

```text
 Index Scan using idx_orders_customer on orders
  (cost=0.43..8.45 rows=3 width=72)
  (actual time=0.021..0.031 rows=3 loops=1)
  Index Cond: (customer_id = 42)
  Buffers: shared hit=5 read=0
```

**Why this output appears**: All 5 pages needed by the index scan were already in the shared buffer cache (`hit=5, read=0`). The query is CPU-bound rather than I/O-bound, and the low buffer count reflects the selectivity of the predicate.

##### Example 2: PostgreSQL – I/O-heavy sequential scan

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) FROM large_table WHERE status = 'active';
```

**Expected output** (problematic):

```text
 Aggregate  (cost=... rows=1 width=8)
  (actual time=500.000..500.001 rows=1 loops=1)
  Buffers: shared hit=100 read=50000
  ->  Seq Scan on large_table  (cost=... rows=1000 width=0)
        (actual time=0.010..450.000 rows=500000 loops=1)
        Filter: (status = 'active'::text)
        Rows Removed by Filter: 9500000
        Buffers: shared hit=100 read=50000
```

**Why this output appears**: The sequential scan read 50,000 pages from disk (`shared read=50000`) and found only 100 in cache. The `Rows Removed by Filter: 9500000` shows that most rows were discarded. This query is heavily I/O-bound and would benefit from an index on `status`.

##### Example 3: PostgreSQL – Temp blocks from a disk-spilling sort

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders ORDER BY total DESC;
```

**Expected output**:

```text
 Sort  (cost=... rows=1000000 width=72)
  (actual time=5000.000..5500.000 rows=1000000 loops=1)
  Sort Key: total DESC
  Sort Method: external merge  Disk: 102400kB
  Buffers: shared hit=20000 read=1000, temp read=12800 written=12800
  ->  Seq Scan on orders  (cost=... rows=1000000 width=72)
        (actual time=0.010..800.000 rows=1000000 loops=1)
        Buffers: shared hit=20000 read=1000
```

**Why this output appears**: The sort spilled to disk (`external merge Disk: 102400kB`), consuming 12,800 temporary blocks (`temp read=12800 written=12800`). The `temp` blocks are a clear indicator of `work_mem` exhaustion. Increasing `work_mem` or adding an index on `total` would eliminate the spill.

#### Real-World Cases

- **Cache hit ratio**: A query with `shared hit=10000, read=10` is cache-friendly; one with `hit=100, read=50000` is I/O-bound.
- **`work_mem` tuning**: `temp` blocks in sort or hash nodes indicate insufficient `work_mem`.
- **Index validation**: Comparing buffer counts before and after adding an index shows the I/O reduction.

### 11. Loops

#### Definitions

**Core Definition**
`loops` is the number of times a plan node was executed during query execution; actual time and row counts are reported per loop, so the total contribution is `actual time × loops` and `rows × loops`.

**Technical Definition**
In actual execution plans (PostgreSQL `EXPLAIN ANALYZE`, MySQL `EXPLAIN ANALYZE`), each node reports `loops=N`. A node with `loops=1` was executed once. A node on the inner side of a nested loop is executed once per outer row, so its `loops` equals the number of outer rows. The `actual time` and `rows` values are **per loop**, not cumulative. To compute the total time spent in a node, multiply `actual time` (the second number) by `loops`. To compute the total rows produced, multiply `rows` by `loops`. Misreading `loops` is a common source of confusion when analyzing nested loop plans: an inner node with `actual time=0.001..0.001 rows=1 loops=1000` actually contributed approximately 1 second (1000 × 0.001 s) to the query.

**Beginner-Friendly Explanation**
`loops` tells you how many times a step was repeated. In a nested loop, the inner step runs once for every row of the outer step. If the inner step takes 1 millisecond and runs 1,000 times, that is 1 second total—easy to miss if you only look at the per-loop time. Always multiply by loops to see the real cost.

#### Purposes

- To compute the true total time and row count contribution of a node.
- To identify nested loops where the inner side is executed a large number of times.
- To compare per-loop efficiency across nodes with different loop counts.
- To avoid misdiagnosing a “fast” inner node that is actually expensive in aggregate.

#### Syntax Rules and Structure

**Fields**:

```text
(actual time=start..end rows=N loops=L)
```

| Field | Meaning |
|-------|---------|
| `start` | Time to first row, per loop (ms). |
| `end` | Time to last row, per loop (ms). |
| `rows` | Rows returned per loop. |
| `loops` | Number of executions. |

**Total contribution**:

- Total time ≈ `end × loops` (rough approximation; ignores startup overlap between loops).
- Total rows = `rows × loops`.

**Syntax rules**

- `loops=1` means the node was executed once (typical for root nodes and sequential scans).
- Inner nested loop nodes typically have `loops > 1`; `loops` equals the number of outer rows that triggered the inner execution.
- In PostgreSQL, `actual time` is measured per loop; `loops` is shown explicitly.
- In MySQL `EXPLAIN ANALYZE`, `loops=L` is similarly reported per node.

**Constraints and limitations**

- The simple multiplication `end × loops` is an approximation; overlapping I/O and CPU work between loops can make the actual total slightly different.
- A node with `loops=0` may appear in some plans (e.g., a branch not executed due to a `LIMIT`); its actual time is not meaningful.
- `rows` is per loop, so the total rows produced by the node may be much larger than the displayed `rows` value.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Nested loop with high inner loop count

```sql
EXPLAIN ANALYZE
SELECT o.id, c.email
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'pending';
```

**Expected output** (illustrative, problematic):

```text
 Nested Loop  (cost=... rows=10000 width=40)
  (actual time=0.050..2500.000 rows=10000 loops=1)
   ->  Seq Scan on orders o  (cost=... rows=10000 width=8)
         (actual time=0.010..100.000 rows=10000 loops=1)
         Filter: (status = 'pending')
   ->  Index Scan using customers_pkey on customers c
         (cost=0.29..8.31 rows=1 width=32)
         (actual time=0.001..0.001 rows=1 loops=10000)
         Index Cond: (id = o.customer_id)
```

**Why this output appears**: The inner `customers` index scan has `loops=10000` because it is executed once for each of the 10,000 pending orders. Per-loop time is only 0.001 ms, but the total contribution is approximately 10,000 × 0.001 ms = 10 ms (plus overhead), while the outer sequential scan took 100 ms. The total query time is about 2.5 seconds, much of which comes from the repeated inner executions and their cumulative overhead. Misreading the per-loop time as the total would severely underestimate the cost of the inner side.

##### Example 2: MySQL – `loops` on a nested loop inner step

```sql
EXPLAIN ANALYZE
SELECT * FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'pending';
```

**Expected output** (illustrative):

```text
-> Nested loop inner join  (cost=... rows=10000) (actual time=0.050..2500.000 rows=10000 loops=1)
    -> Filter: (o.status = 'pending')  (cost=... rows=10000) (actual time=0.010..100.000 rows=10000 loops=1)
        -> Table scan on o  (cost=... rows=100000) (actual time=0.005..80.000 rows=100000 loops=1)
    -> Single-row index lookup on c using PRIMARY (id=o.customer_id)
        (cost=... rows=1) (actual time=0.001..0.001 rows=1 loops=10000)
```

**Why this output appears**: The inner index lookup runs 10,000 times, once per pending order. The per-loop time is tiny, but the loop count reveals that the inner side is the dominant repeated operation. If the inner lookup were missing an index (e.g., a table scan per outer row), the total cost would be catastrophic.

#### Real-World Cases

- **Nested loop diagnosis**: An inner node with `loops=100000` and 0.01 ms per loop contributes ~1 second; without multiplying by loops, the node appears “fast.”
- **Join strategy validation**: A nested loop with a large outer input and high inner loop count may be a sign that a hash join would be more efficient.
- **Index effectiveness**: Inner index scans with `loops` equal to outer rows are efficient only if the per-loop cost is low; high per-loop cost × high loops indicates a missing or inefficient index.
