# Comprehensive Programming Cheat Sheet: Query Anti-Patterns

## Topic Overview

### Definitions

**Core Definition**  
Query anti-patterns are recurring SQL coding practices that are syntactically valid and often produce correct results, but systematically degrade performance, scalability, or maintainability by preventing the optimizer from using indexes, generating excessive work, or obscuring intent.

**Technical Definition**  
A query anti-pattern is a structural or stylistic construct that undermines one or more optimizer capabilities—sargability (the ability to use an index for a predicate), cardinality estimation, join enumeration, or set-based execution. Common categories include non-sargable predicates (functions or implicit casts applied to indexed columns), row-by-row processing masquerading as SQL (N+1 queries, correlated subqueries in `SELECT`), unnecessary work (overuse of `DISTINCT`, sorting, aggregation, `UNION` when `UNION ALL` suffices), and constructs that defeat index usage (`LIKE '%...'`, `OR` across different columns, large `IN` lists). Anti-patterns are context-dependent: a construct that is harmless on a 1,000-row table can be catastrophic on a 100-million-row table.

**Beginner-Friendly Explanation**  
Query anti-patterns are "common mistakes that look fine but make the database work much harder than necessary." They are like taking a detour on every trip: the destination is the same, but you waste time, fuel, and patience. Recognizing these patterns is the first step to writing queries that scale.

### Key Characteristics

- **Context-sensitive severity**: Anti-patterns may be negligible on small tables but crippling at scale; the same query can be fast in development and slow in production.
- **Optimizer-defeating**: Most anti-patterns prevent the use of indexes, statistics, or set-based algorithms, forcing full scans, repeated execution, or per-row computation.
- **Subtle correctness traps**: Some anti-patterns (implicit conversions, `NOT IN` with `NULL`) can silently produce wrong results as well as poor performance.
- **Widely generated by tools**: ORMs, query builders, and reporting tools frequently emit anti-patterns such as `SELECT *`, N+1 queries, and overuse of `DISTINCT`.
- **Fixable by rewriting, not tuning**: Anti-patterns usually require query restructuring (sargable predicates, joins instead of subqueries, `EXISTS` instead of `IN`), not parameter changes.
- **Measurable**: Every anti-pattern has a characteristic execution-plan signature (e.g., `Seq Scan` with `Filter`, `DEPENDENT SUBQUERY`, `Using temporary`, `filesort`).

### Prerequisites

- Understanding of `SELECT`, `WHERE`, `JOIN`, `GROUP BY`, `ORDER BY`, and subqueries.
- Familiarity with B-tree indexes and how they accelerate predicates.
- Knowledge of `EXPLAIN` / execution plans and how to read scan types.
- Awareness of SQL's three-valued logic (`NULL`) and implicit type conversion rules.
- Familiarity with the target engine's optimizer behavior and statistics.

### Related Programming Areas

- Query optimization and execution plan analysis.
- ORM configuration and query generation.
- Index design and sargability analysis.
- Application performance engineering and API design.
- Database code review and static analysis.

## Core Concepts and Features

### 1. `SELECT *`

#### Definitions

**Core Definition**  
`SELECT *` retrieves every column from every referenced table, regardless of whether the application needs them.

**Technical Definition**  
`SELECT *` expands to all columns of the `FROM` relations at parse or rewrite time. This defeats **covering index** optimizations (the engine cannot answer the query from index pages alone because it needs heap access for non-indexed columns), increases network transfer and memory consumption, and breaks silently when the table schema changes (adding or reordering columns changes result shape). In views, `SELECT *` is expanded at creation time in most engines, so later column additions to base tables do not appear in the view—a subtle correctness trap.

**Beginner-Friendly Explanation**  
`SELECT *` means "give me everything." It is convenient in ad-hoc exploration, but in application code it fetches columns you never use, forces the database to read more data than necessary, and can break your application when someone adds a column.

#### Purposes

- To explore table contents quickly during development or debugging.
- To retrieve all columns when the application genuinely needs every column.
- To simplify ad-hoc queries where schema knowledge is unavailable.
- To generate dynamic result sets in tools that adapt to schema changes.

#### Syntax Rules and Structure

**Anti-pattern**:

```sql
SELECT * FROM orders WHERE customer_id = 42;
```

**Preferred**:

```sql
SELECT order_id, order_date, total
FROM orders
WHERE customer_id = 42;
```

**Component breakdown**:

| Form | Columns fetched | Covering index possible? | Schema-change risk |
|------|-----------------|--------------------------|--------------------|
| `SELECT *` | All columns | No (needs heap) | High |
| Explicit column list | Only needed columns | Yes | Low |

**Syntax rules**:

- `SELECT *` is expanded to the full column list at query parse time.
- In a view definition, `SELECT *` is frozen at creation; new columns are not automatically included.
- In joins, `SELECT *` returns duplicate column names, causing ambiguity in some clients and ORMs.

**Constraints and limitations**:

- `SELECT *` prevents index-only scans because the engine cannot guarantee that all columns are present in the index.
- Wide tables with `TEXT` or `JSON` columns amplify network and memory costs dramatically.
- Column order and count changes can break `INSERT ... SELECT *` and application code that relies on positional binding.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – `SELECT *` prevents index-only scan

```sql
-- Create a covering index.
CREATE INDEX idx_orders_customer_covering
ON orders (customer_id) INCLUDE (order_date, total);

-- Anti-pattern: SELECT * requires heap access.
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE customer_id = 42;

-- Preferred: explicit columns enable index-only scan.
EXPLAIN (ANALYZE, BUFFERS)
SELECT order_date, total FROM orders WHERE customer_id = 42;
```

**Expected output** (anti-pattern):

```text
Index Scan using idx_orders_customer_covering on orders
  Index Cond: (customer_id = 42)
  Buffers: shared hit=25
```

**Expected output** (preferred):

```text
Index Only Scan using idx_orders_customer_covering on orders
  Index Cond: (customer_id = 42)
  Heap Fetches: 0
  Buffers: shared hit=5
```

**Why this output appears**: `SELECT *` requests columns not present in the covering index, forcing a heap fetch for each matching row. The explicit column list is fully covered by the index, enabling an `Index Only Scan` that touches far fewer buffers.

#### Real-World Cases

- **ORM-generated queries**: Many ORMs default to `SELECT *`; configuring explicit projections reduces I/O.
- **API responses**: Endpoints returning full entities when clients need only a few fields.
- **Wide analytical tables**: Fetching 200 columns when 5 are used increases transfer time tenfold.

### 2. N+1 Queries

#### Definitions

**Core Definition**  
The N+1 query anti-pattern executes one query to retrieve a list of N parent records and then N additional queries—one per parent—to retrieve related child records, resulting in N+1 round trips instead of a single join.

**Technical Definition**  
N+1 queries arise when an application iterates over a result set and issues a dependent query for each row (typically through an ORM's lazy-loading behavior). The total cost is `1 + N` network round trips, `1 + N` query parses/plans, and `1 + N` index lookups, whereas a single join or `IN` query would require one round trip. The pattern is especially harmful in high-latency environments (remote databases, serverless) because each round trip adds network latency.

**Beginner-Friendly Explanation**  
Imagine ordering a pizza and then calling the restaurant once for each topping to ask if it is ready. N+1 queries are the database equivalent: fetching a list of 1,000 orders, then calling the database 1,000 more times to get each order's customer.

#### Purposes

- To understand why application pages slow down as data volume grows.
- To recognize lazy-loading ORM behavior that generates per-row queries.
- To replace loops of dependent queries with set-based joins or `IN` queries.
- To reduce network round trips and database connection pressure.

#### Syntax Rules and Structure

**Anti-pattern (application code)**:

```text
orders = SELECT id FROM orders WHERE status = 'pending'  -- 1 query
for each order in orders:
    customer = SELECT name FROM customers WHERE id = order.customer_id  -- N queries
```

**Preferred (single join)**:

```sql
SELECT o.id, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'pending';
```

**Component breakdown**:

| Approach | Round trips | Parses | Index lookups |
|----------|-------------|--------|---------------|
| N+1 loop | 1 + N | 1 + N | 1 + N |
| Single join | 1 | 1 | 1 (hash/merge) |

**Syntax rules**:

- N+1 occurs when the child query depends on a value from the parent loop.
- Batching with `WHERE id IN (...)` reduces N+1 to 2 queries (1 parent + 1 batched child).
- Eager loading in ORMs (e.g., `JOIN FETCH`, `Include()`, `selectinload`) eliminates the pattern.

**Constraints and limitations**:

- Batching has an upper bound on `IN` list size; very large lists may need chunking.
- Joins can multiply parent rows if the relationship is one-to-many; use `DISTINCT` or a subquery aggregate carefully.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: SQL Server – N+1 vs. single join

```sql
-- Anti-pattern: one query per customer (simulated).
-- Application issues:
SELECT OrderID FROM Orders WHERE Status = 'Pending';  -- returns 10,000 rows
-- Then 10,000 times:
SELECT CustomerName FROM Customers WHERE CustomerID = @id;

-- Preferred: single join.
SELECT o.OrderID, c.CustomerName
FROM Orders o
JOIN Customers c ON c.CustomerID = o.CustomerID
WHERE o.Status = 'Pending';
```

**Expected output**: The join returns 10,000 rows in a single round trip; the N+1 version performs 10,001 round trips.

**Why this output appears**: The single join allows the optimizer to choose a hash or merge join, processing all rows in one pass. The N+1 version incurs 10,000 network round trips, 10,000 parses, and 10,000 index lookups—orders of magnitude more overhead.

#### Real-World Cases

- **ORM lazy loading**: Django, Hibernate, SQLAlchemy, and Entity Framework lazy-load relationships by default.
- **REST APIs**: Listing resources and fetching related resources per item.
- **Report generation**: Iterating over rows in application code instead of aggregating in SQL.

### 3. Functions on Indexed Columns

#### Definitions

**Core Definition**  
Applying a function to an indexed column in a predicate—such as `UPPER(col) = 'X'` or `DATE(col) = '2025-01-01'`—prevents the optimizer from using a standard index on that column, because the index stores the raw column values, not the function results.

**Technical Definition**  
A predicate is **sargable** (Search ARGument-able) if the optimizer can translate it into an index range scan. Wrapping the indexed column in a function makes the predicate non-sargable unless a **function-based index** (also called an expression index) exists on that exact expression. The optimizer cannot infer that `UPPER(email) = 'A@B.COM'` implies `email = 'a@b.com'` because collation and case-folding rules are complex; it must evaluate the function per row.

**Beginner-Friendly Explanation**  
If you have an index on a person's last name, searching `WHERE last_name = 'Smith'` uses the index. But `WHERE UPPER(last_name) = 'SMITH'` forces the database to compute `UPPER` on every row, which is like reading the entire phone book to find names that become "SMITH" when uppercased.

#### Purposes

- To recognize when a predicate is non-sargable and causing a full scan.
- To rewrite predicates so the indexed column appears alone on one side.
- To decide when a function-based index is the appropriate fix.
- To understand collation and case-sensitivity implications.

#### Syntax Rules and Structure

**Anti-pattern**:

```sql
SELECT * FROM users WHERE UPPER(email) = 'ALICE@EXAMPLE.COM';
SELECT * FROM orders WHERE DATE(created_at) = '2025-01-01';
SELECT * FROM products WHERE price * 1.1 > 100;
```

**Preferred (sargable)**:

```sql
SELECT * FROM users WHERE email = LOWER('ALICE@EXAMPLE.COM');
SELECT * FROM orders
WHERE created_at >= '2025-01-01' AND created_at < '2025-01-02';
SELECT * FROM products WHERE price > 100 / 1.1;
```

**Function-based index (when the function is unavoidable)**:

```sql
CREATE INDEX idx_users_lower_email ON users (LOWER(email));
SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';
```

**Component breakdown**:

| Form | Sargable? | Index usable? |
|------|-----------|---------------|
| `col = value` | Yes | Yes |
| `FUNC(col) = value` | No | Only with expression index |
| `col OP value` (rewritten) | Yes | Yes |

**Syntax rules**:

- The indexed column must appear alone on one side of the comparison.
- Date range predicates (`>= start AND < next_day`) replace `DATE(col) = '...'`.
- Arithmetic can often be moved to the constant side (`price > 100/1.1`).
- Expression indexes must match the expression exactly, including case and function.

**Constraints and limitations**:

- Expression indexes add write overhead and storage.
- Some functions (e.g., `LOWER` with non-deterministic collation) cannot be indexed.
- The optimizer may not use expression indexes if the expression differs syntactically (e.g., `LOWER(col)` vs. `lower(col)`).

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – `DATE()` function prevents index usage

```sql
-- Anti-pattern
EXPLAIN ANALYZE
SELECT * FROM orders WHERE DATE(created_at) = '2025-01-01';

-- Preferred
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE created_at >= '2025-01-01' AND created_at < '2025-01-02';
```

**Expected output** (anti-pattern):

```text
Seq Scan on orders  (cost=0.00..25000.00 rows=5000 width=72)
  Filter: (date(created_at) = '2025-01-01'::date)
  Rows Removed by Filter: 995000
```

**Expected output** (preferred):

```text
Index Scan using idx_orders_created_at on orders
  Index Cond: ((created_at >= '2025-01-01') AND (created_at < '2025-01-02'))
  Buffers: shared hit=25
```

**Why this output appears**: `DATE(created_at)` is computed for every row, preventing the B-tree on `created_at` from being used for an index range scan. The range rewrite exposes the raw column, allowing the index to seek directly to the matching date.

#### Real-World Cases

- **Timestamp filtering**: `DATE(created_at) = ...` is one of the most common anti-patterns in reporting queries.
- **Case-insensitive lookups**: `UPPER(email) = ...` without a `LOWER(email)` expression index.
- **Arithmetic in predicates**: `price * 1.1 > 100` prevents index use on `price`.

### 4. Implicit Type Conversions

#### Definitions

**Core Definition**  
An implicit type conversion occurs when the database automatically converts a value from one data type to another to evaluate a comparison; when the conversion is applied to the indexed column rather than the constant, it defeats index usage.

**Technical Definition**  
Type resolution rules determine which operand is converted. In many engines, the column is converted to match the constant's type when the types differ in a way that favors the literal (e.g., comparing a `VARCHAR` column to an integer literal causes the column to be cast to numeric). When the column is cast, the index on the original column type cannot be used. Additionally, implicit conversions can produce **incorrect results** when values are truncated, rounded, or compared under unexpected collation rules.

**Beginner-Friendly Explanation**  
If you compare a text column to a number, the database may convert every row's text to a number before comparing. That means it cannot use the index on the text column—and it may also match rows you did not expect.

#### Purposes

- To identify why a predicate on an indexed column is not using the index.
- To fix data-type mismatches between application parameters and column definitions.
- To avoid silent correctness bugs from implicit conversion.
- To design schemas with consistent data types across join keys.

#### Syntax Rules and Structure

**Anti-pattern**:

```sql
-- phone_number is VARCHAR; comparing to integer forces column cast.
SELECT * FROM customers WHERE phone_number = 5551234;

-- Join keys with mismatched types.
SELECT * FROM orders o JOIN customers c ON c.id = o.customer_id;  -- id INT, customer_id VARCHAR
```

**Preferred**:

```sql
SELECT * FROM customers WHERE phone_number = '5551234';
-- Align column types in the schema.
ALTER TABLE orders ALTER COLUMN customer_id TYPE INT USING customer_id::int;
```

**Component breakdown**:

| Scenario | Conversion direction | Index usable? |
|----------|---------------------|---------------|
| `varchar_col = integer_literal` | Column → numeric | No |
| `integer_col = varchar_literal` | Literal → integer | Yes (if valid) |
| Join keys with different types | One side cast | Often no |

**Syntax rules**:

- Prefer matching literal types to column types; quote string literals for character columns.
- Align join-key types across tables.
- In PostgreSQL, use explicit `CAST` on the constant side to force the desired direction.

**Constraints and limitations**:

- PostgreSQL has no implicit conversion from `integer` to `text` in comparisons, but it does convert `text` to `integer` in some contexts—behavior differs by engine.
- SQL Server's data type precedence rules convert lower-precedence types to higher-precedence ones; `VARCHAR` has lower precedence than `INT`, so the column is converted.
- MySQL performs extensive implicit conversion and may silently return wrong results.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: SQL Server – `VARCHAR` column compared to integer

```sql
-- Anti-pattern: column converted to INT, index unusable.
SELECT * FROM Customers WHERE PhoneNumber = 5551234;

-- Preferred: string literal matches column type.
SELECT * FROM Customers WHERE PhoneNumber = '5551234';
```

**Expected output** (anti-pattern plan excerpt):

```text
Table Scan (Customers)
  Predicate: CONVERT_IMPLICIT(int, [PhoneNumber], 0) = 5551234
```

**Expected output** (preferred plan excerpt):

```text
Index Seek (Customers.IX_PhoneNumber)
  Seek Keys: PhoneNumber = '5551234'
```

**Why this output appears**: SQL Server's data type precedence converts `PhoneNumber` to `INT` for the comparison, wrapping the column in `CONVERT_IMPLICIT` and preventing the index seek. The string literal avoids the conversion.

#### Real-World Cases

- **Phone numbers and ZIP codes**: Stored as `VARCHAR` but compared to numeric literals.
- **Join keys with mismatched types**: `INT` versus `BIGINT` or `VARCHAR` versus `CHAR`.
- **Date literals**: Comparing `DATE` columns to string literals in engines that convert the column.

### 5. Non-Sargable Predicates

#### Definitions

**Core Definition**  
A non-sargable predicate is a `WHERE` condition that cannot be translated into an index range scan, forcing the database to evaluate the condition on every row.

**Technical Definition**  
Sargability requires that the indexed column appear as a bare column reference on one side of a comparison, with a constant or runtime value on the other side. Non-sargable constructs include functions on the column, leading-wildcard `LIKE` patterns, arithmetic on the column, `OR` across different columns, `NOT` and `<>` in some cases, and comparisons between two columns. The optimizer may still use an index for other predicates in the same query, but the non-sargable predicate is applied as a post-filter.

**Beginner-Friendly Explanation**  
A sargable predicate is one the index can "seek" directly to. A non-sargable predicate is one the index cannot help with, so the database must check every row.

#### Purposes

- To identify predicates that prevent index usage.
- To rewrite conditions into sargable forms.
- To understand when a full scan is unavoidable (e.g., leading-wildcard search).
- To choose the right index type (B-tree vs. trigram vs. full-text) for non-sargable patterns.

#### Syntax Rules and Structure

**Non-sargable examples**:

```sql
WHERE UPPER(name) = 'ALICE'          -- function on column
WHERE name LIKE '%alice%'            -- leading wildcard
WHERE price + 10 > 100               -- arithmetic on column
WHERE col1 = col2                    -- column-to-column comparison
WHERE col <> 'X'                     -- negation (sometimes)
WHERE status = 'A' OR priority = 1   -- OR across columns
```

**Sargable equivalents**:

```sql
WHERE name = 'ALICE'
WHERE name LIKE 'alice%'             -- prefix only
WHERE price > 90                     -- arithmetic moved
WHERE col1 = 'X'                     -- compare to constant
WHERE col IN ('A', 'B')              -- positive list
-- OR across columns may need UNION ALL or an index merge
```

**Component breakdown**:

| Predicate type | Sargable? | Fix |
|----------------|-----------|-----|
| `col = constant` | Yes | — |
| `FUNC(col) = constant` | No | Expression index or rewrite |
| `col LIKE 'prefix%'` | Yes | — |
| `col LIKE '%suffix'` | No | Trigram/full-text index |
| `col + n > constant` | No | Move arithmetic |
| `col1 = col2` | No | Join or computed column |

**Syntax rules**:

- Prefix `LIKE 'abc%'` is sargable; suffix or infix patterns are not.
- `OR` across the same column can often be rewritten as `IN`.
- `OR` across different columns may require `UNION ALL` or index merge.

**Constraints and limitations**:

- Some non-sargable patterns (e.g., suffix search) require specialized index types (GIN trigram, full-text).
- Collation and case sensitivity affect whether prefix `LIKE` is sargable.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Leading wildcard prevents index use

```sql
-- Anti-pattern
EXPLAIN ANALYZE
SELECT * FROM products WHERE name LIKE '%widget%';

-- Preferred (prefix search is sargable)
EXPLAIN ANALYZE
SELECT * FROM products WHERE name LIKE 'widget%';

-- For infix search, use a trigram index.
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_products_name_trgm ON products USING gin (name gin_trgm_ops);
```

**Expected output** (anti-pattern):

```text
Seq Scan on products  (cost=0.00..2500.00 rows=100 width=60)
  Filter: (name ~~ '%widget%'::text)
  Rows Removed by Filter: 99900
```

**Expected output** (prefix):

```text
Index Scan using idx_products_name on products
  Index Cond: (name ~~ 'widget%'::text)
```

**Why this output appears**: A leading wildcard cannot be translated into an index range because the B-tree is ordered by the full string prefix. A prefix pattern can seek to the starting point. For infix search, a trigram index supports `LIKE '%...%'` by indexing three-character substrings.

#### Real-World Cases

- **Search features**: `LIKE '%term%'` on large product or user tables.
- **Case-insensitive matching**: `UPPER(col) = ...` without expression index.
- **Date comparisons**: `DATE(col) = ...` as discussed.

### 6. Overuse of `DISTINCT`

#### Definitions

**Core Definition**  
Overusing `DISTINCT` means applying duplicate elimination to a result set that is already unique, or using `DISTINCT` to mask a join-fanout problem that should be solved by fixing the join or the query structure.

**Technical Definition**  
`DISTINCT` forces the engine to sort or hash the entire result set to remove duplicates, adding `O(n log n)` CPU and potentially spilling to disk. When the result is already unique (because a primary key or unique constraint is present in the `SELECT` list), `DISTINCT` is redundant. When `DISTINCT` is used to hide duplicate rows caused by a one-to-many join, it masks the underlying cardinality problem and may still produce incorrect results if non-key columns differ.

**Beginner-Friendly Explanation**  
`DISTINCT` is a de-duplication step. If your data is already unique, it is wasted work. If your data has duplicates because of a bad join, `DISTINCT` hides the problem instead of fixing it—and it can still give wrong answers.

#### Purposes

- To eliminate unnecessary sort/hash operations.
- To reveal underlying join-fanout problems.
- To verify that `DISTINCT` is semantically required.
- To replace `DISTINCT` with `GROUP BY` or `EXISTS` when appropriate.

#### Syntax Rules and Structure

**Redundant `DISTINCT`**:

```sql
-- Anti-pattern: id is a primary key, so DISTINCT is redundant.
SELECT DISTINCT id, name FROM products;
```

**Masking join fanout**:

```sql
-- Anti-pattern: join to orders multiplies product rows; DISTINCT hides it.
SELECT DISTINCT p.id, p.name
FROM products p
JOIN orders o ON o.product_id = p.id;
```

**Preferred (EXISTS)**:

```sql
SELECT p.id, p.name
FROM products p
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.product_id = p.id);
```

**Component breakdown**:

| Scenario | `DISTINCT` needed? | Better alternative |
|----------|-------------------|--------------------|
| Unique key in `SELECT` | No | Remove `DISTINCT` |
| One-to-many join | No | `EXISTS` or `GROUP BY` |
| Genuine duplicate values | Yes | Keep `DISTINCT` |

**Syntax rules**:

- `DISTINCT` applies to the entire `SELECT` list, not individual columns.
- `DISTINCT` and `GROUP BY` are not equivalent when aggregates are involved.
- `EXISTS` tests for the presence of a related row without multiplying rows.

**Constraints and limitations**:

- `DISTINCT` may still be required for genuine duplicate-elimination use cases.
- Replacing `DISTINCT` with `EXISTS` changes result semantics if the application expects one row per duplicate.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Redundant `DISTINCT` removal

```sql
-- Anti-pattern
EXPLAIN ANALYZE
SELECT DISTINCT customer_id, name FROM customers;

-- Preferred (customer_id is primary key)
EXPLAIN ANALYZE
SELECT customer_id, name FROM customers;
```

**Expected output** (anti-pattern):

```text
Unique  (cost=... rows=10000)
  ->  Seq Scan on customers
```

**Expected output** (preferred):

```text
Seq Scan on customers  (cost=... rows=10000)
```

**Why this output appears**: `customer_id` is a primary key, so every row is already unique. `DISTINCT` adds a `Unique` node that sorts or hashes the result unnecessarily. Removing it eliminates the deduplication step.

#### Real-World Cases

- **Reporting queries**: `SELECT DISTINCT` added defensively to "clean up" results.
- **ORM-generated joins**: `DISTINCT` used to hide fanout from eager-loaded collections.
- **Views**: `DISTINCT` in a view forces deduplication even when the caller does not need it.

### 7. Overuse of `OR`

#### Definitions

**Core Definition**  
Overusing `OR` means combining multiple conditions with `OR` in a way that prevents the optimizer from using a single index scan, often forcing a full table scan or a costly index merge.

**Technical Definition**  
A predicate `col1 = 'A' OR col2 = 'B'` requires the union of rows matching either condition. If `col1` and `col2` are different columns with separate indexes, the optimizer may perform an **index merge** (bitmap OR in PostgreSQL, index merge in MySQL, or `OR` expansion in SQL Server) or fall back to a full scan. `OR` across the same column can often be rewritten as `IN`, which is sargable. `OR` across different columns may require `UNION ALL` to use indexes efficiently.

**Beginner-Friendly Explanation**  
If you ask for "rows where city = 'Paris' OR country = 'France'," the database may have to check every row, because it cannot use one index for both conditions. Splitting the query into two indexed queries and combining them can be much faster.

#### Purposes

- To recognize when `OR` is forcing a full scan.
- To rewrite `OR` as `IN`, `UNION ALL`, or `EXISTS` where appropriate.
- To understand when `OR` is benign (same column) versus harmful (different columns).
- To design indexes that support `OR` predicates (e.g., composite or covering indexes).

#### Syntax Rules and Structure

**Benign `OR` (same column, rewritable to `IN`)**:

```sql
-- Before
SELECT * FROM orders WHERE status = 'pending' OR status = 'shipped';

-- After
SELECT * FROM orders WHERE status IN ('pending', 'shipped');
```

**Harmful `OR` (different columns)**:

```sql
-- Anti-pattern: OR across different indexed columns
SELECT * FROM customers
WHERE city = 'Paris' OR country = 'France';

-- Preferred: UNION ALL with separate index usage
SELECT * FROM customers WHERE city = 'Paris'
UNION ALL
SELECT * FROM customers WHERE country = 'France' AND city <> 'Paris';
```

**Component breakdown**:

| `OR` pattern | Sargable? | Fix |
|--------------|-----------|-----|
| Same column equality | Yes (rewrite to `IN`) | Use `IN` |
| Different columns, both indexed | Maybe (index merge) | `UNION ALL` |
| Different columns, one unindexed | No | `UNION ALL` or composite index |
| Range and equality mixed | Depends | Rewrite or composite index |

**Syntax rules**:

- `OR` conditions on the same column should generally be `IN`.
- `OR` across columns may trigger an index merge if the engine supports bitmap operations.
- `UNION ALL` requires manual deduplication if rows can match both branches.

**Constraints and limitations**:

- `UNION ALL` may duplicate rows if a row satisfies both branches; use `UNION` or add exclusion predicates.
- Index merge strategies consume memory and may not be available in all engines.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – `OR` across different columns

```sql
-- Anti-pattern
EXPLAIN ANALYZE
SELECT * FROM customers WHERE city = 'Paris' OR country = 'France';

-- Preferred
EXPLAIN ANALYZE
SELECT * FROM customers WHERE city = 'Paris'
UNION ALL
SELECT * FROM customers WHERE country = 'France' AND city <> 'Paris';
```

**Expected output** (anti-pattern):

```text
Seq Scan on customers  (cost=0.00..25000.00 rows=100 width=60)
  Filter: ((city = 'Paris') OR (country = 'France'))
  Rows Removed by Filter: 990000
```

**Expected output** (preferred):

```text
Append
  ->  Bitmap Heap Scan on customers  (city = 'Paris')
  ->  Bitmap Heap Scan on customers  (country = 'France' AND city <> 'Paris')
```

**Why this output appears**: The single `OR` predicate cannot be split across two separate index scans, so the optimizer falls back to a sequential scan. The `UNION ALL` allows each branch to use its own index, with the exclusion predicate preventing duplicates.

#### Real-World Cases

- **Search filters**: Multi-field search where users can filter by any combination of fields.
- **Status and priority filters**: `OR` across two independently indexed enum columns.
- **Geographic queries**: `city = ... OR region = ...`.

### 8. Overuse of Subqueries

#### Definitions

**Core Definition**  
Overusing subqueries means relying on nested `SELECT` statements where a join, `EXISTS`, or CTE would express the logic more efficiently and readably.

**Technical Definition**  
Subqueries can be **scalar** (return one value), **row** (return one row), **table** (return a result set in `FROM`), or **correlated** (reference outer-query columns). Correlated subqueries execute once per outer row unless the optimizer can unnest them. Non-correlated subqueries may be materialized once or folded into the parent query. Overusing subqueries often means using correlated subqueries in `SELECT` (see anti-pattern 13) or `IN (SELECT ...)` where `EXISTS` or a join would allow semi-join optimization.

**Beginner-Friendly Explanation**  
Subqueries are queries inside queries. They are fine in moderation, but using them everywhere can force the database to run the inner query repeatedly, when a single join would do the job once.

#### Purposes

- To recognize subqueries that can be rewritten as joins or `EXISTS`.
- To reduce repeated execution of correlated subqueries.
- To improve readability by replacing deep nesting with CTEs.
- To enable semi-join and anti-join optimizations.

#### Syntax Rules and Structure

**Subquery in `SELECT`**:

```sql
SELECT o.id,
       (SELECT c.name FROM customers c WHERE c.id = o.customer_id) AS cname
FROM orders o;
```

**Preferred (join)**:

```sql
SELECT o.id, c.name AS cname
FROM orders o
LEFT JOIN customers c ON c.id = o.customer_id;
```

**`IN` subquery**:

```sql
SELECT * FROM customers
WHERE id IN (SELECT customer_id FROM orders WHERE total > 1000);
```

**Preferred (`EXISTS`)**:

```sql
SELECT * FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.total > 1000);
```

**Component breakdown**:

| Subquery form | Optimization | Preferred replacement |
|---------------|--------------|------------------------|
| Scalar in `SELECT` | May be correlated | `LEFT JOIN` |
| `IN (subquery)` | Semi-join possible | `EXISTS` or join |
| `NOT IN (subquery)` | Anti-join with `NULL` trap | `NOT EXISTS` |
| Derived table | May be merged | CTE |

**Syntax rules**:

- `NOT IN` returns no rows if the subquery returns any `NULL`; `NOT EXISTS` is safer.
- Derived tables require aliases; CTEs improve readability.
- Correlated subqueries in `WHERE` may be unnestable; check `EXPLAIN`.

**Constraints and limitations**:

- Subqueries are sometimes the clearest expression of intent; overuse is the anti-pattern, not use itself.
- Some engines optimize `IN` subqueries into semi-joins automatically; others do not.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – `IN` subquery vs. `EXISTS`

```sql
-- Anti-pattern: IN with a large subquery
EXPLAIN ANALYZE
SELECT * FROM customers
WHERE id IN (SELECT customer_id FROM orders WHERE total > 1000);

-- Preferred: EXISTS with early termination
EXPLAIN ANALYZE
SELECT * FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.total > 1000);
```

**Expected output** (anti-pattern, excerpt):

```text
Hash Semi Join
  Hash Cond: (customers.id = orders.customer_id)
  ->  Seq Scan on customers
  ->  Hash
        ->  Seq Scan on orders
              Filter: (total > 1000)
```

**Expected output** (preferred, excerpt):

```text
Nested Loop Semi Join
  ->  Seq Scan on customers c
  ->  Index Scan using idx_orders_customer on orders o
        Index Cond: (customer_id = c.id)
        Filter: (total > 1000)
```

**Why this output appears**: PostgreSQL can optimize both forms, but `EXISTS` allows a nested loop semi-join with index lookup and early termination, which is faster when few customers have qualifying orders. The `IN` form builds a full hash of the subquery result.

#### Real-World Cases

- **Existence checks**: `IN (SELECT ...)` vs. `EXISTS`.
- **Scalar lookups**: Correlated scalar subqueries in `SELECT` (see anti-pattern 13).
- **Nested reporting queries**: Deeply nested subqueries that could be CTEs.

### 9. Overuse of `UNION`

#### Definitions

**Core Definition**  
Overusing `UNION` means using `UNION` (which eliminates duplicates) when `UNION ALL` (which preserves rows) would be correct and faster, or using `UNION` to combine result sets that could be expressed as a single query.

**Technical Definition**  
`UNION` performs a deduplication step (sort or hash) after concatenating the inputs, adding `O(n log n)` cost. `UNION ALL` simply concatenates, with no deduplication. When the input branches are known to be disjoint (e.g., partitioned by date or category), or when duplicates are acceptable, `UNION ALL` is semantically equivalent and faster. `UNION` is also often used where a `CASE` expression or a single query with `OR`/`IN` would suffice.

**Beginner-Friendly Explanation**  
`UNION` stacks two lists and removes duplicates. `UNION ALL` just stacks them. If you already know the lists do not overlap, the duplicate-removal step is wasted work.

#### Purposes

- To replace `UNION` with `UNION ALL` when duplicates are impossible or acceptable.
- To recognize when a single query can replace a `UNION`.
- To reduce sort/hash overhead in reporting queries.
- To preserve multiplicity when counting or auditing.

#### Syntax Rules and Structure

**Anti-pattern**:

```sql
SELECT id FROM orders_2024
UNION
SELECT id FROM orders_2025;
```

**Preferred (disjoint partitions)**:

```sql
SELECT id FROM orders_2024
UNION ALL
SELECT id FROM orders_2025;
```

**Single-query alternative**:

```sql
SELECT id FROM orders WHERE year IN (2024, 2025);
```

**Component breakdown**:

| Form | Deduplication | Cost |
|------|---------------|------|
| `UNION` | Yes | Sort/hash |
| `UNION ALL` | No | Concatenation |
| Single query with `IN`/`OR` | Depends | Index scan |

**Syntax rules**:

- Use `UNION ALL` when branches are disjoint (partitioned tables, mutually exclusive statuses).
- Use `UNION` when duplicates must be removed.
- A single query with `IN` or `OR` may replace a `UNION` over the same table.

**Constraints and limitations**:

- `UNION ALL` produces duplicates if branches overlap; verify disjointness.
- Replacing `UNION` with a single query may not be possible when branches reference different tables.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – `UNION` vs. `UNION ALL`

```sql
-- Anti-pattern: unnecessary deduplication over disjoint partitions
EXPLAIN ANALYZE
SELECT id FROM orders_2024
UNION
SELECT id FROM orders_2025;

-- Preferred
EXPLAIN ANALYZE
SELECT id FROM orders_2024
UNION ALL
SELECT id FROM orders_2025;
```

**Expected output** (anti-pattern):

```text
Unique  (cost=... rows=200000)
  ->  Append
        ->  Seq Scan on orders_2024
        ->  Seq Scan on orders_2025
```

**Expected output** (preferred):

```text
Append  (cost=... rows=200000)
  ->  Seq Scan on orders_2024
  ->  Seq Scan on orders_2025
```

**Why this output appears**: The `UNION` adds a `Unique` node that sorts or hashes the combined result to remove duplicates. Because the 2024 and 2025 partitions are disjoint, no duplicates exist, so `UNION ALL` produces the same result without the deduplication cost.

#### Real-World Cases

- **Time-partitioned tables**: `UNION ALL` over yearly or monthly partitions.
- **Status-segmented reports**: Combining mutually exclusive status groups.
- **ETL staging**: Appending extracts from different sources where overlaps are impossible.

### 10. Unnecessary Sorting

#### Definitions

**Core Definition**  
Unnecessary sorting means including an `ORDER BY` clause—or a construct that forces a sort—when the result order is not required by the application or when an index could provide the order for free.

**Technical Definition**  
Sort operations are blocking and can spill to disk when the data exceeds `work_mem`. `ORDER BY` in a subquery without `LIMIT` is semantically irrelevant and may be discarded by the optimizer, but some engines still execute it. Sorting is often introduced by `DISTINCT`, `GROUP BY`, `UNION`, or window functions that require ordered input. The anti-pattern is sorting data that does not need to be sorted, or sorting in a way that cannot use an index.

**Beginner-Friendly Explanation**  
If nobody is going to look at the rows in a specific order, sorting them is wasted work. And if an index already stores rows in the order you need, the database can read them in order without an explicit sort.

#### Purposes

- To remove `ORDER BY` clauses that are not needed.
- To use indexes that provide the required order.
- To avoid disk-spilling sorts in large queries.
- To recognize sorts introduced implicitly by other operations.

#### Syntax Rules and Structure

**Anti-pattern**:

```sql
-- ORDER BY in subquery without LIMIT (ignored or wasted)
SELECT * FROM (SELECT * FROM orders ORDER BY created_at DESC) sub;

-- Sorting a large result that the application does not order.
SELECT * FROM orders ORDER BY random();
```

**Preferred**:

```sql
SELECT * FROM orders;  -- no order needed

-- Or use an index that provides order.
CREATE INDEX idx_orders_created_at ON orders (created_at DESC);
SELECT * FROM orders ORDER BY created_at DESC LIMIT 100;
```

**Component breakdown**:

| Sort source | Avoidable? | Fix |
|-------------|-----------|-----|
| `ORDER BY` on unindexed column | Sometimes | Add index or remove |
| `ORDER BY` in subquery without `LIMIT` | Yes | Remove |
| Sort for `DISTINCT` | Yes | Remove redundant `DISTINCT` |
| Sort for `GROUP BY` | Sometimes | Hash aggregate |
| Sort for merge join | Sometimes | Hash join |

**Syntax rules**:

- `ORDER BY` without `LIMIT` in a subquery is irrelevant; remove it.
- Indexes on the sort columns can eliminate explicit sorts.
- `LIMIT` combined with an index on the sort column enables top-N heapsort.

**Constraints and limitations**:

- Some sorts are required by the semantics (e.g., `ORDER BY` in the outer query).
- Index-provided order requires the index column order to match the `ORDER BY` direction and null placement.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Index eliminates sort

```sql
-- Anti-pattern: sort on unindexed column
EXPLAIN ANALYZE
SELECT * FROM orders ORDER BY total DESC LIMIT 10;

-- Preferred: index on total provides order
CREATE INDEX idx_orders_total ON orders (total DESC);
EXPLAIN ANALYZE
SELECT * FROM orders ORDER BY total DESC LIMIT 10;
```

**Expected output** (anti-pattern):

```text
Limit
  ->  Sort  (Sort Method: top-N heapsort  Memory: 35kB)
        Sort Key: total DESC
        ->  Seq Scan on orders
```

**Expected output** (preferred):

```text
Limit
  ->  Index Scan using idx_orders_total on orders
        Index Cond: ...
```

**Why this output appears**: Without an index, the query sorts all rows before taking the top 10. With an index on `total DESC`, the query reads the first 10 index entries and fetches only those rows, eliminating the sort entirely.

#### Real-World Cases

- **Pagination**: `ORDER BY` with `LIMIT` benefits from an index on the sort column.
- **Subquery ordering**: `ORDER BY` inside a derived table without `LIMIT` is usually wasted.
- **Reporting**: Sorting large result sets that the client will re-sort anyway.

### 11. Unnecessary Aggregation

#### Definitions

**Core Definition**  
Unnecessary aggregation means using `GROUP BY` or aggregate functions when the result does not require grouping—for example, grouping by a unique key, or aggregating data that will be used at row level.

**Technical Definition**  
`GROUP BY` forces the engine to sort or hash the input, compute aggregates per group, and produce one row per group. When the grouping columns include a unique key, every group contains exactly one row, and the aggregation is a no-op. When the application needs row-level detail, aggregation destroys information that must then be reconstructed. Aggregate subqueries that are re-executed per outer row (correlated aggregates) are a related anti-pattern.

**Beginner-Friendly Explanation**  
If each group has exactly one row, grouping is pointless. And if you need to see individual rows, don't collapse them into groups—you'll just have to undo the grouping later.

#### Purposes

- To eliminate `GROUP BY` when the grouping key is unique.
- To avoid destroying row-level detail that is needed downstream.
- To recognize correlated aggregate subqueries that re-execute per row.
- To choose between hash aggregation and sort-based aggregation.

#### Syntax Rules and Structure

**Redundant `GROUP BY`**:

```sql
-- Anti-pattern: id is a primary key, so grouping adds nothing.
SELECT id, COUNT(*) FROM orders GROUP BY id;

-- Preferred: no grouping needed.
SELECT id, 1 AS count FROM orders;
```

**Aggregation destroying detail**:

```sql
-- Anti-pattern: aggregating then joining back to detail
SELECT o.id, agg.total
FROM orders o
JOIN (SELECT customer_id, SUM(total) AS total
      FROM orders GROUP BY customer_id) agg
  ON agg.customer_id = o.customer_id;
```

**Preferred (window function)**:

```sql
SELECT o.id, SUM(o.total) OVER (PARTITION BY o.customer_id) AS customer_total
FROM orders o;
```

**Component breakdown**:

| Scenario | Aggregation needed? | Alternative |
|----------|---------------------|-------------|
| Unique key in `GROUP BY` | No | Remove grouping |
| Per-group total alongside detail | No | Window function |
| Correlated aggregate subquery | No | Derived table or window |

**Syntax rules**:

- `GROUP BY` on a unique key produces one row per group; the aggregate is trivial.
- Window functions compute per-group aggregates without collapsing rows.
- Derived tables compute aggregates once and join them back.

**Constraints and limitations**:

- Removing `GROUP BY` changes the result if the grouping key is not actually unique.
- Window functions may require a sort and may be slower than a one-time aggregation for very large groups.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Redundant `GROUP BY` on primary key

```sql
-- Anti-pattern
EXPLAIN ANALYZE
SELECT customer_id, COUNT(*) FROM customers GROUP BY customer_id;

-- Preferred
EXPLAIN ANALYZE
SELECT customer_id, 1 AS count FROM customers;
```

**Expected output** (anti-pattern):

```text
HashAggregate  (cost=... rows=10000)
  Group Key: customer_id
  ->  Seq Scan on customers
```

**Expected output** (preferred):

```text
Seq Scan on customers  (cost=... rows=10000)
```

**Why this output appears**: `customer_id` is a primary key, so every group contains one row and `COUNT(*)` is always 1. The `HashAggregate` node is pure overhead; removing the `GROUP BY` eliminates the hash table construction and aggregation.

#### Real-World Cases

- **Detail-plus-summary queries**: Window functions replace self-joins to aggregate subqueries.
- **ORM aggregate calls**: `GROUP BY` on primary keys generated by ORMs.
- **Reporting layers**: Aggregating early then joining back to detail.

### 12. Large `IN` Lists

#### Definitions

**Core Definition**  
A large `IN` list is an `IN` predicate containing hundreds or thousands of literal values, which can degrade performance due to parsing overhead, optimizer limitations, and inefficient access paths.

**Technical Definition**  
`IN` lists with many values are internally expanded into `OR` chains or sorted arrays. Very large lists (thousands of items) can exceed optimizer limits, cause excessive parse time, and prevent efficient index usage. The optimizer may choose a full scan because the list is too large to seek efficiently, or it may sort the list and perform a merge-style comparison. The anti-pattern is especially common when applications use `IN` to filter by a list of IDs retrieved from another query or external source.

**Beginner-Friendly Explanation**  
`WHERE id IN (1, 2, 3, ..., 10000)` asks the database to check 10,000 values. For a few dozen values this is fine, but for thousands it is better to load the values into a temporary table and join, so the database can use a hash join instead of a giant list.

#### Purposes

- To recognize when an `IN` list is too large for efficient optimization.
- To replace large `IN` lists with joins to temporary tables or `VALUES` lists.
- To batch or chunk very large `IN` lists at the application layer.
- To use `ANY(array)` or table-valued parameters where supported.

#### Syntax Rules and Structure

**Anti-pattern**:

```sql
SELECT * FROM orders
WHERE customer_id IN (1, 2, 3, ..., 10000);  -- thousands of literals
```

**Preferred (join to a values list)**:

```sql
SELECT o.*
FROM orders o
JOIN (VALUES (1), (2), (3), ... ) AS ids(id)
  ON o.customer_id = ids.id;
```

**Preferred (temporary table)**:

```sql
CREATE TEMP TABLE temp_ids (id INT);
-- Bulk insert the IDs.
SELECT o.* FROM orders o JOIN temp_ids t ON o.customer_id = t.id;
```

**Component breakdown**:

| Approach | Parse cost | Optimizer behavior | Best for |
|----------|-----------|---------------------|----------|
| Large `IN` list | High | May scan or sort | Small lists (< ~1000) |
| `VALUES` join | Moderate | Hash join | Hundreds to thousands |
| Temp table | Low per query | Hash join with stats | Very large lists |

**Syntax rules**:

- `IN` lists are expanded at parse time; very large lists increase parse and plan time.
- `VALUES` lists are limited by the engine's maximum expression depth.
- Temporary tables can be indexed and analyzed, giving the optimizer better statistics.

**Constraints and limitations**:

- Temporary table creation and population add round trips; batch inserts are needed for very large lists.
- Some engines have hard limits on `IN` list size or query text length.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Large `IN` list vs. `VALUES` join

```sql
-- Anti-pattern: 10,000-element IN list
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE customer_id IN (1,2,3,...,10000);

-- Preferred: join to VALUES list
EXPLAIN ANALYZE
SELECT o.*
FROM orders o
JOIN (VALUES (1),(2),(3),...,(10000)) AS ids(id)
  ON o.customer_id = ids.id;
```

**Expected output** (anti-pattern):

```text
Seq Scan on orders  (cost=0.00..25000.00 rows=10000 width=72)
  Filter: (customer_id = ANY ('{1,2,3,...,10000}'::integer[]))
```

**Expected output** (preferred):

```text
Hash Join  (cost=... rows=10000)
  Hash Cond: (o.customer_id = ids.id)
  ->  Seq Scan on orders o
  ->  Hash
        ->  Values Scan on "*VALUES*"
```

**Why this output appears**: The large `IN` list is evaluated as an array membership test per row, forcing a sequential scan. The `VALUES` join allows a hash join with the small values list as the build side, which can be faster for large lists—though the optimizer may still choose a scan if the list covers most of the table.

#### Real-World Cases

- **Application filters**: Users select hundreds of checkboxes, generating a large `IN` list.
- **Batch operations**: Processing a list of IDs retrieved from another system.
- **ORM `IN` expansion**: ORMs expand collections into `IN` lists without size limits.

### 13. Correlated Subqueries in `SELECT`

#### Definitions

**Core Definition**  
A correlated subquery in the `SELECT` list is a scalar subquery that references a column from the outer query, causing it to be evaluated once per outer row.

**Technical Definition**  
Correlated scalar subqueries in `SELECT` cannot be unnested as easily as subqueries in `WHERE`, because the optimizer must preserve the one-value-per-row semantics. In many engines, the subquery is executed once per outer row, producing `N` executions for `N` outer rows. The anti-pattern is especially severe when the subquery is expensive (aggregation, `DISTINCT`, or multi-table joins) and the outer result set is large. Rewriting as a `LEFT JOIN` with a pre-aggregated derived table or a window function eliminates the per-row execution.

**Beginner-Friendly Explanation**  
A correlated subquery in `SELECT` means "for every row in the outer query, run this inner query." If the outer query returns 100,000 rows, the inner query runs 100,000 times. A join runs it once.

#### Purposes

- To recognize per-row subquery execution in execution plans.
- To rewrite correlated scalar subqueries as joins or window functions.
- To eliminate the `DEPENDENT SUBQUERY` plan node.
- To improve performance on large result sets.

#### Syntax Rules and Structure

**Anti-pattern**:

```sql
SELECT o.id, o.total,
       (SELECT SUM(oi.amount) FROM order_items oi WHERE oi.order_id = o.id) AS item_total
FROM orders o;
```

**Preferred (pre-aggregated join)**:

```sql
SELECT o.id, o.total, COALESCE(agg.item_total, 0) AS item_total
FROM orders o
LEFT JOIN (
    SELECT order_id, SUM(amount) AS item_total
    FROM order_items
    GROUP BY order_id
) agg ON agg.order_id = o.id;
```

**Preferred (window function for per-group totals)**:

```sql
SELECT o.id, o.total,
       SUM(oi.amount) OVER (PARTITION BY o.id) AS item_total
FROM orders o
LEFT JOIN order_items oi ON oi.order_id = o.id;
```

**Component breakdown**:

| Form | Executions of inner query | Plan node |
|------|---------------------------|-----------|
| Correlated scalar subquery | Once per outer row | `DEPENDENT SUBQUERY` |
| Pre-aggregated join | Once | `Hash Join` + `HashAggregate` |
| Window function | Once (plus join) | `WindowAgg` |

**Syntax rules**:

- A scalar subquery must return at most one row; otherwise, runtime error.
- `LEFT JOIN` preserves outer rows with no match; use `COALESCE` for defaults.
- Window functions require the join to be present, which may multiply rows; use `DISTINCT` or `GROUP BY` carefully.

**Constraints and limitations**:

- Pre-aggregation changes semantics if the subquery returns `NULL` vs. `0`; use `COALESCE`.
- Some engines can unnest simple correlated scalar subqueries automatically; complex ones cannot.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: MySQL – Correlated scalar subquery vs. pre-aggregated join

```sql
-- Anti-pattern
EXPLAIN ANALYZE
SELECT o.id, o.total,
       (SELECT SUM(oi.amount) FROM order_items oi WHERE oi.order_id = o.id) AS item_total
FROM orders o;

-- Preferred
EXPLAIN ANALYZE
SELECT o.id, o.total, COALESCE(agg.item_total, 0) AS item_total
FROM orders o
LEFT JOIN (SELECT order_id, SUM(amount) AS item_total
           FROM order_items GROUP BY order_id) agg
  ON agg.order_id = o.id;
```

**Expected output** (anti-pattern, excerpt):

```text
id | select_type        | table | type | rows | Extra
1  | PRIMARY            | o     | ALL  | 100000 |
2  | DEPENDENT SUBQUERY | oi    | ref  | 3    | Using where
```

**Expected output** (preferred, excerpt):

```text
id | select_type | table | type | rows | Extra
1  | PRIMARY     | o     | ALL  | 100000 |
1  | PRIMARY     | agg   | ref  | 1    | Using where
2  | DERIVED     | oi    | ALL  | 300000 | Using temporary; Using filesort
```

**Why this output appears**: The `DEPENDENT SUBQUERY` in the anti-pattern plan signals that the inner query re-executes once per outer row (100,000 times). The preferred version aggregates `order_items` once (`DERIVED` subquery) and joins it, eliminating per-row execution.

#### Real-World Cases

- **Order totals**: Per-order item totals computed via correlated subqueries.
- **Latest event per entity**: Correlated subqueries to find the most recent row.
- **ORM N+1 in disguise**: Correlated scalar subqueries generated by ORM annotations.

### 14. Wildcard Prefixes in `LIKE`

#### Definitions

**Core Definition**  
A wildcard prefix in `LIKE` means a pattern beginning with `%`, such as `LIKE '%term'` or `LIKE '%term%'`, which prevents the use of a standard B-tree index because the match can start anywhere in the string.

**Technical Definition**  
B-tree indexes are ordered by the full string prefix. A `LIKE 'prefix%'` predicate can be translated into an index range scan because the prefix anchors the search. A leading wildcard (`'%suffix'`) or infix wildcard (`'%infix%'`) has no anchor, so the B-tree cannot seek and the engine must scan all rows or use a specialized index. Trigram indexes (PostgreSQL `pg_trgm`, MySQL `FULLTEXT`, SQL Server full-text) index substrings and can support infix search.

**Beginner-Friendly Explanation**  
An index is like a phone book sorted by last name. Searching for "Smith%" is fast because you can flip to the S section. Searching for "%smith%" is slow because the name could be anywhere—you have to read every entry.

#### Purposes

- To recognize leading-wildcard searches that force full scans.
- To choose appropriate index types (trigram, full-text) for infix search.
- To rewrite queries to use prefix search where possible.
- To understand the trade-off between search flexibility and performance.

#### Syntax Rules and Structure

**Anti-pattern**:

```sql
SELECT * FROM products WHERE name LIKE '%widget%';
SELECT * FROM users WHERE email LIKE '%@example.com';
```

**Preferred (prefix search)**:

```sql
SELECT * FROM products WHERE name LIKE 'widget%';
```

**Specialized index (PostgreSQL trigram)**:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_products_name_trgm ON products USING gin (name gin_trgm_ops);
SELECT * FROM products WHERE name LIKE '%widget%';
```

**Component breakdown**:

| Pattern | Sargable? | Index type |
|---------|-----------|------------|
| `'prefix%'` | Yes | B-tree |
| `'%suffix'` | No | Trigram / full-text |
| `'%infix%'` | No | Trigram / full-text |
| `'_x%'` | Yes (with care) | B-tree (single-char wildcard at start may still scan) |

**Syntax rules**:

- Prefix patterns are sargable with a B-tree index and default collation.
- Trigram indexes support `LIKE '%...%'` and `ILIKE` in PostgreSQL.
- Full-text indexes support word-based search, not arbitrary substring search.

**Constraints and limitations**:

- Trigram indexes add write overhead and storage.
- Full-text search changes semantics (stemming, stop words) compared to `LIKE`.
- Case-insensitive infix search requires `ILIKE` or `LOWER()` with expression indexes.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: PostgreSQL – Trigram index for infix search

```sql
-- Anti-pattern
EXPLAIN ANALYZE
SELECT * FROM products WHERE name LIKE '%widget%';

-- After trigram index
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_products_name_trgm ON products USING gin (name gin_trgm_ops);
EXPLAIN ANALYZE
SELECT * FROM products WHERE name LIKE '%widget%';
```

**Expected output** (anti-pattern):

```text
Seq Scan on products  (cost=0.00..2500.00 rows=100 width=60)
  Filter: (name ~~ '%widget%'::text)
  Rows Removed by Filter: 99900
```

**Expected output** (trigram index):

```text
Bitmap Heap Scan on products
  Recheck Cond: (name ~~ '%widget%'::text)
  ->  Bitmap Index Scan on idx_products_name_trgm
        Index Cond: (name ~~ '%widget%'::text)
```

**Why this output appears**: The trigram index indexes three-character substrings, allowing the engine to find candidate rows that contain "wid," "idg," "dge," etc., and then recheck the full pattern. This avoids scanning the entire table.

#### Real-World Cases

- **Product search**: Users typing partial product names.
- **Email domain filtering**: `LIKE '%@example.com'` on large user tables.
- **Log analysis**: Searching message text for keywords.

### 15. OR Conditions on Different Columns

#### Definitions

**Core Definition**  
`OR` conditions on different columns combine predicates on separate indexed columns, often preventing the optimizer from using a single index and forcing a full scan or costly index merge.

**Technical Definition**  
A predicate like `WHERE col1 = 'A' OR col2 = 'B'` requires the union of rows matching either condition. If `col1` and `col2` have separate indexes, the optimizer can sometimes perform an **index merge** (bitmap OR in PostgreSQL, index merge in MySQL, `OR` expansion in SQL Server), but many optimizers fall back to a full scan when the predicate is complex or the indexes are not suitable. Rewriting as `UNION ALL` with appropriate exclusion predicates allows each branch to use its own index.

**Beginner-Friendly Explanation**  
Asking for "rows where city = 'Paris' OR country = 'France'" is hard for the database because it needs two different indexes. Splitting into two queries and combining them lets each index do its job.

#### Purposes

- To recognize `OR` across different columns as a performance risk.
- To rewrite as `UNION ALL` when each branch can use its own index.
- To design composite indexes that cover `OR` predicates where possible.
- To understand when index merge is available and when it is not.

#### Syntax Rules and Structure

**Anti-pattern**:

```sql
SELECT * FROM customers
WHERE city = 'Paris' OR country = 'France';
```

**Preferred (`UNION ALL`)**:

```sql
SELECT * FROM customers WHERE city = 'Paris'
UNION ALL
SELECT * FROM customers WHERE country = 'France' AND city <> 'Paris';
```

**Preferred (index merge, when supported)**:

```sql
-- PostgreSQL may use BitmapOr automatically:
-- BitmapOr
--   -> Bitmap Index Scan on idx_city
--   -> Bitmap Index Scan on idx_country
```

**Component breakdown**:

| `OR` scope | Index merge possible? | Recommended fix |
|------------|----------------------|-----------------|
| Same column, equality values | Yes (rewrite to `IN`) | `IN` |
| Different columns, both indexed | Sometimes | `UNION ALL` |
| Different columns, one unindexed | No | `UNION ALL` |
| Mix of range and equality | Depends | `UNION ALL` or composite index |

**Syntax rules**:

- `OR` across the same column with equality values should be `IN`.
- `UNION ALL` requires an exclusion predicate on subsequent branches to prevent duplicates, or use `UNION` if duplicates must be removed.
- Composite indexes can sometimes support `OR` if the predicates align with the index prefix.

**Constraints and limitations**:

- `UNION ALL` duplicates rows that match both branches unless exclusion predicates are added.
- Index merge strategies consume memory and may not be chosen for large result sets.
- Composite indexes cannot generally satisfy `OR` across unrelated columns.

#### Multiple Annotated Complete Step-by-Step Code Examples

##### Example 1: MySQL – `OR` across columns vs. `UNION ALL`

```sql
-- Anti-pattern
EXPLAIN ANALYZE
SELECT * FROM customers
WHERE city = 'Paris' OR country = 'France';

-- Preferred
EXPLAIN ANALYZE
SELECT * FROM customers WHERE city = 'Paris'
UNION ALL
SELECT * FROM customers WHERE country = 'France' AND city <> 'Paris';
```

**Expected output** (anti-pattern, excerpt):

```text
id | select_type | table     | type | key | rows | Extra
1  | SIMPLE      | customers | ALL  |     | 100000 | Using where
```

**Expected output** (preferred, excerpt):

```text
id | select_type  | table     | type | key             | rows | Extra
1  | PRIMARY      | customers | ref  | idx_city        | 500  |
2  | UNION        | customers | ref  | idx_country     | 8000 | Using where
```

**Why this output appears**: The single `OR` predicate causes a full table scan (`type = ALL`) because MySQL cannot use two separate indexes efficiently for this condition. The `UNION ALL` allows each branch to use its respective index (`idx_city`, `idx_country`), dramatically reducing rows examined.

#### Real-World Cases

- **Multi-field search**: Users filter by any combination of city, country, or category.
- **Status and type filters**: `OR` across independent enum columns.
- **Data quality queries**: Finding rows matching either of two independent conditions.

## Summary: Anti-Pattern Decision Matrix

| Anti-pattern | Plan signature | Performance cause | Primary fix |
|--------------|----------------|-------------------|-------------|
| `SELECT *` | `Index Scan` + heap fetch; no `Index Only Scan` | Extra columns prevent covering index | Explicit column list |
| N+1 queries | Many short queries; `DEPENDENT SUBQUERY` | Per-row round trips | Join or batched `IN` |
| Functions on indexed columns | `Seq Scan` + `Filter: FUNC(col)` | Non-sargable predicate | Rewrite or expression index |
| Implicit type conversions | `Seq Scan` + `CONVERT_IMPLICIT` | Column cast defeats index | Match data types |
| Non-sargable predicates | `Seq Scan` + `Filter` with function/wildcard | No index seek possible | Sargable rewrite or specialized index |
| Overuse of `DISTINCT` | `Unique` / `Using temporary` | Unnecessary sort/hash | Remove or replace with `EXISTS` |
| Overuse of `OR` | `Seq Scan` + `OR` filter | Cannot use one index for multiple columns | `IN`, `UNION ALL`, or composite index |
| Overuse of subqueries | `DEPENDENT SUBQUERY` | Per-row execution | Join, `EXISTS`, or CTE |
| Overuse of `UNION` | `Unique` after `Append` | Unnecessary deduplication | `UNION ALL` |
| Unnecessary sorting | `Sort` with `external merge` | Blocking sort, spill | Remove `ORDER BY` or add index |
| Unnecessary aggregation | `HashAggregate` / `GroupAggregate` | Unneeded grouping | Remove `GROUP BY` or use window function |
| Large `IN` lists | `Seq Scan` + array membership | Parse and evaluation overhead | `VALUES` join or temp table |
| Correlated subqueries in `SELECT` | `DEPENDENT SUBQUERY` per row | N executions | Pre-aggregated join or window function |
| Wildcard prefixes in `LIKE` | `Seq Scan` + `LIKE '%...'` | No index anchor | Prefix search or trigram index |
| `OR` on different columns | `Seq Scan` + `OR` filter | No single index applicable | `UNION ALL` or index merge |
